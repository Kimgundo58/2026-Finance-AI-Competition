### 판단

**폐쇄 목록을 코드에 박지 않았다.** `비목` enum 은 `_비목_어휘집.json` 의
`guided_json_enum` 을 **실행 시점에** 읽는다(`rule_base.md` §1-b). 복사해 두면 어휘집이
바뀌어도 조용히 옛 목록으로 강제하고 `rules.비목` 조인이 끊긴다 — 오늘 오전 3차 작업에서
정확히 그 사고(개수만 맞고 문자열이 다름)를 겪었다. 테스트가 "소스에 비목 문자열이
박혀 있지 않은지"까지 검사한다.

같은 이유로 **F 필드 경로도 하드코딩하지 않았다.** `tenant` 3개 테이블의
`information_schema` 컬럼에서 만든다. 컬럼 `정부지원_현금` → 경로 `F1.정부지원.현금`

F5 만 리터럴인 이유: 저장하지 않는 축이라 컬럼이 존재할 수 없다. 근거를 주석에 달았다.

**`판정_스키마(s번호들)` 에 S번호 집합을 넣으면 인용을 enum 으로 닫는다.**
§3-4 가 "컨텍스트에 부여된 S번호 집합 안에서만" 이라 했다. 디코딩 단계에서 막으면
검증기가 폐기할 일이 애초에 줄어든다. 집합을 안 주면 패턴(`^S\d{2,3}$`)만 건다 —
조립기가 S번호를 아직 못 정한 단계용.

**사양에 없어 내가 정한 것 2개** (§3-4 와 어긋나게 만든 건 아니고, 비어 있던 자리다):

| 항목 | 정한 값 | 근거 |
|---|---|---|
| `전제.미충족시` enum | `가능 \| 조건부 \| 불가` (3-way) | §3-4 예시가 `"불가"` 뿐이라 값 목록이 없었다. **`판단불가` 는 뺐다** — 전제는 "이 사실이 아니면 이렇게 된다" 라서 결론이 있어야 한다 |
| 인용 0건 처리 | 판정 → `판단불가` 로 강등 | §3-4 에 명시 없음. CLAUDE.md "모든 실패의 기본값은 판단불가" + "인용은 S번호 추출" 원칙상 근거 없는 판정이 나가면 안 된다 |

**계약(시그니처)은 바꾸지 않았다.** 강등 규칙 중 셋(vlm·verified·F스키마)이 DB 사실을

```python

```

`검증(출력, s맵)` 2인자 호출이 그대로 동작한다(실DB 스모크로 확인). 조립기 코드는
바꿀 필요가 없다. 키워드를 안 주면 라이브 DB 조회가 기본이다.

**`unmapped_premise` 는 DB 에 쓰지 않는다.** 지시대로 반환만 한다
(`최종응답.미매핑전제`). 그리고 매핑이 F 스키마 밖이라고 **전제를 폐기하지는 않았다** —
전제 자체는 유효한데 F 스키마가 결손일 수 있다. 폐기하면 그 사실이 사라져

## 2026-08-31 (2차) · 인용 치환 완성 + check_items 39행

중앙세션이 (a)·(c) 를 승인·지시해 이어서 했다. `version` 은 중앙세션이 채워줬다.

### 판단

**인용 치환은 검증기가 한다** (중앙세션 확정, `LLM.md` §3-4 [2겹] 표가 (6) 단계에 배치).
조립기가 하면 s맵에 원문을 통째로 실어 넘겨야 해 계약이 무거워진다.

**`corpus.chunks` 에 이미 `조번호·조제목·항호·version·text` 가 다 있다.** 청크는
`documents` 를 조인할 필요가 `extraction` 뿐이다. `chunks.version` 은 `documents.version`
과 **불일치 0** (실측) 이라 `COALESCE(c.version, d.version)` 으로 받는다.

**항 추출은 자르기지 요약이 아니다.** `article`·`l3` 는 조 전체가 오므로 s맵의 항호로
잘라내는데, 반환값은 **반드시 본문의 정확한 부분 문자열**이다. 마커를 못 찾으면
조 전체를 주고 `원문범위='조전체(항호 미발견)'` 로 그 사실을 알린다 — 지어내지 않는다.
청크는 이미 항 단위(§3-7)라 자르지 않고 `text` 를 그대로 쓴다(`원문범위='청크'`).

**항호는 s맵(조립기)이 정본.** 청크 DB 값과 다르면 조립 사고이므로 강등사유에 남기되
s맵 값을 채택한다. 조용히 넘기면 다른 항을 인용해 놓고 맞다고 우기게 된다.

**s맵에 있는데 DB 에 없으면 인용을 폐기한다.** 죽은 id 는 원문을 붙일 수 없고,
원문 없는 인용은 화면에서 검증 불가다.

**버전스탬프는 s맵 전체가 아니라 인용된 것만 모은다.** 전체를 쓰면 인용하지도 않은
문서의 판본이 화면에 붙는다.

**`check_items` 는 TRUNCATE 하지 않는다.** `tenant.plan_tasks.코드` 가 FK 로 참조한다 —
`TRUNCATE ... CASCADE` 는 **사용자가 체크해 둔 진행상황을 통째로 지운다.** 이 테이블이
존재하는 이유(재판정 간 진행상황 유지)를 정면으로 깨는 짓이다. upsert + 목록에서 빠진
code 만 DELETE 로 바꿨다. 참조 중인 code 를 지우려 하면 FK 가 막아 준다.

**항목은 "판정" 이 아니라 "할 일" 로 압축했다.** "귀금속은 원칙적으로 구매 불가" 는
판정이지 행동이 아니다 → "귀금속·보석·원석이면 사전승인을 먼저 받으세요".
근거는 **L1 통합관리지침 조문만** 썼다 — 전 사업 공통 항목이라 사업별 세부관리기준을
걸면 다른 사업에서 거짓이 된다.

**🔴 §3-4 와 어긋나게 만든 것 1건.** §3-4 의 `해야할일` 은 `{항목, 설명}` 2필드인데,
`02_frontend.sql` 은 "code 는 guided_json enum 으로 그대로 들어간다" 를 요구한다.
두 사양이 충돌한다. → `판정_스키마(코드들=...)` 인자로 갈랐다. 주면 `code` 필수 +
`check_items.code` enum, 안 주면 §3-4 원형 그대로. 검증기도 `code` 가 없으면 통과시킨다.
**사양 정리는 오너·중앙세션 몫이다.**

`'2026.7.1'` 이 나오길래 오기입을 의심했다 — **LIKE 가 창업지원법·시행령까지 잡은
내 쿼리 실수였다.** 지침은 `'제14차, 2025.12.23'` 로 정확하다. 확인 없이 보고했으면
중앙세션이 멀쩡한 데이터를 다시 뒤졌을 것이다.

### 남은 것

- `참조사슬` 은 여전히 빈 배열 — `refs` 레코드는 조립기 몫
- `해야할일` code 사양 충돌(§3-4 vs `02_frontend.sql`) — 오너 결정
- `check_items` 39행은 **전 사업 공통(사업명=NULL)** 뿐이다. 사업별로 갈리는 항목
  (모두의창업 국외여비 전면 불가 등)은 아직 없다
- ①/④ 프롬프트 본문 미착수 (중앙세션 B0/B6 과 조율 필요)
