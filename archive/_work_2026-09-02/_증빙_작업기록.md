## 2026-08-31 · 비목 문자열 정본 정렬 + 증빙 별칭 도출

`corpus.rules.비목` 2종을 어휘집 enum 으로 교정하고, `evidence_sources.해당비목` 78종을
정본 10종에 매핑하는 함수를 만들고, `rules.증빙` 미일치 16종의 별칭 후보를 뽑았다.

### 입력

- `2026_Finance_DATA_FOR_RAG/_비목_어휘집.json` — **정본**. `guided_json_enum` 10종,
  `enum_검수대기` 0 (확정)
- `corpus.rules` 54행 · `corpus.evidence_sources` 124행 (읽기)
- `scripts/seed_rules.py` · `scripts/load_evidence.py` (수정 대상)

### 판단

**🔴 어휘집에는 비목 필드가 둘이다. 조인 키는 `enum` 이다.**

| 필드 | 값 예시 | 용도 |
|---|---|---|
| `guided_json_enum` | `기계장치` / `특허권등무형자산취득비` | **조인 키.** LLM guided_json 이 뱉는 값 |
| `비목` | `기계장치, 공구·기구` / `특허권 등 무형자산 취득비` | 원문 표기. 화면용 |

2차 작업에서 `비목` 쪽 표기를 `rules.비목` 에 넣었다. `rules.비목 = f_exec.비목` 조인이
전부 0행이 될 값이었고, CHECK 제약이 없는 컬럼이라 조용히 실패한다.

**어떻게 놓쳤나 — 검사가 개수만 셌다.** 2차 검증이 `count(DISTINCT 비목) = 10` 이었다.
10종이 맞고 문자열이 틀린 상태를 통과시킨다. 3차에서 **집합 비교**로 바꿨다
(`seed_rules.py::정본_비목_enum()` + `main()`). 이제 실행할 때마다 어휘집을 읽어
`DB - 정본` / `정본 - DB` 양방향을 찍는다. 개수 비교는 다시 쓰지 않는다.

**`해당비목` 을 억지로 10종에 밀어 넣지 않았다.** CSV 78종은 세 계통이 섞여 있다.

| 계통 | 종수 | 처리 |
|---|---|---|
| 창업패키지 비목 (정본 8 + 표기차이 1) | 9 | 정본 10종으로 매핑 |
| 지급수수료 **세목** (접두사형 13 + 민낯형 9) | 22 | 정본 `지급수수료` 로 접음 |
| TIPS·국가연구개발 비목 | 43 | 🔴 매핑 안 함. 원본 보존 |
| 주관기관 비목 (회의비) | 1 | 매핑 안 함 |
| 비목 아님 (사업비 구성·자기부담 현물·전 비목 공통 규정) | 3 | 매핑 안 함 |

**🔴 TIPS 를 매핑하지 않은 이유** (억지 매핑을 기각한 근거):
1. 위임 계통이 다르다. TIPS 비목(연구재료비·연구활동비·연구수당·간접비)은
   「국가연구개발혁신법」 계통, 10종은 「중소기업창업 지원법」 통합관리지침 제36조
   표-10 계통이다. 이름이 겹쳐 보여도(재료비 vs 연구재료비) 정의·증빙·한도가 다르다.
2. `corpus.rules` 에 TIPS 룰이 없다(비목 체계 상이 + 우선순위 조항 부재로 제외).
   evidence 쪽만 매핑하면 rules 에 없는 비목으로 조인해 **무음 0행**이 된다.
3. "별도 값"(`TIPS:재료비` 같은 것)도 만들지 않았다 — enum 10종 밖의 값이 조인 축에
   섞이면 guided_json 생성 때 같은 문제가 되돌아온다.
→ 정본값 `None` + 분류 태그. **원본 `해당비목` 은 손대지 않았다.**

**민낯형 세목의 계통 판별은 CSV `패키지` 열로 했다** (추측하지 않았다).
`멘토링비`·`사무실임차료`·`보관료`·`기자재임차비`·`시험·인증비`·`장비 수리비`·
`전시회·박람회 참가비`·`세무·회계비`·`기술보호비` → "7개 패키지 공통" 또는 창업패키지 열거.
`회의비`·`출장비`·`연구재료비`·`간접비(총괄)`·`국제공동연구개발비` → "TIPS" 단독.

**정규화 결과를 DB 에 쓰지 않았다.** `해당비목` 을 덮어쓰면 원본이 사라지고, 컬럼 추가는
스키마 소유가 아니다. 함수만 만들고 `--map` 이 커버리지를 찍는다. 적용 경로는 막아 뒀다
(`sys.exit`). → 아래 "남은 것" 의 컬럼 2개 신설이 선행 조건.

**별칭 후보는 적용하지 않았다.** 생성기를 `scripts/` 본체가 아니라 `scripts/_work/` 에 뒀다
— 본체에 두면 누군가 파이프라인에 물릴 수 있다. 생성기는 돌 때마다 라이브 DB 의 미일치
목록과 표를 대조하고, 어긋나면 산출물을 내보내지 않고 멈춘다(낡은 표 방지).

**룰 세션이 "모호"·"정본 없음" 으로 남긴 2건은 실측으로 풀렸다.**
- `통장사본` → rules 사용처가 예비·초기 **인건비 2행뿐**. CSV `근로자 통장사본`
  해당비목=`['인건비']`, `거래처 통장사본`=`['재료비','외주용역비','기계장치','광고선전비']`.
  인건비 맥락이므로 근로자 쪽. (신뢰도 중간 — 별칭보다 rules 원문을 고치는 편이 낫다)
- `계약서`(세무회계 세목) → CSV `계약서(과업내용 포함)` 행의 해당비목에 **`세무·회계비` 가
  실제로 들어 있다.** CSV 편집자가 그 행으로 묶었다. (신뢰도 중간)

### 함정

**`count(DISTINCT x) = N` 은 문자열 검사가 아니다.** 이번 버그의 원인이자, 2차 보고서가
"정확히 일치" 라고 쓸 수 있었던 이유다. 정본이 파일에 있으면 파일을 읽어 집합 비교한다.

**CSV `해당 비목` 은 이미 세목 축을 갖고 있다.** 78종 중 22종이 지급수수료 세목이다
(`지급수수료-멘토링비` 접두사형과 `멘토링비` 민낯형이 섞여 있다). 작업 4의 답이 여기 있었다
— 아래 참조.

**`corpus.item_alias` 가 이미 존재한다** (`상품명 → 비목`, embedding 포함). 증빙 별칭은
서류명 축이라 여기 들어갈 수 없다. 별칭 테이블을 새로 만들 거면 item_alias 와 축이 다르다는
점을 먼저 확인할 것.

### 남은 것

**🔴 작업 4 결론 — `rules` 에 세목 컬럼을 만들 필요가 없다. 축이 이미 DB 에 있다.**

`corpus.evidence_sources.해당비목` 을 **역인덱스**로 쓰면 세목별 증빙이 바로 나온다.
실측 (세목 12종 전부 해소):

| 세목 | seed dict | evidence 역인덱스 |
|---|---|---|
| 기술이전비 | 3 | 5 |
| 학회(세미나)참가비 | 3 | 3 |
| 전시회(박람회)참가비 | 3 | 3 |
| 시험·인증비 | 2 | 3 |
| 멘토링비 | 3 | 5 |
| 기자재임차비 | 3 | 3 |
| 장비 수리비 | 3 | 3 |
| 사무실임차료 | 3 | 3 |
| 운반·보험·보관료 | 4 | 6 |
| 회계감사비 | 1 | 1 |
| 세무회계비 | 1 | 1 |
| 법인설립비 | 2 | 2 |

`SELECT 증빙명 FROM corpus.evidence_sources WHERE '멘토링비' = ANY(해당비목)` → 5종.
현재 화면에 나갈 27~34종 대신 1~6종이다. **스키마 변경 0.**
필요한 건 세목 별칭 4건뿐이다 (seed dict 키 → CSV 표기):
`학회(세미나)참가비→학회·세미나 참가비` / `전시회(박람회)참가비→전시회·박람회 참가비` /
`운반·보험·보관료→운반비·보험료·보관료 3종` / `세무회계비→세무·회계비`.

기각한 대안:
- **rules 에 세목 컬럼 신설** — `UNIQUE(layer, 기관ID, 사업명, 비목)` 이 깨진다.
  지급수수료가 사업당 12행이 되어 54행 → 약 120행. 그러고도 아래 (⚠️) 가 그대로 남는다
- **check_items 단계 분기** — `check_items` 에도 세목 컬럼이 없다(사업명·비목·구분뿐).
  같은 문제를 한 테이블 뒤로 미룰 뿐이다

⚠️ **진짜 미결은 스키마가 아니라 "세목을 어디서 받는가" 다.**
`tenant.expense_plans.확정비목` 과 `tenant.f_exec.비목` 은 **비목만** 담는다. 세목 입력이
없으면 어떤 방식이든 좁힐 수 없다. 선택지는 셋이고 전부 오너 결정 대상이다:
1. ① 정규화 LLM 의 guided_json 을 2단으로 (비목=지급수수료 일 때만 세목 enum) — LLM.md §3-4
2. 화면에서 사용자가 고른다 ("지급수수료 — 어떤 거래인가요?") — 호출 수 불변, 가장 싸다
3. 코드가 `질문원문`·`거래처` 에서 키워드로 추정 (멘토링→멘토링비, 임차→사무실임차료) —
   세목 이름이 서로 구별되어 규칙이 짧다. 실패 시 합집합으로 폴백
→ **권고: 2번.** LLM 호출 수·스키마·재현성을 전부 건드리지 않는다.
   그때까지 `rules.증빙` 합집합은 그대로 두는 게 맞다 — "이 비목에서 나올 수 있는 전체"
   라는 의미는 유효하고, 좁히는 일은 표시 단계의 몫이다.

**`해당비목` 정규화 적용에는 컬럼 2개가 필요하다** (스키마 소유자 결정):
```sql
ALTER TABLE corpus.evidence_sources
  ADD COLUMN 해당비목_정본 TEXT[],   -- 정본 10종. 조인용
  ADD COLUMN 해당비목_분류 TEXT[];   -- 정본|표기차이|지급수수료_세목|R&D계통|주관기관비목|비목아님
```
원본 `해당비목` 은 그대로 둔다. `load_evidence.py::정본비목()` 이 값을 만든다.
**ALTER 하지 않았다.**

**별칭 16종 검수 대기.** `scripts/_work/_증빙_별칭후보.json`. 신뢰도 '높음' 12종은 그대로
적용해도 되고, '중간' 3종은 근거를 읽고 확인해야 한다. '판단필요' 1종
(`교육 이수 계획서(교육일정 포함)`)은 별칭이 아니라 **CSV 신규 등록 후보**다 —
창업중심대학 [참고4] 고유 증빙이고 CSV 124종에 없다.

**`(국외) 출장신청서` 는 별칭 전에 CSV 쪽 손질이 필요하다.** CSV `출장신청서` 행의
해당비목이 `['TIPS-연구활동비(출장비)']` 뿐이라 창업패키지 여비에 붙어 있지 않다.
창업중심대학 [참고4] 가 국외여비 증빙으로 요구한다.

**`통장사본` 은 별칭보다 rules 원문 교정이 낫다.** 예비·초기 인건비 2행의 `통장사본` 을
`근로자 통장사본` 으로 고치면 별칭 없이 해소된다. 다만 그 2행은 verified=true 라 손대지 않았다.

**이전 기록 정정** — `_rules_작업기록.md` 의 "distinct 비목 10 (어휘집 10종과 정확히 일치)"
는 틀렸다. 개수만 맞고 문자열 2종이 달랐다. 위 §작업 1 이 정정본이다.
