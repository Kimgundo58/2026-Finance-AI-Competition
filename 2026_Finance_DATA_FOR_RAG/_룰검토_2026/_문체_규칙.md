# 문체 규칙 — md 작성·정리 기준

오너가 준 스타일 가이드(minzkn.com/vibecoding/pages/markdown-style-guide.html)와
오너 지시(2026-09-04)를 합친 것이다.

읽는 사람은 이 프로젝트를 처음 보는 사람이다. 그 사람이 한 번에 이해하면 통과.

## 1. 어투

**1-1. 특수 괄호를 쓰지 않는다**

`«»` `「」` 는 전부 뺀다. 인용은 큰따옴표, 강조는 볼드.

- 나쁨: 「불가」를 말하는 자리는 «허용» 컬럼이 아니라 금지예시다
- 좋음: 불가를 말하는 자리는 금지예시다

🔴 **예외 — 문자열 안의 괄호는 문체가 아니다.** 아래는 그대로 둔다.

1. 실제 파일명·경로: `중기부/[양식] 「사업화 지원금 지원」 분야 신청서류.hwp`
2. 명령어 안: `mv "「구」 폴더" 새폴더`
3. 규정 원문 인용 블록 안
4. 용어 치환 예시 표의 값 (바꾸면 예시 자체가 바뀐다)

바꾸기 전에 그 괄호가 **우리가 쓴 문장인지 남의 문자열인지** 본다.
파일명을 고치면 경로가 깨지고, 명령어를 고치면 롤백이 안 된다.

**1-2. "~가 아니다"로 뜻을 세우지 않는다**

먼저 무엇인지 말한다. 아니라는 말은 필요할 때만 뒤에 붙인다.

- 나쁨: 병목은 어휘의 부재가 아니라 매칭이다
- 좋음: 진짜 문제는 매칭이다. 단어가 없어서가 아니라, 있는 단어가 안 걸린다

**1-3. 🔴 는 문서당 3개까지**

진짜 함정이나 사고 위험에만 쓴다. 강조가 많으면 강조가 사라진다.

**1-4. 강조는 문서의 20% 이내**

볼드가 많으면 어디가 중요한지 알 수 없다.

**1-5. AI 티 나는 표현을 지운다**

아래 표현은 뜻을 안 더한다. 지우거나 바꾼다.

| 지울 표현 | 어떻게 |
|---|---|
| ~라고 할 수 있다 / ~인 셈이다 | 그냥 단정한다 |
| 즉, / 다시 말해 / 결론적으로 / 정리하자면 | 앞 문장을 고쳐 쓴다 |
| ~하는 것이 중요하다 / ~할 필요가 있다 | 무엇을 하라고 직접 쓴다 |
| 사실상 / 본질적으로 / 근본적으로 | 지운다 |
| ~에 대해 / ~을 통해 / ~에 의해 | 우리말 어순으로 바꾼다 |
| 본 문서는 ~를 다룬다 | 무엇을 하는 문서인지 바로 쓴다 |
| A가 아니라 B다 (대구를 반복) | 한 번만 쓴다 |

예:

- 나쁨: 본 문서는 룰 검토 결과에 대해 다룬다. 즉, 5행을 수정했다고 할 수 있다.
- 좋음: 룰 74행을 다시 봤다. 5행을 고쳤다.

## 🔴 1-6. 문체 규칙은 «우리가 쓴 산문» 에만 적용한다

문장 쪼개기 · 군더더기 제거 · 괄호 정리 · 목록화는 **우리 문장**에만 한다.
아래는 대상이 아니다.

1. 인용 블록(`>`) 안
2. 코드 블록(` ``` `) 안
3. 인라인 코드(`` ` ``) 안
4. 규정 원문을 옮긴 문장 — 블록이 아니어도 원문이면 그렇다
5. **법령·규정 이름을 감싼 낫표** — 「공무원 여비 규정」은 한국 법령 표기 관행이다

🔴 **실제로 이 규칙 때문에 인용이 4건 깨졌다.** 문체 정리로 파일을 다시 쓰면서
인용문 안의 괄호를 군더더기로 보고 뺐다. 생략 표시도 안 달았다.

| 뺀 것 | 결과 |
|---|---|
| `(이하 "지침" 이라 한다)` | 약칭 정의가 사라져 뒤 문장이 안 붙는다 |
| `산업안전보건법 제129조에 따른` | 법률 근거가 사라졌다 |
| `과제수행에 따른 현물로만 계상할 수 있고` | **조건부가 전면 금지로 읽힌다** |

셋째가 제일 나쁘다. 뺀 부분이 하필 예외였다.

**규정 원문은 길어도 줄이지 않는다.** 길이가 문제면 그 인용을 통째로 빼거나
표 밖으로 옮기지, 안을 줄이지 않는다.

🔴 **짧게 쓰고 싶으면 조를 바꿔 인용한다. 문장을 깎지 않는다.**
규정에서 군더더기로 보이는 삽입절은 대개 약칭 정의·법률 근거·조건 한정이다. 빼면 뜻이 뒤집힌다.

**인용은 손으로 옮겨 적지 말고 코퍼스에서 잘라 온다.** 다시 타이핑하면 그때 깎인다.
실제로 코퍼스에서 슬라이스한 세션은 인용 손상이 0건이었다.

**인용을 통째로 빼도 되는 건 논지가 그 인용에 안 걸릴 때뿐이다.**
절을 접다가 인용이 빠지면, 남은 산문이 근거 없는 주장이 된다. 줄이 늘어도 인용을 남긴다.

## 🔴 1-7. 인용을 고쳤는지 코퍼스로 확인한다

문서를 다시 쓴 뒤에는 **검사기 말고 코퍼스로** 확인한다.

1. 문서의 인용 블록과 인라인 코드를 뽑는다
2. `corpus.doc_articles` 전문과 공백 무시로 대조한다
3. 안 걸리는 게 나오면 **어느 글자부터 갈리는지** 출력해 원문과 나란히 본다
4. 라벨 붙인 인용과 우리 산문 블록은 걸러낸다

`…` 생략 표시가 남아 있으면 그것도 복원 대상이다. 조각이 다 실재해도 인용이 아니다.

🔴 **「코퍼스에 있나」만 보면 안 걸린다.** 줄인 문자열도 원문 안에 있으니 통과한다.
두 축으로 봐야 한다.

1. 고치기 **전(`git show HEAD:`) 인용**을 뽑아 지금 문서에서 **짧아졌는지** 본다
   (볼드 `**` 를 먼저 벗긴다. 안 벗기면 가짜 짧아짐이 쏟아진다)
2. **표 칸 전수**로 앞 15자는 코퍼스에 있는데 전체는 없는 칸을 찾는다. 잘린 인용의 지문이다

## 2. 문장과 문단

**2-1. 한 문장에 한 가지만**

접속사가 두 개 이상이면 두 문장으로 나눈다. 40자쯤에서 끊는다.

**2-2. 한 문단은 3~5줄**

6줄 넘으면 무조건 쪼갠다. 핵심 메시지는 첫 문장에 둔다.

**2-3. 절차·조건이 이어지면 목록으로**

나쁜 예:

> API 키를 발급받으려면 먼저 콘솔에 접속하고 계정을 생성한 후 결제 정보를 등록하고
> 새 키를 생성하면 되는데 이때 키를 환경 변수에 저장해야 하며 코드에 직접 입력하면 안 됩니다.

좋은 예:

> API 키 발급 절차:
>
> 1. 콘솔 접속 및 계정 생성
> 2. 결제 정보 등록
> 3. 새 키 생성
> 4. 환경 변수에 키 저장
>
> 코드에 키를 직접 입력하지 마세요.

주의사항은 목록 밖에 한 줄로 뺀다.

## 3. 제목

- 수준을 건너뛰지 않는다. `##` 다음에 `####` 를 쓰지 않는다
- 명사형으로 통일한다. "설치하기" 대신 "설치 방법"
- 같은 수준끼리 형태를 맞춘다
- `##` 은 3~7개 범위로 유지한다
  - 🔴 예외: **찾아보는 문서**(대조표·색인·부록)는 절이 많아도 둔다. 3~7개는 통독하는 문서 기준이다

## 4. 목록

- 순서가 중요하면 `1.`, 아니면 `-` 를 쓴다. 문서 전체에서 기호를 하나로 통일한다
- 문장 끝 표현을 통일한다. 한 목록 안에서 문장형과 단어형을 섞지 않는다
- 중첩은 2단계까지. 3단계가 필요하면 하위 절로 뺀다

## 5. 표

- **열은 3~4개까지.** 5개 넘으면 모바일에서 깨진다
- 칸에 긴 문장을 넣지 않는다. 길면 표 밖에 설명을 둔다
- **상수 열은 뺀다.** 모든 행이 같은 값이면 열이 아니라 전제다. 표 위에 한 줄로 적는다
- 열이 많으면 **묻는 질문이 다른 두 표로 나눈다.** 반으로 자르는 게 아니다
  - 예: 8열 판정표 → 「판정 요약」 3열 + 「칸별 근거」 4열

🔴 **예외 — 색인표는 열이 많은 게 기능이다.** 사람이 찾아보는 표(법령 링크 색인 등)는
열을 접으면 찾기가 나빠진다. 접지 말고 둔다.

## 6. 코드와 경로

- 코드 블록에 언어를 지정한다 (` ```bash `, ` ```sql `, ` ```json `)
- 명령어·파일 경로·컬럼명·함수명은 인라인 코드로 쓴다: `scripts/pdftext.py`, `금지적중()`
- 환경 변수는 대문자 인라인 코드: `SUDDOE_DSN`
- 비밀 키는 플레이스홀더로 쓴다

## 7. 용어

- 전문용어는 첫 등장에 괄호로 한 줄 풀이한다
  - 예: `금지적중()` (사용자가 적은 품목이 룰의 금지 목록에 걸리는지 보는 함수)
- 표기를 통일한다: `rule 440` · `금지예시` · `허용 칸` · `판정이유`

## 8. 링크

- 링크 텍스트에 내용을 담는다. "여기", "이 문서" 같은 표현을 쓰지 않는다

## 9. 문서 구조

기술 문서는 이 순서를 따른다.

1. 개요·목적
2. 사전 조건
3. 핵심 개념
4. 단계별 절차
5. 예제
6. 문제 해결
7. 관련 문서

첫 3줄은 표·기호 없이 평문 요약으로 쓴다.

## 이 프로젝트에서 다르게 가는 것

- **파일명은 한글을 유지한다.** 가이드는 소문자 하이픈을 권하지만
  이 저장소는 한글 파일명이 관행이고 문서끼리 링크가 걸려 있다
- **100줄 상한은 `docs/` 에만 적용한다.** `_룰검토_2026/`·`_골든셋_2026/` 은 작업 산출물이라 대상이 아니다
- **120줄 넘는 문서는 머리에 안내를 한 줄 단다**
  - 예: `이 문서는 적용 절차(§1~4)와 검증 기록(§5~8)으로 나뉜다. 적용만 볼 사람은 §4까지.`

## 손대면 안 되는 것

- 숫자·`rule_id`·파일 경로·판정·근거 원문. **문체만 고친다**
- 대조축으로 일부러 남긴 낡은 값. 지우면 논지가 죽는다
- `archive/` 전체. 소급 수정 금지다
- 🔴 `docs/기록/` 은 **코드 블록 언어 지정만** 한다 (오너 판단, 2026-09-04).
  기호·🔴·문단은 그대로 둔다. 기록에서는 `「」` 가 인용과 서술을 가르고,
  🔴 는 그때 무엇을 위험으로 봤는지를 남긴 것이라 기호가 곧 내용이다

## 🔴 도구가 낸 수를 그대로 믿지 않는다

검사기가 위반을 많이 뱉으면, 고치기 전에 **표본을 서너 개 열어본다.**

실제로 두 번 걸렸다.

1. 검사기가 코드 블록 안을 산문으로 셌다. 「6줄+ 문단 80개」가 고치니 **0개**였다.
   전부 규정 원문 인용 블록이었다
2. 룰 전수 스캔이 rule 450 을 놓쳤다. 더 강한 문장이 예외를 가렸다

**측정 도구가 틀리면 그 값으로 원문을 고치게 된다.**
숫자가 한쪽으로 쏠리면 도구를 먼저 의심한다.

"안 고쳤다"를 검사기 숫자로 말하지 않는다. `git diff` 나 원문 대조로 보인다.

## 확인 방법

고친 뒤 스스로 읽는다. 하나라도 걸리면 다시 고친다.

1. 한 문장을 두 번 읽어야 뜻이 잡힌다
2. 처음 보는 사람이 모를 단어가 설명 없이 나온다
3. 🔴 가 4개 이상이다
4. 표에 열이 5개 이상이다
5. 6줄 넘는 문단이 있다
