## 준비

- 핫스팟(SSH 허용 대역)에 연결한다. SSH 가 안 되면 `설정.연결 = "mock"` 으로 흐름 · 화면 가지만 볼 수 있다.
- VS Code 로 이 작업트리 폴더를 연다: `code ".claude/worktrees/판정디버깅"`
- `debug/설정.py` 에서 한 문장 · 화면 1 칸 · 계정(이메일) · 추적 범위를 고른다.
- 시작하면 `운영 배포 SHA` 와 `이 코드 SHA` 를 비교해 찍는다. 다르면 `git -C .claude/worktrees/판정디버깅 merge --ff-only origin/main`.

- 터미널에는 단계별 방식과 같은 [화면] · [재시도] · ◆ 판정 내부 · [디버그 ③] 줄과 단계마다 `── 기록:` 줄이 나온다. 판정 뒤에는 `[판정 결과]` 와 「같은 입력의 이전 판정과 비교」(판정 · 인용 doc_id 조번호 · 검증코드, `실행기록/판정비교.json`)가 나온다.
- 흐름 요청은 잠금으로 하나씩 처리한다. 판정 내부 중단점은 `설정.서버_판정내부_멈춤 = True` + VS Code 디버거일 때만(입력을 기다리지 않는다). **이 중단점 경로는 디버거로 직접 확인하지 않았다.**
- **핫 리로드**: 흐름 요청마다 `설정.핫리로드_대상`(assemble_context · retrieve · ontology_lookup · ontology_context · normalize_run · expense_input_check · web_research · item_classify · question_generate · orchestrate) 파일이 바뀌었으면 다시 읽고 `from X import Y` 로 가져간 참조와 키트 패치를 다시 건다. 터미널 `[핫 리로드] X.py 다시 읽음 · 참조 n곳 바꿈`. 문법 오류면 `[핫 리로드 실패]` 를 찍고 이전 코드로 계속 돈다. server/* · llm_qwen · research_runtime · response_cache · _lib/db 는 대상이 아니다(서버를 다시 띄운다).
- **응답 재생**: ① ② ③ 요청 본문(멱등키 제외) · 계정이 같고 그 요청이 실행한 scripts/ · server/ 파일(호출 추적이 본 파일)이 그대로면 녹화한 응답을 바이트 그대로 보내고 조사 세션을 그 요청이 끝났을 때로 되돌린다(`[재생] NN_questions 0.1s (바뀐 파일 없음)`). 파일이 바뀌면 `[새로 실행] 바뀐 파일: …`. 판정 · 실패 응답(다시시도 · 오류 · 상태 실패)은 재생하지 않는다. 녹화는 서버 프로세스 메모리에만 있다. 끄기: `설정.응답재생 = False`.
- 예) `assemble_context.py` 시스템 프롬프트를 고치고 화면에서 같은 지출을 다시 점검 → ① ② ③ 은 [재생], 판정만 새 프롬프트로 돈다.
- 다른 쓰기(프로필 · 첨부 · 팀 · L3 등)는 `403 디버그 서버는 운영 DB 에 쓰지 않습니다` 와 `[쓰기 막힘]` 줄. 디버그 서버를 끄면 메모리 저장소도 사라진다.
- 단계별 방식에서 `설정.화면API_주소 = "http://127.0.0.1:8000"`(또는 env `SUDDOE_DEBUG_API`)이면 1~6번 칸 요청을 떠 있는 디버그 서버로 보낸다(계획 저장 포함, 「Bearer debug」 = 설정.이메일 계정).

## 검색만 다시 (LLM 없음)

`python debug/판정_단계별.py 검색다시 debug/실행기록/<시각>/NN_judge` (또는 Interactive 에서 `검색_다시(폴더)`, launch 「검색만 다시」). 판정_인자.json 으로 `orchestrate.판정()` 을 운영 순서로 돌리되 근거구성(_새_프롬프트단계) 앞에서 멈춘다. 고친 핫 리로드 대상 모듈을 먼저 다시 읽고, 녹화한 판정내부/*.json 과 적용 규범 · 근거 조문 · 검색 청크 · 참조 확장 · L3 조문의 추가(+) · 빠짐(-) · 순위 이동(↕)을 찍는다. 터널 포트는 15437 · 11083 이라 디버그 서버와 같이 돌릴 수 있다. 추가 규정 조회(④-2 LLM)는 건너뛰므로 녹화에 그 결과가 있으면 그만큼 차이로 보인다(줄로 알려 준다).

## 운영과 다른 점

- DB 쓰기는 하지 않는다. 응답 캐시 · 질문세트 · 조사 세션은 이 프로세스 메모리, 판정 기록은 파일로 남긴다. 계획을 저장하지 않아(plan_id 없음) 「저장」 이벤트는 `plan_id 없음` 이고, 판정 요청의 `정규화` 는 프론트 `저장할정규화` 와 같은 모양으로 키트가 만든다.
- 로그인은 `설정.이메일` 로 `tenant.로그인주체` 를 불러 정한다(토큰 검증 생략). mock 은 게스트.
- SSH 터널 때문에 SQL 이 느리다. `DB시간_예산에서_빼기` 가 그 시간을 예산에서 뺀다. 호출 추적도 파이썬을 느리게 한다.
- `예산초` 가 운영 세션 예산(600초, v061 부터 · 그 전 300초)보다 크면 웹 조사 벽시계 상한(② · ④-2 · ③-R)과 판정 마감(660초)도 늘린다. `/api/judge` 는 시작할 때 세션 예산을 600초 · LLM 40회 이상으로 늘린다(운영과 같다). 계획 · 도구 횟수 상한은 그대로다. 운영 그대로 재현할 때는 600.
- 단계 사이에서 멈춘 시간은 예산에서 빠진다. 하루 요청 한도는 끈다(`요청한도_끄기`).
