## 3. GPU 상태 계약 실측 — 모달 mock 설계 전제 (server/gpu_watchdog.py:410-426)

```
GET  /api/gpu/status   → {"상태":"가동|중지|기동중","유휴초":n,"종료예정초":n|null,
                           "경고초":n,"유휴임계초":n,"제어가능":bool}
                          (캐시값 반환 — 폴링해도 RunPod API 안 침)
POST /api/gpu/keepalive → 워치독.keepalive() (유휴 타이머 리셋, 「더 쓸게요」용)
```

🔴 **`POST /api/gpu/wake` 는 아직 없다** — Q2 지시서 항목1이 이걸 새로 만드는 일이다(0904 실측
문서에도 "둘뿐"이라 적혀 있음, 직접 코드로 재확인함). 지금 구조는 «깨우기 전용 엔드포인트»가 아니라
`POST /api/normalize`·`/api/judge` 호출 자체가 `게이트()`를 태워 상태가 중지/기동중이면
`GPU기동실패` 를 던지고 그게 판단불가로 닫힌다(`gpu_watchdog.py:387-397`).
`기동_진행()` 제너레이터(L340-385)가 SSE 로 `{"단계":"기동","설명":"..."}` 이벤트를 이미 내보내고 있음
— 로그인 직후 모달이 아니라 **판정 SSE 스트림 안에서** 기동 이벤트가 나오는 구조로 보인다.

→ 결론(관측): `POST /api/gpu/wake` 는 코드에 없다. `POST /api/normalize`·`/api/judge` 가 스스로
`게이트()`를 태우고, 상태가 중지·기동중이면 `GPU기동실패`를 던져 판단불가로 닫힌다. `기동_진행()`
제너레이터가 판정 SSE 스트림 안에서 이미 `{"단계":"기동","설명":...}` 이벤트를 내보낸다.

→ 추론(중앙 승인, 09-04): 없는 `wake` 계약에 UI 를 맞추면 Q2 가 못 낼 때 화면이 죽는다. 오늘 GPU 는
거의 안 켜므로(오너 「과사용 절대 금지」) QA 팀원이 실제로 밟을 경로는 「GPU 꺼짐 → 판단불가 + 문의초안」
쪽일 가능성이 높다. **순서를 ㄷ(빨간 오류로 안 그리기) → ㄱ(판정 SSE 기동 이벤트로 대기 표시,
경과시간 세기 — 10~12분은 추정치라 고정 숫자로 안 박는다) → ㄴ(status 폴링, 사용중 표시) → ㄹ(wake
서면 트리거만 추가) 로 만든다.** `기존 wake 폴링 모달` 설계는 폐기.
