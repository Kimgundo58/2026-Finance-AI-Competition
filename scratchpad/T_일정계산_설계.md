## 0. 결론부터 — «맨 먼저 셀 것»을 셌더니 대부분 이미 있었다

```
🔴 기한 «규칙» 은 이미 있다 — corpus.check_items.기본_오프셋일, 52건 «전부» 값이 채워져 있다
🔴 계산식도 이미 있다 — server/routes_tasks.py::_실_동기화() 가
     due_date = 집행예정일 + timedelta(days=기본_오프셋일)
   을 «이미 실행 중» 이다 (목 경로 아니라 실 경로, DB 에 INSERT/UPDATE 까지 한다)
🔴 API 도 이미 있다 — POST /api/plans/{id}/tasks:sync · POST .../tasks · PATCH .../tasks/{id}
   ai-8c 짐작대로 «새 API 는 필요 없다»가 맞다
🔴 기준일 없을 때 처리도 이미 맞게 돼 있다 — 집행예정일 또는 기본_오프셋일이 None 이면
   due_date=None (routes_tasks.py:311-314). 추정 날짜를 만들어 넣지 않는다
🔴 DB CHECK 까지 있다 — ck_check_items_오프셋부호 (db/init/04_agent.sql:234) 가
   결제전=음수·결제후=양수 부호를 «적재 시점에» 막는다. 부호 실수는 이미 구조적으로 막혀 있다
```

**그래서 이 설계 문서가 다룰 것은 "처음부터 설계"가 아니라 "이미 있는 걸 확인하고,
«실제로 빈» 두 자리만 채우는 제안"이다.**

## 2. 세 갈래 재확인 결과

### (1) 기한 «규칙» — 있다. 다만 «오프셋 숫자 자체»의 검증은 빠져 있었다 (신규 발견)

`기본_오프셋일`은 52건 전부 채워져 있다(값 범위 -14~+30). 그런데 로드 전 통과조건
"(c) 수치 접지"(seed_check_items.py 주석)는 **「항목·설명 문장이 말하는 금액·기간」**만
인용 조문과 대조하지, **오프셋 정수 컬럼 자체의 숫자**는 대조 대상이 아니다 — "항목" 텍스트에
"14일"이라는 글자가 없으면 검사할 문자열이 없기 때문이다. 그래서 오프셋 숫자는 컬럼에
박히는 순간부터 사람이 눈으로 넣은 값을 그대로 믿는 구조다.

🔴 **실제로 걸린 사례** — `국외출장사전보고`(사업명=NULL, 공통) `기본_오프셋일=-14`.
레인 O(check_items 52건 근거 재확인, 오늘 앞서 한 작업)에서 이미 이 항목을 "불일치"로
잡았다: L1 제43조(공통 근거)엔 "출국일 이전에" 보고하라고만 있지 «14일»이라는 숫자가
없다. 실제로 "14일"이 명시된 곳은 **재도전성공패키지 제17조①**뿐이다(예비·초격차 등
다른 사업은 "출국일 이전"까지만 있고 숫자가 없음). 즉 재도전 하나의 숫자가 공통(NULL)
행에 얹혀 8개 사업 전부에 뿌려지고 있다 — 사업마다 실제 요구 기한이 다르거나 «없을»
수도 있는데 전부 "D-14"로 뜬다.
→ 제안: 이 항목을 공통(NULL, -14)에서 **재도전성공패키지 전용 행(-14)**으로 옮기고,
  나머지 사업(공통 근거로만 남는 것)은 기본_오프셋일을 **NULL**로 낮춘다(체크리스트에는
  뜨되 캘린더 기한은 없음 — "출국일 이전"이라는 사실만 있고 정량 기한이 없으므로 정직하다).
  같은 패턴(어느 사업 하나의 숫자가 공통 행에 얹혔는지)이 52건 중 더 있는지는 O 레인
  산출물(scratchpad/O_check_items_근거.json)의 "L1 근거초과" 유형 11건을 한 번 더
  훑으면 나온다 — 시간상 이번엔 이 1건만 실측했다.

### (2) 기한의 «근거» — 진짜 빈 칸이다

`corpus.check_items.근거`(JSONB)는 **그 체크항목이 왜 존재하는지**의 근거이지,
**그 오프셋 «숫자»가 어디서 왔는지**의 근거가 아니다. 지금은 이 둘이 같은 칸에
뭉쳐 있어서, "자산등록=30"이 「제39조⑦의 '취득한 날로부터 1개월 이내'를 30일로
환산한 값이다」라는 걸 사람이 기억으로만 안다 — 코드 어디에도 안 적혀 있다.

**추가 제안**: `corpus.check_items`에 `기한근거 TEXT` (또는 `JSONB`) 한 칸 추가.
```sql
ALTER TABLE corpus.check_items ADD COLUMN 기한근거 TEXT;
-- 예: 자산등록      -> "제39조⑦ '취득한 날로부터 1개월 이내 등록' → 30일"
--     비교견적준비   -> "제38조④ 2인 이상 견적 요건은 있으나 '몇 일 전'은 명시 없음 → 임의값(협의 필요)"
--     국외출장사전보고(재도전용) -> "재도전 제17조① '출장예정일 14일 전까지' → 14일(재도전 고유, 공통 아님)"
```
빈 칸이 남아도 된다 — 위 (1)처럼 "임의값"이라고 «정직하게 적는 것» 자체가 목적이다.
지금은 그 임의성이 완전히 안 보인다(코드 값과 검증된 근거가 시각적으로 구분이 안 됨).

### (3) 기준일이 없을 때 — 이미 옳게 처리돼 있다 (재확인만)

`_실_동기화()`(routes_tasks.py:311-314)가 `집행예정일 is None or 오프셋 is None`이면
`due_date=None`을 그대로 쓴다. 그 위의 API(`할일동기화`)도 이 값을 그대로 받아
INSERT하므로 "아마 이때쯤"을 만드는 코드 경로 자체가 없다. **추가 설계 불필요.**

## 3. 타임존 — 계산 자체엔 문제 없다. 다만 «원칙을 문서에 못박아야» 한다

```
집행예정일 : DATE (db/init/02_frontend.sql:91)
due_date   : DATE (db/init/02_frontend.sql:129)
계산       : Python date + timedelta(days=n)  — 시(時)·분·초·TZ 가 아예 없다
```
**그래서 `due_date = 집행예정일 + 기본_오프셋일` 이 식 자체는 TZ 로 하루가 갈릴 여지가
없다** — DATE 대 DATE 덧셈이라 서버가 UTC 든 KST 든 결과가 같다. ai-8c 가 지적한
"DB TimeZone=Etc/UTC" 문제는 **이 계산에는 해당하지 않는다.**

🔴 그런데 이 코드베이스엔 "오늘"을 서버가 직접 계산하는 다른 함수가 이미 있고,
그건 **UTC 자정** 기준으로 못박혀 있다:
```
server/main.py:117           _오늘()  — 비용가드 일일캡 리셋용
server/gpu_watchdog.py:326   "날짜 경계는 비용가드._오늘()과 같은 UTC 자정이다"
```
지금은 `할일`쪽에 "오늘"을 서버가 계산하는 코드가 «없다»(GET /api/tasks 는 정렬만
하지 D-day 뱃지를 만들지 않는다 — 그 계산은 프론트가 브라우저 로컬시간으로 하는 것으로
보인다. 한국 사용자면 우연히 KST 라 지금은 안 터진다). 하지만 나중에 "마감 D-3 알림"·
"지연됨" 배지 같은 걸 **서버**에 넣게 되면, 위 `_오늘()` 패턴을 그대로 베끼기 쉽다 —
그러면 자정 전후 9시간 구간에서 하루가 갈린다.

**설계 원칙(못박기)**: **이 프로젝트에서 "오늘"과 관련된 날짜 비교(지연·D-day·마감
알림)는 전부 KST(Asia/Seoul) 자정 기준으로 계산한다.** UTC 자정 기준 `_오늘()`은
비용가드·GPU 워치독처럼 "내부 운영 시각"에만 쓰고, 사용자에게 보이는 날짜 판단에는
쓰지 않는다. — 지금 당장 코드를 고칠 필요는 없다(현재 안 쓰고 있으므로), 다음 사람이
서버 쪽에 D-day 계산을 넣을 때 참조할 자리로 이 문서에 못박아 둔다.

## 4. 정리 — 실제로 «만들어야 할 것»은 둘 뿐이다

```
① corpus.check_items.기한근거 칼럼 추가 (오프셋 숫자의 출처, 없으면 "임의값"이라고 적는다)
② 국외출장사전보고 등 "공통 근거인데 숫자는 사업 하나에서 왔다" 패턴을 O 레인 산출물
   기준으로 전수 재검토 — 이번엔 1건(국외출장사전보고)만 실측 확인했다
그 외(계산식·API·NULL 처리·부호 검사)는 «이미 완성돼 있다». 새로 설계할 게 없다.
```

## 5. 하지 않은 것

- DB·scripts 고치지 않았다 — 위 ①②는 «제안»이고 SQL 은 예시일 뿐, 실행하지 않았다
- 52건 전부의 "오프셋 숫자 vs 조문 실측 대조"는 시간상 다 못했다. `국외출장사전보고`
  1건만 O 레인 결과와 겹쳐 확인했다 — 나머지 51건 중 같은 패턴이 더 있을 가능성은
  «있다»(부인 못함), 없다고 말한 적 없다
