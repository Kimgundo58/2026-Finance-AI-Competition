## 1. 결제후 필요 증빙 — 렌더는 정상, 저장 단계가 버그

**실화면 확인** (prototype@ssudo.kr, 경상국립대 창업중심대학):
- "결제 후 필요 증빙" 섹션은 **이미 화면에 있다**(스크롤 하단, "3" 카드). 프론트 필터링(`adapt.ts:243`
  `할일들.filter(t.구분==="결제후")`)도 정상 — 있으면 그린다.
- plan 23495(홍보영상 외주 25,000,000원): `판정상세.해야할일`에 `외주검수조서`·`거래처증빙수취`
  (둘 다 check_items 마스터 기준 구분='결제후')가 **정상적으로 포함**됨 — LLM도 정상.
- 그런데 `tenant.plan_tasks`에 저장된 실제 행은 **14개 코드 전량 구분='결제전'**(외주검수조서·
  거래처증빙수취 포함). 화면의 "0/0"은 저장이 잘못됐기 때문.

**원인**: `server/routes_tasks.py::_실_동기화()` → `_체크항목_조회(코드)` → `_질의()`가
실패하면 조용히 `[]`을 반환(`_common.py::_질의` 기본 동작, `예외전파=False`) → 구분이
`None` → `구분 = 구분 or "결제전"`(routes_tasks.py:353)로 전부 덮임.
로컬 DB로는 완전히 동일한 쿼리가 정상 작동(`외주검수조서`→`결제후` 확인) — 코드 로직 자체는
무죄. **production 쪽에서만 실패하는 것으로 보이나, production DB에 직접 못 붙어 정확한
실패 원인(스키마 드리프트 vs 배포 지연 vs 연결 이슈)까지는 못 좁혔다.**

**적용한 수정** (`server/routes_tasks.py`, diff 아래): `_체크항목_조회()`가 실패/빈 결과일
때 **로그를 남기도록** 바꿨다. 동작(안전한 결제전 기본값)은 그대로 — `_질의()`의 전역
스왈로우 정책은 안 건드렸다(37개 호출부 영향 범위 밖). 이제 이 실패가 재현되면 Cloud Run
로그에서 바로 잡힌다. **다음 사람 할 일**: production Cloud SQL에서
`SELECT 구분 FROM corpus.check_items WHERE code='외주검수조서'` 한 줄 — 빈 결과면
스키마/데이터 drift, 있으면 배포본이 낡은 것.

pytest 로컬 확인: `test_tasks.py`(7) + `test_contract.py`+`test_tenant_isolation.py`(71+1xfail)
전부 통과 — 회귀 없음.

## 2. 비목후보[].설명 — 이미 안전하게 처리돼 있다, 서버 필드 추가는 보류 권장

프론트(`checkumait-app.tsx:3050`, `lib/server-types.ts:96`)를 다시 보니 이미
`설명?: string | null` **옵셔널**로 타입이 잡혀 있고, `c.설명 ? [...] : []`로 없으면
그냥 설명 줄을 안 그린다. **크래시·깨진 화면 없음** — HANDOFF의 "영원히 안 그려진다"는
사실이지만 "고장"은 아니다(프론트가 서버의 미래 확장을 미리 대비해 둔 상태).

서버(`models.py:76 비목후보`)에 `설명`을 채우려면 `_폼_비목후보()`/`normalize_run.정규화()`가
쓰는 LLM 스키마(`호출자리1_스키마`)에 필드를 추가하고 프롬프트도 바꿔야 한다 — **정규화 경로
전체(판정 1건당 필수 LLM 호출)에 영향**이라 이 자리에서 가볍게 건드릴 범위가 아니라고
판단했다(오늘 토큰 예산 이슈도 있었음). 제안: 지금은 그대로 두고, 필요해지면 별도 레인에서
스키마+프롬프트 A/B로 다룬다.
