# recheck_queue BASIS_AMENDED 표본 검증 (레인 R)

**30건 중 30건 완료 · 근거유효 15 / 근거변경됨 15 / 확인불가 0**

작성: 레인 R · 검증 방법: DB SELECT만(읽기전용), recheck_queue UPDATE 없음.

## 표본 방법

```sql
SELECT queue_id, 사업명, 비목, doc_id, 조번호, 구doc_id, 구조번호, 유사도, 요약
FROM corpus.recheck_queue
WHERE 사유코드='BASIS_AMENDED' AND 상태='대기'   -- 모집단 264건
ORDER BY random()
LIMIT 30
```
🔴 seed 는 안 걸었다(고정 seed 로 재현하는 대신, **뽑힌 queue_id 30개를 아래에 그대로 적어
재현 가능하게 했다** — DB 상태가 바뀌어도 이 30건 자체는 queue_id 로 다시 조회할 수 있다).
앞자르기 아님 — 사업명 7종(L1 상위지침 포함)에 분산 확인.

초격차 스타트업 프로젝트 5 · 초기창업패키지 3 · 예비창업패키지 1 · 재도전성공패키지 1
→ 한 사업에 쏠리지 않음. 264건 전체의 분포를 보증하진 않지만 이 표본은 단일사업 편향은 아니다.

**「없다 vs 못 봤다」 함정(㉠) 점검**: 30건 전부 `doc_id+조번호` 조합으로 신판 조문을 바로
찾았다. 조 제목 재매칭이 «필요했던» 경우는 매칭 실패 0건 — 다만 아래 «2961»은 조번호로
찾아지긴 했으나 **찾아진 조문이 엉뚱한 조문**이어서 별도로 조제목 재매칭을 했다(밑에 상술).

```

     · 9건은 0906 표 복구(table_splice)로 «신판만» 마크다운 표로 재포맷돼서 생긴

   조문»이 나온다 — 신판 제29조는 «사업비 집행»(참고3·4 인용, 점검·회계감사)이다.
   조 제목 "자기부담사업비" 로 신판을 재매칭하니 «제28조»가 진짜 후속 조문이었고,

   → recheck_queue 의 (doc_id, 조번호) 포인터를 그대로 믿고 대조하면 완전히 엉뚱한
     조문을 「이게 신판이다」로 착각한다. 조번호는 «재사용»될 수 있다 — 없어지는

   유사도 숫자만으로 위험도를 가늠하면 안 된다는 근거다
```
