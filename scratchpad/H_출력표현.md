## H-2① 「전제.사실」 minLength — 5 (오너 초안 12 아님, 조건부 승인)

```
llm_schema.py 판정_스키마() — "사실": {"type":"string","minLength":5}
```

**근거(실측, run 195 원출력 전제.사실 180개)**
```
길이<=4자  100/180(55.6%) «전부» 가비지 — S번호 패턴 76건("S03" 등) + 맨 단어 24건
          ("용도"·"증빙"·"인건비") — 예외 0건
정상 사실도 짧다 — "사전승인 완료"(7자) · "수량 과하지 않음"(9자) 실재
=> 오너 초안 12 는 이 둘을 «수집 손실» 시킨다. 5 는 손실 없이 확인된 가비지를 막는다.
```

🔴 **ai-8c 조건부 승인의 조건 — 반드시 남기라고 한 문장**
```
문법 제약은 지식을 만들지 않는다. 실패의 «모양» 을 바꿀 뿐이다.
  지금  3자 가비지를 뱉는다
  이후  5자 이상으로 «늘어난» 가비지를 뱉을 수 있다 — "시제품 제작"(6자) 류 명사구가
       5~14자 구간에 «이미» 섞여 있어(같은 실측), 그 자리로 옮겨갈 뿐일 수 있다
=> «부분 방어» 다. 「가비지 100건이 사라진다」로 세지 않는다 — 사라지는지는 GPU 를
   켜야 안다. 이 세션은 그걸 확인하지 «않았다»(할 수 없었다).
```

## H-2② 「전제.매핑」(F필드) — enum 안 닫음, B0/B5.5 안내로 대신

```
DB 실측 — F필드 후보 16개 중 11개가 «0행» 테이블 소속
  f_profile(F1)  5개 실사용컬럼, 1행 존재
  f_exec(F3)     6개 컬럼, «0행»
  f_personnel(F4) 5개 컬럼, «0행»
```
지시서의 "짧거나 비면 enum 으로 닫지 말고 프롬프트 예시로" 조건에 해당한다고 판단해
guided_json 은 안 건드렸다(리스크 회피 — ai-8c 도 동의). 대신:
```
assemble_context.py B0(고정) 에 추가:
  "전제.매핑" 은 규정 조항이 아니라 «확인이 필요한 필드» 다. 예: F1.협약종료일 ·
  F4.고용형태 · F3.거래처.
```
🔴 **표기 사고 하나 잡고 고쳤다** — 처음에 "f_profile.협약종료일" 식(테이블명 그대로)
으로 썼는데, 실제 검증 규칙(`llm_validate.py::f_경로집합()`)은 `F1`·`F3`·`F4` 축
번호 표기를 쓴다. 고치지 않았으면 LLM 이 내 예시를 그대로 따라 써도 검증기가
「매핑 밖」으로 폐기했을 것이다 — 코드를 안 읽고 예시만 손으로 썼으면 냈을 결함.

## H-2③ 해야할일·확인필요 — B0/B5.5 안내문 신설 + 전제 원문 치환 배선

### 프롬프트에 실제로 안내가 들어갔다 (실측)

H-1 확정 원인 그대로 — B6 프롬프트가 "해야할일"을 한 글자도 설명 안 했다.
`assemble_context.py::조립()` 에 다음을 추가했다:
```
B0(고정)   "해야할일" 이 뭘 위한 필드인지 · 후보에 없는 code 를 지어내지 말 것
B5.5(가변) 그 사업의 check_items 후보 목록(code·항목·설명) — 코드들 을 주면 실린다
```
🔴 **B0 에 후보 목록 «자체» 는 안 넣었다** — 사업마다 38~41개로 달라 prefix 캐시가
문항마다 깨진다(ai-8c 지시). 후보는 B5(가변) 뒤에 실었다.

**실측(gold_id=330, 예비창업패키지, 코드들 40개 전달)**
```
프롬프트 길이  552자 -> 4,337자 (check_items 40건이 실제로 실렸다 — 그 안 눈으로 확인함)
```
🔴 이건 **비용**이다 — 문항당 토큰이 늘고 지연이 늘 수 있다. 「해야할일 0개 문제를
고쳤다」로 안 쓴다. 「원인 셋(check_items 미전달·B6 안내 없음·minItems 없음) 중
앞의 둘을 프롬프트 레벨에서 닫았다」다. minItems 는 그대로 뒀다(강제하면 해당
없는 문항에도 code 를 지어낼 위험 — 골든셋 실측 "해야할일 보유율: 가능 26%" =
비는 게 «맞는» 경우가 실제 있다).

### 「S03」 이 화면에 안 나가게 — 전제 원문 치환 배선 (H-2③의 진짜 요구)

`전제.근거조항`(S번호)이 `인용`과 «같은 s맵 체계» 인데 문서/원문으로 안 풀려서
`server/inquiry.py` 가 "지침은 「S03」이 정하고 있습니다" 를 낼 뻔했다(관측 — 아직
실제로 나간 적은 없다, 근거조항 미매핑이면 (5)에서 폐기되어 왔다. 위험은 매핑됐는데
«문서로 안 풀린» 경우다).

`llm_schema.py::전제` 데이터클래스에 `인용`과 같은 필드(doc_id·조번호·조제목·원문·
원문범위)를 추가하고, `llm_validate.py::검증()` 의 전제 루프에서 `s번호_메타()` 로
채운다. `인용`과 다른 점 하나 — DB 미스여도 **전제를 폐기하지 않는다**(`사실` 자체는
유효한 정보라서). 대신 `PREMISE_DB_MISSING` 강등코드를 남긴다.

🔴 **원문은 코드가 DB 에서 치환한다. LLM 은 원문을 안 쓴다** — CLAUDE.md 원칙 그대로.
치환 주체도 `인용`과 같다: 조립기(3)가 아니라 (6) 검증·강등기다.

**돌려서 확인함(GPU 0, DB 0 — s맵/메타 합성)**
```
S01(정상): 전제목록[0] = {..., doc_id:'d1', 조번호:'제41조', 조제목:'인건비',
           원문:'인건비 지급 대상은…', 원문범위:'항'}
S99(DB미스): doc_id~원문범위 전부 None · 강등코드 PREMISE_DB_MISSING · 사실은 안 지워짐
llm_validate.py --self-test  층B 회귀 전건 통과(무변경)
```

🔴 **문서를 실제로 조립하는 문장 템플릿("지금 정보로는...")은 안 만들었다.** 위
작업으로 백엔드는 이제 «완결된 데이터»(문서명·조번호·원문)를 갖췄지만, 그걸 그
정확한 문장 모양으로 짜 붙이는 코드는 아직 없다. `server/inquiry.py::문의초안()`
이 판단불가→기관문의 용도로 있고, 화면(조건부의 "확인 필요") 쪽엔 그런 조립 함수가
없다 — 있는지 찾아봤고 없다(`grep '지금 정보로는' scripts/ server/` = 0건). 프론트가
구조화된 필드를 받아 직접 그리는 패턴(`server/main.py` 의 `_할일_보강` 등)이 이미
있어서, 이 문장 조립도 프론트 몫일 가능성이 있다 — **판단을 안 하고 그대로 남긴다.**

## H-3 「결제 전/후」— 스키마 단순화 + 실제 조회 배선 + 증빙 전수검사

### 해야할일 스키마 — code 만 LLM, 항목·설명은 DB (ai-8c 승인)

```
llm_schema.py 판정_스키마() — 코드들 있을 때:
  이전  required=["code","항목","설명"]  (LLM 이 셋 다 씀)
  이후  required=["code"]                (LLM 은 code 만. 항목·설명 properties 에서도 뺌)
        🔴 코드들 없을 때(폴백, §3-4 원형) 분기는 «그대로» 뒀다 — 같이 고치면 무너진다
```
근거: `인용`(S번호만 LLM)과 같은 자리다. `체크코드_enum` 독스트링이 "이 테이블의
존재 이유가 «안정 식별자»" 라고 이미 말한다 — 지금까지의 스키마가 그 원칙에서
벗어나 있었다(늘리는 게 아니라 되돌리는 것 — ai-8c 판단).

**배선 — 같은 커밋에서 항목·설명을 채우는 코드를 넣었다** (안 넣으면 「code 만
있고 글자 없는 빈 껍데기」가 돼 지금(0개)보다 나빠진다):
```
llm_validate.py::체크항목_본문(codes, dsn)  corpus.check_items -> {항목,설명}
llm_validate.py::검증() 5-b            체크코드(허용코드) 준 실전 호출만 새 경로.
                                       옛 계약(체크코드 미제공)은 손 안 댐 —
                                       그래서 층B 회귀가 그대로 산다(아래 실측)
```

**돌려서 확인함**
```
정상 code            -> {code, 항목, 설명} DB 값으로 채워짐(실 DB 조회, 40/40 code 일치)
허용목록 밖 code       -> TASK_CODE_INVALID, 폐기
허용됐는데 DB 에 없는 code -> {code} 만 남김, TASK_DB_MISSING (폐기 안 함)
jsonschema 샘플 accept/reject 7건 — 전부 설계대로(아래 표)
llm_validate.py --self-test  층B 회귀 전건 통과(무변경 — 이게 중요하다. 처음엔
  `c is not None` 으로 갈랐다가 옛 계약 호출까지 걸려 8건이 깨졌었다. `허용코드
  is not None`(체크코드 «전달 여부») 으로 다시 가르고 나서 통과했다 — 실측으로 잡음)
```

| 샘플 | 결과 |
|---|---|
| 사실="S03"(3자) | 거부 (minLength 5) |
| 사실="용역금액 2천만원 미만"(12자) | 통과 |
| 사실 정확히 5자 | 통과 (경계) |
| 사실 정확히 4자 | 거부 (경계) |
| 해야할일 {code}만 | 통과 |
| 해야할일 {code,항목,설명} | 거부 (additionalProperties) |
| 해야할일 code=폐쇄목록 밖 | 거부 (enum) |

### 증빙→발급처 — 표본 아니라 «전수» 검사함 (오너가 직접 지목한 항목)

```
corpus.rules.증빙 채워진 71행 전부(사업·비목 가리지 않고) 대조
  전체 증빙 항목(중복 포함) 609건 · 고유 증빙명 71종
  evidence_sources.증빙명 과 일치  609/609 (100%) · 조인 실패 0건
```
🔴 창업중심대학 인건비 10/10(표본 하나) 을 「전체가 그렇다」로 넘기지 않았다 —
전 사업·전 비목을 실제로 세었고, 결과는 표본과 같았다(0건 불일치). 그렇다고
"완벽하다"로 안 쓴다 — 이름이 일치한다는 뜻이지, 발급처 «내용» 이 맞는지는
이 검사 범위 밖이다.

**배선** — `orchestrate.py::증빙_발급처(cur, 룰)` 신설, 판정 응답에 `증빙목록` 키로
얹었다. `룰.증빙`(매치된 규정의 증빙 배열) 을 그대로 쓰고, 없는 이름이면(실측상
없었지만) **발급처를 비우고 이름만** 낸다 — 지어내지 않는다.

**돌려서 확인함(실 DB)**: 인건비 규정 하나로 `증빙_발급처()` 를 직접 호출 —
10종 전부 실제 발급처 문자열로 채워짐(예: "4대사회보험 정보연계센터(4insure.or.kr)").

### 「【결제 전】/【결제 후 — 증빙】」 2섹션 리터럴 문자열은 안 만들었다

H-2③ 과 같은 이유다 — 그 정확한 문자열을 조립하는 코드가 지금 아무 데도 없다
(`grep '결제 전\|챙기실 서류\|하실 일' scripts/ server/` = 실사용 코드 0건). 대신
백엔드는 이제 그 섹션을 채울 «재료» 를 전부 구조화해서 갖고 있다:
```
【결제 전】(1) 하실 일   <- 해야할일[].항목 (이제 DB 원문, 구분='결제전' 로 이미 걸러짐,
                          server/main.py::_할일_보강 이 구분·유형을 얹는다)
       (2) 근거        <- 전제[].doc_id·조번호·원문 (이번에 새로 채워짐)
【결제 후 — 증빙】(1) 챙기실 서류  <- 증빙목록[].증빙명 (이번에 새로 신설)
             (2) 어디서 받나    <- 증빙목록[].발급처 (이번에 새로 신설)
```
문자열로 짜 붙이는 자리를 backend(scripts/ 또는 server/)에 새로 만들지, 프론트가
이 구조화 필드를 직접 그릴지는 **정하지 않았다** — server/main.py 가 이미 구조화된
필드를 그대로 넘기고 프론트가 그리는 패턴을 쓰고 있어서(`_할일_보강` 등), 그
쪽에 가깝다고 «추정» 만 하고 판단은 넘긴다.

## 확인된 것 / 확인 «안» 된 것 (ai-8c 요구대로 갈라 쓴다)

```
확인된 것
  · 스키마가 설계대로 바뀐다(jsonschema accept/reject 7건 전부 의도대로)
  · 오프라인 검증()이 새 경로·옛 경로 둘 다 통과한다(합성 데이터 + 실 DB 조회 둘 다)
  · 기존 층B 회귀 전건 통과 — 회귀 없음
  · 프롬프트에 check_items·F필드 안내가 실제로 실린다(문자 그대로 확인)
  · 증빙→발급처 조인 실패 0/609(전수) · 체크항목 DB 조회 40/40 일치(전수, 예비창업)

확인 «안» 된 것 (GPU 필요 — 이 레인 밖)
  · 이 변경들이 실제 판정에서 해야할일·전제를 «채우는가»
  · minLength 5 가 가비지를 «줄이는가» 아니면 «모양만 바꾸는가»
```
