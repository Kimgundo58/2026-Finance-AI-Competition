## ③ 재시도 정책 — 두 파일이 다르고, 그게 맞다

**adapter.py(`LocalVLLM.호출`, 죽은 경로)**: 좁게 짰다. `_재시도가능()` 이 "서버에
안 닿고 끊긴" 경우(`URLError`·`ConnectionError`)만 재시도하고, 읽기 타임아웃·HTTP
524(`HTTPError`)는 즉시 올린다 — 이미 서버에 요청이 도달해 생성이 시작됐을 수 있는
상태에서 재시도하면 GPU 가 같은 프롬프트를 두 번 생성한다는 게 처음 내 판단이었다.

**normalize_run.py(`llm_호출`, 실경로)**: **의도적으로 다르다 — 좁히지 않았다.**
ai-04 가 바로잡아 준 지점이다 — 이 도메인의 vLLM 추론 호출은 DB 를 쓰지 않는 순수
조회성이라 "두 번 생성"의 대가가 GPU 요금뿐이고, 지금 우선순위는 요금 절약보다
성공률이다. 그리고 실측으로 그 "묻지마 재시도"(기존 `재시도=1`)가 **이미 정규화
38건·판정 10건, 도합 48건을 살리고 있다**는 게 확인됐다 — 여기에 멱등성 검사를
들이대면 그 48건이 판단불가로 되돌아간다. `adapter.py` 의 `_재시도가능()` 독스트링에
**"두 파일이 왜 다른지"** 를 명시해 뒀다 — 다음 사람이 "통일하자"며 좁은 정책을
실경로에 옮기면 이 48건이 죽는다는 경고와 함께.

부작용 하나는 적어 둔다: 이 무조건 재시도 때문에 판정LLM 「성공」 지연의 상위 분위가
234~253초로 뭉쳐 있다 — 1차 시도가 524 로 죽고 2차가 성공한 걸 하나로 합산해 「성공
92초」 처럼 보이게 만든 것이다(`실측_프록시_125초천장.md`). 이 재시도 정책은 안
바꿨으므로 다음 run 에서도 이 뭉침은 그대로 나타날 것이다 — **퇴행이 아니라 이미
있던 특성**이니 «이번에 갑자기 234초짜리가 생겼다」로 오독하지 말 것.

## ②'' 최종 — 검증 완료, 결정됨 (ai-04 실측, 2026-09-05)

내 A/B ①②는 **조건에 못 닿았다** — 테스트 프롬프트가 `max_tokens=2000`을 사고
(reasoning)만으로 다 써서 36초 만에 `finish_reason=length`로 끝났다(125초 천장 근처도
못 갔다). 이건 파싱 버그가 아니라 시험 설계 문제였다 — ai-04 가 `ignore_eos=True`로
재설계해 실제로 잡았다:

```
ⓐ stream=false   HTTP 524   125.91초
ⓑ stream=true    성공       214.44초 · 12,000토큰 · TTFB 1.68초
ⓒ stream=false   HTTP 524   125.74초 (재현)
```

**천장 125.8초 확정. 스트리밍이 그 위 214초를 통과시킨다.** 덤으로 stream 유무와
무관하게 completion_tokens·본문이 완전히 같은 걸 확인해 "전송 계층 수정이지 판정
변수가 아니다"가 추론에서 관측으로 바뀌었다.

**결정**: `SUDDOE_LLM_STREAM` 기본값 "1"(커밋 977572c). **동시성은 6 유지** — 근거
(125초 천장)가 사라졌으니 6→4 로 바꾸는 게 오히려 «바뀐 변수 둘» 이 된다는 이 보고
§②' 의 논지 그대로 채택됐다. 스모크 10문항(동시6·스트리밍) 실패경로 0, 전량 295
run 진행 중.

**남은 캐비엇 두 개** (ai-04 가 짚음, 값 해석 시 유지할 것):
- ③(정규화 단일시도 최대 44.4초)은 **동시성 1** 에서 잰 값이다 — run 194 는 동시6 에서
  정규화 p50 45.7초였으니 같은 문항이 동시6 에서 4배 가까이 늘어날 수 있고, 그러면
  꼬리가 176초권으로 **천장 위**다. "상향만으로 74건이 거의 다 산다"의 근거로 쓸 때
  분모(동시성 조건)가 다르다는 점을 반드시 같이 적을 것
- ④(동시6 스트리밍 각 38초)는 **같은 프롬프트 6개**라 `--enable-prefix-caching`이
  prefill 을 사실상 공짜로 만들었다 — 실제 워크로드(문항마다 프롬프트가 다름)에서
  같은 값이 나온다고 읽으면 안 된다

내 A/B 스크립트의 ②「조각수 0」은 별도로 확인해 회신함 — 프로덕션 `_sse_수집`
버그가 아니라 내 임시 카운터가 `reasoning_content`를 안 세게 짜서 생긴 값(위와
같은 원인: 그 요청도 사고가 예산을 다 먹었다). `_sse_수집`은 `content`·
`reasoning_content`를 이미 따로 모은다 — 라이브 run 에 영향 없음.

## ⑤ 오너가 다음 run 후 확인할 것

정규화 60초 수정은 **run 을 새로 돌리지 않아도 이미 확정된 근거로 판단 가능**하다 —
성공 정규화 p50(45.7초)이 새 기본값(240초)보다 한참 아래이므로 60~125초권은 대부분
사라질 것으로 기대되지만, **판단불가율은 항상 「모델선택/실패경로」로 갈라 세라** —
실패경로가 줄어도 그만큼이 전부 「가능/불가」로 뒤집히는 게 아니라 「정상적으로
판단불가에 도달」로 넘어가는 문항도 섞인다. 실패경로 96 → 0 이 목표가 아니라 **96 중
정규화 몫(74)이 얼마나 줄었는지, 524 몫(19)이 채택한 처방에 따라 얼마나 줄었는지**를
갈라서 봐야 한다.

```
확인할 표 (eval.run_items.원출력, 새 run_id)
  실패단계별 건수                    (정규화 / 판정LLM / null)
  강등사유 텍스트 재집계               TimeoutError 비중이 줄었는가
  성공 판정LLM 지연의 p90~p99          234~253초 뭉침 — §③ 대로 그대로 남아 있는 게 정상
  524 발생 건수 자체                  ⓐ/ⓑ 중 적용한 처방이 «듣는지» 의 직접 증거
  (스트리밍을 켰다면) 정규화 지연의 우측꼬리     125초 위가 실제로 사라졌는가(§④ A/B ③ 대조)
```

**조건 비교 시 주의**: 이 run 의 `eval.runs.설정`(사업필터·정답출처·동시성·코퍼스버전)이
run 194 와 같은지 반드시 확인하고, 다르면 이 보고의 수치와 직접 빼지 마라
(project memory [[past-run-not-reproducible]]).
