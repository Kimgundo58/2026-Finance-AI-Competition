## 추론 — 여기부터는 위 값에서 내가 세운 것이다

- **분포가 124.8초에서 잘려 있다.** 우리 클라이언트 타임아웃은 판정 180초 · 정규화 60초다.
  판정이 180초 전에 124.8초에서 딱 멈추는 건 우리가 자른 게 아니다 — **프록시가 자른다.**
  실패 판정 251초 ≈ 125.5초 × 2회 시도가 같은 값을 두 번 보여준다
- ⇒ **«클라이언트 타임아웃 상향» 은 판정(524)에 아무 효과가 없다.** 인계 문서의
  「HTTP 524 는 상향으로 못 푼다」가 맞았고, 이제 그 천장의 «값» 이 125초로 확정됐다
- ⇒ 반대로 **정규화 74건은 상향으로 풀린다.** 60초는 프록시 천장이 아니라 우리 기본값이고,
  성공 정규화 p50 이 45.7초라 **중앙값이 이미 벽에 붙어 있었다.** 74건은 모델이 못 푼 게
  아니라 우리가 60초만 준 것이다
- 🔴 **판단불가 33.2% 중 실패경로 96건은 「모델선택」이 아니다** — 다시 확인됨

## 처방 후보와, 각각이 «무엇을 못 하는지»

```
⑴ 정규화 타임아웃 60 → 상향        정규화 74건에 직접 듣는다. 판정 524 에는 무효
⑵ 동시 6 → 4                       요청당 지연이 줄어 천장 아래로 내려온다
                                    🔴 다만 «충분한지» 는 못 보장한다 — 아래 셈 참고
⑶ 스트리밍(`stream=true`)           524 의 조건(「응답을 시작 안 했다」)을 없앤다.
                                    TTFT 2.41초에 첫 바이트가 나가므로 천장 자체가 사라진다
                                    판정 결과는 안 바뀐다 — 온도 0 · 같은 본문 ·
                                    guided_json 은 logits 단계라 전송 방식과 무관하다
⑷ SSH 터널                          프록시를 통째로 우회. 팟 생성 시점에 키가 붙어야 한다
```

### 🔴 ⑵ 만으로 충분하다고 «확정하지 마라»

```
동시6 에서 125초를 넘긴 판정 «시도» 를 세면
  524 로 죽은 시도  19문항 × 2회 = 38
  재시도로 살아난 것 (1차 시도가 천장 초과)  10
  ⇒ 약 48 / 약 265 시도 = 18%     ⇒ 동시6 의 p82 가 125초다

동시4 로 내리면 요청당 지연이 대략 4/6 배 (GPU 포화 가정)
  p82  125 → 83초        ← 여유 있다
  꼬리 (최장 생성 1,457토큰 ≈ p50 의 2.7배)  약 191 → 127초   ← 🔴 아직 천장 위다
```

⇒ **동시4 만 하면 소수의 524 가 남을 수 있다.** 남아도 run 은 성립하지만
「타임아웃을 고쳤다」고 말할 수 없게 된다. ⑶ 이 이 꼬리를 없앤다.

## 그래서 ⑶ 을 «믿고» 넣지 않는다 — 재는 방법을 먼저 정한다

Cloudflare 가 SSE 를 버퍼링하지 않는다는 건 **일반론이고 이 프록시에서 안 쟀다.**
켜기 전에 팟에서 A/B 를 돌린다 (5분·GPU 비용 무시 가능):

```
같은 프롬프트(생성이 확실히 125초를 넘는 것) 로
  ① stream=false → HTTP 524 가 나는가        ← 천장이 실재하는지 재확인
  ② stream=true  → 끝까지 오는가             ← 처방이 듣는지
둘 다 만족해야 스트리밍을 기본으로 켠다. ①이 재현 안 되면 천장 가설부터 다시 본다
```
