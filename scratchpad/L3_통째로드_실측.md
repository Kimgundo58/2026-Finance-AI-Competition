# L3 통째로드 실측 — B0+B1(L3)+B2+B3+B4+B5+B6 조립 후 글자수·토큰수

2026-09-06 · 담당: 골A-후반 레인(ai-d9) · 배정: ai-8c
🔴 GPU 안 켰다. LLM 호출 0회 — `orchestrate` 의 실제 배선(정규화 dry·검색 C·L3 로드 E·룰 B·f요약)만
그대로 태워 `조립()` 까지만 실행했다. 임베딩은 CPU(`device="cpu"`)로 돈다.

## 0. 전제 확인 (ai-8c 실측 그대로)
```
eval.runs 194·195 설정.L3.B1블록_문항수 = 0  →  61.4% 는 L3 없이 잰 점수
tenant.l3_articles org_id=cfeba091-251a-5ae4-8cc9-88c6e6679440(경상국립대 창업중심대학사업단)
   = 207조 · 26,569자. 이 org 가 전체 L3 의 대부분.
```

## 1. 방법
- `l3_load.로드(cur, org_id, 사업명)` 로 이 org 의 L3 를 실제 경로 그대로 로드 — 장(章) 필터 적용
  결과 **207조 전부 통과**(장 필터로 빠진 조 0). L3 는 문항과 무관한 고정 블록이다.
- `사업명='창업중심대학'` 골든셋 37건(DB 전량, 표본 아님) 각각에 대해
  `orchestrate._비목확정 → _검색(C, 실제 dense+BM25) → _effective(B, 실제 룰) → b4_문장 → b5_문장`
  을 실행하고, `assemble_context.조립()` 으로 B0~B6 을 실제로 만들었다.
- 토큰수는 **추정이 아니라 실측**이다 — 로컬에 캐시된 `Qwen/Qwen3-32B-AWQ` 토크나이저를
  `HF_HUB_OFFLINE=1` 로 오프라인 로드해 `tok.encode(프롬프트)` 로 직접 셌다.
- 글자수 기준 max_model_len 여유 계산에 필요한 토큰/자 비율도 이 37건에서 **직접 관측**했다
  (아래 §4) — `eval_e2e.py` 의 기존 가정(0.76)과 별개로 실측치를 냈다.

## 2. 결과 — 37건 분포 (자수/토큰수 둘 다 최대·p90·중앙으로)
```
토큰수  최대 34,743 · p90 34,144 · 중앙 31,256 · 최소 28,385   (한도 40,960 대비 최대 84.8%)
글자수  최대 53,296 · p90 50,622 · 중앙 43,873 · 최소 38,839
max_model_len(40,960) 초과: 0/37건 — 관측된 37건 중에서는 없다
```
최대 문항 gold 562 블록별 자수: `B0=409 · B1=34,515 · B2=5,231 · B3=9,134 · B6=260` (B4·B5 없음)

## 3. 🔴 고정비 구조 — B1(L3) 이 예산을 먼저 먹는다
```
B0(고정 시스템지시)  409자              — 전 문항 동일
B1(L3 통째)      34,515자              — 전 문항 동일 (질문과 무관, 207조 전부)
                 ≈ 25,300토큰 (관측 비율 0.733 적용) = 40,960 의 61.8%를 질문 읽기 전에 이미 씀
B2(L1·L2 검색)   2,834~9,658자 (중앙 5,598)   — 문항마다 변동
B3(참조확장)     1,437~11,541자 (중앙 6,916), 25/37건에만 존재  — 문항마다 변동
B4(룰 결과)      100~165자, 8/37건에만 존재   — 있어도 영향 미미
B5(F 요약)       **0/37건 — 한 번도 안 나왔다** (이 org 에 tenant.f_profile 행이 없다)
B6(질문)         평균 ~260자
```

## 4. 🔴 관측된 37건은 안전하지만, B2·B3 최대치가 겹치면 넘친다
```
관측 최대는 gold 562 하나(84.8%)뿐이고, B2 최대(9,658자)와 B3 최대(11,541자)는
서로 «다른 문항»에서 나왔다 — 같은 질문에서 둘 다 최대로 겹친 적은 이 37건엔 없다.
그런데 B2·B3 은 검색 결과·참조 개수로 서로 독립적으로 변하므로, 구조적으로는 겹칠 수 있다.

최악결합 시나리오 (B0+B1 고정 + B2최대 + B3최대 + B6중앙) = 56,389자
  토큰 환산  관측최대비율(0.733) 적용 → 41,318 토큰 (한도 대비 100.9%) 🔴 초과
             관측중앙비율(0.728) 적용 → 41,061 토큰 (한도 대비 100.2%) 🔴 초과
             기존 코드 가정치(0.76)  적용 → 42,856 토큰 (한도 대비 104.6%) 🔴 초과
```
→ **37건 실측만 보면 "됨"이지만, B2·B3 가 각자 관측한 최대치로 겹치는 질문이 오면
"한도 초과"가 3가지 환산 방식 전부에서 나온다.** 표본 37건이 그 조합을 우연히 피해갔을
뿐일 수 있어, "안 넘친다"로 결론 못 낸다.

## 5. L3 누수 점검 (④) — 0건, 물리분리 확인
```

  B0=0 · B1=2 · B2=0 · B3=0 · B6=0
→ L1·L2 검색 경로(B2)·참조확장(B3)에 L3 문구가 섞여 들어온 흔적 없음.
  CLAUDE.md 의 "L3 는 검색 경로와 물리 분리" 원칙이 조립 결과에서도 성립한다.
```

## 6. 잘리는 순서 (③) — 없다. 이게 발견이다
```
assemble_context.py·orchestrate.py 전체에 max_model_len 관련 자르기 로직이 없다
(_자르기() 는 표 행 분해용 함수이지 컨텍스트 길이 자르기가 아니다 — 이름만 같다).
🔴 기존 코드 주석이 이미 말하고 있었다 (eval_e2e.py:865):
   "넘치면 에러가 아니라 «앞이 잘린 채 조용히 답한다» — 질문이 사라진 오답이다"
→ 앱 레벨의 우선순위 자르기(예: B3부터 버린다 같은)는 없고, 넘으면 vLLM/토크나이저
  경계에서 조용히 잘린다. 무엇이 남고 무엇이 잘리는지 앱이 통제하지 않는다.
```
