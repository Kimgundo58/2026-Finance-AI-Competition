## D-1. `POST /admin/gpu/pod` 500 — 진짜 원인이 안 보였다

```
변경  server/_common.py::_실행()   `예외전파: bool = False` 추가 (_질의() 와 같은 계약)
      server/main.py::admin_gpu_pod()   예외전파=True 로 켜고 try/except 로 감싸
                                        HTTPException(500, f"...{type(e).__name__}: {e}")
기본값 False 유지 — 다른 호출부(persist.py·routes_l3.py·routes_orgs.py·
routes_tasks.py·main.py:625) 는 한 글자도 안 바뀐다(코드도 안 건드림, 인자를 안 주면
그대로 -1 삼킴 동작).
```

### 검증 — 실제로 쳐 봤다(DB 쓰기 없이)

```
1) _실행('SELECT 1/0')                    -> -1                (기존 동작 유지, 확인)
2) _실행('SELECT 1/0', 예외전파=True)      -> DivisionByZero 예외가 «진짜로» 올라옴
3) admin_gpu_pod() 함수를 «직접 호출»(auth 통과, _실행 을 mock 으로 죽여서 검사) —
   실제 ops.gpu_pod 는 안 건드리고 함수의 예외처리 경로만 실행:
   HTTPException(500, "ops.gpu_pod 갱신 실패 — RuntimeError: <원래 예외 메시지>")
   -> «-1» 이 아니라 «진짜 예외 클래스·메시지» 가 응답에 실리는 것까지 확인
4) pytest 전체 306 passed·3 xfailed — 회귀 없음(변경 전과 동일 기준선)
```
🔴 **실제 Cloud Run 환경에서 이 UPDATE 가 왜 죽는지 자체는 아직 모른다** — 이건 그
원인을 «드디어 볼 수 있게» 만든 것이다. 다음에 누가 이 엔드포인트를 다시 치면
`ops.gpu_pod 갱신 실패 — <진짜 클래스>: <진짜 메시지>` 가 그대로 나올 것이다. 실제
운영 호출까지는(쓰기라서) 내가 안 했다 — 중앙이 한 번 쳐 보면 원인이 나온다.

## D-2. 워치독 「거짓 가동」

```
변경  server/gpu_watchdog.py::현황()   "팟_조회됨": self._팟상태 != 알수없음  신설
프론트 「상태」 3어휘(가동|중지|기동중) 계약은 «그대로» — 늘리지 않았다.
```

### 왜 이 식으로 계산했나

`self._팟상태` 는 조회가 «성공» 했을 때만 가동/중지/기동중 중 하나로 갱신되고
(`한번_검사()`:448·`기동_진행()`:500 — "조회가 성공했다 — 상태 API 가 실물을 비추게
한다"), 조회가 «실패»(예외·404·빈 응답)하면 `알수없음` 이 되거나(부팅 직후 초기값도
`알수없음`) 이전 값이 그대로 남는다. 즉 `_팟상태 != 알수없음` 은 "지금 화면에 보이는
「상태」가 «실제 최근 조회 결과» 인가, «모르는 걸 가동으로 접은 것» 인가" 를 정확히
가른다 — 별도 상태 머신을 새로 만들지 않고 «이미 있는 신호» 를 노출한 것뿐이다.

### 검증 — 실제로 GPU워치독.현황() 을 호출해서 재현

```
1) D-2 실측 시나리오 재현(RunPod 계정 팟 0개 -> 조회 알수없음):
     _팟상태 = 알수없음 로 강제
     현황()['상태']     == '가동'   (기존 계약 그대로 — 어휘 안 늘림, 확인)
     현황()['팟_조회됨'] == False   (거짓 가동이 드러남)
2) 정상 가동 케이스: 상태='가동'·팟_조회됨=True
3) 정상 중지 케이스: 상태='중지'·팟_조회됨=True   (중지도 «조회 성공» 이라 True 가 맞다)
4) tests/test_gpu_watchdog.py 기존 23건 전건 통과 — 회귀 없음
5) pytest 전체 306 passed·3 xfailed
```

```

```
