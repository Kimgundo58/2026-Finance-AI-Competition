## 가. `l3_articles` 비목 태깅 — 스키마 제안

```
tenant.l3_articles 에 컬럼 1개 추가(제안, 미실행):
    비목  text NULL     -- 정본 비목 10종 중 하나. 못 정하면 NULL(=태깅 안 됨)

태깅 코드는 «새로 안 짠다» — l3_load.py 의 비목어휘()·비목추정() 이 이미 있다
(l3룰() 이 지금도 조문 순회하며 이 두 함수로 비목을 추정한다. 업로드/재파싱 시점에
같은 호출을 한 번 더 해서 컬럼에 «적어두기만» 하면 된다).
🔴 제목 패스 우선(제목만=True) 실패 시에만 본문 패스 — 지금 l3룰() 이 쓰는 순서 그대로.
동점이면 None(=태깅 안 됨) — 비목추정() 의 기존 규칙을 그대로 물려받는다(㉣ 참고).

🔴 안전장치 — 총칙/정의/공통 조는 태깅 대상에서 아예 뺀다
   조제목에 "총칙|정의|공통|적용범위|목적" 이 있으면 비목추정() 을 부르지 않고
   무조건 NULL 로 둔다. 이런 조는 여러 비목에 걸쳐 있을 개연성이 높은데
   단일 비목으로 커밋되면 다른 비목 판정에서 통째로 사라진다(㉣).
```

## 나. 판정 시 로드 범위 — "그 비목 조 + 태깅 안 된 조"

```
l3_load.로드() 시그니처에 비목 인자를 추가(제안):
    로드(cur, org_id, 사업명, 비목=None)
      비목 없음(하위호환)         → 지금과 같음(207조 전부)
      비목 있음                  → WHERE 비목 = :비목 OR 비목 IS NULL

🔴 «태깅 안 된 조를 반드시 포함»하는 이유 — 실측(§㉠)에서 태깅 안 된 조가
   84/207(40.6%) · 10,893자(41.0%)다. 이 40%를 빼면 그 안에 있는 제약(예: 자산관리 공통 조,
   협약 전반 조건)이 조용히 사라진다. 안 됨=제외가 아니라 안 됨=«모르니 넣는다»다.

호출 시점 — orchestrate.판정() 은 (2)-a 비목확정 뒤에 (3)-a L3 로드를 부른다(지금 순서
그대로). 비목이 이미 정해진 뒤에 로드하므로 배선 순서를 안 바꿔도 된다.
```

## 다. 상한과 자르는 순서

```
🔴 자르기 발동 조건 (㉡) — "넘치면"이 아니라 숫자로:
   추정토큰 = len(B0+B1+B2+B3+B4+B5+B6) × 0.76        ← 보수적 상수, 아래 근거
   여유예산 = max_model_len(40,960) − 판정_최대토큰(3,000) = 37,960   ← eval_e2e.py 기존 상수 재사용
   추정토큰 > 37,960  이면 자르기 시작

   🔴 비율 0.76 을 쓰는 이유 — 이번 실측(§4)에서 직접 관측한 비율은
      최소 0.638 · 중앙 0.728 · 최대 0.733 이고, 기존 코드 가정은 0.76 이다.
      «어느 쪽으로 틀려도 안전한 쪽»은 토큰을 더 많이 추정하는 쪽(0.76) —
      실제보다 크게 잡아야 자르기가 «늦게 켜져서 넘치는» 사고가 아니라
      «일찍 켜져서 덜 자르는» 쪽으로 실패한다. 실측 최대(0.733)보다 큰 값이라 안전 방향이다.

   🔴 **상수 불일치 발견(ai-8c 확인) — "3,000" 이 지금 코드와 안 맞는다.**
      `eval_e2e.py:880` 은 `max_tokens` 를 3,000 으로 «가정»하는데,
      `orchestrate.py:85` 의 실제 기본값은 `판정_최대토큰 = 1500`(env `SUDDOE_판정_최대토큰`
      없으면 1500). 3,000 을 빼면 입력 예산을 **1,500 토큰 더 좁게** 잡는 셈이다
      (정확한 여유예산은 40,960−1,500=39,460 인데 위 식은 37,960 을 쓴다).
      🔴 이게 «처음 나는 사고가 아니다» — `orchestrate.py:82-84` 주석이 이미 적어놨다:
      "run 191 은 라벨이 3000 인데 코드는 1500 이었고 어느 쪽이 돌았는지 확인할 수단이
      0 이었다." 리터럴 3,000 을 그대로 베끼면 같은 사고를 이 설계가 다시 상속한다.
      방향은 안전한 쪽이다(예산을 더 좁게 잡을수록 자르기가 더 일찍 켜지고, 그 실패
      방향은 위에서 이미 "안전"이라고 정한 쪽과 같다) — 다만 «왜 안전한지»를 몰라도 안전한
      게 아니라, «좁게 잡힌 걸 몰랐던 채» 우연히 안전했던 것과 같은 사고가 반복될 수 있다.
      **제안**: 리터럴 3,000/1,500 어느 쪽도 박아넣지 말고, 발동조건 계산 시점에
      `orchestrate.판정_최대토큰` 을 **읽어서** 여유예산을 구하고, 실제로 읽은 값을
      `잘림` 필드(§다 아래)에 같이 남긴다 — 예: `잘림={"...", "판정_최대토큰_사용값": 1500}`.
      그래야 다음 사람이 run 191 때처럼 "어느 쪽이 돌았는지 확인할 수단이 0" 인 상황을
      다시 안 만든다.

버릴 순서 (근거 우선순위 낮은 것부터):
   1순위로 버림   B3 참조확장 — 상위 참조는 "왜 이게 적용되나"의 보조설명이지 1차 근거가
                 아니다. 폐포 리스트에서 «뒤에서부터»(참조 깊이가 깊거나 늦게 추가된 것부터)
                 하나씩 제거하며 재계산, 예산 안에 들 때까지 반복
   2순위로 버림   B2 검색 하위순위 — top5 중 랭크 5→4→3 순으로 제거(랭크 1·2는 최후까지 유지)
   🔴 «절대 안 자름»  B1(L3, 나의 비목필터로 이미 줄어든 채) · B4(룰 조회 결과, 코드가 낸
                 확정 결론) · B0(시스템 지시) · B6(질문 자체)
                 이 넷은 근거의 정본이거나 질문 자체다. 자르면 "판정이 뭘 보고 냈는지"가
                 사라진다

   B2·B3 를 다 버려도 여전히 초과면(B1 이 극단적으로 큰 org) → LLM 을 부르지 않고
   즉시 판단불가로 닫는다. 강등코드 신설 제안: CONTEXT_OVERFLOW
   (기존 "s맵 0건 → NO_CITATION"과 같은 자리 — "모든 실패의 기본값은 판단불가"를 그대로 적용)

🔴 잘렸다는 사실을 응답에 남긴다(제안 필드):
   응답["잘림"] = {"발동": true,
                 "제거블록": ["B3:일부(3건)", "B2:랭크4-5"],
                 "제거전_추정토큰": 42,856, "제거후_추정토큰": 36,210}
   지금처럼 조용히 vLLM 경계에서 잘리면 "질문이 사라진 오답"이 로그에 «흔적 없이» 남는다
   (eval_e2e.py:865 가 이미 그 사고를 적어놨다). 이 필드가 있으면 최소한 «잘렸다»는
   사실은 decisions 테이블·프론트에 남는다.
```

## ㉢ "자르면 판정이 나빠지는가" — 측정 방법

```
지금은 모른다. 재는 법(이 프로젝트가 계속 쓰는 잣대 그대로 — 다른 run 으로 A/B):

① 베이스라인 run   L3 필터(가·나) 켜짐 · 자르기(다)는 이번 실측상 거의 안 켜짐(㉠) →
                    "필터만 켠 판" 으로 먼저 하나 뜬다
② 스트레스 run      자르기를 «강제로 발동»시키는 합성 입력이 필요하다 — 이번 37건 자연
                    표본은 최악결합을 안 만들었다(§4). orchestrate.판정() 의 기존 `주입=` 스위치
                    (`'db'|'timeout'|'schema'|'empty'|'cite'`) 자리에 `'overflow'` 를 追加하는
                    설계만 제안한다 — B2 top_k 를 강제로 늘리거나(top_k=20) 폐포 깊이를 강제로
                    늘려 B2+B3 합이 최악결합 수준(약 21,000자)이 되게 만든 뒤 자르기 경로를 통과
                    시킨다. LLM 은 그 다음에야 불린다 — 여기까지도 dry 로 자르기 로직만 잴 수 있다
③ 비교              ②(자름) vs ②를 자르기 없이 그냥 넘친 채 보낸 판(대조군, 오늘의 "조용히
                    잘리는" 현행 동작) — 같은 합성 입력, eval.runs 에 다른 run_id 로 각각 기록
                    일치율·혼동행렬·강등코드 를 CLAUDE.md 의 "조건이 다른 run 끼리 빼지 않는다"
                    원칙대로 같은 설정(설정.코퍼스버전·사업필터 등) 아래서만 비교한다
🔴 판단불가율은 "잘림 발생/미발생" 으로 «갈라» 센다(CLAUDE.md 지표 원칙) — 한 숫자로 합치면
   자르기 때문에 는 판단불가가 다른 원인 탓처럼 보인다
```

## ㉣ 태깅이 틀렸을 때 — 위험과 완화

```
위험 시나리오
  조 X 가 실제로는 「기계장치」와「지급수수료」둘 다에 걸리는 공통 제약인데
  비목추정() 이 confident 하게 「기계장치」하나만 골라 버리면 —
  지급수수료 판정 때 그 org 는 조 X 를 «영영 못 본다». 조 X 안의 금지·한도가
  조용히 사라지고, 규정이 실제로는 막는데 모델은 "가능"을 낼 수 있다.
  🔴 이게 이 제품에서 가장 피해야 하는 방향(틀린 가능)과 정확히 같다.

이미 있는 완화 (구현 없이도 지금 성립)
  · 비목추정() 은 동점이면 None 이다(l3_load.py:150-155) — «확신 없는 조»는 이미
    자동으로 "태깅 안 됨"(=항상 포함) 쪽으로 떨어진다. 위험은 confident-but-wrong 케이스뿐이다
  · 가 항목의 총칙/정의/공통 가드가 그 confident-but-wrong 중 상당수(전 비목 공통 조항류)를
    사전에 걸러낸다

이번에 새로 넣을 완화 (설계 제안)
  · 태깅 커버리지 감사 — l3_load.미분류() 가 이미 «비목은 잡히는데 룰 추출 실패»를 보여준다.
    같은 자리에 «태깅 자체가 맞는지» 표본 검수를 얹는다: 태깅된 조 중 N% 를 사람이
    골A 방식(원문 대조)으로 스팟체크 — 몇 %는 오너/후속 세션이 정한다. 이 설계 문서 범위 밖
  · 태깅은 «판정을 막지 않는다, 넓히기만 한다»는 원칙 재확인 — 태깅이 틀려서 위험한 방향은
    "빼야 할 걸 빼는" 게 아니라 "넣어야 할 걸 빼는" 쪽 하나뿐이다(그 반대: 태깅이 틀려서
    쓸모없는 조가 더 들어오는 건 예산만 손해고 안전 방향이다) — 그래서 가/나 설계가
    "모호하면 포함" 한쪽으로만 기울게 짰다
```

## ③ 자르는 순서 — 선택지만 낸다 (결정 안 함)

```
🔴 전제: retrieve.폐포수집() 의 폐포 순서는 참조 깊이·SQL 반환 순서일 뿐 relevance 점수가

   배정에서 이미 확인). 그래서 순서 기준 자체를 다시 고를 필요가 있다 — 아래는 옵션과

A. 참조 깊이 기준 — 깊이 2·3(간접 참조)부터, 깊이 1(직접 인용)은 최후

   손실  한도·요율 자체가 별표에만 있는 경우가 많다(위와 같은 사례). 별표를 먼저 버리면
        «판정에 쓸 숫자 자체»가 없어질 수 있다

        늘고, 임베딩 유사도 자체도 오탐이 있다(§ 어휘 레인이 이미 실측한 문제와 같은 종류)
```
