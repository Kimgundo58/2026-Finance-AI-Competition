# F2 — 적용 근거 표시 결함 (2026-09-07, ai-36)

## 원인

`인용` 매핑이 프론트 안에서 **세 갈래**로 갈려 있었다 — 그중 화면이 실제로 타는 갈래(`judge.ts`
"인용" SSE 핸들러)가 2026-09-06 수정 대상에서 빠져 있었다.

1. `lib/adapt.ts` `인용을규정으로()` — 2026-09-06에 `문서명보기()`·항호 표시까지 고쳐진 «정상» 경로.
   하지만 **중복 제거는 없었다** — 같은 (doc_id, 조번호)가 항호만 다르게 여러 건 오면 그대로
   여러 건으로 찍힌다.
2. `lib/judge.ts` "인용" SSE 케이스 — **①과 무관하게 따로** 매핑하고 있었다. `source: 문자(o["doc_id"])`
   로 `문서명보기()`를 거치지 않아 raw doc_id 가 그대로 나갔고, 항호도 title에만 붙이고
   본문은 안 잘라 조 전체가 나갔다. **실화면에서 새로 판정을 받은 직후(판정실행 → SSE)
   렌더링되는 게 바로 이 경로다.**
3. `상세를계획으로()`가 판정 직후 다시 상세를 읽어와 ①로 덮어쓰긴 하지만(`judge.ts:215
   바탕.rules.length ? 바탕.rules : 인용`), 저장이 안 되는 경우(목 서버·404 폴백 등)엔 ②가 그대로 화면에 남는다.

DB 실측(`tenant.decisions.인용`, decision_id=73)으로 원본 데이터 모양도 확인함 — `doc_id`가
내부 표기 그대로 저장돼 있고(`L1_중소기업창업_지원사업_통합관리지침_제14차개정_20251223`),
`원문범위='청크'`인데 `원문`에 조 전체(제38조 10개 항)가 들어 있는 사례가 실재한다 —
`llm_schema.py:144`의 "청크는 이미 항 단위" 전제가 이 문서에서는 깨져 있다(백엔드 소관,
이번 수정 범위 밖. 프론트가 항호로 한 번 더 방어한다).

## 고친 것

`lib/adapt.ts`에 **단일 진입점** 두 개 신설, `lib/judge.ts`가 이걸 가져다 쓰도록 통일:

- `항추출(본문, 항호)` — `scripts/llm_validate.py:_항_추출()`과 같은 규칙(항 마커로 슬라이스,
  못 찾으면 원문 그대로). 인용은 생성이 아니라 추출이라는 원칙 그대로 유지.
- `인용정리(인용들)` — 같은 (doc_id, 조번호)를 한 건으로 묶고, 항호를 합쳐 제목에 붙이고
  (`제38조 외주용역비 ③④`), 본문은 각 항호별 `항추출()` 결과만 중복 없이 이어붙인다.
  `문서명보기()`는 여기서 한 번만 적용된다.
- `상세를계획으로()`(adapt.ts:259)와 `judge.ts`의 "인용" SSE 케이스(judge.ts:157) **둘 다
  이 함수 하나만** 부른다 — 기존 `인용을규정으로()`는 삭제.
