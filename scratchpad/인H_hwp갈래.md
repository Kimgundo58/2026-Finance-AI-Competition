# 인H — HWP 갈래 뚫기 (2026-09-06)

목표: 구형 `.hwp`(OLE) 를 «표를 살려» 파싱한다 — `hwp_extract.py` 는 PARA_TEXT 만
훑어 표 구조가 없다. `L3_시연적재_안내.md §5` 가 검증한 LibreOffice+H2Orestart 경유
`.docx` 변환을 배선했다.

## 변경 파일 (2개, 둘 다 새 갈래 «추가» — 기존 경로 미수정)

```
scripts/stage0_extract.py
  + _find_soffice()        soffice 실행파일 탐색 (env SOFFICE_BIN · PATH · 기본 설치경로)
  + _libreoffice_docx()    ASCII 임시명 복사 -> soffice --headless --convert-to docx
                           실패(미설치·변환오류·타임아웃) 시 예외 없이 None 반환
  ~ extract_hwp()          OLE 분기 «직전» 에 위 갈래 삽입. 변환 성공 시 extract_docx() 로
                           넘긴다. 변환 실패 / extract_docx 파싱 실패 시 기존 hwp_extract
                           경로로 폴백 (경고 로그만 남기고 예외 안 던짐)

scripts/stage0_articles.py
  ~ split_articles() 단락 폴백  `re.split(r"\n{2,}", text)` 결과가 0~1개일 때만
                           (= 빈 줄이 아예 없는 문서) 단일 개행(`\n`) 기준으로 재분할.
                           빈 줄이 «있는» 기존 문서는 조건이 안 걸려 그대로 동작한다
```

## 검증 — 지정된 3문서 (HWP 원본 + 한컴 PDF 둘 다 있는 것)

측정 방법:
```
새 경로   .hwp -> _libreoffice_docx() -> extract_docx() -> split_articles(text)
          (doc_id 를 안 줬다 — table_splice 미개입. 이 갈래 «자체» 의 원 산출을 잰다)
표 행수(새 경로)   변환된 .docx 를 python-docx 로 직접 열어 모든 표의 <w:tr> 실측 합
          (extract() 의 셀->줄 변환과 별개로 표 구조 자체를 잰다)

지금 경로  .pdf(한컴 변환본) -> extract_pdf() -> split_articles(text, doc_id=...)
          (doc_id 를 줬다 — 이게 실제 운영 경로. table_splice 가 오염된 붙임/참고
          섹션을 _tables.json 표로 갈아끼운다)
표 행수(지금 경로)  `_tables.json`(Stage 0-T, pdfplumber.extract_tables) 의 그 doc_id
          행 수 총합 — 이게 지금 파이프라인이 표를 세는 유일한 근거다
```

## 추론 (관측과 분리) — 조 개수 ±1 은 무엇인가

```
예비창업: 새 경로에만 있는 것 = 제25조(주관기관 최종평가) · 부칙 제1조(시행일) [별도 라벨]
          지금 경로에만 있는 것 = 제1조[2](시행일) · 붙임2 (본문이 「| 비목 | | 내용 |」 헤더뿐)
  -> 지금(PDF) 경로가 이 문서의 부칙 경계를 못 잡아 부칙의 "제1조(시행일)"을
     본칙 제1조의 «중복» 으로 오분류한 것으로 보인다(추정 — RE_BUCHIK 매칭 실패 원인은
     안 팠다). 제25조가 지금 경로에서 안 보이는 것도 같은 부칙 오분류의 파급으로 추정.
     이건 «지금 PDF 경로 자체의 기존 동작» 이고 이번에 손대지 않았다(경계 규칙 2).

초기창업: 새 경로에만 있는 것 = 붙임1 (【붙임 1】주관기관 사업비 비목 해설표)
  -> 지금(PDF) 경로가 이 문서에서 «붙임1» 표제를 붙임2 와 못 갈랐거나 놓친 것으로
     추정(원인 미확인). 마찬가지로 새 코드가 아니라 지금 경로 쪽 현상이다.

TIPS: 조개수 완전 일치(53=53). 개요형(outline_numbered) 문서라 부칙/붙임 경계
     문제가 덜한 것으로 보인다(추정).

-> 조 개수는 대체로 맞는다(±1, 3건 중 2건). 어긋난 1건은 «새 경로의 결함» 이 아니라
   «지금 PDF 경로가 이미 갖고 있던» 부칙/붙임 경계 인식의 약점으로 보인다(추정).
```

## 추론 — 표 행수는 왜 30~70% 더 나오는가

```
예비창업 표를 «붙임 라벨 단위» 로 다시 묶어 보면(지금 경로는 표 하나가 페이지가
넘어가면 pdfplumber 가 별도 표로 쪼갠다):
  붙임1  새경로 표9(32행) ≈ 지금경로 표6+표7(15+18=33행)   차이 1행
  붙임2  새경로 표11(30행) ≈ 지금경로 표8+표9(12+21=33행)  차이 3행
  본문(붙임 아닌 부분)  새경로 9개 표 49행 vs 지금경로 6개 표 28행  차이 21행 «미해명»

TIPS 는 변환된 docx 표 94개 중 30개가 1행×1열짜리다(관측). 이건 서식/별지의
체크박스·서명란 같은 레이아웃 상자가 LibreOffice 변환에서 표로 잡힌 것으로
보인다(추정) — 이것만 빼도 688-30=658행으로 지금 경로(406행)와 여전히 크게 차이 난다.

-> «페이지 넘어가는 표를 pdfplumber 가 쪼개는 것» 은 붙임 라벨 단위 차이(1·3행)를
   설명하지만, 본문 표의 21행 차이와 TIPS 의 큰 격차(658 vs 406)는 «표를 더 잘
   살렸다» 인지 «없는 표를 만들었다» 인지 이 세션에서 못 갈랐다. 관측만 있고
   원인 확정은 못 했다 — 추측으로 채우지 않는다.
```
