## F4 — 「org 당 여러 행일 수 있다」를 어떻게 접었나 (제일 어려운 부분)

```
0행    F4 를 비운다({}). 인원 데이터가 없다 — 인라인요청으로 간다. (기존과 동일)
1행    스칼라로 접는다. 이 org 의 유일한 인원이라 안전하다.
2행+   🔴 «접지 않는다». F4 를 비운다({}) — 아무 직원이나 대표로 고르면
       "엉뚱한 사람의 고용형태로 조건을 검증한 뒤 조용히 통과시키는" 틀린
       즉시검증이 나온다. 원칙 7(모르면 보류)을 그대로 따른다.
       stderr 경고 로그를 남긴다("N행 — 한 값으로 못 접어 F4 를 비운다").
```
**왜 이렇게 정했나**: `전제.매핑`이 "F4.고용형태" 처럼 «어느 사람인지»를 가리키는 정보
없이 컬럼 경로만 준다. 2행 이상이면 이 자리에서 「어느 인원 얘기인지」를 판별할 방법이
코드에 없다(그 판별은 사람 이름 등 별도 식별자가 매핑에 실려야 하는데 지금 계약엔 없다).
값을 하나 골라 접으면 실측 불가능한 자신감을 만든다 — 그래서 자동 검증은 포기하고
사용자가 화면에서 직접 답하는 인라인요청으로 넘긴다. **이건 "F4 를 못 쓴다"는 게 아니라
"1인 org(현재 시연 데이터 그대로)"에서는 F4 가 즉시 작동하고, 다인원 org 에서는 안전하게
보류로 떨어진다**는 뜻이다.

## F3(f_exec) — 배선만, 값 기대 안 함

```

   «집행 건별 로그» 라 f_personnel 과 성격이 다르다 — 데이터가 쌓이면 "org 하나에
   여러 집행"이 «정상 상태» 가 되어 2행+ 규칙(=보류)이 «거의 항상» 걸릴 것으로
   예상한다. 이 규칙이 F3 에도 맞는지는 실제 데이터가 쌓인 뒤 다시 봐야 한다 —
   지금은 판단할 재료가 없어 판단을 미룬다(다음 세션 과제로 남긴다).
```

## 검증 — 셋 다 실측함

**(1) 전/후 즉시검증·인라인요청 건수** — 실 DB(f_personnel 0행)로는 F4 가 아직
발현할 데이터가 없어, 배선 자체는 합성 f값으로 검증했다(전제해소 로직 자체를 재는
것이지 룰 내용을 재는 게 아니라서 이 방법이 맞다고 판단):
```
전제 샘플 2건: [F4.고용형태 매핑 1건, F1.협약종료일 매핑 1건]
전(F4 없음)   즉시검증 1 · 인라인요청 1
후(F4 1행 있다고 가정)  즉시검증 2 · 인라인요청 0   <- F4 매핑 건이 정확히 넘어감
```
실제 org(cfeba091-…)로 F1 만 돌려도 여전히 정상 동작(협약시작일·협약종료일·
정부지원_현금·자기부담_현금 4건 값 확인, F4·F3 는 0행이라 기여 0 — 예상대로).

**(2) 평가 경로(org_id=None) 즉시검증 0 확인**
```
b5_값(cur, None) -> {}  (기존과 동일, 게스트 취급)
f값_경로키({}) -> {}
전제해소(..., org_id=None, f값={}) -> 즉시검증 0 · 인라인요청 2 (전부)
```
🔴 F4·F3 를 추가해도 org_id=None 경로는 안 건드렸다(함수 맨 앞 `if not org_id: return {}`
가 그대로 있다) — run 비교의 기준선이 안 깨진다.

**(3) 실패해도 트랜잭션이 안 죽는지**
```
실측 — F1/F4/F3 를 «각각 독립 try/except+rollback» 으로 감쌌다. 그중 하나를
일부러 없는 컬럼으로 깨뜨려 확인:
  F1 정상 조회 -> F4 «일부러 깨뜨림»(UndefinedColumn) -> rollback ->
  F3 정상 조회(0행, 정상) -> 맨 뒤 무관 쿼리(corpus.rules count) 정상(74)
=> F4 가 죽어도 F1 이 이미 모은 값은 안 사라지고, F3·뒤따르는 쿼리 다 산다.
   (2026-09-06 아침 협약총액 버그가 «전체를 죽였던» 것과 다른 설계 — 그때는
   try/except 가 하나뿐이라 첫 실패가 전부를 삼켰다. 이번엔 3구간을 갈랐다)
```
