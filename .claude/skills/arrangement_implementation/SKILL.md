# 실제 구현 기록

`실제 구현.md` 한 파일에 최신 항목이 위로 쌓인다.

## 왜 남기나

이 프로젝트는 **문서가 코드를 앞서고, 결정이 여러 번 뒤집혔다.** 산출물만 남기면
6주 뒤에 "이 숫자가 왜 이렇게 나왔는지" 를 아무도 모른다. 재현하려면 판단 근거가 있어야 한다.

`작업 현황.md` 와 역할이 다르다.

| | 담는 것 |
|---|---|
| `작업 현황.md` | 일자별 진척 · 맥락 변화 · 결정 이력 |
| **`실제 구현.md`** | **산출물 하나가 어떻게 만들어졌는가.** 입력 · 판단 · 실측 · 함정 |

## 언제 쓰나

기록한다 — 코드 작성 · 데이터 산출 · 스키마 변경 · 파일 생성/삭제 · 파싱·태깅 실행
기록하지 않는다 — 조사 · 문서 읽기 · 논의 · 계획 수립 (계획은 실행할 때 함께 적는다)

## 항목 형식

```markdown
## YYYY-MM-DD · <작업명>

<한 문장. 무엇을 만들었나.>

### 입력
어떤 파일 · 어떤 명령 · 어떤 전제로 시작했나. 경로를 적는다.

### 판단
결정마다 한 줄. **대안과 기각 사유를 함께 적는다.**
근거가 실측이면 수치를, 문서면 문서명과 절 번호를 댄다.

### 실측
숫자. 추정과 실측을 섞지 않는다. 추정이면 그렇게 표시한다.

### 함정
막힌 곳과 그 이유. 다음에 같은 자리에서 막히지 않게.

### 남은 것
보류 · 미검증 · 사람 확인 대상.

### 산출물
파일 경로와 스키마.
```

레인 도식(`lanes` 스킬)은 **비교·분업·분기가 있을 때만** 넣는다. 단순 절차에는 넣지 않는다.

## 문체 규칙

**사실과 수치로 쓴다. 형용사를 뺀다.**

| 금지 | 대신 |
|---|---|
| "성공적으로 완료했습니다" | "완료. 33조 추출" |
| "훌륭한 / 완벽한 / 강력한" | (수치로) |
| "~을 통해 ~할 수 있습니다" | "~하면 ~된다" |
| "먼저 ~하고, 다음으로 ~하며" | 목록으로 |
| "중요한 점은 ~라는 것입니다" | 그냥 그 사실을 쓴다 |
| "~해보겠습니다 / ~하려고 합니다" | 실행 기록이므로 과거형 |
| 이모지 장식 | 🔴 는 위험 표시로만. 나머지 금지 |
| 존댓말 · 설명체 | 평서체 |

**추가 규칙**

- 실패·보류를 숨기지 않는다. 안 된 것을 적지 않으면 다음 사람이 같은 데서 막힌다
- 근거 없는 단정 금지. 확인 못 한 것은 "미확인" 이라고 쓴다
- 요약을 반복하지 않는다. 같은 말을 두 번 쓰지 않는다
- 수치에는 출처를 붙인다 (어느 파일 · 어느 명령의 결과인가)
- 남이 읽을 문서가 아니라 **6주 뒤의 자신이 읽을 문서**로 쓴다

## 실측과 추정을 구분한다

```
조 33개                    <- 실측 (split_jo.py 출력)
조 30~40개 예상            <- 추정. 이렇게 표시한다
```

이 프로젝트는 "2~5분" 으로 추정한 임베딩이 실제로 35~40분이 걸린 전례가 있다.
추정을 실측처럼 적으면 일정이 무너진다.

## 마무리

- 항목을 쓴 뒤 `실제 구현.md` 최상단에 있는지 확인한다 (최신이 위)
- 이전 항목을 고치지 않는다. 정정이 필요하면 **새 항목에서 정정**하고 이전 항목에 한 줄 링크를 단다
- 커밋하지 않는다. 사용자가 결정한다
