# 레인 다이어그램

`||` 로 세로 분할한 텍스트 도식. **각 레인은 "누가/무엇이 맡는가", 각 행은 "언제"** 다.

```
[ LLM ]  말을 만든다        || [ RAG ]  근거를 찾는다      || [ RULE ] 숫자를 비교한다
===========================-||-===========================-||-===========================
(1) 정규화                  ||                             ||
    자연어 -> JSON          ||     (관여 안 함)            ||     F 프로필 로드
----------------------------||-----------------------------||----------------------------
            [ 게이트 ]  스코어 < 임계치  ->  판단불가
```

## 🔴 손으로 그리지 않는다

**공백을 눈으로 맞추면 반드시 틀어진다.** 한글은 2칸, ASCII 는 1칸이라 내 눈에 맞아 보여도
다른 터미널·에디터에서 `||` 가 어긋난다. 반드시 렌더러를 거친다.

```bash
export PYTHONIOENCODING=utf-8 && python .claude/skills/lanes/lane.py <spec>.json
```

spec 은 스크래치패드에 쓴다. 렌더러가 **정렬을 검증하고, 위반이 있으면 출력 대신 거부**한다
(exit 1). 거부되면 고쳐서 다시 돌린다 — 거부된 결과를 손으로 때워 내보내지 않는다.

## 문자 제약 (렌더러가 강제)

**ASCII 와 한글만 쓴다.** 아래는 터미널마다 1칸/2칸이 갈려 거부된다.

| 쓰지 말 것 | 대신 |
|---|---|
| 이모지 `🤖 ⚙️ 🔑 ⚠️ ⛔` | `[ LLM ]` `*` `!` `X` |
| 동그라미 숫자 `① ② ③` | `(1) (2) (3)` |
| 화살표 `→ ▶ ↳` | `->` `+-` |
| 가운뎃점 `·`, 곱셈 `×`, `✕ ✅` | `/` `,` `X` `O` |
| 괘선 `─ │ ┌ ┬` | `-` `|` `+` |

레인 **밖**(본문 산문, 제목, 표)에서는 이모지를 써도 된다. 정렬 대상이 아니다.

## spec 형식

```json
{
  "title": "온라인 — 요청 1건이 흐르는 길",
  "width": "auto",
  "rows": [
    { "cells": [ ["[ A ] 맡는 일"], ["[ B ] 맡는 일"], ["[ C ] 맡는 일"] ] },
    { "sep": "=" },
    { "cells": [ ["(1) 정규화", "    자연어 -> JSON"],
                 ["    (관여 안 함)"],
                 ["    F 프로필 로드"] ] },
    { "sep": "-" },
    { "full": "        [ 게이트 ]  스코어 < 임계치 -> 판단불가" }
  ]
}
```

| 키 | 뜻 |
|---|---|
| `width` | 레인 한 칸의 폭. `"auto"` 면 내용에서 계산. 보통 26~28 |
| `cells` | 레인별 줄 배열. 레인 수는 첫 `cells` 로 결정 — 이후 전부 같아야 한다 |
| `sep` | 구분선. `"="` 는 굵은 단락, `"-"` 는 단계 구분 |
| `full` | 레인을 가로지르는 한 줄. 게이트·분기·전역 조건에 쓴다 |

레인 수는 2~4가 한계다. 5개면 폭이 모자라 읽히지 않는다.

## 구성 (3단 세트)

한 번 요청받으면 보통 이 셋을 함께 낸다.

**1. 흐름도** — 시간 순. 위에서 아래로.
- 각 행은 한 단계. 그 단계에서 놀고 있는 레인은 `(관여 안 함)` 이라고 **명시**한다.
  비워두면 "누락"인지 "무관"인지 읽는 사람이 모른다
- 단계 번호는 원문 설계 문서의 번호를 그대로 쓴다 (`(4)-a` 처럼)
- 마지막 `sep: "="` 아래에 **요약 푸터** — 레인별 호출 수·소요 시간

**2. 경계표 — "무엇을 *안* 하는가"**
설계에서 진짜 중요한 건 각자가 하는 일이 아니라 **하지 않기로 한 일**이다.
같은 레인 구조로 한 장 더 그리고, 각 항목에 **왜 안 하는지 한 줄**을 붙인다.

```
LLM 이 안 하는 것        || RAG 가 안 하는 것        || RULE 이 안 하는 것
-------------------------||--------------------------||-------------------------
검색어 생성              || 관계 추론 (GraphRAG X)   || 조문 본문 요건 컴파일
 -> 코드가 쿼리를 짠다   ||  -> 적힌 참조만 따라간다 ||  -> 해석이 고정되어 틀린다
```

**3. 오프라인/재료 계통** — 필요할 때만. 레인이 아니라 **세로 트리**로 그린다.
단계별 산출물이 어느 레인으로 흘러드는지 `-> [RAG]` `-> [RULE]` 로 태깅한다.

## 내용 규칙

- **원문 문서에서만 가져온다.** 그림을 채우려고 추측을 넣지 않는다.
  근거 문서와 절 번호를 도식 앞뒤에 밝힌다
- **미결·선택 사항은 그렇게 표시한다.** `! 필수 아님`, `(미결 #7)`.
  확정된 것처럼 그리면 도식이 결정을 앞질러 버린다
- 셀 한 줄은 짧게. 넘치면 렌더러가 거부한다 — 줄이거나 `width` 를 올린다
- 들여쓰기로 계층을 준다: 단계명 0칸, 내용 4칸, 하위 6~8칸
- 도식 아래에 **한 줄 요약**을 붙인다. 그림이 말하려는 한 문장

## 마무리

- 렌더 결과는 코드 블록으로 그대로 내보낸다
- spec 파일은 스크래치패드에 남기고 프로젝트에는 넣지 않는다.
  단, 사용자가 문서에 넣으라고 하면 렌더 결과(텍스트)만 넣는다
- 도식이 기존 설계 문서와 어긋나면 **그림을 맞추지 말고 어긋난 사실을 보고**한다
