## 조문 변경 (옛 판 XML ↔ 새 판, 공백 제거 비교)

조번호 체계는 7건 모두 그대로다(옛 판 · 새 판 조번호 집합 차이 없음. 옛 판에만 있던 공공재정법 시행령 별표2 · 소득세 시행령 제88조 · 제216조의4 는 새 판에 `삭제` 로 있다). 소득세법 시행령은 공백 제거 비교로 54항목(조 52 · 별표 2)이 다르고, 개정 표기 · 따옴표까지 빼면 53항목(조 51 · 별표 2)이다. 처음 적은 「50개」는 비교 정의를 재현하지 못해 고쳤다. 표기 차이가 섞였고, 제36조① 이 가리키는 조를 정하지 않아 조별로 판단하지 않았다. 나머지 달라진 조는 `판대조.md` 조치 칸.

옛 XML 은 시행 전 문구를 담고 있었다(부칙 확인: 산안법 제175조제4항제2호의2 등, 소득세 시행령 별표3의3 2027-01-01 · 별표5 2028-01-01). 새 판 페이지는 지금 시행 중인 문구다. 그래서 일부 조 · 별표는 개정이 아니라 시행 시점 차이이고, 개정 표기가 옛 판보다 이를 수 있다.

- 운영요령 제20조⑦ 자기부담 확인, 제21조⑧ 재원 비율 집행 신설 등 사업비 조문이 바뀌었다. **묶음 C 추출은 새 판 본문으로 한다.**
- 1차 범위로 든 보조금법 시행령 제15조, 공공재정법 제8 · 9 · 16 · 28~31조, 시행령 제4조, 창업지원법 시행령 제40조, 산안법 제129조는 안 바뀌었다.

## 파일을 어떻게 읽었나

- 법령정보센터 OPEN API(DRF)는 신청자 이메일 ID(OC)가 있어야 해서 쓰지 않았다(개인 정보 전송 금지). 공개 본문 페이지(`lsInfoR.do`, `admRulInfoR.do`)를 그대로 저장소에 두고 `scripts/law_html_articles.py` 로 읽는다. 법령 6건은 머리글 `[시행 …]` · `nwYn=Y`, 운영요령은 저장 HTML 에 `nwYn` 이 없어 머리글과 공개 페이지 재요청으로 현행을 확인했다.
- 표기는 옛 XML 경로에 맞췄다: 둥근 따옴표 → `"`, `<개정 2021. 1. 5.>` → `<개정 2021.1.5>`, 조 끝 안내줄(`[전문개정 …]`) 제거, 표 · 수식 그림은 대체 글. 부칙 제외. 대체 글의 LaTeX(`\frac` · `\times` 등, 소득세 시행령 30조 · 창업지원법 시행령 제13조)는 글로 바꾼다(`(A) / (B)`, `×`, `(A/ B)의 n제곱근`). 인용 원문이 화면에 그대로 나가기 때문이다. 로컬 DB 의 그 31조는 적재 뒤 본문 · 청크 · 임베딩 · BM25 를 다시 넣어 JSON 과 맞췄다(본문 차이 0 확인). 운영은 고친 JSON 으로 적재하므로 따로 할 일이 없다.
- 별표: 페이지에 본문이 없다. 옛 XML 별표내용과 개정 표기가 같고 글이 96% 이상 같으면 옛 본문을 재사용하고, 다르면 새 판 첨부 PDF 글을 쓴다(5건, 표가 풀린다). 파일별 출처는 `_law_sources.json`.
- 집행지침: 편 · 장 단위 69항목 + 표지. 제3자 지침: 제1~24조 · 부칙 · 붙임. 공고: 소제목 단위 35항목(`p{쪽}-{순번}`, 화면에는 `N쪽`), 표 7쪽(p1 · 2 · 10 · 12 · 19 · 28 · 33)은 PDF 쪽을 보고 마크다운 표로 복원. 복원 입력은 `ontology/수집/조문/`.
- 조문 JSON 은 `law_html_articles.py` 가 만든 조에 별표 · 메타를 손으로 붙인 것이고, 집행지침 · 제3자 · 공고를 만든 코드는 저장소에 없다. **다시 만들 수 없으니 JSON 자체가 원천이다.** 스크립트는 기존 `--out` 을 덮어쓰지 않는다.

## 운영 반영 절차 (사용자 승인 뒤, 8-7 기준. 아직 안 했다)

운영 DB 판을 `판대조.md` 와 먼저 대조한다. 옛 판 doc_id 가 `적재목록.json` 의 `대체` 와 다르면 멈추고 다시 대조한다. 명령은 전부 `cd /opt/suddoe/deploy/ncp` 에서 실행한다. 호스트 python 은 쓰지 않는다.

1. 코드 배포 전 마이그레이션: 먼저 `SELECT to_regclass('corpus.norms')` 로 온톨로지 스키마를 본다. NULL 이면 `2026-11-06_온톨로지.sql` 을 적용한다. 이어서 `2026-11-06_운영요령_참조정리.sql`, `2026-11-06_모두의창업_참조_태그_보정.sql`, `2026-11-07_적재형식_html.sql`(없으면 HTML 원본 접수가 CHECK 에 걸린다).
2. 이 브랜치 코드 배포. 코드가 운영요령 새 doc_id 를 참조 대상으로 쓰되 적재 전에는 옛 판으로 잇는다(`build_refs.py` 의 `corpus.get`). 그래서 배포와 적재 사이에 문서 업로드를 멈출 필요는 없다.
3. 적재. 이미지에는 `ontology/수집/` · 원본 파일이 없어 저장소를 읽기 전용으로 붙인다. 먼저 `--확인만`:
   ```bash
   docker compose run --rm -v /opt/suddoe:/repo:ro -e SUDDOE_INGEST_DSN="postgresql://suddoe_ingest:<비밀번호>@db:5432/suddoe" \
     api python scripts/corpus_restored_load.py --목록 /repo/ontology/수집/적재목록.json --저장소 /repo --확인만
   ```
   통과하면 `--확인만` 을 빼고 tmux 안에서 돌린다. 안내 책자를 포함한 11건을 목록 순서대로 넣고, 소득세 시행령이 마지막이다. 판을 올릴 때 활성화 트랜잭션이 옛 판 참조를 새 판으로 옮기므로 끊기는 구간이 없다. 끊겨도 같은 명령을 다시 돌리면 active 문서를 건너뛴다. 안내 책자가 운영에 L3 로만 있어도 L2 로 따로 들어간다.
4. `2026-11-07_현행판_참조이동.sql`, 이어서 `2026-11-07_참조_보정.sql` 실행(모두 `--single-transaction`). 새 판이 일부만 active 이거나 제3자 행을 못 찾으면 멈춘다. NOTICE 행 수를 로컬 값과 비교한다.
5. `ontology/schema.json` 반영 후 `ontology_load.py`(같은 방식으로 저장소를 붙여 실행). 이번 로컬 작업에서는 다른 에이전트가 원천 JSON 을 고치는 중이라 돌리지 않았다.
6. API 재시작. `retrieve.py --q` · `ux_flow_check` 로 확인.
