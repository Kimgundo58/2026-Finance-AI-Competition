# 수집과 보관

이 문서가 답하는 질문:
- 사용자에게서 무엇을 받고, 무엇을 저장하는가
- PMS 원문은 왜 서버로 보내지 않는가
- 개인정보 관점에서 지금 문제없다고 확인된 것은 무엇인가

## 🔒 원칙 — PMS 원문은 서버로 보내지 않는다

브라우저에서 정규식으로 파싱해 **확인된 숫자만** 전송한다. **실명·과제번호가 서버에
도달하면 안 된다.** 스크린샷 업로드는 지원하지 않는다 ([[2-5_사실축]] §PMS 입력 참조).

## A. 수집 항목 대장

`저장` 열은 설계 계획이다 — 구현 코드 존재 여부는 [[0_현황]] 별도 확인.

| 항목 | 무엇에 쓰나 | 저장 | 위험 |
|---|---|---|---|
| 계정 이메일·비밀번호 해시 | 인증·F 프로필 귀속 | 계획(위탁 Supabase) | 유일한 직접식별 항목 |
| F1 협약금액·기간 | 한도 분모, 시기 역산 | 계획 | 개인사업자면 개인정보화 가능 |
| F2 사업계획서 원문 | 과업범위 추출 | **저장 안 함**(파싱 후 폐기) | 영업비밀 + 실명 다수 |
| F2 과업범위 요약 | 포섭 판단 | 계획 | 요약에도 실명 잔존 가능 |
| F3 집행내역(비목·거래처·인별×월별) | 한도 비교 | 계획 | "인별×월별"이 그 자체로 개인정보 |
| F4 인력(참여율·소속유형·고용형태) | 인건비 참여율 판정 | 계획(**이름 저장 ✕**) | 조합만으로 사실상 특정 가능 |
| F5 거래처(친족·전직·구매명의) | 이해충돌 판정 | 건별, 판정 후 폐기 | 제3자 정보 — 동의 주체가 아니다 |
| F6 기업정보(업력·매출·지분) | 자격 판정 | 계획 | 지분은 개인 보유분이면 개인정보 |
| F7 수혜이력 | 중복지원 판정 | 계획 | 법인정보 |
| 질문 원문(화면 3 자유텍스트) | ① 정규화 입력 | 실재 `decisions.질문원문` | 자유 텍스트라 항목 통제 불가 — 마스킹 대상([[9_미결]]) |
| 업로드 파일(L3 규정·협약서) | 조 단위 적재 | Storage, 파싱 성공 시 삭제(협약서는 조항·날짜만 남기고 원본 폐기) | 협약서에 대표자 실명·서명 포함 |
| 판정 로그 | 재현성·평가 | 실재 `decisions` | 보관기간·삭제경로 컬럼 없음([[9_미결]]) |

## C. 확인 완료 — 고칠 필요 없음

| # | 결론 |
|---|---|
| C-1 | 민감정보(§23, 시행령 4종 열거) 미해당 — F1~F7 어느 것도 안 걸린다 |
| C-2 | 고유식별정보(§24, 시행령 4종 열거) 미해당 — 사업자등록번호도 대상 아님 |
| C-3 | 신용정보법 미적용 — 신용을 판단하지 않고 신용정보를 주고받지 않는다 |
| C-4 | 전자금융거래법 — 미적용 가능성 높으나 조문 미확인(코퍼스에 원문 없음) |
| C-5 | 공공기관 전용 의무(§32 파일등록·§33 영향평가) 미해당 — 민간 서비스 |
| C-6 | PMS 스크린샷 기각 + 클라이언트 파싱 대안 — 설계가 법을 앞섰다, 그대로 유지 |
| C-7 | 게스트 경로가 §16③(최소정보 외 미동의로 서비스 거부 금지)를 구조적으로 만족 — **없애면 안 된다** |
| C-8 | F4 이름 미저장·F2 원문 미저장 원칙 자체는 옳다(강제할 코드가 없는 건 별개 미결) |
| C-9 | `scripts/index_guard.py` 류 "규칙은 문서가 아니라 게이트" 문화 — 개인정보 경계도 같은 패턴으로 밀 수 있다 |
