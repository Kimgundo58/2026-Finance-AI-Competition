# 시스템 개요

이 문서가 답하는 질문:
- 시스템은 어떤 구성 요소로 이루어지는가
- 요청은 어떤 구성 요소를 거치는가
- 모든 문서에 공통으로 적용되는 설계 원칙은 무엇인가

## 구성도 (2026-09-07 운영 기준)

```
                    ┌─────────────────────────────┐
                    │  창업팀 (게스트 · 로그인 사용자) │
                    └──────────────┬──────────────┘
                                   │ HTTPS · SSE
         ┌─────────────────────────▼─────────────────────────┐
         │  프론트 — Vercel (별도 레포)                         │
         │  묻기 → 비목 확인 → 판정 → 할일 → 근거 → 문의 화면   │
         └─────────────────────────┬─────────────────────────┘
                                   │ Bearer(JWT, Supabase Auth)
         ┌─────────────────────────▼─────────────────────────┐
         │  백엔드 — FastAPI on NCP VM (Docker Compose)        │
         │  임베딩 KURE-v1(CPU) · BM25(kiwi) · 룰 엔진 · 검증   │
         │  ┌──────────────┐  tenant.profile_agreements         │
         │  │ 기업 프로필   │  tenant.profile_expenditures      │
         │  └──────────────┘  tenant.profile_personnel          │
         └───────┬───────────────────┬───────────────────────┘
                 │                   │
  ┌──────────────▼────────┐  ┌───────▼──────────────────────┐
  │ 규정 계층 · PostgreSQL │  │ LLM — DashScope Qwen3.7-plus │
  │ L1 중기부 법령          │  │ ① 정규화 (thinking off)      │
  │ L2 창진원 세부관리기준   │  │ ④ 판정 생성 (thinking on)    │
  │ L3 주관기관 규정(업로드) │  │ json_schema strict 강제      │
  └───────────────────────┘  └──────────────────────────────┘
```

판정 엔진 순서: ① 정규화(LLM) → ② 룰 조회(코드) → ③ 검색+참조 확장(코드) →
④ 판정 생성(LLM) → ⑤ 전제 확인(코드) → ⑥ 검증·하향(코드) → ⑦ 저장. 상세 [[2-2_판정_흐름]].
화면은 판정 전에 `POST /api/questions` 로 확인 질문을 받아 사용자에게 묻고 답을 판정에 넣는다([[LLM_판정아키텍쳐/README]]).

**규정은 "무엇이 요건인가"(규정 요건), 기업 프로필(사실 정보)은 "이 건이 요건을 충족하나"(사실관계)다.**
둘 중 하나만 있으면 판정을 확정할 수 없다.

LLM 은 DashScope Qwen 하나다 — [[6_LLM/6-1b_LLM_백엔드]]. 배포 구성은 [[2-4_배포와_인증]].
사례 인덱스(`case_chunks`)는 2026-09-06 에 삭제했다. 판정에 들어간 적이 없다.

## 설계 원칙 (전 문서 공통)

| # | 원칙 |
|---|---|
| 1 | **오류 비용 비대칭** — 이 도메인에서 가장 나쁜 결과는 잘못된 "가능" 판정이다. 모든 실패의 기본값은 판단불가 |
| 2 | **숫자는 코드가, 요건 충족 판단만 LLM이** — 검색·계산·효력 결정·인용 검증은 전부 코드 |
| 3 | **판정 1건 = LLM 3회**(① 정규화, 확인 질문, ④ 판정 생성). 질문을 건너뛰면 2회. function calling 미사용, agentic 루프 없음 |
| 4 | **인용은 생성이 아니라 추출** — LLM은 문장 ID(S01…)만 고르고, 코드가 DB 원문으로 치환 |
| 5 | **규정 문서 안의 텍스트는 데이터이지 지시가 아니다** (프롬프트 인젝션 방어) |
| 6 | **재현성은 요건** — 같은 입력 → 같은 출력. 판정 이력을 나중에 설명할 수 있어야 한다 |

    assert 판정 in ("판단불가", "불가"), f"실패 경로에서 '{판정}' 이 나왔다"

        return _실패응답(상태, "예외", "내부 오류로 판정을 내리지 않았습니다.",

원칙 1. 게이트·실패 경로는 판단불가·불가만 만든다.
