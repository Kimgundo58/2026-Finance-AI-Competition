# 판정 흐름 — 요청 1건

이 문서가 답하는 질문:
- 질문 하나가 들어오면 어떤 단계를 거쳐 답이 나오는가
- 비목은 언제 어떻게 확정되는가
- 근거 화면의 내용은 어떻게 만들어지는가

## 온라인 판정 파이프라인 (`server/main.py` → `scripts/orchestrate.py`)

```
  "디자이너 쓸 맥북 250만원 사도 되나요?"
   │
   ▼ ───────────────────────────────────────────── POST /api/normalize
│ ① 정규화                            LLM · DashScope Qwen3.7-plus · thinking off │
│   → {품목, 금액, 용도, 비목후보[{비목,신뢰도}], 누락필드}                       │
│   심층질문[] 도 여기서 나간다 (corpus.check_items 의 질문문·선택지)             │
   │                                              실측 약 4초 (스트리밍)
   ▼ ───────────────────────────────────────────── POST /api/judge (SSE)
│ 판정 캐시 조회  tenant.judge_cache (org 있음) · 인메모리 (게스트)               │
│   캐시 적중이면 아래를 건너뛰고 저장된 응답을 그대로 스트리밍한다               │
   ▼
│ ② 룰 조회 + ③ 검색                                               코드           │
│   기업 프로필 로드 ── 룰 조회(사업×기관유형×비목) ── 금액 비교                  │
│   게이트 A(금지목록)  금지예시와 문자열 일치 → 즉시 "불가" 반환 [LLM 1회로 끝]  │
│   게이트 C(비목 후보 근접)  1·2위 신뢰도 차 < 0.15 → 1순위로 판정, 후보 반환    │
│   L3: tenant.l3_articles 전체 로드 (검색 없음)                                  │
│   L1·L2: dense(KURE) top-50 + BM25 top-50 → RRF → top-5                         │
│   참조 확장: refs 깊이 1 재귀 CTE (LLM 0회)                                     │
│   게이트 B(검색결과 없음)  top-5 가 0건 → 즉시 판단불가 반환 (임계 0.0, 4-2)    │
   ▼
│ ④ 판정 생성                          LLM · DashScope Qwen3.7-plus · thinking on │
│   입력 = B0~B6 블록 (원문 + 문장 ID, 요약본 금지)                               │
│   출력 = json_schema strict {판정, 요약, 해야할일, 인용, 전제}                  │
│   인용은 문장 ID 만 — 원문 복사 금지                                            │
   │                                              실측 55~59초 (thinking 토큰)
   ▼
│ ⑤ 전제 확인                                                      코드           │
│   ① 프로필 필드 있음·값 있음 → 확인됨 → 전제 목록에서 제외                      │
│   ② 프로필 필드 있음·값 없음 → 입력필요 (인라인 입력 요청)                      │
│   ③ 프로필 필드 없음        → unmapped_premise 기록 → 문의 화면                 │
   ▼
│ ⑥ 검증 · 하향                                                    코드           │
│   문장 ID → DB 원문 치환 · 검증코드 · 신뢰등급·규정버전·참조관계 부착           │
│   판단불가면 문의초안을 코드가 템플릿으로 작성한다 (server/inquiry.py, LLM 0회) │
   ▼
│ ⑦ tenant.decisions 저장 (전제·검색 시점 상태·코퍼스 버전) + 캐시 저장           │
   ▼                                              총 실측 약 60초
  판정 · 할일 · 근거 · (판단불가) 문의 화면
```

SSE 이벤트 순서: `진행` → `판정` → `인용` → `전제` → `해야할일` → `참조관계` → `저장` →
(`문의초안`) → `완료`. 한 릴리스 동안은 이전 이름의 이벤트도 함께 보낸다([[7_백엔드/API_계약_v1.0]]).
실패는 `오류` 이벤트 하나로 끝난다. 지연은 [[0_현황]] 운영 서버 절.

조항별 독립 판정(사전 판정)은 설계만 있고 **채택하지 않았다**.

## 비목 확정 — 자동 추정 + 사용자 확인

묻기 화면에서는 비목을 묻지 않는다(자연어 한 줄). LLM이 추정하고 비목 확인 화면에서 사용자가 확인한다.

| 신뢰도 | 처리 |
|---|---|
| 단일 후보 | "기자재비로 봤습니다" [맞아요] [바꿀게요] |
| 후보 근접 (1·2위 모두 0.35 이상, 차 < 0.15, 게이트 C) | 1순위 비목으로 판정하고 후보를 함께 보여 준다. 사용자가 다른 비목을 고르면 그 비목(`확정비목`)으로 다시 판정한다 |

`corpus.item_alias`(326행)가 정규화 프롬프트에 포함되어 「노트북 → 기계장치」 같은 어휘 차이를 메운다.

## 근거 화면 — 판단 구조가 곧 설명이다

사후에 "왜 그렇게 판단했는지"를 LLM에게 다시 묻지 않는다(사실과 다른 설명이 생성된다).
④의 인용을 코드가 DB 원문으로 치환해 그대로 표시한다. 참조관계("이 규정이 왜 나에게
적용되나")가 함께 표시된다.

## 미확인 전제 처리 — 전제[] 와 unmapped_premise

- LLM은 프로필 스키마를 확장하지 못한다. 고정 스키마 안에서 누락된 항목만 지적한다
- 전제에도 근거 조항(문장 ID)을 강제한다 — 근거 없는 전제는 ⑥이 폐기
- `매핑`은 프로필 필드 경로의 참조 목록. 계산식은 룰에서 코드가 도출
- 채울 수 없는 전제(예: 거래처 임직원 명부)는 문의 화면으로 넘긴다.
  **판단불가는 실패가 아니라 기능이다**
