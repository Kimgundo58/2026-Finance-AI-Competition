# 판정 흐름 — 요청 1건

이 문서가 답하는 질문:
- 질문 하나가 들어오면 어떤 단계를 거쳐 답이 나오는가
- 비목은 언제 어떻게 확정되는가
- 화면 7의 근거는 어떻게 만들어지는가

## 온라인 판정 파이프라인 (`server/main.py` → `scripts/orchestrate.py`)

```
  "디자이너 쓸 맥북 250만원 사도 되나요?"
   │
   ▼ ───────────────────────────────────────────── POST /api/normalize
│ ① 정규화                       LLM · DashScope Qwen3.7-plus · thinking off │
│   → {품목, 금액, 용도, 비목후보[{비목,신뢰도}], 누락필드}                  │
│   심층질문[] 도 여기서 나간다 (corpus.check_items 의 질문문·선택지)       │
   │                                              실측 약 4초 (스트리밍)
   ▼ ───────────────────────────────────────────── POST /api/judge (SSE)
│ 판정 캐시 조회  tenant.judge_cache (org 있음) · 인메모리 (게스트)          │
│   적중이면 아래를 건너뛰고 저장된 응답을 그대로 흘린다                     │
   ▼
│ ② 룰 조회 + ③ 검색                                     코드            │
│   F 프로필 로드 ── 룰 조회(사업×기관유형×비목) ── 금액 비교              │
│   게이트 A  금지예시 «문자» 적중 → 즉답 "불가"  [LLM 1회로 끝]         │
│   게이트 C  비목 1·2위 신뢰도 차 < 0.15 → 두 갈래 판정 → "선택필요"      │
│   L3: tenant.l3_articles 통째 로드 (검색 없음)                          │
│   L1·L2: dense(KURE) top-50 + BM25 top-50 → RRF → top-5                │
│   참조 확장: refs 깊이 1 재귀 CTE (LLM 0회)                             │
│   게이트 B  top-5 가 0건 → ⑥ 판단불가 직행 (임계 0.0 확정 — 4-2 참조)    │
   ▼
│ ④ 판정 조립                     LLM · DashScope Qwen3.7-plus · thinking on │
│   입력 = B0~B6 블록 (원문 + S번호, 요약본 금지)                          │
│   출력 = json_schema strict {판정, 요약, 해야할일, 인용, 전제}           │
│   인용은 S번호만 — 원문 복사 금지                                        │
   │                                              실측 55~59초 (thinking 토큰)
   ▼
│ ⑤ 전제 해소                                              코드          │
│   ① F 있음·값 있음 → 즉시 검증 → 소멸                                    │
│   ② F 있음·값 없음 → 인라인 입력 요청                                   │
│   ③ F 없음        → unmapped_premise 로깅 → 화면 9                       │
   ▼
│ ⑥ 검증 · 강등                                             코드          │
│   S번호 → DB 원문 치환 · 강등코드 22종 · 신뢰등급·버전스탬프·참조사슬 부착 │
│   판단불가면 문의초안을 코드가 조립한다 (server/inquiry.py, LLM 0회)      │
   ▼
│ ⑦ tenant.decisions 저장 (전제·검색 시점 상태·코퍼스 버전) + 캐시 적재      │
   ▼                                              총 실측 약 60초
  화면 5 판정 · 6 할일 · 7 근거 · (판단불가) 9 문의
```

SSE 이벤트 순서: `진행` → `판정` → `인용` → `전제` → `해야할일` → `참조사슬` → `저장` →
(`문의초안`) → `완료`. 실패는 `오류` 하나로 닫는다. 지연은 [[0_현황]] 실서버 절.

④-a 포섭 스크리닝(조항별 독립 판정)은 설계만 있고 **채택하지 않았다**.

## 비목 확정 — 자동 추정 + 사용자 컨펌

화면 3에서는 비목을 묻지 않는다(자연어 한 줄). LLM이 추정하고 화면 4에서 컨펌받는다.

| 신뢰도 | 처리 |
|---|---|
| 단일 후보 | "기자재비로 봤습니다" [맞아요] [바꿀게요] |
| 갈림 (1·2위 차 < 0.15, 게이트 C) | 두 경로를 모두 판정해 결과를 보여주고 고르게 한다 |

`corpus.item_alias`(326행)가 정규화 프롬프트에 실려 「노트북 → 기계장치」 같은 어휘 갭을 메운다.

## 화면 7 — 판단 구조가 곧 설명이다

사후에 "왜 그렇게 판단했는지"를 LLM에게 다시 묻지 않는다(지어낸 서사가 나온다).
④의 인용을 코드가 DB 원문으로 치환해 그대로 그린다. 참조사슬("이 규정이 왜 나에게
적용되나")이 함께 렌더된다.

## 결핍 처리 루프 — 전제[] 와 unmapped_premise

- LLM은 F 스키마를 확장하지 못한다. 고정 스키마 안에서 결핍만 지적한다
- 전제에도 근거 조항(S번호)을 강제한다 — 근거 없는 전제는 ⑥이 폐기
- `매핑`은 F필드 경로의 참조 목록. 계산식은 룰에서 코드가 도출
- 채울 수 없는 전제(예: 거래처 임직원 명부)는 화면 9로 넘긴다.
  **판단불가는 실패가 아니라 기능이다**
