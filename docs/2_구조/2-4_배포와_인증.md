# 배포와 인증

이 문서가 답하는 질문:
- 시스템은 어디에서 무엇으로 돌아가는가
- 데이터는 어디까지 나가고 어디서 멈추는가
- 개인정보는 어떻게 계층화해 저장하는가

## 배포 토폴로지

```
╔══════════════════════════════════════════════════════════════════════╗
║  브라우저 — 정적 프론트                                               ║
║   게스트: 화면 3~9 판정 가능 (F축 없이, 전제[] 다수)                  ║
║   로그인: Supabase Auth → F축 프로필 저장 · 판정 이력 · 전제 해소     ║
╚═══════════════════════════════│══════════════════════════════════════╝
                                │  HTTPS / SSE (스트리밍) · Bearer(JWT)
╔═══════════════════════════════▼══════════════════════════════════════╗
║  앱 서버 (FastAPI) — Cloud Run                                       ║
║   인증·SSE / 판정 오케스트레이터 / 룰 엔진 / 전제 해소기 /            ║
║   인용 검증기 / LLM 어댑터                                           ║
║   임베딩 KURE-v1 (CPU, 워커당 ~1.5GB — 사양이 동시성 한계)           ║
║   kiwipiepy (쿼리 토큰화)                                            ║
╚══════════╤══════════════════════════════╤════════════════════════════╝
           │ 데이터 경계 ①                │ 데이터 경계 ②
╔══════════▼════════════════╗  ╔══════════▼════════════════════════════╗
║  GCP · asia-northeast3    ║  ║  LLM 서빙 — vLLM (RunPod / 자체 GPU)  ║
║  Cloud SQL PG17 +pgvector ║  ║  전 호출 자리 오픈소스 (Qwen3)        ║
║   2vCPU/8GB · SSD 20GB    ║  ║  F축 포함 호출 자리는 외부 API 금지    ║
║  corpus · tenant · eval   ║  ║  (어댑터 f_axis 통과 조건)            ║
╚═══════════════════════════╝  ╚═══════════════════════════════════════╝
```

- 데이터가 밖으로 나가는 경계는 **둘**이다(LLM 서빙 + 관리형 DB 저장). 원문·실명이
  안 나가는 것은 저장 계층화 덕분이지 인프라 덕분이 아니다
- **Supabase 는 인증(Auth)만 쓴다 — 데이터는 저장하지 않는다.** 저장은 전량 Cloud SQL
- `eval`(정답셋)이 같은 DB 에 있어도 **검색 인덱스 투입 금지는 그대로**다.
  막는 것은 저장 위치가 아니라 `scripts/index_guard.py` 다
- `tenant` 격리는 **RLS + 코드 이중**으로 그대로 간다 — RLS 는 Postgres 기능이라
  관리형이 바뀌어도 살아 있다. 다만 「anon 키로 새는」 갈래는 사라졌다 (PostgREST 없음)

### 용량 — SSD 20GB 를 고른 근거 (2026-09-03 실측)

**총 335MB** = corpus 323 / tenant 2.2 / eval 1.4.
큰 순서로 `chunks` 151MB · `chunk_terms` 103MB · `doc_articles` 40MB · `refs` 21MB.

> 관측: 335MB. 추론: 20GB 면 **60배 여유**이고, 코퍼스가 지금의 몇 배로 늘어도 용량이
> 병목이 되지 않는다. Supabase 무료 500MB 한도에 걸렸던 이유가 바로 이 숫자다 —
> 한도가 사라졌으므로 「판정 엔진이 관리형이냐 로컬 DB 냐」 갈림길도 함께 사라졌다.

## 인증 — 프론트와 백엔드의 분담

```
프론트  Supabase Auth 로그인 → JWT  ||  백엔드  Bearer 수신 → pyjwt 검증(RS256/ES256)
        Bearer 헤더로 첨부           ||          → email 클레임 → accounts → org_id 주입
```

- 검증키는 **JWKS 공개주소**에서 가져온다 — 프론트·백엔드가 나눠 갖는 비밀값이 없다
- `org_id` 는 토큰이 주장하는 값이 아니라 **서버가 조회해 주입**한다.
  L3 격리(`org_id = :현재기관`)가 여기에 걸려 있다
- 🔴 **조인 열쇠는 `sub` 가 아니라 `email` 이다** (`server/auth.py:29-34`, `:189-196`).
  `tenant.accounts` 에 `sub` 컬럼이 없어서다 — `accounts.sub UUID UNIQUE` 를 추가하면
  `_계정조회()` 한 함수만 바꾸면 된다. 그때까지는 `email` 클레임이 없는 토큰은 403
- 데모 갈래(HS256 · 서버 자체 서명 · `org` 클레임 직결)가 따로 있고 `iss` 로 가른다.
  갈래마다 **허용 알고리즘을 고정**한다 — 안 고정하면 JWKS 공개키가 HMAC 비밀키가 된다

## 개인정보 — 저장 계층화

| 데이터 | 저장 | 비고 |
|---|---|---|
| 계정 | ✅ `accounts` (`email` ↔ `org_id`) | 이메일은 조인 열쇠라 **있다**. 비밀번호는 없다(`pw_hash` 비움) — Supabase Auth 가 든다 |
| F1 협약 · F3 집행내역 (숫자) | ✅ | 민감도 낮음 |
| F4 인력 | ✅ | **이름 저장 ✕** — 역할·수치만 |
| F5 거래처 | ⚠️ 건별, 판정 후 폐기 | 체크박스 결과만 |
| F2 사업계획서 원문 · PMS 원문 | 🔴 **저장 ✕** | 파싱 후 폐기, 구조화 결과만 |

- 개인정보처리방침·수집 동의·파기 정책·컬럼 암호화 필요.
  🔴 **위탁처가 바뀌었다** — 저장 위탁은 Google(Cloud SQL), 인증 위탁은 Supabase.
  [[9-1_법적_지적사항]] B-8 과 [[부록/법적_점검_전문]] 은 아직 Supabase 저장을 전제로 쓰여 있다
- **F축이 프롬프트에 들어가는 LLM 호출은 자체 통제 하드웨어 강제** — 어댑터 `f_axis` 통과 조건
- **게스트 경로 유지**: 로그인은 관문이 아니라 정확도 다이얼이다
  ("협약 정보 입력하면 미확인 전제 2개가 사라집니다")
