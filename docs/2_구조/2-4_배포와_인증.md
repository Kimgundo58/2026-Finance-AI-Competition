# 배포와 인증

이 문서가 답하는 질문:
- 시스템은 어디에서 무엇으로 실행되는가
- 데이터는 어디까지 나가고 어디서 멈추는가
- 개인정보는 민감도에 따라 어떻게 나눠 저장하는가

## 배포 토폴로지 (NCP VM 1대, `deploy/ncp`)

```
╔══════════════════════════════════════════════════════════════════════╗
║  브라우저 — 프론트 (Vercel, 별도 레포)                                 ║
║   게스트: 판정 가능 (기업 프로필 없이, 전제[] 다수)                   ║
║   로그인: Supabase Auth → 기업 프로필 저장 · 판정 이력 · 전제 확인    ║
╚═══════════════════════════════│══════════════════════════════════════╝
                                │  HTTPS / SSE (스트리밍) · Bearer(JWT)
╔═══════════════════════════════▼══════════════════════════════════════╗
║  NCP VM (Ubuntu, 2vCPU/8GB) — Docker Compose: caddy · api · db       ║
║  caddy: HTTPS(Let's Encrypt) 리버스 프록시 · 요청 본문 상한 35MB      ║
║  api (FastAPI): 인증·SSE / 판정 파이프라인 / 룰 엔진 / 전제 확인 /    ║
║   인용 검증 / 판정 캐시                                              ║
║   임베딩 KURE-v1 (CPU, 기동 시 동기 워밍업 약 44초)                   ║
║   kiwipiepy (쿼리 토큰화)                                            ║
╚══════════╤══════════════════════════════╤════════════════════════════╝
           │ 내부 연결 (같은 VM)          │ 데이터 경계 (외부 API)
╔══════════▼════════════════╗  ╔══════════▼════════════════════════════╗
║  db 컨테이너 (같은 VM)     ║  ║  LLM — DashScope (Alibaba, 국제 리전)  ║
║  PG17 + pgvector          ║  ║  Qwen3.7-plus · ①정규화 ④판정         ║
║   외부 포트 미노출         ║  ║  json_schema strict                   ║
║  corpus · tenant          ║  ║                                       ║
╚═══════════════════════════╝  ╚═══════════════════════════════════════╝
```

- 데이터가 밖으로 나가는 경계는 LLM API 하나다(DB 는 같은 VM 의 컨테이너). 원문·실명이
  나가지 않는 것은 민감도별 저장 정책 때문이다(아래 표)
- **LLM 은 외부 API 다.** 기업 프로필 요약이 들어간 프롬프트도 DashScope 로 보낸다
- **Supabase 는 인증(Auth)만 쓴다 — 데이터는 저장하지 않는다.** 저장은 전량 VM 의 PostgreSQL
- 운영 DB 에는 `eval`(골든셋)이 없다. 로컬처럼 같은 DB 에 있어도 **검색 인덱스 투입 금지**는
  저장 위치가 아니라 `scripts/retrieve.py` 의 FILTER 가 막는다
- `tenant` 격리는 **RLS + 코드 이중**이다. RLS 는 `tenant.current_org()`(GUC `app.org_id`)와
  `tenant.current_account()`(GUC `app.account_id`)를 읽고, 앱은 비특권 롤 `suddoe_app` 으로 접속한다.
  L3 는 기관(주관기관) 단위, 기업 데이터(프로필·계획·할일·판정·캐시)는 계정 단위다 — [[3-5_저장소_스키마]]

코드: `db/init/01_schema.sql` · `tenant.current_org()` · RLS 정책
```sql
CREATE FUNCTION tenant.current_org() RETURNS uuid
...
    IF v IS NULL OR v = '' THEN
        v := nullif(current_setting('app.org_id', true), '');
    END IF;
...
CREATE POLICY org_isolation ON tenant.l3_articles   USING (org_id = tenant.current_org());
...
CREATE POLICY account_isolation ON tenant.decisions USING (
    org_id = tenant.current_org() AND account_id IS NOT DISTINCT FROM tenant.current_account());
```

코드: `server/_common.py` · `_rls_org_설정()`
```python
    if org is None:
        return
    conn_or_cur.execute("SELECT set_config('app.org_id', %s, true), set_config('app.account_id', %s, true)",
                        (str(org), str(account) if account else ""))
```
코드 쪽은 매 트랜잭션에 검증된 org·계정만 GUC 로 설정한다(데모 세션은 계정이 없어 빈 값). 세 번째 인자 `true` 가 트랜잭션 한정이다.
- main 에 병합하면 자동 배포된다. `db/migrations`·`deploy/ncp` 변경은 손으로 적용한 뒤 `deploy.sh --force` 로 배포한다 — [[8_운영/8-8_CI_CD]]
- 백업은 `backup.sh` 가 매일 pg_dump 로 만든다. 스키마 변경은 `db/migrations/` 를 수동 적용한다

### 용량 (2026-09-03 측정)

**총 335MB** = corpus 323 / tenant 2.2 / eval 1.4.
큰 순서로 `chunks` 151MB · `chunk_terms` 103MB · `doc_articles` 40MB · `refs` 21MB.
VM 디스크(SSD 50GB)에 덤프 14개를 보관해도 여유가 크다.

## 인증

프론트는 Supabase Auth JWT 를 Bearer 로 보내고 백엔드가 검증해 `org_id` 를 주입한다 — 상세는 [[2-4b_인증]].

## 개인정보 — 민감도별 저장 정책

| 데이터 | 저장 | 비고 |
|---|---|---|
| 계정 | O `accounts` (`email` ↔ `org_id`) | 이메일은 조인 키라 **있다**. 비밀번호는 없다(`pw_hash` 비움) — Supabase Auth 가 관리한다 |
| 협약 · 집행내역 (숫자) | O | 민감도 낮음 |
| 참여인력 | O | **이름 저장 X** — 역할·수치만 |
| 특수관계(거래처) | 건별, 판정 후 폐기 | 체크박스 결과만 |
| 과업범위(사업계획서) 원문 · PMS 원문 | **저장 X** | 파싱 후 폐기, 구조화 결과만 |
| 질문 원문 · 판정 결과 | O `decisions` | 판정 프롬프트는 DashScope 로 나간다 |

- 저장은 네이버클라우드 VM(자체 운영 PostgreSQL), 인증 위탁은 Supabase, LLM 처리 위탁은 Alibaba Cloud(DashScope).
- **게스트 경로 유지**: 로그인은 필수가 아니다. 로그인해 기업 프로필을 저장하면 정확도가 올라간다
  ("협약 정보 입력하면 미확인 전제 2개가 사라집니다")
