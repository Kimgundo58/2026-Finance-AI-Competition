# 배포와 인증

이 문서가 답하는 질문:
- 시스템은 어디에서 무엇으로 돌아가는가
- 데이터는 어디까지 나가고 어디서 멈추는가
- 개인정보는 어떻게 계층화해 저장하는가

## 배포 토폴로지 (NCP VM 1대, `deploy/ncp`)

```
╔══════════════════════════════════════════════════════════════════════╗
║  브라우저 — 프론트 (Vercel, 별도 레포)                                 ║
║   게스트: 화면 3~9 판정 가능 (F축 없이, 전제[] 다수)                  ║
║   로그인: Supabase Auth → F축 프로필 저장 · 판정 이력 · 전제 해소     ║
╚═══════════════════════════════│══════════════════════════════════════╝
                                │  HTTPS / SSE (스트리밍) · Bearer(JWT)
╔═══════════════════════════════▼══════════════════════════════════════╗
║  NCP VM (Ubuntu, 2vCPU/8GB) — Docker Compose: caddy · api · db       ║
║  caddy: HTTPS(Let's Encrypt) 리버스 프록시 · 요청 본문 상한 35MB      ║
║  api (FastAPI): 인증·SSE / 판정 파이프라인 / 룰 엔진 / 전제 해소 /    ║
║   인용 검증 / 판정 캐시                                              ║
║   임베딩 KURE-v1 (CPU, 기동 시 동기 워밍업 약 44초)                   ║
║   kiwipiepy (쿼리 토큰화)                                            ║
╚══════════╤══════════════════════════════╤════════════════════════════╝
           │ 데이터 경계 ①                │ 데이터 경계 ②
╔══════════▼════════════════╗  ╔══════════▼════════════════════════════╗
║  db 컨테이너 (같은 VM)     ║  ║  LLM — DashScope (Alibaba, 국제판)     ║
║  PG17 + pgvector          ║  ║  Qwen3.7-plus · ①정규화 ④판정         ║
║   외부 포트 미노출         ║  ║  json_schema strict                   ║
║  corpus · tenant          ║  ║                                       ║
╚═══════════════════════════╝  ╚═══════════════════════════════════════╝
```

- 데이터가 밖으로 나가는 경계는 LLM API 하나다(DB 는 같은 VM 의 컨테이너). 원문·실명이
  나가지 않는 것은 저장 계층화 덕분이다
- **LLM 은 외부 API 다.** F축 요약이 들어간 프롬프트도 DashScope 로 보낸다
- **Supabase 는 인증(Auth)만 쓴다 — 데이터는 저장하지 않는다.** 저장은 전량 VM 의 PostgreSQL
- 운영 DB 에는 `eval`(정답셋)이 없다. 로컬처럼 같은 DB 에 있어도 **검색 인덱스 투입 금지**는
  저장 위치가 아니라 `scripts/retrieve.py` 의 FILTER 가 막는다
- `tenant` 격리는 **RLS + 코드 이중**이다. RLS 는 `tenant.current_org()`(GUC `app.org_id`)를
  읽고, 앱은 비특권 롤 `suddoe_app` 으로 접속한다 — [[3-5_저장소_스키마]]
- 배포는 수동이다(서버에서 `git pull && docker compose up -d --build api`) — [[8_운영/8-6_NCP_배포]]
- 백업은 `backup.sh` 가 매일 pg_dump 로 만든다. 스키마 변경은 `db/migrations/` 를 수동 적용한다

### 용량 (2026-09-03 측정)

**총 335MB** = corpus 323 / tenant 2.2 / eval 1.4.
큰 순서로 `chunks` 151MB · `chunk_terms` 103MB · `doc_articles` 40MB · `refs` 21MB.
VM 디스크(SSD 50GB)에 덤프 14개를 보관해도 여유가 크다.

## 인증 — 프론트와 백엔드의 분담

```
프론트  Supabase Auth 로그인 → JWT  ||  백엔드  Bearer 수신 → pyjwt 검증(RS256/ES256)
        Bearer 헤더로 첨부           ||          → email 클레임 → accounts → org_id 주입
```

- 검증키는 **JWKS 공개주소**(`SUDDOE_JWKS_URL`)에서 가져온다 — 프론트·백엔드가 나눠 갖는 비밀값이 없다
- `org_id` 는 토큰이 주장하는 값이 아니라 **서버가 조회해 주입**한다.
  L3 격리(`org_id = :현재기관`)가 여기에 걸려 있다. 자기신고 `org_id` 파라미터는
  `SUDDOE_ORG_PARAM=0` 으로 막혀 있다(`server/auth.py`)
- 조인 열쇠는 `sub` 가 아니라 `email` 이다. `tenant.accounts` 에 `sub` 컬럼이 없어서다.
  `email` 클레임이 없는 토큰은 403
- 데모 토큰(HS256 · 서버 자체 서명 · `org` 클레임 직결)이 따로 있고 `iss` 로 구분한다.
  토큰 종류마다 **허용 알고리즘을 고정**한다 — 고정하지 않으면 JWKS 공개키가 HMAC 비밀키로 쓰일 수 있다

## 개인정보 — 저장 계층화

| 데이터 | 저장 | 비고 |
|---|---|---|
| 계정 | O `accounts` (`email` ↔ `org_id`) | 이메일은 조인 열쇠라 **있다**. 비밀번호는 없다(`pw_hash` 비움) — Supabase Auth 가 든다 |
| F1 협약 · F3 집행내역 (숫자) | O | 민감도 낮음 |
| F4 인력 | O | **이름 저장 X** — 역할·수치만 |
| F5 거래처 | 건별, 판정 후 폐기 | 체크박스 결과만 |
| F2 사업계획서 원문 · PMS 원문 | **저장 X** | 파싱 후 폐기, 구조화 결과만 |
| 질문 원문 · 판정 결과 | O `decisions` | 판정 프롬프트는 DashScope 로 나간다 |

- 저장은 네이버클라우드 VM(자체 운영 PostgreSQL), 인증 위탁은 Supabase, LLM 처리 위탁은 Alibaba Cloud(DashScope).
- **게스트 경로 유지**: 로그인은 관문이 아니라 정확도 다이얼이다
  ("협약 정보 입력하면 미확인 전제 2개가 사라집니다")
