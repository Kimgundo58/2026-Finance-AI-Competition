# 기업 프로필

이 문서가 답하는 질문:
- 기업 프로필은 무엇을 저장하는가
- 사실이 없어도 판정이 나가는 이유는 무엇인가
- PMS 데이터는 어떻게 안전하게 입력받는가

## 기업 프로필은 규정 밖의 "사실"이다

조문 다수가 규정 밖의 사실을 요건으로 건다. 기업 프로필(사실 정보)은 판정에 쓰는 사실관계다:

```
"사업계획서 상의 사업화를 위해 필요한 기계장치…"  ← 과업 범위를 알아야 (과업범위)
기자재비 한도 20%                                 ← 기집행액을 알아야 (집행내역)
협약기간 밖 집행 불가                              ← 협약 기간을 알아야 (협약)
```

## 프로필 항목

| 항목 | 필드 | 갱신 |
|---|---|---|
| **협약** | 총 협약금액(**재원 2종** — 정부지원·자기부담) · 시작일 · 종료일 | 1회 |
| 과업범위(사업계획서) | 사업화 과업 요약 (원문 저장 안 함) | 1회 |
| **집행내역** | **비목별 · 거래처별 · 인별×월별** 누적, 재원 2종 집계 | 수시 |
| **참여인력** | 타 사업 참여율 · **소속기관 유형** · 고용형태 · 겸직 | 1회 |
| 특수관계(거래처) | 친족 · 전직 임직원 · 구매 명의 | 건별, 판정 후 폐기 |
| 기업정보 | 업력 · 매출 · 지분 | 1회 |
| 수혜이력 | 타 사업 중복지원 | 1회 |

- **재원 2종**: `{정부지원, 자기부담}` — `tenant.profile_expenditures.재원` CHECK 제약이 이 둘뿐이다.
  현물 형태는 뺐다(2026-08-31) — 현물 계상은
  지출이 아니라 사전승인 판정 대상이 아니다. 자기부담 구성비율 룰(현금 5%↑/현물 20%↓)은
  이 결정으로 검증 불가해졌다
- **집행내역 집계 기준 3개**: 비목별 한도 · 동일 거래처 누적(2천만원 심의) · 인별월별 상한
- **참여인력 소속기관 유형**: 참여율 상한이 100% / 130%로 달라진다
- MVP(예비/초기창업패키지)의 핵심은 **협약·집행내역·참여인력**. 특수관계·기업정보·수혜이력은 후순위
- 건별 사실(품목·금액·시기)은 기업 프로필이 아니라 ① 정규화가 그때그때 받는다
- **프로필 항목은 고정되지 않는다.** 부족한 항목은 `unmapped_premise` 집계([[2-2b_근거와_전제]])로
  드러나고, 빈도가 높은 미매핑 전제를 필드로 추가한다
- 저장 스키마: [[3-5_저장소_스키마]] (`tenant.profile_agreements` · `profile_expenditures` · `profile_personnel`).
  API 필드 이름은 `협약` · `집행내역` · `참여인력` · `특수관계`
- 판정 프롬프트와 `전제[].매핑` 값은 아직 경로 접두어 `F1.`(협약) · `F2.`(과업범위) · `F3.`(집행내역) ·
  `F4.`(참여인력) · `F5.`(특수관계)를 쓴다. LLM 에 보이는 문자열이라 프롬프트 재평가와 함께 바꾼다

코드: `db/init/01_schema.sql` · `tenant.profile_expenditures`
```sql
CREATE TABLE tenant.profile_expenditures (
    exec_id     BIGSERIAL PRIMARY KEY,
    profile_id  UUID NOT NULL REFERENCES tenant.profile_agreements(profile_id) ON DELETE CASCADE,
    비목        TEXT NOT NULL,                 -- 비목 어휘집 enum
    재원        TEXT NOT NULL CHECK (재원 IN ('정부지원','자기부담')),
    ...
    거래처      TEXT,                          -- 동일 거래처 누적(2천만원 심의)용
    인력역할    TEXT,                          -- 인별월별 집계용. 이름 아님
    귀속월      DATE,
    금액        NUMERIC NOT NULL,
```
생략한 `형태`(현금·현물) 컬럼은 `db/init/04_validation_eval.sql` 이 지운다.

코드: `scripts/llm_validate.py` · `프로필_테이블`
```python
# 프로필 필드 경로는 tenant 의 실제 컬럼에서 만든다. 경로 표기는 "F1.정부지원.현금" 형식이고
# 컬럼 정부지원_현금 의 '_' 가 '.' 이 된다.
프로필_테이블 = {"F1": "profile_agreements", "F3": "profile_expenditures", "F4": "profile_personnel"}
# profile_agreements 에 있지만 접두어가 따로 붙은 컬럼
프로필_특례 = {"F2": {"과업범위요약"}}
# 저장하지 않는 항목(판정 후 폐기). 테이블이 없으므로 항목명을 그대로 허용한다
비저장_항목 = {"친족", "전직임직원", "구매명의"}
```

## 협약·집행내역 입력 — PMS 텍스트 붙여넣기

K-Startup PMS "사전승인 신청" 화면에 집행협약한도액(협약 항목)·신청가능금액이 현금/현물
분리로 표시된다. 사용자가 그 표를 **드래그 복사 → textarea 붙여넣기 → 브라우저에서
정규식 파싱(서버 전송 없음) → 숫자만 폼에 자동 입력 → 확인 후 확인된 숫자만 서버 전송.**
원문(실명·과제번호 포함)은 서버에 도달하지 않는다. 스크린샷 업로드는 지원하지 않는다.

## 입력 최소화 원칙

입력 경로를 추가할 때마다 이 5개 질문을 통과시킨다:

```
1. 판정에 필요한 최소 단위가 무엇인가?   문서 / 필드 / 체크박스 하나
2. 그 단위보다 큰 것을 받고 있지 않은가?
3. 사용자가 "무엇을 주는지" 알 수 있는가?
4. 값이 틀렸을 때 책임이 누구에게 남는가?   ← 사용자가 입력한 값이어야 책임이 사용자에게 남는다
5. 원문 없이 구조화 결과만으로 기능이 유지되는가?
```
