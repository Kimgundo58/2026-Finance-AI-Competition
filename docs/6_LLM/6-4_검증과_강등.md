## 5. 검증·강등(6) — 마지막 방어선

강등코드의 기준 목록은 `scripts/llm_validate.py` 의 `강등코드_전체`(24개)다.
`tenant.decisions` 의 CHECK(`db/init/04_agent.sql`)가 같은 목록을 쓰고, 코드를 추가할 때는
`db/migrations/` 에 CHECK 교체 마이그레이션을 함께 낸다. 목록 밖의 코드는 `_강등()` 에서 예외가 난다.

측정(run_id=191, 93문항): `PREMISE_UNMAPPED` 43 · `CITE_HANG_MISMATCH` 13 · `VLM_DOWNGRADE` 7 ·
`TASK_STATE_UNSOURCED` 1 외에는 적중하지 않았다. 나머지 코드의 연결 여부는
`python scripts/orchestrate.py --fault all --dry` 로 확인한다.

판정이 LLM 출력과 달라지면(강등) LLM 의 `요약` 대신 최종 판정에 맞는 정형 문장으로 바꾼다.
판단불가 배지 옆에 "가능하다"는 LLM 요약이 남지 않게 하기 위해서다. 강등은 `불가` 를 만들지 않는다.

| 조건 | 조치 |
|---|---|
| 인용 0개 | 판단불가 |
| "가능"인데 인용이 B등급뿐 / L3 단독 | 조건부 강등 |
| 붙은 룰이 **전부** `verified=false` 인데 "가능" | 조건부 강등 (`UNVERIFIED_RULE`) |
| 인용 `기관ID` 가 NULL도 현재기관도 아님 | 즉시 폐기 + 사고 로그 |
| 참조 확장에 끊긴 참조 있었음 | 경고 + 신뢰등급 하향 |
| `extraction='vlm'` 청크 인용 | A등급 금지 + "판독본 기반" 경고 |

precedence 는 여기서도 적용된다 — L3 근거의 "불가"가 L2 우선 규칙에 걸리면 뒤집힌다.

위 표의 `UNVERIFIED_RULE` 행은 `llm_validate.py` 가 `effective_rule` 의 `룰들[].verified` 로 판단한다
(`not any(verified)`, 하나라도 검수됐으면 통과). `rule_lookup` 이 따로 내던 강등 권고 필드는 읽는 곳이 없어 삭제했다.

## 6. 화면에 나갈 때 지키는 것

- 틀린 "가능"이 최악(환수 5배) — 근거 인용 못 하면 무조건 판단불가
- 참조가 구판 조번호일 수 있다 — 조 제목으로 재매칭, 보정 사실을 답변에 병기
  (예: "귀 기관 규정은 제33조라 하지만 현행 기준 제39조입니다")
- 위임 사슬을 함께 보여준다("지원법§2→시행령§2⑤→고시§4") — 조항 하나만 던지지 않는다
- L3가 없으면 그 사실을 말한다("L1·L2 기준으로는 가능, 다만 소속 기관 규정이 더 엄격할 수 있음")
- 사례 인덱스(`corpus.case_chunks`, 193행)는 쓰지 않는다. B등급 인용 자체가 안 나오므로
  "R&D 사례 참고" 라벨 규칙은 적용 대상이 없다. 판정 인덱스는 여전히 L1·L2 +
  현재 기관 L3 뿐이라는 물리 분리 원칙은 그대로다(사라진 건 사례 테이블이지 경계가 아니다).
  `orchestrate._사례()` 호출부 2곳(판단불가 경로·일반 경로)을 뺐다 — dry 응답에 `유사사례`
  키가 없다
- 이 서비스는 정보 표시이지 법률 대리가 아니다 — 단정 표현 금지, 담당자 확인 문구 유지
