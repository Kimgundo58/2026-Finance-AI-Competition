# LLM 호출 설계

이 문서가 답하는 질문:
- LLM 은 몇 번, 무엇을 위해 불리는가
- 호출 자리별로 어떤 역할을 하는가
- 오케스트레이션 순서는 어떻게 고정되는가

> 어떤 모델·백엔드가 실제로 도는지(vLLM↔DashScope 전환·thinking 설정·검증 사다리)는
> [[6-1b_LLM_백엔드]] — 이 문서는 호출 자리·예산·분기만 다룬다.

## 0. LLM 이 하는 일은 하나

**포섭** — 이 사실이 이 요건에 해당하는가. 검색어 생성·도구 호출·숫자 계산·효력 판단은
전부 코드가 한다. 오케스트레이터는 LLM 이 아니다 — 코드가 순서를 지휘한다
(멀티 에이전트 오케스트레이션 없음 · agentic multi-hop 없음).

## 1. 호출 자리

| 호출 자리 | F축 | 역할 |
|---|---|---|
| ① 정규화 | O | 자유문 → 구조화 입력. thinking 불필요(추출 작업) |
| L3 문서 파싱 | — | **LLM 아님** — HWPX/DOCX/PDF 텍스트를 코드가 조·항으로 가른다. 스캔본 판독(비전 API·Document AI)은 배선만 있고 운영에서 꺼져 있다 |
| ④-a 스크리닝 | — | 설계만. 미채택 |
| ④-b 판정 조립 | O(B5=F프로필) | B0~B6 근거로 4-way 판정 |
| 문의초안 | — | **LLM 아님** — 판단불가일 때 판정이 쥔 전제·인용으로 코드가 조립(`server/inquiry.py`) |

지금 어떤 모델이 각 자리를 도는지는 [[6-1b_LLM_백엔드]] §1.

## 2. 요청 1건 — 단계별 주체와 예산

예산은 합계가 아니라 **배분**이 정보다 — 어디가 느린지가 병목 진단의 재료다.

| # | 단계 | 주체 | 예산 |
|---|---|---|---|
| (1) | 입력 정규화 | LLM | 스트리밍 |
| (2)-a | 비목 확정 | 코드 | ~150ms |
| (2)-b | L3 룰 조회(먼저) | 코드(SQL) | <10ms |
| (2)-c | 통과 조건 판정 | 코드 | ~0 |
| (2)-d | L1·L2 룰 + 효력 결정 | 코드(SQL) | <20ms |
| (2)-e | 금액 비교 | 코드 | ~0 |
| (3)-a | L3 통째 로드 | 코드(SQL) | <20ms |
| (3)-b | 필터 확정(L1·L2만) | 코드(SQL) | ~10ms |
| (3)-c | dense 검색 | pgvector | <200ms |
| (3)-d | sparse 검색 | BM25(SQL) | <50ms |
| (3)-e | RRF 결합 | 코드 | ~0 |
| (3)-f | 참조 확장 수집(깊이1) | 코드 | <30ms |
| (4) | 판정 조립(B0~B6) | LLM | 스트리밍 |
| (5) | 전제 해소 | 코드 | ~0 |
| (6) | 검증·강등 | 코드 | ~0 |
| (7) | 로깅 | 코드 | ~0 |

(3)-a(L3) 와 (3)-b~f(검색)는 독립이라 병렬. LLM 호출은 **2~3회**(① 정규화, ④ 조립,
조건부 ④' 근거 보강 재판정).

「폐포(B3) 없이 먼저 판정하고 근거가 모자라면 붙여 다시 판정한다」(④') — 호출 수 상한은
**3회 고정**, 「근거가 모자란가」는 **코드가** 정한다(LLM 에게 안 되묻는다).

## 3. 통과 조건과 분기

| 통과 조건 | 결과 | LLM 호출 |
|---|---|---|
| A. 금지목록 적중 | 즉답 "불가" | 0회 |
| B. 검색 결과 0건 (임계 0.0 확정) | 판단불가 | 1회((1)만) |
| C. 비목 신뢰도 갈림 | 두 경로 모두 판정해 나란히 표시 | 2배 |
| D. 정상 경로 | (4)까지 | 2~3회 |
