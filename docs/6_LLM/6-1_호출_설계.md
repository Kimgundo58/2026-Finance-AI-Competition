# LLM 호출 설계

이 문서가 답하는 질문:
- LLM 은 몇 번, 무엇을 위해 불리는가
- 호출 지점별로 어떤 역할을 하는가
- 오케스트레이션 순서는 어떻게 고정되는가

> 어떤 모델이 실제로 실행되는지(DashScope 모델·thinking 설정·모델 교체 검증 절차)는
> [[6-1b_LLM_백엔드]] — 이 문서는 호출 지점·예산·분기만 다룬다.

## 0. LLM 이 하는 일은 하나

**요건 충족 판단(포섭)** — 이 사실이 이 요건에 해당하는가. 검색어 생성·도구 호출·숫자 계산·효력 판단은
전부 코드가 한다. 오케스트레이터는 LLM 이 아니다 — 코드가 순서를 지휘한다
(멀티 에이전트 오케스트레이션 없음 · agentic multi-hop 없음).

## 1. 호출 지점

| 호출 지점 | 기업 프로필 | 역할 |
|---|---|---|
| ① 정규화 | O | 자유문 → 구조화 입력. thinking 불필요(추출 작업) |
| L3 문서 파싱 | — | **LLM 아님** — HWPX/HWP/PDF 텍스트를 코드가 조·항으로 나눈다. 스캔본은 OCR 하지 않고 파싱 실패로 처리한다 |
| 사전 판정(스크리닝) | — | 설계만. 미채택 |
| ④ 판정 생성 | O(B5=기업 프로필) | B0~B6 근거로 4종 판정 |
| 문의초안 | — | **LLM 아님** — 판단불가일 때 판정 결과에 포함된 전제·인용으로 코드가 템플릿으로 작성(`server/inquiry.py`) |

각 지점에서 어떤 모델이 실행되는지는 [[6-1b_LLM_백엔드]] §1.

## 2. 요청 1건 — 단계별 주체와 예산

예산은 합계가 아니라 **배분**이 정보다 — 어디가 느린지가 병목 진단의 근거다.

| # | 단계 | 주체 | 예산 |
|---|---|---|---|
| (1) | 입력 정규화 | LLM | 스트리밍 |
| (2)-a | 비목 후보 조회 | 코드 | ~150ms |
| (2)-b | L3 룰 조회(먼저) | 코드(SQL) | <10ms |
| (2)-c | 게이트 판정 | 코드 | ~0 |
| (2)-d | L1·L2 룰 + 효력 결정 | 코드(SQL) | <20ms |
| (2)-e | 한도 비교 | 코드 | ~0 |
| (3)-a | L3 전체 로드 | 코드(SQL) | <20ms |
| (3)-b | 필터 확정(L1·L2만) | 코드(SQL) | ~10ms |
| (3)-c | dense 검색 | pgvector | <200ms |
| (3)-d | sparse 검색 | BM25(SQL) | <50ms |
| (3)-e | RRF 결합 | 코드 | ~0 |
| (3)-f | 참조 확장 수집(깊이1) | 코드 | <30ms |
| (4) | 판정 생성(B0~B6) | LLM | 스트리밍 |
| (5) | 전제 확인 | 코드 | ~0 |
| (6) | 검증·하향 | 코드 | ~0 |
| (7) | 로깅 | 코드 | ~0 |

(3)-a(L3) 와 (3)-b~f(검색)는 독립이라 병렬. LLM 호출은 **2~3회**(① 정규화, ④ 판정 생성,
조건부일 때 근거를 보강한 재판정).

「참조 확장(B3) 없이 먼저 판정하고 근거가 모자라면 붙여 다시 판정한다」(재판정) — 호출 수 상한은
**3회 고정**, 「근거가 모자란가」는 **코드가** 정한다(LLM 에게 안 되묻는다).

## 3. 게이트와 분기

| 게이트 | 결과 | LLM 호출 |
|---|---|---|
| A. 금지목록 일치 | 즉시 "불가" 반환 | 0회 |
| B. 검색결과 없음 (최소 유사도 0.0 확정) | 판단불가 | 1회((1)만) |
| C. 비목 후보 신뢰도 근접 | 1순위 비목으로 판정하고 후보를 함께 반환 | 2~3회 |
| D. 정상 경로 | (4)까지 | 2~3회 |
