# LLM 호출 설계

이 문서가 답하는 질문:
- LLM 은 몇 번, 무엇을 위해 불리는가
- 호출 자리별로 어떤 모델이 도는가
- 오케스트레이션 순서는 어떻게 고정되는가

## 0. LLM 이 하는 일은 하나

**포섭** — 이 사실이 이 요건에 해당하는가. 검색어 생성·도구 호출·숫자 계산·효력 판단은
전부 코드가 한다. 오케스트레이터는 LLM 이 아니다 — 코드가 순서를 지휘한다
(멀티 에이전트 오케스트레이션 없음 · agentic multi-hop 없음).

## 1. 호출 자리 (전 호출 자리 오픈소스)

| 호출 자리 | F축 | 모델 | 실행 |
|---|---|---|---|
| ① 정규화 | ✅ | Qwen3 8B | 로컬(vLLM) |
| F 문서 파싱 | ✅ | Qwen3 8B | 로컬(vLLM) |
| ④-a 스크리닝(선택) | ⚠️ | 미정 | 채택 자체가 미결 |
| ④-b 판정 조립 | ✅(B5=F프로필) | Qwen3 32B thinking + 투표 N=3~5 | RunPod·vLLM |
| ⑤ 문장 생성 | ✕ | Qwen3 8B | 동일 서버 · 판단불가 경로 전용, 2회 셈 밖 |

`f_axis: bool` 호출 자리가 외부 제공자로 라우팅되면 예외를 던진다(코드 통과 조건 —
`scripts/adapter.py` 구현·`GET /admin/gate` 로 노출. "미구현"은 낡은 서술이었다).
🔴 **2026-09-05 오너 해제** — `CLAUDE.md`의 「외부 API 금지」가 풀려 F축 제외 조건은
원칙상 없어졌다. 이 코드 게이트는 그대로라 실동작은 안 바뀐다(정규화·판정조립은 여전히
외부로 못 나간다) — 게이트를 어떻게 바꿀지는 `docs/9_미결.md` 「설계됐으나 미구현」 참고.

## 2. vLLM 운영 규칙

| 항목 | 값 |
|---|---|
| 스키마 강제 | guided_json |
| thinking 병용 | `--reasoning-parser qwen3`(추론 종료 후부터 문법 적용, 측정도 이 구성으로) |
| 양자화 | AWQ(`awq_marlin` 커널 확인) |
| 컨텍스트 | `--max-model-len` 은 프롬프트 예산(1~2만 토큰)에 맞춤 |
| 캐시 | prefix caching |
| GPU | 8B/14B 로컬 4090 · 32B AWQ L40(48GB)@US-KS-2 |

## 3. 요청 1건 — 단계별 주체와 예산

🔴 예산은 합계가 아니라 **배분**이 정보다 — 어디가 느린지가 병목 진단의 재료다.

| # | 단계 | 주체 | 예산 |
|---|---|---|---|
| (1) | 입력 정규화 | LLM | 스트리밍 |
| (2)-a | 비목 확정 | 코드 | ~150ms |
| (2)-b | L3 룰 조회(먼저) | 코드(SQL) | <10ms |
| (2)-c | 통과 조건 판정 | 코드 | ~0 |
| (2)-d | L1·L2 룰 + 효력 결정 | 코드(SQL) | <20ms |
| (2)-e | 금액 비교 | 코드 | ~0 |
| (3)-a | L3 통째 로드 | 코드(SQL) | <20ms |
| (3)-b | 필터 확정(L1·L2만) | 코드(SQL) | ~10ms |
| (3)-c | dense 검색 | pgvector | <200ms |
| (3)-d | sparse 검색 | BM25(SQL) | <50ms |
| (3)-e | RRF 결합 | 코드 | ~0 |
| (3)-f | 참조 확장 수집(깊이1) | 코드 | <30ms |
| (4) | 판정 조립(B0~B6) | LLM | 스트리밍 |
| (5) | 전제 해소 | 코드 | ~0 |
| (6) | 검증·강등 | 코드 | ~0 |
| (7) | 로깅 | 코드 | ~0 |

(3)-a(L3) 와 (3)-b~f(검색)는 독립이라 병렬. LLM 호출은 **2~3회**(① 정규화, ④ 조립,
조건부 ④' 근거 보강 재판정) — 위 ~3.2s(p50)는 이 실측 이전 값이라 아래 92초와 조건이
다르다(재확인 전이라 어느 쪽이 어떤 상황을 잰 것인지 병기만 한다).

✅ **2026-09-05 오너 해제 — CLAUDE.md 확정 원칙 갱신.** 판정 1건 92초(정규화 25 + 판정 66,
프롬프트 읽기 55초 포함)이고 프롬프트의 76%가 B3(폐포)다. B3 를 빼면 프롬프트 26k→5.5k
토큰, 판정 66→23초. 그래서 **「폐포 없이 먼저 판정하고 모자라면 붙여 다시」(④')** 가
열렸다 — 단 호출 수 상한은 **3회 고정**, 「근거가 모자란가」는 **코드가** 정한다(LLM 에게
안 되묻는다), 동시발사 안도 후보, 무엇을 고르든 A/B("폐포 없이 몇 % 맞히나")가 먼저다.
원문은 `CLAUDE.md` 확정 원칙 절.

## 4. 통과 조건과 분기

| 통과 조건 | 결과 | LLM 호출 |
|---|---|---|
| A. 금지목록 적중 | 즉답 "불가" | 0회 |
| B. 검색 스코어 미달 | 판단불가 | 1회((1)만) |
| C. 비목 신뢰도 갈림 | 두 경로 모두 판정해 나란히 표시 | 2배 |
| D. 정상 경로 | (4)까지 | 2~3회 |

## 5. 검증 사다리 — 배치 유지의 관문

```
1. baseline → 2. 투표 N=3~5 → 3. 금지목록 룰분리 → 4. 프론티어 격차측정
→ 5. 격차시 캘리브레이션 QLoRA → 6. AWQ 배포 양자화 그대로 정답셋 재실행
```

투표 불일치는 판단불가로 보낸다. 파인튜닝 표적은 **판정 캘리브레이션**
(기관별 수치 학습 금지). API 대체 경로 재론 조건이 "4단계에서 치명 오답 0 이 깨질 때"였는데,
🔴 2026-09-05 오너가 그 조건을 기다리지 않고 직접 열었다(`CLAUDE.md` 참고, F축 제외 없이) —
사다리는 품질 검증 절차로는 그대로 유효하다.
