# LLM 호출 설계

이 문서가 답하는 질문:
- LLM 은 몇 번, 무엇을 위해 불리는가
- 호출 자리별로 어떤 역할을 하는가
- 오케스트레이션 순서는 어떻게 고정되는가

> 어떤 모델·백엔드가 실제로 도는지(vLLM↔DashScope 전환·thinking 설정·검증 사다리)는
> [[6-1b_LLM_백엔드]] — 이 문서는 호출 자리·예산·분기만 다룬다.

## 0. LLM 이 하는 일은 하나

**포섭** — 이 사실이 이 요건에 해당하는가. 검색어 생성·도구 호출·숫자 계산·효력 판단은
전부 코드가 한다. 오케스트레이터는 LLM 이 아니다 — 코드가 순서를 지휘한다
(멀티 에이전트 오케스트레이션 없음 · agentic multi-hop 없음).

## 1. 호출 자리 (전 호출 자리 오픈소스)

| 호출 자리 | F축 | 역할 |
|---|---|---|
| ① 정규화 | ✅ | 자유문 → 구조화 입력. thinking 불필요(추출 작업) |
| F 문서 파싱 | ✅ | L3 업로드 문서 → 조·항 구조화 |
| ④-a 스크리닝(선택) | ⚠️ | 채택 자체가 미결 |
| ④-b 판정 조립 | ✅(B5=F프로필) | B0~B6 근거로 4-way 판정 |
| ⑤ 문장 생성 | ✕ | 판단불가 경로 전용 문장화, 2회 셈 밖 |

지금 어떤 모델이 각 자리를 도는지는 [[6-1b_LLM_백엔드]] §1.

## 2. 요청 1건 — 단계별 주체와 예산

🔴 예산은 합계가 아니라 **배분**이 정보다 — 어디가 느린지가 병목 진단의 재료다.

| # | 단계 | 주체 | 예산 |
|---|---|---|---|
| (1) | 입력 정규화 | LLM | 스트리밍 |
| (2)-a | 비목 확정 | 코드 | ~150ms |
| (2)-b | L3 룰 조회(먼저) | 코드(SQL) | <10ms |
| (2)-c | 통과 조건 판정 | 코드 | ~0 |
| (2)-d | L1·L2 룰 + 효력 결정 | 코드(SQL) | <20ms |
| (2)-e | 금액 비교 | 코드 | ~0 |
| (3)-a | L3 통째 로드 | 코드(SQL) | <20ms |
| (3)-b | 필터 확정(L1·L2만) | 코드(SQL) | ~10ms |
| (3)-c | dense 검색 | pgvector | <200ms |
| (3)-d | sparse 검색 | BM25(SQL) | <50ms |
| (3)-e | RRF 결합 | 코드 | ~0 |
| (3)-f | 참조 확장 수집(깊이1) | 코드 | <30ms |
| (4) | 판정 조립(B0~B6) | LLM | 스트리밍 |
| (5) | 전제 해소 | 코드 | ~0 |
| (6) | 검증·강등 | 코드 | ~0 |
| (7) | 로깅 | 코드 | ~0 |

(3)-a(L3) 와 (3)-b~f(검색)는 독립이라 병렬. LLM 호출은 **2~3회**(① 정규화, ④ 조립,
조건부 ④' 근거 보강 재판정).

✅ **2026-09-05 오너 해제 — CLAUDE.md 확정 원칙 갱신.** 판정 1건 92초(정규화 25 + 판정 66,
프롬프트 읽기 55초 포함)이고 프롬프트의 76%가 B3(폐포)다. B3 를 빼면 프롬프트 26k→5.5k
토큰, 판정 66→23초. 그래서 **「폐포 없이 먼저 판정하고 모자라면 붙여 다시」(④')** 가
열렸다 — 단 호출 수 상한은 **3회 고정**, 「근거가 모자란가」는 **코드가** 정한다(LLM 에게
안 되묻는다), 동시발사 안도 후보, 무엇을 고르든 A/B("폐포 없이 몇 % 맞히나")가 먼저다.
원문은 `CLAUDE.md` 확정 원칙 절.
