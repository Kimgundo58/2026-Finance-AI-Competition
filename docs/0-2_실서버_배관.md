# 0-2. 실서버 배관 — 무엇이 실제로 막고 있었나

실서버에서 저장이 왜 안 됐는지, 무엇으로 닫았는지를 적는다.
여기를 다 고쳐도 판정 정확도는 안 오른다. 그건 [[0-1_판정_정확도]] 소관이다.
아래 본문은 2026-09-03 시점 기록이라 문장을 다듬지 않았다.

## 지금 상태 (2026-09-04 실측)

본문이 막고 있다고 적은 두 갈래는 다 닫혔다.

| 본문이 적은 것 | 지금 |
|---|---|

현재 리비전은 `suddoe-api-00011-pzw` 다.

## 실서버 실측 (2026-09-03)

주소는 `https://suddoe-api-1081277785480.asia-northeast3.run.app` 다.

- `/api/health` 200 · `"모드":"live"` · 0.27초 · `/api/orgs` 413건 · CORS PATCH 200 + ACAO
- DB 는 Cloud SQL `suddoe-db`(asia-northeast3). 로컬 덤프 321MB 적재 오류 0 · 12테이블 행수 일치

### 정정 (2026-09-03 오후 · ai-b2 + 중앙 실측)

오전에 GRANT 미적용으로 실서버 쓰기가 전멸했다고 적은 것은 틀렸다. 갈라 쓴다.

**DB 층은 이미 열려 있었다.** GRANT 는 진작 쳐져 있었다.
`pg_policies` tenant 12개와 `org_isolation` 정책이 운영에 실재한다.
비특권 롤 `suddoe_app` 으로 Cloud SQL 에 직접 붙어 `tenant.expense_plans` INSERT 가 성공했다
(plan_id 23226 · 커밋 · 재조회 · 삭제).
`decisions` · `f_profile` · `l3_documents` · `plan_tasks` 도 성공했다.
남의 `org_id` 는 42501 로 막힌다. 격리는 정상이다.

실제로 비어 있던 구멍은 `ALTER DEFAULT PRIVILEGES … ON SEQUENCES` 하나였고 이날 쳤다.
없으면 새 표에서 INSERT 는 되고 serial 시퀀스만 42501 이라 RLS 위반과 증상이 같다.

**그런데 API 로는 여전히 못 썼다.** 무인증 `POST /api/plans` 가 이렇게 답했다.

```json
{"오류": "지출계획을 저장하지 못했습니다 (DB 연결 실패)", "상태": 503}
```

이 문구가 거짓이다. 기전은 이렇다.

1. 주체가 없으니 `_org_세우기()` 가 GUC 를 안 세운다
2. `current_org()` 가 NULL 이 된다
3. RLS 가 INSERT 를 42501 로 막는다
4. `_질의()` 가 예외를 삼켜 빈 배열을 준다
5. `routes_plans.py:283` 이 503 을 만든다

원인 셋이 한 문구로 나온다. DB 다운 · RLS 차단 · 제약 위반이 구분되지 않는다.

**막고 있던 것은 권한이 아니라 신원이었다.** 로그인이 안 되면 GUC 가 안 선다.
로그인은 `tenant.accounts` 0행이고 읽기 정책이 없어 비특권 롤 조회가 0행이라 막혀 있었다.
처방은 `SECURITY DEFINER` 로그인 조회 함수다.

## 실서버 롤에서 판정이 조용히 닫힌다 (2026-09-03 관측 · 2026-09-04 닫힘)

로컬 DB · 비특권 `suddoe_app` · GUC 세운 채 · `orchestrate.전제해소(기록=True)` 실호출 · 롤백.

| | 관측 |
|---|---|
| ⓐ | `_unmapped_적재()` → 42501 InsufficientPrivilege. 대조군 `postgres` 는 통과 |
| ⓑ | 같은 트랜잭션의 `decisions` INSERT → 25P02 InFailedSqlTransaction |
| ⓒ | `orchestrate.py:705` 의 `except Exception` 이 받아 판단불가로 닫는다 |

ⓒ 의 결과는 판정 판단불가 · 요약 내부 오류로 판정을 내리지 않았습니다 · `decision_id` 없음이다.
예외는 안 샌다. HTTP 는 정상 응답이다.

증상은 사라지는 것이 아니라 조용히 판단불가로 닫히는 것이다.
그리고 판단불가율이 모델선택처럼 보인다.
실서버 롤로 도는 run 이 섞이면 그 run 의 판단불가율은 모델 값이 아니다.

🔴 **한 겹 더 있다.** `COMMIT` 이 성공을 돌려주는데 아무것도 안 저장된다
(ai-a3 · 비특권 롤 실측 · 롤백).

```text
1) expense_plans INSERT (GUC 세움)   ✅ plan_id=24835
2) unmapped_premise INSERT           🔴 42501
3) 앞선 INSERT 재조회                 🔴 InFailedSqlTransaction
4) conn.commit()                     ✅ «성공» — 예외를 안 던진다
   잔여물                            0건
```

abort 된 트랜잭션의 `COMMIT` 은 조용히 ROLLBACK 으로 처리되고 예외를 안 던진다.
`orchestrate.py:778` 의 `conn.commit()` 이 정상 반환하니 코드는 저장했다고 믿는다.
회귀를 세울 때 `rowcount` 나 예외가 안 났다로 통과시키면 뚫린다. 새 트랜잭션에서 되읽어야 한다.

🔴 **빈도는 46.2% 이고, 상관이 아니라 동치다** (ai-a3 · 코드로 확인).
`orchestrate.py:683` 이 `해소["미매핑"]` 으로 `PREMISE_UNMAPPED` 를 단다.
`_unmapped_적재` 는 `if c and 기록:` 에서 도는데 `c` 가 곧 그 값이다.
코드가 붙는 조건이 이 INSERT 가 도는 조건과 같다.

run 191 에서 `PREMISE_UNMAPPED` 는 43/93 = 46.2% 다. 서버는 `기록` 을 안 넘겨 기본값 True 다.
로컬 `decisions` 80건에서도 42건 = 52.5% 다(ai-b2, 닻 다름).
실서버 판정 약 절반이 조용히 저장에 실패한다.

> 로컬 `unmapped_premise` 89행은 BYPASSRLS 인 `postgres` 로 쌓인 값이다.
> 실서버 빈도를 이 표로는 못 잰다.

원인은 셋이고 갈라서 고친다.

1. **스키마·정책.** `unmapped_premise` 는 org 축이 없는 전사 통계표인데 RLS 만 켜고 정책이 0개다.
   08-31 의도는 읽기를 닫는 것이었는데 `ENABLE RLS` 가 쓰기까지 닫았다. 오너 결정 사항이다
2. **코드 결함은 아니다.** INSERT 에 `org_id` 가 없는 건 맞지만 그 표에 `org_id` 컬럼이 없다
3. **별개 결함.** `_unmapped_적재()` 에 `try/except` 가 없다. 통계 한 줄이 판정 저장을 죽인다

🔴 **`try/except` 만 붙이면 안 고쳐진다.** 파이썬에서 예외를 삼켜도 PostgreSQL abort 는 안 풀린다.
`SAVEPOINT` 와 `ROLLBACK TO SAVEPOINT` 가 있어야 한다(psycopg3 면 `with conn.transaction():` 중첩).
이 문장이 없으면 다음 사람이 `try/except` 만 붙이고 닫는다.
`91fd456` 이 savepoint 로 처리했고 PR #17 로 들어왔다.

## 처방이 듣는다는 증거

같은 스크립트로 두 브랜치를 나란히 태웠다
(ai-a3 · 비특권 롤 · 비자동커밋 · GUC · 미매핑 1건).

| | 전제해소 예외 | COMMIT | 새 tx 되읽기 |
|---|---|---|---|
| 수정 전 | 42501 InsufficientPrivilege | 성공 반환 | **0건 — 소실** |
| 수정 후 | 없음 (stderr 로그만) | 성공 반환 | **1건 — 산다** |

두 줄 다 `COMMIT` 이 성공을 돌려준다. `rowcount` 나 예외 없음으로 통과시키면 둘이 똑같이 초록이다.

첫 실판정 3건이 그 조건이었다. `decisions` 4275·4276·4277 셋 다 `강등코드={PREMISE_UNMAPPED}` 다.
로컬 `postgres`(bypassrls)로 돌아 살아남았을 뿐이다.
실서버 롤이었으면 3/3 이 판단불가로 닫히고 아무것도 안 남았다.

run 191 은 이 오염에서 자유롭다. 로컬 `postgres` 로 돌아 이 경로가 발화하지 않았다.
판단불가 4건 = 모델선택 0 + 실패경로 4 는 그대로 유효하다.
