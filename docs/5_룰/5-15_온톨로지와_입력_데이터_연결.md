## ① 협약 기간을 게이트 입력으로 (5-14 D 와 합침)

- 지금: 화면은 사용일자(예상 지출일)를 항상 받는다. 코드는 기한일이 지난 의무를 빼는 데만 쓴다(`scripts/ontology_gate.py` `_기한_지남`). 프로필의 협약시작일 · 협약종료일은 판정 프롬프트에 글로만 들어가고(`scripts/orchestrate.py` `_프로필값_읽기`) 사용일자와 비교하는 코드가 없다. 모두의 창업 범위에서 대상에 시간 노드가 든 규범 15 는 비목 출발점으로는 하나도 닿지 않는다(조율 세션 · 독립 확인).
- 설계: (1) 시간 노드가 대상인 규범과 `확인시점` 구조화 조건이 있는 규범은 질문 글과 무관하게 **항상** 조회에 넣는다(공통 시점 규범). (2) 게이트 입력에 프로필 협약시작일 · 협약종료일을 넣고, `확인시점 = 협약기간 내` 같은 구조화 조건을 사용일자와 비교해 코드가 평가한다. 날짜는 사실 입력이라 금액과 같은 급이다: 조건이 참이고 규범이 AI검증 금지면 **코드 불가**, 의무 · 요건이면 조건 줄, 조건이 거짓이면 그 규범을 접는다. (3) 프로필에 협약 날짜가 없으면(게스트) 지금처럼 건너뛰고 「협약 기간을 프로필에 적으면 확인해요」 한 줄만 둔다. (4) 5-14 D 의 「언제 집행하나요?」 질문과 LLM 날짜 추출은 사용일자 칸이 빈 요청에서만 쓰는 예비 길이다.
- 내리기만 한다. 프로필이 없는 사용자는 변화 없음.
- 구현(07ed484, E119): 위 (1)(2) 대신 기준 규범 `규범:공통/운영요령#제21조③/의무/1` 하나로 판단한다(`확인시점` 조건은 발견 시점 규범 2개뿐이라 안 씀, 화면 예상 지출일은 선택 칸). 자세한 규칙은 [[5-14_LLM_보완_지점]] D 구현 줄. 7개 사업 544조합 × 날짜 6종 스캔: 올라감 0, 날짜 없음 · 기간 안은 전과 같음(구현 세션 집계, 검토 세션은 자체 검사 재실행만: gate 296 · judge 194 · selftest 통과).

## ② 비율 한도의 분모를 프로필에서

- 지금: 「총사업비의 75% 이하」 「현물은 20% 이하」 「취득가액의 10%」 처럼 분모가 5-7d 값 목록에 없는 한도는 의무 문장으로 두었다(9d 결정 대기, 도약 · 재도전 · 창업중심대학).
- 설계(2026-11-08 사용자 결정 「유연성」): 행을 의무 → 한도로 되돌리는 재추출 · 재검증은 하지 않는다. **판정 때** 코드가 그 의무 문장 · 근거 발췌에서 정규식(`_금액표현` · `_수와단위` 꼴)으로 숫자 · 단위 · 연산을 뽑고, 기존 확인 질문 LLM 호출이 코드가 준 enum 에서 각 숫자의 역할(분자 · 분모 · 상한 · 하한 · 해당없음)을 고른다. 결과는 노드결정처럼 질문세트 저장값에 두고 판정이 다시 검사해 `_비교값들` 로 계산한다. 대상은 AI검증 행뿐이다. **사용자 결정: 넘으면 코드 불가**(한도 행과 같은 효과. LLM 역할 표시의 실수 위험은 사용자가 감수). 안에 들면 조건 줄은 그대로 둔다(내리기만). 역할이 「해당없음」 이거나 enum 밖 · 숫자가 둘 이상 겹치면 계산하지 않는다. 쓴 숫자 · 역할은 ④ 의 규범 칸에 남긴다.
- 분모 값: 프로필 `정부지원_현금` · `자기부담_현금` + **새 칸 `자기부담_현물`**(`db/init/04_validation_eval.sql` 이 뺀 두 칸 중 하나만 되살린다. 이 사업들의 현물은 자기부담 쪽이고 정부지원 현물은 없다. 로컬 DB 확인, 운영 미확인). 총사업비 = 정부지원_현금 + 자기부담_현금 + 자기부담_현물, 현물 비율 = 자기부담_현물 / 총사업비. 바뀌는 곳: 마이그레이션(로컬 먼저, 운영 보류 규칙) · `server/models.py` · `server/routes_profile.py` · 캐시 해시 · `scripts/orchestrate.py` 프로필 읽기 · 프론트 프로필 입력 칸(`써도돼요_frontend_ontology` 브랜치, 같은 PR). 프로필 칸이 비면 「확인 필요: 협약 금액을 프로필에 적어 주세요」 줄(미확정한도 구분)로 내려간다. `취득가액` 은 이번 지출 금액이 곧 취득가액이면 그대로, 아니면 미확정.
- 사용자 결정 끝: 9d 「비교 기준이 지출 금액이 아닌 상한」 은 이 방식으로 닫는다. 5-7d 분모 목록 · 변환기는 바꾸지 않는다.
- 구현(cd7c0af, 사용자 결정 변경): 구성 비율 규범은 **판정이 아니라 프로필 경고**다. 검증된 비율 규범 6개가 전부 「…로 구성해야」 꼴로 대상이 절차 노드라 지출 조회가 닿지 않기 때문이다. GET · PUT `/api/profile?사업명=` 이 코드로 비율을 계산해 `협약경고` 를 돌려주고 판정에는 영향이 없다(위 판정 때 숫자 추출 경로는 이 규범들에 쓰지 않았다). 도약 의무/1 · /3 은 미검증이라 제외. 지출 단위 비율(취득가액 10% 등)은 그대로 의무 문장.

## ③ 누적 금액을 지출 기록으로

- 지금: 누적범위가 동일업체합계 · 월 · 협약기간이면 게이트가 「누적 금액을 알려주시면」 칸을 낸다(`scripts/ontology_gate.py` `_누적표`). `profile_expenditures` 는 바로 이 용도로 만들어졌는데(표 주석 「동일 거래처 누적(2천만원 심의)용」) 읽지 않는다.
- 설계: 게이트 입력을 만들 때 코드가 `profile_expenditures` 를 합산한다: 동일업체합계 = 같은 profile · 비목 · 거래처(정규화한 글자) 금액 합, 월 = 같은 귀속월 합, 협약기간 = 전부 합. 재원 · 형태는 규범 조건이 가르면 그대로 거른다. 합에 이번 지출 금액을 더해 비교한다. 거래처가 입력에 없거나 기록이 없으면 지금처럼 묻고, 사용자가 적은 값이 있으면 둘 중 **큰 값**(내리는 쪽).
- 구현(2026-11-08, 사용자 결정 변경): `profile_expenditures` 는 쓰는 코드가 없어 행이 0 이다(로컬 두 DB 확인, `PUT /api/profile` 이 집행내역을 저장하지 않음). 대신 **`tenant.expense_plans`** 를 합산한다 — 같은 계정 · 사업 · 확정비목, 계획마다 `실제지출액` 이 있으면 그것 아니면 `금액`, 지금 계획(plan_id)은 뺀다. 판정이 불가인 계획은 `실제지출액` 이 없을 때만 뺀다 — 실제로 쓴 돈은 판정과 무관하게 누계에 든다(2026-11-09, Codex 검토 반영, 내리는 쪽만). 지출 계획 조회가 실패하면 조용히 건너뛰지 않고 판단불가다. 합 + 이번 금액이 한도를 넘으면 한도초과, 아니거나 기록이 없으면 전과 같다. `expense_plans` 에는 `거래처` · `집행예정일` · `실제지출일` 칸이 있으므로(로컬 확인) 누적범위별로 가른다: 동일업체합계 = 거래처 글자를 정규화해 같은 것만, 월 = 실제지출일(없으면 집행예정일)의 달이 같은 것만, 협약기간 = 전부. 거래처가 비면 동일업체 누계는 지금처럼 묻는다. 같은 지출을 계획 두 개로 적으면 틀린 불가가 날 수 있다(사용자가 감수). 누적 **임계값**(동일업체 2천만원 → 사전 심의 등)에도 같은 합을 쓴다(검토 세션 결정): 합 + 이번 금액이 부가세 후보 어느 쪽으로도 임계값을 넘을 때만 켜지고, 켜진 의무 줄은 「이번 지출」 줄 + 출처 줄로 나간다(조건부 상한, 코드 불가 없음). 애매하면(부가세 후보에 따라 갈림) 지금처럼 묻는다. 합산한 계획 ID 는 ④ 규범 칸에 남긴다. 계획의 사업명 · 확정비목은 판정과 같은 표준화 이름으로 맞춰 합친다.
- 화면: 「기록된 누적 1,200만원 + 이번 900만원 = 2,100만원」 처럼 출처 한 줄. 내부 ID 없음.

- 지금: `tenant.decisions` 에 조문 인용(JSONB)만 있고 규범 칸이 없다. 판정 LLM 출력 스키마(`scripts/llm_schema.py`)도 문장 ID 뿐이라 어느 규범이 결과를 갈랐는지 알 수 없다. 규범별 정확도를 못 잰다([[5-9_검증과_측정]]).

- 쓰임: `eval` 과 합쳐 규범별 적중 · 오판 집계, 잔여 행 결정의 근거. 화면 변화 없음.

## ⑤ L3 를 규범으로

- 지금: 기관 규정은 조문째 프롬프트에 들어가고(`scripts/ontology_context.py`) 비목 연결 초안만 LLM 이 만든다(`scripts/l3_link.py`). 기관이 정한 한도 · 금지는 코드 게이트가 못 쓴다.
- 설계(2026-11-08 사용자 결정): 업로드마다 추출자 2 + 검증자 + 전수 대조를 돌리지 **않는다**. L3 는 지금처럼 파싱 + `l3_link` 노드 연결까지만 하고, 숫자는 ② 와 같은 판정 때 경로로 다룬다 — 연결된 L3 조문에서 정규식이 숫자 · 단위 · 연산을 뽑고 확인 질문 LLM 이 역할을 고르며, 넘으면 코드 불가(② 와 같은 규칙, L3 가 더 엄할 때만 — 효력 순위 [[5-2_효력_결정]] · 5-2b). 기관 금지는 조문 글로 판정 LLM 이 가른다(코드 불가 없음). L3 숫자 · 역할도 ④ 규범 칸에 남겨 추적한다.
- 비용 · 시간: 업로드 때 LLM 호출 추가 없음. 판정 때 호출 수 그대로(질문 호출에 얹음). 프론트 변경 없음. 버린 안(업로드마다 추출 파이프라인)은 9d 에 「사용자 결정으로 보류」 로 남긴다.
- 구현 규칙(검토 세션 확인, 2026-11-08): 후보는 **사용 중 문서의 확정된 연결**(`l3_articles.concept_ids` NOT NULL)로 이번 노드 경로에 닿는 L3 조문만. 미확정 연결(NULL, 지금처럼 원문으로 주입) · `l3_link` 초안은 코드 불가에 쓰지 않는다(틀린 연결 + 틀린 역할 = 틀린 불가). 로컬에는 확정 연결이 아직 0 이라 기관이 마이페이지에서 확정한 뒤에만 돈다. 코드 불가는 기존 효력 순위 경로에서 L3 가 이 사업에 효력 있을 때만, L1 · L2 가 우선이거나 못 가르면 조건 줄. 역할 표시는 질문세트와 노드결정 보조 키에 저장하고(조문 · 노드에 달린 값이라 질문 글과 무관), 판정이 후보를 다시 만들어 ID 와 숫자 글이 그대로일 때만 쓴다. 「L3 가 더 엄할 때만」 = L3 상한 초과는 L3 가 효력 있으면 불가(더 느슨한 L3 상한을 넘으면 L1 · L2 도 넘는 것이라 기존 길이 처리).

## 공통으로 지키는 것

- LLM 호출 수 · 출력 스키마는 바뀌지 않는다(⑤ 의 배치 추출은 판정 경로 밖).
- 코드는 내리기만 한다. 프로필 · 기록 · 날짜는 사실 입력이라 그대로 쓰되, 사용자 입력과 다르면 더 엄한 쪽.
- 내부 ID 는 화면에 안 나온다. 출처(프로필 · 기록)는 한 줄로 보인다.
- 운영 수치는 운영 DB 로만 잰다. 마이그레이션은 로컬 · 평가 DB 먼저.

## 측정

- ① ③: dev 90 중 「확인 필요」 줄이 사라진 문항 수, 코드 판정으로 바뀐 문항 수(화면 경로, LLM 없음으로 먼저).
- ②: 의무 → 한도로 돌아간 행 수와 그 행의 코드 비교가 도는 문항 수.
- ④: 규범 칸이 채워진 판정 비율 100%, 규범별 집계 쿼리 하나.
- ⑤: 시험 org 의 L3 한 건으로 추출 → 게이트 작동까지 한 슬라이스 먼저.
