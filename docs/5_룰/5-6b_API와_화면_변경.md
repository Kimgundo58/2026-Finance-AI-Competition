# API 와 화면 변경

이 문서가 답하는 질문:
- 화면 단계마다 어느 엔드포인트가 무엇을 주고받는가
- L3 업로드 연결 화면은 어떻게 동작하는가
- 검증 코드 · 저장 · 프런트엔드에서 무엇이 바뀌는가

상태: 설계안 v2.1 (2026-11-06). 미구현. 판정 결합은 [[5-6_판정_결합과_검증]], 검색은 [[4-4_검색_재설계]]. 계약 문서 `docs/7_백엔드/API_계약_v1.0.md` 와 `openapi.json` 을 같이 고친다.

## 판정 흐름

| 단계 | 화면 | 엔드포인트 (전부 기존) | 요청에 더하는 것 | 응답에 더하는 것 |
|---|---|---|---|---|
| ① 입력 | 사용 내용 · 용도 · 금액 · **부가세 구분(포함 · 공급가액 · 모름)** · 사용일자 | `POST /api/normalize` (SSE, 캐시 유지) | `부가세구분` | `분류후보: [{비목, 세목, 표시문}]`(최대 3, 온톨로지 레이블 안에서만) · `수치` |
| ② 분류 확인 | "지급수수료 > 멘토링비로 보고 판정해요" 첫 후보 자동 선택, **확정 필수**(지금 확정비목과 같은 규칙) | — | — | — |
| ③ 추가 입력 + 확인 질문 | 숫자 칸(멘토링 시간 · 인원 · 일수 · 박수 · 계약총액 · 출장지 구분)과 예 · 아니오 질문이 한 화면 | `POST /api/questions` | `확정세목`(없으면 null) | `추가입력: [{키, 라벨, 단위, 형식}]`(코드가 확정 세목의 한도 · 임계값 분모에서 만든다, LLM 아님) · `질문` · `용어풀이: [{용어, 풀이}]` |
| ④ 판정 | 결과 | `POST /api/judge` | `확정세목` · `추가입력값: {키: 값}` · `부가세구분` | `분류: {비목, 세목, 표시문}` · `근거경로: [문장]` · `코드판정: {종류, 비교값, 한도, 발췌} \| null` · `용어풀이` |

- `확정비목` 은 지금의 10종 enum 그대로다. 세목은 서버가 ID 로 풀고 화면에는 표시문만 간다
- 부가세 구분이 `모름` 이고 비교에 필요하면 ③ 에 코드가 만든 예 · 아니오 질문 "입력한 금액은 부가세가 포함된 금액인가요?" 를 더한다. LLM 호출은 늘지 않는다
- 추가 입력을 비우면 그 한도는 비교하지 않고 결과의 조건에 "멘토링 시간을 알려주시면 시간당 한도를 확인해요" 가 붙는다
- `코드판정.종류` ∈ `금지 · 한도초과 · 부가세기준미정`. `근거경로` 문장은 문서 표시명 + 조번호를 `→` 로 잇는다("모두의 창업 제33조② → 지침 제42조 → 모두의 창업 제36조①"). 노드 ID · 규범 ID · S01 은 응답에 넣지 않는다
- 응답 `용어풀이` 는 `검수단계` 가 `AI검증` 이상인 것만. 캐시 키에 `확정세목` · `추가입력값` · `부가세구분` 을 넣는다

## L3 업로드 연결

| 단계 | 화면 | 엔드포인트 | 동작 |
|---|---|---|---|
| 업로드 | 지금 화면 | `POST /api/l3` (기존) | 파싱 뒤 백그라운드에서 연결 초안 LLM(조 50개씩 묶어 호출, 실패하면 그 묶음은 미연결). 코드가 superseded L2 · L1 본문과 같은 문장을 찾아 "옛 판 문구" 표시 |
| 확인 | 조문 목록 + 추천 세목, 기본 전부 수락, 조마다 고치기 · 해제, "나중에" 가능 | `GET /api/l3/current` (기존) 에 `연결: [{article_id, 조번호, 세목 표시문, 상태}]` | 확인 전에는 판정이 L3 전체를 넣는다(지금과 같음) |
| 저장 | "저장" | `PATCH /api/l3/{doc_id}/links` (신설) `{article_id: [concept_id]}` | 같은 org 계정이면 가능(RLS `org_isolation`). `concept_ids` NULL = 미확인, `[]` = 확인했고 해당 세목 없음(공통으로 항상 주입) |
| 재업로드 | — | — | 새 문서의 조문은 미연결로 시작. 이전 문서에서 조제목이 같은 조의 연결을 초안에 재사용 |

L3 교체는 HEAD 에 이미 구현돼 있다(커밋 07f9407, `scripts/l3_parse.py` `적용문서_정리`). 운영 반영 여부는 확인 과제다.

## 검증 코드 · 저장

- `scripts/llm_validate.py` 의 `검증코드_전체` 와 제약 `decisions_검증코드_check` 에 `ONTOLOGY_BAN`(금지 일치) · `LIMIT_EXCEEDED`(한도 초과) · `VAT_BASIS_UNKNOWN`(부가세 기준 미정 → 판단불가)을 더한다. 미확정 규범 하향은 기존 `UNVERIFIED_RULE` 을 쓴다
- 코드 판정(LLM 0회)도 `tenant.decisions` 에 저장한다. `코드판정` 과 `근거경로` 를 응답 캐시에 같이 넣는다

## 프런트엔드 (`wori1206/2026-Finance-AI-Competition_Frontend`, 브랜치)

| 화면 | 바꾸는 것 |
|---|---|
| 입력 | 부가세 구분 선택 |
| 분류 · 질문 | 분류 확인 문구와 고치기, 추가 입력 칸, 질문 아래 풀이 |
| 결과 | 코드 판정의 비교값 · 발췌, 조건 목록, 근거 경로, 풀이 |
| L3 업로드 | 연결 확인 목록과 저장 |

컴포넌트 이름은 구현 때 그 저장소에서 확인한다. 기존 컴포넌트와 디자인 톤을 쓴다. `python scripts/ux_flow_check.py` 가 ① → ④ 와 L3 경로를 돈다.
