# 추출 에이전트 지침

이 문서가 답하는 질문:
- 추출 에이전트에게 무엇을 주고 무엇을 받는가 (팀이 작성자 없이 돌릴 수 있게)
- 두 독립 추출을 무슨 키로 비교하는가
- 결과 파일 형식은 무엇인가

상태: 설계안 v2.1 (2026-11-06). 구현: 모두의 창업 추출(시범 · 묶음 17개 · 재추출 8개) 로컬 끝, 나머지 6개 사업 전(실행 기록 `ontology/추출/모두의_창업/실행기록.md`, 2026-11-08). 프롬프트 · 출력 형식 · 검증자 할 일은 다음 사업용으로 2026-11-08 고쳤고([[5-12_다른_사업_추출]]), 모두의 창업 68개는 커밋 `d16a42a` 의 프롬프트로 돌렸다. 다음 사업의 묶음 · 재추출 순서는 5-12 가 우선한다. 절차는 [[5-7_원문_추출_절차]], 칸 정의는 같은 문서의 추출표, ID 규칙은 [[5-8b_원천_JSON_형식]].

## 입력 묶음 (묶음마다 폴더 하나)

```
ontology/추출/모두의_창업/<묶음>/
  입력_원문.md        조 · 항 단위로 자른 DB 본문 + PDF 대조 결과(차이는 [원문결함] 표시). 조문 ID 를 머리말로
  입력_문서키.json    schema.json 의 사업키 · 문서키 · 문서 표시명
  입력_기존노드.json  이전 묶음에서 확정된 개념 ID 목록(중복 생성을 막는다). 첫 묶음은 빈 목록
  추출_A.md · 추출_B.md   추출자 두 명의 결과 (아래 형식)
  비교.md             비교 스크립트 출력
  실행기록.json       scripts/extraction_run.py 가 남기는 기록. 다음 사업부터([[5-12_다른_사업_추출]])
```

다음 사업부터 추출자마다 입력 3개만 든 작업 폴더(`<묶음>/작업_A/` · `작업_B/`)에서 돌리고 결과를 묶음 폴더로 옮긴다. 먼저 끝난 쪽 결과와 `입력_명세.json` 을 보지 않게 하려는 것이다. 재추출도 같다.

## 에이전트 프롬프트 (그대로 쓴다. Opus 5.5, effort high)

```
You extract concepts, relations and norms from Korean startup-grant regulations, one provision at a time.
Read docs/5_룰/5-5_규범_구조.md, docs/5_룰/5-7_원문_추출_절차.md (section 추출표) and docs/5_룰/5-8b_원천_JSON_형식.md first.
Input: 입력_원문.md (provisions with IDs), 입력_문서키.json, 입력_기존노드.json.
For every provision ID in the input, write one 추출표 block in the output format below. Do not skip provisions; write
"해당 없음" when a provision yields nothing.
Rules: quote excerpts verbatim from 입력_원문.md (after the normalization in 5-8b); one norm per effect per sentence;
operators as written (이상/초과/이하/미만); unknown things go to 모르는 것, never guessed; reuse IDs from 입력_기존노드.json
when the concept already exists; never open corpus.rules, corpus.item_alias, golden sets or any file outside the input folder.
Open only the three input files, the three documents above and the section 출력 형식 of docs/5_룰/5-7b_추출_에이전트_지침.md.
If the input folder holds any file other than the three inputs, stop and report it.
Every 금지 and 의무 gets `문장`: one plain Korean sentence in 합니다체 that the user will read, faithful to the provision, with no IDs,
no table separators, no double quotes and no " | ". Exception: a 금지 whose excerpt is only a table title leaves 문장 empty.
Use the narrowest node the text names as 대상. When a premise in the provision limits a norm, carry it into that norm's `조건` with its
excerpt; never let a 금지 block more than the text limits.
Write 임계값 only when the number compares with the amount of the expense or contract being judged, or with a running total that fits
누적범위. A number about anything else (program size, total received) goes into the `조건` of the 의무 it triggers. A 한도 that fails
the same test stays a 한도, with the reason in 모르는 것.
Add `기한일 YYYY-MM-DD` only for one end date of a submission or application duty, after which the guidance no longer matters. Leave it
out for a use or spending period, two end dates in one norm, a date repeating yearly, or a year the document does not establish.
Output: write 추출_<A|B>.md in the input folder. Return only the counts of provisions, concepts, relations and norms.
```

## 출력 형식 (추출표 1장 = 조 · 항 1개)

```
### 조:모두의창업#제36조①
원문: "멘토링비"는 1인 1일 최대 30만원 한도(시간당 10만원 초과 불가)이며, … 공제 후 집행하여야 한다.
개념: 세목:창업/지급수수료/멘토링비 (기존) · 주체:멘토 (신규) · 시간:1인1일 (신규) · 시간:시간당 (신규)
관계: 세목:창업/지급수수료/멘토링비 -상위-> 비목:창업/지급수수료 [원문명시] 근거 조:모두의창업#별지2/지급수수료/정의 "멘토링비, 기자재임차비"
      조:모두의창업#제36조① -준용-> 소득세법 시행령 (조문 미특정) 근거 "소득세법 시행령을 준용하여"
규범: 규범:모두의창업/제36조①/한도/1  | 대상 세목:…/멘토링비 | 값 300000 원 | 위반연산 초과 | 분모 인,일 | 부가세 정의없음 | 근거 "1인 1일 최대 30만원 한도"
      규범:모두의창업/제36조①/한도/2  | 대상 세목:…/멘토링비 | 값 100000 원 | 위반연산 초과 | 분모 시간 | 근거 "시간당 10만원 초과 불가"
      규범:모두의창업/제36조①/임계값/1 | 대상 세목:…/멘토링비 | 값 125000 원 | 발동연산 초과 | 결과 의무/1 | 근거 "12만 5천원을 초과하는 경우"
      규범:모두의창업/제36조①/의무/1  | 문장 기타소득세 등을 공제한 뒤 집행해야 합니다. | 근거 "기타 소득세 등을 공제 후 집행하여야 한다"
모르는 것: 소득세법 시행령 어느 조인가 · 30만원 한도의 부가세 기준
용어 후보: 기타소득세 · 공제 · 준용
```

규범 줄의 칸은 ` | ` 로 나눈다. 필요하면 `조건 "발췌"` · `기한일 YYYY-MM-DD` 칸을 더한다. 비교 스크립트는 큰따옴표 안을 발췌로 읽으므로(`scripts/extraction_compare.py:26`, `:98`) `문장` 에는 큰따옴표를 쓰지 않는다. 칸 값에 ` | ` 가 들어가면 칸이 조용히 갈린다.

## 비교 (코드, `scripts/extraction_compare.py` — 팀 작성, 입력은 추출_A.md · 추출_B.md)

- 규범 비교 키: (조문 ID, 종류, 정규화 수치[값 · 단위 · 연산 · 분모], 대상 집합). 순번은 비교에 쓰지 않는다(두 추출자가 다르게 매길 수 있다)
- 개념 비교 키: (종류, 정식명 정규화). 관계 비교 키: (src, 관계, dst)
- 출력 `비교.md`: 일치 · A만 · B만 · 값이 다른 것. 일치율 = 일치 / (일치 + A만 + B만). 불일치는 전부 검증 에이전트에게 넘긴다
- 발췌 검사: 모든 발췌가 정규화한 입력 원문의 부분 문자열인지. 실패는 그 행을 `발췌오류` 로 표시
- `문장` · `기한일` · `조건` 은 비교 키가 아니다(`scripts/extraction_compare.py:135`). 달라도 일치로 세므로 일치율로 잡히지 않고, 검증자가 원문과 대조해 정한다
- 이 스크립트는 저장소 코드다. CI 의 DB 없는 검사에 `--self-test`(고정 입력 2벌로 기대 결과)를 넣는다

## 검증과 확정 (자동)

제3 에이전트(검증자, Opus 5.5 high)가 `비교.md` · 추출_A · 추출_B · PDF 원문(표 복원본)을 받아 조 단위로 판정한다.
입력 폴더 밖은 열지 않고, 두 추출이 같아도 발췌 · 수치 · 연산을 원문과 다시 대조한다.
결과: 일치 + 원문 확인 → `AI검증` · 한쪽만 맞음 → 맞는 쪽을 `AI검증` · 둘 다 틀림 → 검증자가 원문대로 고쳐 `AI대조` 로 표시하고 다음 묶음 전에 재추출 · 못 가름 → `해석미결=true` + 결정 로그.
재추출 1회 뒤에도 `AI대조` 면 더 돌리지 않고 사업별 잔여 목록(`ontology/진단/AI대조_잔여_<사업키>.md`)에 올린다. 처리는 사용자가 정한다([[5-11_전환_계획]], 2026-11-08).
확정본은 `확정.md` 로 저장하고, 그것만 원천 JSON 의 입력이 된다. 사람 판단은 없다(2026-11-06 자동화 결정).
다음 사업부터 검증자는 프롬프트의 문장 · 대상 · 전제 · 임계값 · 기한일 규칙도 원문과 대조하고, 변환기가 옮길 판단 칸(개념 정식명 · 별칭 · 근거, 규범 근거의 칸 구분, 구조화 조건)을 [[5-7d_확정표_형식]] 대로 `확정.md` 에 적는다. 프롬프트는 [[5-7e_검증_프롬프트]]. 변환 뒤 코드 판정 행 전수 대조를 한다([[5-12_다른_사업_추출]]).
