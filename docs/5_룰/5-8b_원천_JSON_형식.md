# 원천 JSON 형식, ID 규칙, 발췌 정규화

이 문서가 답하는 질문:
- 노드 · 조문 · 규범 ID 는 어떻게 만들고 DB 값으로 어떻게 푸는가
- 원천 JSON 의 키는 무엇이고 [[5-5_규범_구조]] 필드와 DB 컬럼에 어떻게 대응하는가
- "발췌는 본문의 부분 문자열" 검사는 어떤 정규화를 거치는가

상태: 설계안 v2.1 (2026-11-06, 독립 검토 반영). 구현: 모두의 창업 원천 · 검사(P2-1 · P2-2) 로컬 끝(2026-11-07). 테이블은 [[5-8_저장과_조회]].

## 키와 ID

| 종류 | 형식 | 예 | DB 로 푸는 법 |
|---|---|---|---|
| 사업키 | `schema.json` 의 `사업키` 표. 값은 `corpus.programs.사업명` | `모두의창업` → `모두의 창업 프로젝트` | 적용사업 컬럼에는 항상 `사업명`(FK) |
| 문서키 | `schema.json` 의 `문서키` 표. 값은 현행 `doc_id`. 판이 바뀌면 표만 바꾼다 | `지침` → `L1_중소기업창업_지원사업_통합관리지침_제14차개정_20251223` | 적재 때 `documents.status='active'` 검사 |
| 조문 ID | `조:<문서키>#<조번호><항><호>`. 표는 `<항>표-N`, 별지 행은 `별지N/<행>/<칸>` | `조:모두의창업#제36조①` · `조:모두의창업#제2조9호` · `조:모두의창업#제35조②표-4` · `조:모두의창업#별지2/지급수수료/유의사항` | `provenance(doc_id, 조번호, 항호)`. 항호 = `#` 뒤의 조번호를 뺀 나머지 |
| 개념 ID | `<종류>:<비목체계>/<경로>` · 행위자는 `주체:<이름>` · 사업한정이면 `@<사업키>` | `비목:창업/지급수수료` · `세목:창업/지급수수료/멘토링비` · `품목:창업/서버임차` · `주체:진출자` | `concepts.concept_id` |
| 규범 ID | `규범:<사업키\|공통>/<조문 키>/<종류>/<순번>`. 순번은 그 항 안의 등장 순서 | `규범:모두의창업/제36조①/한도/1` | `norms.norm_id`. 두 추출자의 비교 키이기도 하다([[5-7b_추출_에이전트_지침]]) |

- 비목은 지침 표-10 의 10개를 공통 노드로 둔다(정답셋 라벨과 같은 집합). 사업이 쓸 수 있는 비목은 `사용` 관계(제33조①)로 적는다. 제34조처럼 한 조가 재료비 · 기계장치를 함께 다루면 두 비목 모두에 `근거` 를 단다
- 제35조에는 표-4 가 둘이다(②와 ③). 표 ID 는 표를 인용한 항에 붙인다

## 발췌 정규화

검사는 "정규화(발췌) ⊂ 정규화(본문)" 이다. 정규화 순서: 유니코드 NFC → 따옴표 통일(`“ ” " ″` → `"`, `‘ ’` → `'`) → 페이지 표식 `- 14 -` 제거 → 공백 · 줄바꿈 연속을 공백 하나로 → 양끝 공백 제거.
DB 본문은 `“멘토링비”는 … 시간당 10만원\n초과 불가` 처럼 굽은 따옴표와 줄바꿈이 섞여 있어(로컬 확인) 정규화 없이는 어떤 발췌도 통과하지 못한다.
발췌는 정규화한 형태로 저장한다. DB 본문이 PDF 와 다른 곳은 `원문결함: true` 로 두고 PDF 복원본 텍스트를 발췌에 쓴다. 적재 검사는 그 행을 DB 본문 대신 `ontology/추출/…/입력_원문.md` 의 복원본과 대조한다.

## 키 대응

| JSON 키 | 5-5 필드 | DB |
|---|---|---|
| 개념.id · 종류 · 정식명 · 별칭 · 상위 · 정의 · 적용사업 · 검수단계 · 근거 | 개념층 | `concepts` · `concept_labels` · `concept_relations(관계='상위')` · `provenance` |
| 관계.src · 관계 · dst · 연결종류 · 적용사업 · 문맥조문 · 적용조문 · 근거 | 관계(상위 · 사용 · 정의 · 준용 · 위임 · 동치 · 서로소 · 개정) | `concept_relations`(`문맥` JSONB 에 문맥조문 · 적용조문) · `provenance` |
| 규범.id · 종류 · 계층 · 적용사업 · 대상 · 수범자 · 승인주체 | 규범 ID · 종류 · 계층 · 적용사업 · 대상 · 행위자 | `norms` 같은 이름 컬럼 |
| 규범.조건 · 수치 · 시점 · 증빙 · 결과 · 예외 · 해석미결 · 검수단계 | 조건 · 수치 · 시점 · 증빙 · 결과 · 예외 · 검수단계 | `norms.조건` · `수치` · `결과` JSONB(`결과` 안에 `시점` · `증빙`(증빙 노드 ID 목록) · `제재`), `예외 TEXT[]`, `해석미결 BOOLEAN`, `검수단계` |
| 규범.근거.수치 · 조건 · 대상 | 칸별 근거 | `provenance(owner_kind='규범', 칸=수치\|조건\|대상)` |

수치 키: `값` · `단위`(원 · % · 개 · 대) · `위반연산`(한도: 초과 · 이상) 또는 `발동연산`(임계값: 이상 · 초과) · `분모`(인 · 일 · 박 · 시간 · 건 · 월 · 계약총액 · 용역비총액) · `분모주체` · `누적범위`(건별 · 동일업체합계 · 월 · 협약기간) · `부가세`(포함 · 공급가액 · 정의없음) · `지역`(특별시 · 광역시 · 그밖).
우선순위 규범의 `조건`: `{"상위": "L1", "하위": "L2", "범위": "unspecified_only|all|상충시", "출처": "규정조항|서비스정책"}`.

검사 · 조회가 읽는 나머지 값(`scripts/ontology_check.py` · `ontology_lookup.py`):
- `결과.활성화`: 임계값이 활성화할 규범 ID 목록(임계값은 필수). `결과.대체`: 이 규범이 대신하는 규범 ID 목록. 대체된 규범은 `적용_규범` 의 규범 목록에서 빠지고 `우선순위_적용` 에 남는다
- `결과.문장`: 조건 칸에 나가는 문장(`scripts/ontology_gate.py:123` `_화면문장`). 다음 사업부터 금지 · 의무는 필수이고(표 제목뿐인 금지는 비운다. `ontology/진단/데이터수정/W1/기록.md:107`) 검사는 미구현이다([[5-12_다른_사업_추출]]). 지금 원천은 금지 41행이 비어 있어 발췌나 대체 문구로 나간다(2026-11-08)
- `결과.기한일`: 끝날 `YYYY-MM-DD`. 사용일자가 지나면 그 의무의 화면 줄이 빠지고 상한은 조건부다(`scripts/ontology_gate.py:642` `_기한_지남`, `:695`). 제출 · 신청 끝날만 적고 사용 기간 끝날은 적지 않는다(`ontology/진단/데이터수정/W2/기록.md:43-55`)
- `예외` 의 규범 ID 는 단서라 원칙을 목록에서 빼지 않는다(조건이 맞을 때만 덮어쓴다). 규범 ID 가 아닌 값은 단서 발췌로 보고 근거 조문과 대조한다
- 준용 대상을 조문으로 특정하지 못하면 `dst` 를 `미특정:<법령명>`(또는 `미특정`) 으로 쓴다. `사용` 의 `src` 는 개념 ID 또는 `사업:<사업키>`
- 근거 항목의 `원문결함: true` 는 DB 본문 대신 `ontology/추출/**/입력_원문.md` 의 같은 조문 ID 블록과 대조한다
- 사업 파일의 관계에 `적용사업` 키가 없으면 그 사업이다(null 이어야 공통). 사업 파일의 개념은 `적용사업` 을 반드시 적는다. 관계에 `검수단계` 가 없으면 `AI초안` 으로 적재한다
- 정식명도 `concept_labels` 에 넣어 `노드_결정` 이 찾는다

## 확정 추출표 → JSON

모두의 창업까지는 확정된 추출표([[5-7_원문_추출_절차]])에서 변환 에이전트가 JSON 을 썼다. 다음 사업부터 `scripts/extraction_to_json.py`(미구현, [[5-12_다른_사업_추출]])가 옮긴다. 판단이 필요한 칸은 검증자가 `확정.md` 에 적고 코드는 판단하지 않는다. 적재 검사([[5-8_저장과_조회]])가 형식 오류를 잡는다.
