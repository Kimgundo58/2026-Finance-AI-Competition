# 검증과 측정

이 문서가 답하는 질문:
- 단계마다 무엇을 어떻게 검증하는가
- 후보 커버율과 판정 효과는 어떤 자료 · 분모 · 스크립트로 재는가
- 적재 · 전환의 수용 기준은 무엇인가

상태: 설계안 v2.1 (2026-11-06). 구현: 원천 검사(P2-2) · 정답셋 연결(P0-5) 로컬 끝, 측정(P5) 전(2026-11-07). 능력 질문은 [[5-4_온톨로지_구조]], 추출은 [[5-7_원문_추출_절차]], 전환은 [[5-11_전환_계획]].

## 단계별 검증

| 단계 | 대상 | 방법 | 통과 기준 | 담당 |
|---|---|---|---|---|
| 원문 품질 | DB 본문 vs PDF 원본 | 표 · 별지는 전수, 조는 diff. 차이 목록 | 차이가 전부 목록에 있고 파서 과제로 등록 | P0-1 |
| 추출 품질 | 추출_A · 추출_B | `scripts/extraction_compare.py` 로 비교 키 일치율([[5-7b_추출_에이전트_지침]]). 불일치는 검증 에이전트가 PDF 원문으로 판정, 못 가르면 `해석미결` | 발췌 100% 통과, `AI검증` 비율 · 해석미결 수 기록 | P1 |
| 스키마 | 원천 JSON | `ontology_check.py`: 코드 검사 + OWL 추론기 | 전부 통과. 일부러 넣은 위반 케이스는 실패 | P2 |
| 능력 질문 | CQ-01 ~ CQ-12 | `ontology/테스트/능력질문.json`(Claude 가 P1 에서 사례 3개 이상 + 기대 조문 · 규범 ID 작성) → `ontology_lookup.py --cq-test` | 전부 일치 | P3-3 |
| 후보 커버율 | 정답셋 v2 모두의 창업 dev 90 = L3 아님 71 + L3 19 | 아래 프로토콜 | 목표: 근거 단위 95% | P5-1 |
| 판정 · 인용 효과 | 같은 문항 실제 판정 | 전후 2회 이상, 옛 경로 vs 새 경로 | 틀린 '가능' 증가 0, 판정+인용 상승 | P5-2 |
| 운영 상태 | 운영 DB 읽기 전용 | 현재 상태 수치는 운영에서 잰다 | 로컬 값으로 대체하지 않는다 | 항상 |

CI 에는 DB 가 없다(`ci.yml`). 능력 질문 테스트와 적재 검사는 Postgres 서비스가 있는 잡을 새로 만든다(P5-1a). 그 전에는 로컬 Stop 훅처럼 돌린다.

사업 × 비목 조회 수치는 온톨로지 수치가 아니다. 온톨로지 수치는 구조를 만든 뒤 그 구조로 탐색한 결과만 쓴다. 운영 수치는 전환 전후에 따로 잰다.

## 커버율 프로토콜

- 자료: 정답셋 v2 는 `golden_v2/`(미추적)에 있고 `eval.run_items` 는 `eval.golden_set` 을 참조한다 → `scripts/golden_v2_load.py` 로 세트 `v2_dev` 에 적재한다. 세트를 고르지 않은 평가는 이 행을 읽지 않는다. 측정: `eval_retrieval.py --세트 v2_dev --사업 "모두의 창업 프로젝트" --기록`
- 정답 라벨의 비목(10종)은 공통 비목 노드와 같은 집합이다. "추정 비목 ≠ 정답 비목" 문항은 따로 센다
- 입력은 화면 경로 값: 사업 = 온보딩 값, 품목 · 세목 · 비목 = 질의 변환 결과 + (측정에서는) 정답 비목으로 확정한 경우와 추정 그대로인 경우 둘 다
- 만드는 동안 평가 문항을 보지 않는다. 추출은 원문만 읽고, dev · test 분리를 유지한다
- 후보 집합: 온톨로지 후보 · 검색 후보 · 병합([[4-4_검색_재설계]]). 분모 둘을 다 적는다: 근거 단위(조 · 항) · 문항 단위(결정 근거 전부 포함). 목표 95% 는 근거 단위
- 스크립트: `scripts/eval_retrieval.py --candidates ontology|search|both`(확장). L3 문항 19개는 L3 연결이 있는 테스트 org 로 따로 돈다
- 놓친 근거는 유형별로 분류한다: 계층 상속 · 준용 · 비목 경계 · 주체 · 사건 · 표 · 별지 · 그 밖. `연결종류` 와 경로를 읽는다

## 판정 효과 프로토콜

- 판정은 온도 0 에서도 실행마다 달라진다(2026-11-02 확인). 전후 각 2회 이상 돌려 범위로 적는다
- 화면 경로로 돈다: 확정 비목 · 세목 · 추가 입력 · 답변 · org 를 넘기는 `scripts/eval_screen_path.py`(신설, `ux_flow_check.py` 를 본보기로). `eval_e2e.py` 는 확정비목 · 답변 · org 를 넘기지 않아 쓰지 않는다
- 코드 판정(금지 · 한도)은 LLM 판정과 따로 센다. 코드 판정이 틀렸으면 규범이 틀린 것이다
- 출시 영향: `AI검증` 미만 규범만 있으면 '가능' 이 조건부로 내려간다. 그래서 전환 조건에 금지 · 한도 · 임계값 규범의 `AI검증` 이상 100% 를 둔다([[5-11_전환_계획]])

## 수용 기준

| 시점 | 기준 |
|---|---|
| 적재 | 검사 전부 통과. `AI검증` 이상 비율과 해석미결 수를 적재 로그에 적는다 |
| 사업 전환 | 금지 · 한도 · 임계값 규범 `AI검증` 이상 100%, 틀린 '가능' 증가 0 (2회), 판정+인용 하락 없음, 판정 p95 지연이 서버 한도 180초 안 |
| 1차 완료 | CQ 전부 통과 + 모두의 창업 커버율 목표 + 능력 질문 테스트가 CI 잡에 들어감 + 운영 수치 기록 |

## 보고 규칙

수치는 측정 조건(DB · 문항 수 · 분모 · 입력 경로 · 날짜) 없이 적지 않는다. 문제 · 원인 · 수치는 직접 확인하고 독립 재확인한 것만 기록한다.
