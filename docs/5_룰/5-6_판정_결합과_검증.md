# 판정 결합

이 문서가 답하는 질문:
- 사용자는 화면에서 무엇을 보고 무엇을 하는가
- 규범들이 어떤 순서로 판정을 만드는가. 어디까지 코드가 하고 어디부터 LLM 이 하는가
- L3 는 어떻게 들어가는가

상태: 설계안 v2.1 (2026-11-06). 구현: P4-3 · P4-4 로컬 끝, 운영 미적용, 판정 효과 미측정. 설계와 다른 선택은 `docs/9b_백로그_온톨로지.md` 의 제안(2026-11-07). 규범은 [[5-5_규범_구조]], 검색은 [[4-4_검색_재설계]], 엔드포인트와 화면은 [[5-6b_API와_화면_변경]].

## 화면 동작 (먼저 정한다)

| 단계 | 사용자가 보는 것 | 사용자가 하는 것 |
|---|---|---|
| 입력 | 사용 내용 · 용도 · 금액 · 부가세 구분(포함 · 공급가액 · 모름) · 사용일자 | 입력 |
| 분류 확인 | "지급수수료 > 멘토링비로 보고 판정해요" (내부 ID 없음) | 맞으면 확정, 틀리면 고른다. 확정 없이는 진행하지 않는다 |
| 추가 입력 + 확인 질문 | 확정 세목의 한도에 필요한 숫자 칸(멘토링 시간 · 인원 · 일수 · 박수 · 계약총액 · 출장지 구분)과 예 · 아니오 질문 최대 3개, 어려운 말에는 풀이 | 아는 것만 채운다. 예 · 아니오 · 모르겠어요 |
| 코드 판정 (LLM 호출 없음) | 「불가」 + 비교에 쓴 값("1일 40만원 > 한도 30만원") + 규범 원문 발췌 | 끝 |
| 의무 발생 | 「조건부」 + 조건 목록("취득가액 500만원 이상 → 사업운영위원회 사전심의 필요") | 조건 확인 |
| 입력 비움 | 결과의 조건에 "멘토링 시간을 알려주시면 시간당 한도를 확인해요" | 다음에 채운다 |
| LLM 판정 | 가능 · 조건부 · 불가 · 판단불가 + 인용 원문 + 근거 경로 | 끝 |

## 결합 순서

```
① 노드 결정       별칭 정확 일치(`rule_lookup._norm`) → 없으면 질의 변환 LLM 후보 → 사용자 확정(필수). 후보가 가까우면 게이트 C
② 적용 규범 집합   사업 → 적용사업 · 공통 규범 → 상위 노드 규범 상속 → 준용 사슬 전개 → 우선순위 규범으로 중복 제거
③ 금지             `AI검증` 이상 규범 + 사용자 확정 노드 + 예외 없음 → 불가 (게이트 A, LLM 0회, `ONTOLOGY_BAN`)
④ 한도             입력이 다 있고 `AI검증` 이상 · 예외 없음 → 비교. 위반이면 불가 (`LIMIT_EXCEEDED`). 부가세 기준이 갈리면 판단불가 (`VAT_BASIS_UNKNOWN`)
⑤ 임계값           발동이면 의무 규범 활성화
⑥ 의무 · 입력 비움 조건부의 조건과 할 일로 붙인다
⑦ 요건             문맥 구성(L3 연결 조문 → 온톨로지 후보 → 검색 후보) → 판정 LLM 1회 → 인용 S01 → 원문 치환
⑧ 검증 · 하향      인용 검사 · 전제 검사 · 답변 반영 · 미확정 규범(`UNVERIFIED_RULE`). 코드는 낮추기만 한다 ([[6-4_검증과_하향]])
```

- `AI검증` 미만 규범과 LLM 추천만으로 정해진 노드는 ③ · ④ 를 발동시키지 못한다. 확정 전 노드는 화면이 막으므로 판정에 오지 않는다
- 해석미결 규범은 ③ · ④ · ⑤ 에 쓰지 않고 ⑦ 의 문맥에만 넣는다

## 합치는 규칙

코드 결과는 판정의 상한이다. '가능' 으로 올리지 않는다.

| 코드 결과 | LLM 판정 | 최종 |
|---|---|---|
| 금지 일치 · 한도 위반 | 호출 안 함 | 불가 |
| 부가세 기준 미정 | 호출 안 함 | 판단불가 |
| 의무 발생 · 입력 비움 · `AI검증` 미만 규범만 있음 | 가능 | 조건부. 조건에 의무와 필요한 입력을 적는다 |
| 위와 같음 | 조건부 · 불가 · 판단불가 | LLM 판정 |
| 위임만 있음 (창업활동자금 등) | 가능 | 조건부. 조건에 "전문기관 집행 가이드 확인" |
| 해당 규범 없음 | 무엇이든 | LLM 판정. 기존 검증 · 하향을 그대로 거친다 |

## 입력값과 규범의 연결

| 입력 | 어디서 오나 | 쓰는 규범 |
|---|---|---|
| 사업 | 온보딩 값 | 전부 |
| 품목 · 세목 · 비목 | 별칭 일치 · LLM 후보 · 사용자 확정 | 전부 |
| 금액 · 부가세 구분 | 입력 화면 | 한도 · 임계값 |
| 인원 · 일수 · 박수 · 시간 · 수량 · 출장지 | 추가 입력(코드가 분모에서 만든 칸), 기업 프로필 | 한도 분모 · 지역 조건 |
| 계약총액 · 선금 · 동일 업체 누적 | 추가 입력. 집행 이력은 미구현 | 비율 한도 · 누적 임계값 |
| 거래처 유형 · 특수관계 | 확인 질문, 거래처 사실 조회(설계 중) | 조건 · 의무 |
| 시점(사용일 · 납품일 · 협약기간) | 입력, 기업 프로필 | 의무 · 조건 |
| 사전승인 · 사전심의 여부 | 확인 질문 | 의무 충족 |

지금은 룰 조회에 금액만 넘긴다(`scripts/orchestrate.py` `_룰조회()`). 구현 순서는 [[5-10_구현_작업목록]].

## L3

```
업로드 때   파싱 → 조문 → 연결 초안(LLM) → 화면에서 확인 → tenant.l3_articles.concept_ids   ([[5-6b_API와_화면_변경]])
판정 때 ⑦   연결된 조문 중 해당 비목 · 세목 · 공통만, 미연결 조문은 전부 주입. L3 는 원문으로만 들어간다(1차에는 L3 규범이 없다)
            옛 경로의 `l3_load.l3룰` · `rule_lookup.l3_상위확인` 은 새 경로에서 부르지 않는다. 상위 규범이 항상 후보에 있기 때문이다
우선순위    제4조② "주관기관의 내부규정과 상충되는 경우 본 관리기준을 우선" → 범위 `상충시`
            L3 가 더 엄격 → 그대로 적용(낮추는 방향). L3 가 더 느슨 → 관리기준으로 판정하고 화면에 "주관기관 안내는 허용하지만 관리기준이 우선" (결정 대기 4, 추천)
            느슨한 L3 는 실제로 있다(로컬 경상국립대 2024 안내문 2건, 하나는 옛 판 복사). 업로드 때 superseded 판과 일치하는 문장에 "옛 판 문구" 경고를 붙인다
```

## 불변식

- 틀린 '가능' 이 최악이다. 모든 실패(DB · 시간 초과 · 스키마 · 빈 후보 · 인용 실패 · 온톨로지 조회 오류)는 판단불가
- LLM 호출은 판정당 2~3회(질의 변환 · 확인 질문 · 판정). 재랭킹 · 도구 호출 루프는 넣지 않는다. 추가 입력 칸과 부가세 질문은 코드가 만든다
- 숫자 비교 · 금지 일치 · 우선순위 · 인용 검사는 코드. LLM 은 요건 충족 판단만
- 금지 · 별칭 일치는 정규화 후 정확 일치. 유사 · 임베딩 일치 없음
- 규정 원문은 데이터다. 지금은 L1 · L2 · L3 모두 같은 래퍼로 들어가고 본문을 이스케이프하지 않는다(`assemble_context.py`). 새 경로는 세 층 모두 이스케이프한다
