# 온톨로지 뼈대

이 문서가 답하는 질문:
- 개념층에 어떤 노드와 관계를 두는가
- 1단계(뼈대)에서 무엇을 채우고 무엇을 비우는가
- 지금 있는 테이블은 어디로 옮기는가

상태: 설계안 (2026-11-02). 개요는 [[5-3_룰_온톨로지_설계]].

## 노드 종류

| 종류 | ID 예 | 1단계 | 지금 있는 곳 |
|---|---|---|---|
| 사업 | `사업:예비창업패키지` | 채운다 | `corpus.programs` (정식명·별칭·비목체계) |
| 비목 | `비목:지급수수료` | 채운다 | `corpus.item_vocab` (창업 체계 10개) |
| 하위항목 | `하위:지급수수료/멘토링비` | 채운다 | `item_vocab.하위항목`. 지금은 지급수수료 17개만 있다 |
| 품목 | `품목:기프티콘` | 원문에 이름이 나온 것만 | `corpus.item_alias` 326행 |
| 문서 | `문서:<doc_id>` | 채운다 | `corpus.documents` (계층·판·시행일·상태) |
| 조항 | `조:<doc_id>#제42조⑦` | 규범·관계가 가리키는 것만 | `corpus.doc_articles` (조 단위) |
| 주체 | `주체:대표자`, `주체:신규채용인력` | 채운다 | 없음. 한도 분모("1인 1대"의 '인')와 적용 대상에 쓴다 |

조항 노드는 조 단위 행에 항·호·목 표기를 붙인 것이다. 원문 위치는 발췌로 확인한다.

## 관계

| 관계 | 방향 | 예 |
|---|---|---|
| 상위 | 하위 노드 → 상위 노드 | `하위:지급수수료/기자재임차비` → `비목:지급수수료` |
| 별칭 | 이름 → 노드 | "예창패" → `사업:예비창업패키지`, "서버 임차" → `하위:지급수수료/기자재임차비` |
| 근거 | 노드·관계 → 조항 + 발췌 | 위 상위 관계 → `조:지침#제42조⑦` "서버 등을 임차하는 경비" |
| 사용 | 사업 → 비목 | 사업별로 쓸 수 있는 비목. 예: 창업활동비(지금 룰에는 예비·모두의 창업에만 있다) |
| 판 대체 | 문서 → 이전 판 | 2026년 재도전 세부관리기준 → 2025년판 |

모든 노드와 관계에 붙는 속성:
- `사업한정`: 특정 사업에서만 성립하면 사업 ID, 공통이면 비운다
- `근거`: `[{조항 ID, 발췌}]`. 발췌는 DB 원문의 부분 문자열이어야 한다
- `연결종류`: `원문명시`(원문이 그 이름을 직접 열거) 또는 `해석`(원문의 상위 범주로 포섭. 예: 클라우드 이용료 → "서버 등")
- `검수단계`: `AI초안` → `AI대조` → `사람확정`

## 채우는 규칙

- 하위항목은 규정이 열거한 것만 둔다(지침 제36조 비목 표와 제37~45조, 세부관리기준 붙임·참고의 비목 표). 사업별 추가 열거는 사업한정 노드로 둔다
- 1단계 품목은 규정 원문에 이름이 나온 것만 넣는다(기프티콘, 유니폼, 퇴직급여충당금 등). 출처는 원문이다
- 사용자 표현에서 온 품목과 `해석` 연결은 2단계에서 넣는다. 지금 정답셋으로 채우면 정답셋 편향(원문에 나온 것만 있음)이 들어간다
- 별칭 조회는 정규화 후 정확 일치만 쓴다. 사업한정 별칭은 그 사업에서만 쓴다
- 사업 이름은 노드 ID 로만 참조한다. 약칭이 키로 들어가는 문제(예: #54 에서 고친 `item_alias.사업명` 의 '초격차')를 막는다

## 지금 테이블에서 옮기는 것

| 지금 | 옮길 곳 | 확인할 것 |
|---|---|---|
| `programs` 8행 | 사업 노드 + 별칭 | TIPS 는 범위 밖으로 표시만 한다 |
| `item_vocab` 18행 | 비목·하위항목 노드 | 지급수수료 외 비목의 하위항목 열거를 원문에서 새로 채운다 |
| `item_alias` 326행 | 품목 노드 + 별칭 관계 | 원문발췌가 있는 209행은 발췌 검사 후 `AI대조`, 나머지 117행은 `AI초안` 으로 들어가 2단계에서 다시 본다. 사업한정 92행 |
| `documents` · `doc_articles` | 문서·조항 노드 | 판 대체 관계를 새로 적는다 |

## 저장

- 원천 파일: `2026_Finance_DATA_FOR_RAG/_ontology.json`. 사람이 검수하는 원본이고 git 으로 이력을 남긴다.
  지금 룰은 DB 에만 있어서 누가 언제 무엇을 바꿨는지 남지 않는다
- 적재 스크립트가 원천 파일을 읽어 DB 테이블을 만든다. 테이블 이름과 컬럼은 [[5-6_판정_결합과_검증]] 의 표현 검증 뒤 정한다
- 적재 때 코드 검사: 발췌가 원문 부분 문자열인가, 상위 관계에 순환이 없는가, 하위항목 개수가 조문 열거 개수와 같은가, 별칭이 두 노드를 가리키지 않는가

## 1단계 시범 산출물 (예비창업패키지 + L1 공통)

1. 사업 노드 1개와 별칭, 사용 비목 관계
2. 창업 체계 비목 10개와 비목별 하위항목(원문 열거) + 근거
3. 주체 노드(대표자, 신규채용인력, 4대보험 참여인력 등 원문이 한도·대상에 쓰는 것)
4. 예비 세부관리기준과 지침에서 원문에 이름이 나온 품목
5. 위 항목 전부 `AI대조` 까지. 사람 확정 대상 목록과 검수용 파일(조문 전문·발췌 위치 포함)
