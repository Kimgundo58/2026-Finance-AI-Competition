# 저장과 조회

이 문서가 답하는 질문:
- 원천 파일(source of truth)은 어디에 두고 런타임 테이블은 무엇인가
- 적재 때 무엇을 검사하고, 다시 적재하면 참조는 어떻게 되는가
- 조회 함수의 인터페이스는 무엇인가. 개정판과 캐시는 어떻게 다루는가

상태: 설계안 v2.1 (2026-11-06). 구현: P3-1 ~ P3-4 로컬 끝, 운영 미적용(2026-11-07). 스키마는 [[5-4b_온톨로지_스키마]], JSON 형식 · ID · 발췌 정규화는 [[5-8b_원천_JSON_형식]], 공존 · 롤백은 [[5-11_전환_계획]].

## 원천 파일

| 항목 | 결정 |
|---|---|
| 위치 | 저장소 `ontology/`. 사람이 검수하는 원본이고 git 이 이력을 남긴다. 지금 룰은 DB 에만 있어 이력이 없다 |
| 파일 | `schema.json`(스키마 번호 · 사업키 · 문서키 · 문서 표시명) · `공통_L1.json` · `<사업키>.json` · `테스트/능력질문.json` · `추출/<사업>/…` |
| 형식 | JSON, 한국어 키. 기존 `_precedence_rules.json` 과 같은 관례 |
| 들어오는 경로 | 확정 추출표 → Claude 가 JSON 작성 → PR → 적재 |

## 테이블

설계 예시 (미구현)
```sql
CREATE TABLE corpus.concepts (
  concept_id TEXT PRIMARY KEY, 종류 TEXT NOT NULL, pref_label TEXT NOT NULL, 정의 TEXT,
  적용사업 TEXT REFERENCES corpus.programs(사업명), 검수단계 TEXT NOT NULL, 원천해시 TEXT NOT NULL,
  CHECK (검수단계 IN ('AI초안','AI대조','AI검증','사람확정','재검토')));
CREATE TABLE corpus.concept_labels (
  concept_id TEXT NOT NULL REFERENCES corpus.concepts ON DELETE CASCADE, alt_label TEXT NOT NULL, 정규화 TEXT NOT NULL,
  적용사업 TEXT REFERENCES corpus.programs(사업명), UNIQUE NULLS NOT DISTINCT (정규화, 적용사업));
CREATE TABLE corpus.concept_relations (
  src_id TEXT NOT NULL, 관계 TEXT NOT NULL, dst_id TEXT NOT NULL, 적용사업 TEXT REFERENCES corpus.programs(사업명),
  연결종류 TEXT, 문맥 JSONB, 검수단계 TEXT NOT NULL, UNIQUE NULLS NOT DISTINCT (src_id, 관계, dst_id, 적용사업));
CREATE TABLE corpus.norms (
  norm_id TEXT PRIMARY KEY, 종류 TEXT NOT NULL, 계층 TEXT NOT NULL, 적용사업 TEXT REFERENCES corpus.programs(사업명),
  대상 TEXT[] NOT NULL, 수범자 TEXT[], 승인주체 TEXT[], 조건 JSONB, 수치 JSONB, 결과 JSONB, 예외 TEXT[],
  해석미결 BOOLEAN NOT NULL DEFAULT false, 검수단계 TEXT NOT NULL, 원천해시 TEXT NOT NULL,
  verified BOOLEAN GENERATED ALWAYS AS (검수단계 IN ('AI검증','사람확정')) STORED,
  CHECK (검수단계 IN ('AI초안','AI대조','AI검증','사람확정','재검토')),
  CHECK (종류 IN ('금지','허용','한도','임계값','의무','요건','우선순위')));
CREATE TABLE corpus.provenance (
  owner_id TEXT NOT NULL, owner_kind TEXT NOT NULL, 칸 TEXT NOT NULL,
  doc_id TEXT NOT NULL REFERENCES corpus.documents, 조번호 TEXT NOT NULL, 항호 TEXT, 발췌 TEXT NOT NULL);
ALTER TABLE tenant.l3_articles ADD COLUMN concept_ids TEXT[];   -- NULL 미확인 · '{}' 확인했고 해당 세목 없음
```

`corpus.terminology` 는 [[6-5_용어_풀이]]. 조문 · 문서는 테이블이 아니라 `provenance` 의 값이고, `concept_relations` 의 `조:` ID 는 적재 때 `doc_articles` 로 확인한다.

읽는 곳(죽은 데이터 금지): `concepts` · `concept_labels` → `노드_결정()`; `concept_relations` → `적용_규범()` · `근거_조문()`, `연결종류` → 측정 분류;
`norms` → `적용_규범()` 과 코드 게이트; `provenance` → 적재 검사 · 화면 발췌 · 근거 경로; `원천해시` → 적재 로그 · 개정 처리; `l3_articles.concept_ids` → 문맥 구성.
권한: `suddoe_app` 읽기, `suddoe_ingest` 쓰기. 테이블 생성은 `db/migrations/`(자동 배포 보류, `docs/8_운영/8-8_CI_CD.md`).

## 적재 (`scripts/ontology_load.py`)

1. 원천 읽기 → 스키마 번호 · 문서키(활성 doc_id) · 사업키(`programs.사업명`) 확인
2. 코드 검사: 정규화 발췌 ⊂ 본문, 계층 순환, 근거 없는 노드 · 규범, 별칭 충돌, 필수 칸, 대상 · 조문 ID 존재
3. `scripts/ontology_check.py`: OWL 생성 → HermiT → 모순 · 불만족 클래스 · 서로소 위반이면 중단
4. 트랜잭션: 적용사업 단위로 **ID 기준 upsert**, 파일에 없는 그 사업의 행은 삭제. 공통(L1)은 별도 단위. `terminology.concept_id` 는 `ON DELETE SET NULL`, `l3_articles.concept_ids` 는 적재 뒤 없는 ID 를 지우고 로그에 남긴다
5. `server/response_cache.py` `_데이터버전_해시_SQL` 에 네 테이블의 **내용 md5**(rules 와 같은 방식)와 `SUDDOE_ONTOLOGY_PROGRAMS` 값을 넣는다. 적재 뒤 데이터 버전 캐시(300초)를 비운다
6. 적재 로그(원천 파일 해시 · 행 수 · 검사 결과 · `AI검증` 이상 비율 · 해석미결 수)

## 조회 함수 (`scripts/ontology_lookup.py`, 읽기 전용)

설계 예시 (미구현)
```python
def 노드_결정(cur, 표현: str, 사업: str) -> list[dict]:
    """rule_lookup._norm 으로 정규화 → 별칭 정확 일치. 사업한정 별칭 → 공통 순. 없으면 빈 목록(LLM 후보는 호출자 몫)."""

def 적용_규범(cur, 사업: str, 대상_id: str) -> dict:
    """대상 + 상위 노드 규범(상속) + 공통 규범 → 우선순위 규범으로 중복 제거.
    반환: {규범: [...], 경로: [("세목:…", "비목:…")], 우선순위_적용: [...]}  (L3 는 여기서 다루지 않는다)"""

def 근거_조문(cur, 규범들: list[dict], 깊이: int = 3) -> list[dict]:
    """규범 근거 조 · 항 + 준용 사슬(깊이 제한) + 별지 해당 행. 온톨로지 후보의 재료([[4-4_검색_재설계]])."""
```

- 상위 · 준용 전개는 재귀 CTE. 깊이 3 이면 세부관리기준 → 지침 → 운영요령 → 법까지 닿는다
- 결과에 경로를 돌려준다. 화면 "근거 경로" 와 측정의 "놓친 유형" 분류에 쓴다
- 인덱스: `concept_labels(정규화)`, `concept_relations(src_id)`, `norms USING GIN (대상)`
- 능력 질문 테스트: `scripts/ontology_lookup.py --cq-test ontology/테스트/능력질문.json` (DB 필요)

## 개정판

- 문서 새 판이 활성화되면(`corpus_ingest.py` 활성화 단계, 작업 P3-4) 그 문서를 가리키는 노드 · 규범의 검수단계를 `재검토` 로 내린다. `verified` 는 자동으로 false
- 화면: 그 규범은 코드 불가를 내지 못한다. 같은 입력이 LLM 판정으로 가고 '가능' 은 조건부로 내려가며 조건 문장으로 보인다([[5-6_판정_결합과_검증]]). 옛 판 조문은 판정 문맥에서 빠지고 새 판은 검색으로 들어온다
- 문서키는 바뀌지 않고 `schema.json` 의 doc_id 만 바뀐다. 적재는 문서키가 활성 판을 가리킬 때만 통과한다
- 모두의 창업 세부관리기준의 시행일은 2026-06-23 으로 기록돼 있다(부칙 행은 DB 에 0건). CQ-11 은 이 값으로 답한다
