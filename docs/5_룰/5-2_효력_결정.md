# 효력 결정

이 문서가 답하는 질문:
- 여러 계층 룰이 부딪히면 무엇이 이기는가
- L3 를 언제 상위까지 보는가
- 병합 결과를 화면에 어떻게 설명하는가

## 0. `precedence_rules` 란

비목 룰이 아니라 **"어느 계층이 이기는가"** 룰이다. 현재 **9행**(2026-09-05, TIPS 추가).
산출: `scripts/archive/indexing/build_precedence.py` → `_precedence_rules.json`.

## 1. 🔴 반대가 규칙이다

"아래가 엄격하면 이긴다"가 아니다. 8개 사업 중 6개(예비·초기·재도전·도약·창업중심대학·
모두의창업)가 제3조(적용범위)에서 "주관기관 내부규정과 상충되면 본 관리기준을 우선한다"고
명시한다. **L3 가 더 엄격해도 진다.**

| 사업군 | 규칙 |
|---|---|
| 예비·초기·재도전·도약·창업중심대학·모두의창업(일반·기술) | L2 > L3 (L3 는 참고로만 병기) |
| 초격차·모두의창업 | 추가로 L1 > L2 (L2 미규정 사항만) |
| TIPS | L1 > L2 (L2 미규정 사항만). **L2 > L3 조항은 없다** — 초격차와 같은 모양이지만 우선규범이 다르다(§1-b) |

TIPS 는 2026-08-31 검수 때 "해당 조항 없음"으로 닫혔던 칸이다. 2026-09-05 재조회에서
16.나.2)가)①(「국가연구개발사업 연구개발비 사용 기준」원칙, 지침 별도규정만 예외)을 찾아
뒤집었다 — 문형이 "적용범위" 조가 아니라 비목 사용기준 조 안에 있어 최초 검색에서 놓쳤다.

## 1-b. 🔑 `우선규범` — 어느 L1 이 우선인가

`L1 > L2` 를 뭉뚱그리면 안 된다. 상위 규범이 사업마다 다르다.

| 사업 | 우선규범 |
|---|---|
| 모두의창업(일반·기술트랙) | 「중소기업창업 지원사업 운영요령」 |
| 초격차 | 요령 및 지침(특정 규범명 없음) |
| TIPS | 「국가연구개발사업 연구개발비 사용 기준」 — 지침·요령 계통이 아니라 R&D 계통 규범이다 |

🔴 모두의창업 로컬트랙을 범위 밖으로 자르는 근거가 "상위 규범이 통합관리지침이 아니다"인데
([[1-2_사업_8종]]), 그 상위 규범 이름이 여기다 — 없으면 그 판단을 재현할 수 없다.

## 2. 병합 알고리즘

```
effective_rule(사업, 비목, 기관) =
    base    = rules WHERE layer IN ('L1','L2') AND 사업=? AND 비목=?
    overlay = rules WHERE layer='L3'          AND 기관=? AND 비목=?
    p       = precedence_rules WHERE 사업=?

    if p 가 "L2 > L3":            base 채택, overlay 는 참고로 화면7 병기
    elif p 가 "L1>L2 미규정만":    비목이 L1에 있으면 L1, 없으면 L2. L3 오버레이
    else:                         대체 경로 — 상위 우선 + 같은 층이면 엄격한 쪽
                                  (허용: 불가>조건부>가능 / 한도: min / 사전승인: OR / 증빙: UNION)
```

병합 결과에 (a) 어느 계층에서 왔는지 (b) 어느 우선순위 조항이 적용됐는지를 기록한다 —
화면7이 "이 한도는 국가 지침이 아니라 OO대 규정입니다"를 그린다.

### 🔴 `unspecified_only` 에서 「관리기준이 이긴다」는 문장을 룰에 쓰지 마라

`범위=unspecified_only`(초격차·모두의창업)면 `_층병합` 이 **허용층우선="L1"** 로 간다.
즉 L2 행의 `허용` 은 «최종 허용» 이 되지 못한다 — L1 행이 있으면 그쪽이 쓰인다.

```
모두의창업 인건비   L2 489 조건부(사전승인 T) · L1 421 조건부(사전승인 F)
최종               허용=L1(421)의 조건부 · 사전승인=OR 이라 T
                   489 를 «불가» 로 바꿔도 최종 허용은 여전히 조건부다
```

**L2 가 실제로 얹는 것은 `사전승인`(OR)·`한도`(min)·`증빙`(UNION)이지 `허용` 이 아니다.**
그러니 룰 문장은 「관리기준이 지침을 이긴다」가 아니라
**「허용은 L1 이 정하고, 이 행은 그 위에 사전승인 조건을 얹는다」**로 쓴다.
2026-09-03 에 489·490 을 만들며 앞 문장을 썼다가 검증 세션이 잡았다 — 둘 다 조건부라
결과는 같았지만, 문서 논리와 코드 논리가 갈린 자리였다.

## 2-1. 🔴 `사전승인_조건` 병합은 UNION 이다 (2026-09-06, 커밋 `8ae285f`)

`_엄격병합`(base, L1+L2)과 `_오버레이`(L3)가 둘 다 `사전승인_조건`을 **첫 non-null 하나만**
쓰고 나머지를 버리고 있었다 — 우선순위 적용도 병합도 아니라 `rows`가 `ORDER BY layer`라
**L1이 항상 이기는 행 순서**였다. 실측(고치기 전): 조건이 2개 이상인 조합 **21개 → 21/21
전부 L1이 이기고 L2가 버려짐**(외주용역비 7·재료비 7·기계장치 5·광고선전비 2) — 예비창업의
"점검항목 1개 이상 부적정이면 집행 불가"가 프롬프트에 **한 번도 실린 적이 없었다**.

L1과 L2는 **충돌이 아니라 다른 사실**이다(L1 "2천만원 초과 시 소위 심의" / L2 "점검항목
부적정이면 집행 불가") — 어느 쪽도 다른 쪽을 대체하지 않으므로 precedence로 풀 문제가
아니라 **둘 다 실어야 하는 문제**다. 그래서 병합 규칙에 `사전승인_조건`을 추가했다:

```
순서   L1 -> L2 -> L3 (rows 의 ORDER BY layer 그대로)
중복   문장 단위 제거 (통째 비교로는 464 처럼 L1 단서를 이미 포함한 L2 문장을 못 거른다)
종결   마침표 없는 조각은 종결부호를 채운다 — 안 그러면 다음 층 문장과 한 문장으로 붙는다
필드출처·적용층에 `조건층`을 추가 — 조건 문장을 준 층도 구속에 기여했다고 기록한다
```

고친 뒤 재검(내 손으로): 21개 조합 **문장 전부 살아남음 · 손실 0**. 되살아난 최대량
(외주용역비 계열) **+162~163자**. 🔴 L3(`_오버레이`)도 같은 결함이었다 — 레인 S가
`l3_load.l3룰()`에서 독립적으로 같은 모양(첫 매치만 반환)을 찾았고, 2개 org 표본에서
"진짜 충돌 0건, 전부 다른 사실"을 확인해 같은 결론(UNION)에 닿았다. `l3_load.l3룰()` 쪽
자체의 "첫 매치만 반환" 구조적 한계는 **아직 안 고쳤다** — [[9_미결]] 참고.

스키마(`사전승인_조건` TEXT→TEXT[], [[5-1_룰_테이블]] §3-3)는 이 커밋과 **별건**이다 —
이건 "병합에서 버려지는" 문제를, 배열화는 "한 행이 조건 2개를 담아야" 하는 문제를 고쳤다.

## 3. L3 게이팅 — 상위를 봐야 하는가

코드가 룰 조회 결과의 **모양만**으로 가른다(LLM 에게 안 묻는다).

| l3 조회 결과 | 상위 확인 |
|---|---|
| 없음("정하지 아니한 사항") | 강제 |
| 참조만("제N조에 따른다") | 강제 + seed_refs |
| L3 가 불가/조건부 | 불필요(상위가 관대해도 결론 불변, 근거 보강용으로만 동반) |
| L3 가 "가능"만 | 🔴 강제 |

**(4)가 강제인 이유** — L3 는 상위 지침이 있다고 전제하고 얹는 문서라 구조적으로 자족하지
않는다. "불가"는 L3 단독으로 안전하지만 **"가능"은 절대 L3 단독으로 확정하지 않는다.**
예외: (2)로 갈렸으면 검색 스코어 미달이어도 판단불가로 보내지 않는다 —
L3 에 인용할 명시 근거가 이미 있다.
