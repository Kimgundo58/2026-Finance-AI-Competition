# 프론트 목 서버 — 배포본이 레포보다 뒤에 있다 (2026-09-03 중앙 실측)

> [[프론트_레포_0903]] §6 을 갈라낸 것이다 (100줄 상한). 레포·`lib/`·환경변수는 그쪽.

프론트 팀원이 올린 Cloud Run 목 서버는 `4ba8d3f` 기준 — 즉 `1e64150` **이전**이다.
레포에서 고친 것이 브라우저에는 아직 안 닿는다.

```
GET  /api/health                                            200  {"모드":"mock"}
OPTIONS /api/plans/1/tasks/11  + Request-Method: PATCH       400   ← 여전히 막혔다
OPTIONS /api/plans             + Request-Method: POST        200   ← 대조군
```

주소: `https://suddoe-mock-api-362008123976.asia-northeast3.run.app`

- 프론트에 「CORS 고쳤다」만 전하면 안 된다. **「`1e64150` 이후로 목 서버를 다시 올려라」**까지 가야 한다
- `GET /api/plans/{id}` 500 도 같은 이유로 배포본엔 살아 있다 (배포본에서 재현은 안 했다)
- 🔴 **정정 (같은 날 오후 · ai-a3 재측정).** 위 괄호에 적었던 「`POST /api/plans` 가 400 · `python-multipart`
  때문으로 추정」은 **사실이 아니다. 다시 재니 201 이다.**
  ```
  POST /api/plans   (목) --data-binary @UTF-8파일 → 201 {"plan_id":7,…}
  POST /api/normalize(목) → SSE 정상 (진행 → 필드 {"품목":"맥북"})
  ```
  400 은 **클라이언트 인코딩 문제**였다. Git Bash 에서 `curl -d '{"사업명":…}'` 로 한글을 인라인으로 넘기면
  바이트가 깨져 `{"detail":"There was an error parsing the body"}` 가 난다. `--data-binary @파일` 로 바꾸면 201 이다.
  🔴 **단서는 「목·실 양쪽이 똑같이 400」이었다는 것이다 — 서버 둘이 같은 증상이면 서버가 아니라 클라이언트다.**
  추정을 「재지 않았다」로 표시해 둔 덕에 뒤집을 수 있었다. 표시가 없었으면 실측으로 굳었다.
  (PATCH 프리플라이트 400 은 **여전히 참이다** — 그건 재배포로만 풀린다)
- 시드 `GET /api/plans/1` 은 200 이다 — 500 은 **새로 만든 계획에서만** 난다는 진단과 어긋나지 않는다
