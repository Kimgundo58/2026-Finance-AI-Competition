## 2. 공통 규약

### 2-1. 게스트 — 미결. 지금은 게스트끼리 서로 보인다

로그인이 없어서 `org_id` 없는 요청은 **공용 게스트 버킷**(`org_id IS NULL`)에 들어간다.
게스트가 전부 같은 버킷이라 **서로의 지출계획과 금액이 보인다.** 알고 있는 결함이고
`tests/test_tenant_isolation.py` 가 "의도가 아니라 현재 상태"로 못박아 두었다.

**2026-09-01 시도했다가 접었다.** "게스트마다 `guest_<uuid>` 를 발급해 프론트가
보관한다"로 가려 했는데 **스키마가 거부한다** — `tenant.expense_plans.org_id` 는
`TEXT` 가 아니라 **`uuid`** 이고 **`tenant.orgs(org_id)` 로 FK** 가 걸려 있다.
그래서 (1) `guest_` 접두사를 못 쓰고 (2) "DB 에 아무것도 안 쓰고 문자열만 발급"이
불가능하다 — `orgs` 에 행이 없는 org_id 는 계획 저장 자체가 안 된다.
남은 길은 게스트마다 `orgs` 행을 만들거나(브라우저 수만큼 증식) 타입·FK 를 바꾸는 것뿐이고,
둘 다 로그인 설계와 함께 정해야 한다.

**서버 쪽은 이미 준비돼 있다** — `_실_생성` 이 `org_id` 를 저장하고 목록·**집계 둘 다**
`_org조건()` 을 탄다. org_id 를 **발급하는 방법**만 정해지면 나머지는 0줄이다.

### 2-2. 오류 — 전부 이 모양

```json
{ "오류": "지출계획 999 을(를) 찾을 수 없습니다", "상태": 404 }
```

422 는 `필드` 가 하나 더 붙는다 (없으면 `null`).

```json
{ "오류": "품목·금액·용도(폼) 또는 질문(자연어) 중 하나는 필요합니다.", "상태": 422, "필드": null }
```

**오류 렌더러는 한 벌만 만들면 된다.** pydantic 기본 `{"detail":[...]}` 는 서버가 걷어냈다.

### 2-3. 상태 어휘 — 판정은 4-way, 배지는 3종  *(v1.0 에서는 2-2 였다)*

| `판정` | 배지 | 설명 문구 |
|---|---|---|
| `가능` | 🟢 특이사항 없음 | 현재 기준으로 집행 가능합니다. |
| `조건부` | 🟡 확인 필요 | 아래 조건을 충족하면 집행할 수 있습니다. |
| `판단불가` | 🟡 확인 필요 | 규정만으로는 결론을 낼 수 없습니다. 주관기관에 문의가 필요합니다. |
| `불가` | 위험 | 현재 계획으로는 집행할 수 없습니다. 계획 수정이 필요합니다. |
| `null` | ⬜ 점검 전 | 판정이 아니라 진행 상태 |

**섞으면 안 되는 축이 셋이다.** 하나로 합치려 하지 말 것.

```text
판정        가능 · 조건부 · 불가 · 판단불가 · null     ← AI 결과
계획.상태   draft · judged                            ← 진행
할일.상태   준비필요 · 집행예정 · 완료                 ← 체크리스트
```

### 2-4. 페이지네이션

`?페이지=1&크기=20` → 응답의 `건수` 는 **필터 적용 후 총 건수**(페이지 건수 아님).

## 3. 지출계획

### 3-1. `GET /api/plans` — 목록 + 통계 한 번에

쿼리: `탭` `사업명` `확정비목` `q`(지출명 검색) `금액_최소` `금액_최대` `정렬` `페이지` `크기` `org_id`

- `탭` = `전체` · `확인필요` · `위험` · `특이사항없음` · `점검전`
- `정렬` = `최근수정순`(기본) · `금액많은순` · `금액적은순` · `지출일순`

```json
{
  "통계": { "전체": 5, "확인필요": 2, "위험": 1, "특이사항없음": 1, "점검전": 1,
            "금액합계": 7380000.0 },
  "건수": 5, "페이지": 1, "크기": 2,
  "항목": [
    { "plan_id": 5, "제목": "전시회 부스 임차", "확정비목": "광고선전비",
      "금액": 3300000.0, "판정": null, "집행예정일": "2026-10-02",
      "updated_at": "2026-09-01T11:00:00+09:00", "사업명": "초기창업패키지",
      "상태": "draft" }
  ]
}
```

🔑 **통계 전용 API 는 없다.** 요구서 §화면6-④ 의 "한 번의 JOIN 이면 다 나온다" 를 그대로
따라 목록 응답에 얹었다. 홈은 `?크기=5`, 목록은 `?크기=20` 으로 같은 경로를 쓴다.

⚠️ **통계는 필터 적용 "전" 전체 기준이다.** 탭을 눌러도 배지 숫자가 흔들리지 않는다.

### 3-2. `POST /api/plans` — 저장 (201)

```json
{ "사업명": "초기창업패키지", "품목": "모니터", "금액": 400000, "용도": "개발용",
  "집행예정일": "2026-09-10", "거래처": null, "추가설명": null,
  "확정비목": "기계장치", "정규화": { }, "제목": null, "org_id": null }
```

`제목`·`질문원문` 을 안 보내면 서버가 채운다. 합성 문장 예:
`"초기창업패키지에서 개발용 모니터 400,000원을 사도 되나요?"`

### 3-3. `GET /api/plans/{plan_id}` — 상세

목록 필드 + `질문원문` `용도` `거래처` `추가설명` `정규화` `latest_decision_id`
`판정상세`(판정 전문 or null) `할일[]` `created_at`.

없으면 404 (`{"오류": "...", "상태": 404}`).

## 4. 할일 "확인필요"

**체크리스트와 캘린더는 같은 행이다.** `due_date` 가 없으면 체크리스트에만,
있으면 캘린더에도 뜬다. 두 화면이 서로 다른 레코드를 보는 게 아니다.

### 4-1. `GET /api/tasks`

쿼리: `상태` `구분` `plan_id` `일정만`(true = 캘린더) `이후`(YYYY-MM-DD) `org_id`

```json
{ "건수": 3,
  "항목": [
    { "task_id": 11, "plan_id": 1, "출처": "ai", "코드": "비교견적준비",
      "구분": "결제전", "항목": "비교견적 3곳 확보",
      "설명": "현재 금액이 250만원으로 「1건 100만원 이상」 기준을 넘습니다. 초기창업패키지 세부관리기준 제18조에 따르면 100만원 이상 구매는 비교견적 3곳을 남겨야 정산 시 인정됩니다.",
      "due_date": "2026-09-02", "유형": "비교견적",
      "날짜_사용자수정": false, "상태": "준비필요",
      "계획제목": "개발용 노트북 구매" }
  ] }
```

`설명` 은 **정적 문자열이 아니다** — 사용자 상태와 근거 조항이 들어간 문장이 온다.
말줄임 없이 2~3줄 들어갈 자리를 잡아 둘 것.

### 4-2. `POST /api/plans/{id}/tasks` — 사용자 직접 추가 (201)

```json
{ "항목": "견적서 3부", "설명": null, "구분": "결제전",
  "due_date": "2026-09-05", "유형": "기타" }
```

`출처` 는 서버가 `user` 로 강제한다. **재판정이 절대 안 건드린다.**
`due_date` 를 보내면 `날짜_사용자수정` 이 자동으로 `true` 가 된다.

### 4-3. `PATCH /api/plans/{id}/tasks/{task_id}` — 토글·날짜

```json
{ "상태": "완료" }          // 또는 { "due_date": "2026-09-12" } / { "유형": "계약" }
```

보낸 필드만 바뀐다. 날짜를 한 번이라도 바꾸면 이후 재판정이 그 날짜를 덮지 않는다.

### 4-4. `POST /api/plans/{id}/tasks:sync` — 판정 결과 적재

판정이 끝난 뒤 프론트가 한 번 호출한다. 출처=`ai` 행만 만든다.

```json
{ "생성": 3, "갱신": 1, "보존_user": 2, "보존_날짜수정": 2,
  "코드매칭": 2, "코드미상": 1 }
```

⚠️ `코드미상` 이 0 이 아닐 수 있다 — 판정 출력에 아직 체크항목 코드가 안 실려서
서버가 텍스트로 되짚기 때문이다. **버그가 아니다.** 화면에는 영향이 없다
(`항목`·`설명` 은 판정이 쓴 문장 그대로 나간다. 코드가 없으면 `구분` 이 기본값
`결제전`, `due_date` 가 `null` 이 될 뿐이다).

**판정에서 온 할일은 프론트가 이 엔드포인트를 부를 필요가 없다.** `/api/judge` 가
`plan_id` 를 받으면 서버가 자동으로 태운다 (§6-1). 여기를 또 부르면 같은 할일이
두 벌 생긴다. 이 엔드포인트는 **재판정·수동 재적재** 전용이다.

`코드` 값은 한글 슬러그다 (`비교견적준비`·`부가세제외`·`세금계산서수취` 등 마스터 52종).
프론트가 코드 문자열로 분기하지 말 것 — 표시는 `항목`·`구분`·`유형` 으로 한다.

## 5. 입력 (화면 8) — `POST /api/normalize`

**입력은 폼이다** (2026-09-01 방향 전환). 자연어 경로는 골든셋 재현용으로만 남는다.

```json
{ "품목": "맥북", "금액": 2500000, "용도": "디자이너 작업용",
  "집행예정일": "2026-09-03", "거래처": "애플코리아", "추가설명": null,
  "사업명": "초기창업패키지",
  "f5": { "친족거래": false, "전직임직원업체": false } }
```

- **필수**: `품목` · `금액` · `용도` · `사업명`
- `거래처` 는 **저장만** 한다 — 판정에 안 쓴다. 라벨에 그렇게 적을 것
- `질문`(자연어)과 폼 필드를 **동시에 보내면 422** 다. 하나만 쓴다
- 비목은 여기서 묻지 않는다. 응답의 `비목후보` 를 화면 9 에서 사용자가 확정한다
- 세목·세세목은 **없다**. 지급수수료 하위항목도 폼에서 묻지 않는다

SSE 이벤트 순서:

```text
event: 진행   {"단계":"정규화","설명":"질문에서 사실을 뽑는 중"}
event: 필드   {"품목":"맥북"}          ← 스트리밍 렌더용. 안 들어도 된다
event: 필드   {"금액":2500000}
event: 필드   {"비목후보":[{"비목":"기계장치","신뢰도":0.82}, ...]}
event: 결과   { 전체 JSON }            ← 이거 하나만 들어도 화면이 그려진다
event: 완료   {"캐시":false}
```

실패하면 `event: 오류` → `event: 완료 {"실패":true}`. **500 을 던지지 않는다.**

## 6. 판정 (화면 10~11) — `POST /api/judge`

기존 계약 그대로. `?목=가능|조건부|불가|판단불가` 로 **4-way 화면을 전부 그려볼 수 있다.**

```text
event: 진행 * → 판정 → 해야할일 → 인용 → 전제 → 참조사슬 → 결과 → 저장 → 완료
판단불가면 문의초안 이벤트가 추가된다
```

### 6-1. `저장` 이벤트 — 판정을 지출계획에 잇는다 (2026-09-01 추가)

요청에 `plan_id` 를 실으면 판정이 그 계획에 붙는다. 붙은 뒤에야 `GET /api/plans` 의
`판정`·통계·탭 3종(확인필요·위험·특이사항없음)이 채워진다 — **`plan_id` 없이 판정만
돌리면 목록은 영원히 "점검 전"이다.**

```json
{ "저장": true, "decision_id": 123, "plan_id": 45,
  "할일": { "생성": 2, "갱신": 0, "보존_user": 0,
            "보존_날짜수정": 0, "코드매칭": 2, "코드미상": 0 } }
```

`저장: false` 일 때는 `사유` 가 붙는다. 셋 다 **정상 경로이지 오류가 아니다** —
빨간 화면을 띄우지 말고 "이 판정은 계획에 저장되지 않았습니다" 정도로 알린다.

| 사유 | 언제 | 프론트가 할 일 |
|---|---|---|
| `plan_id 없음` | 계획 없이 단발 점검(화면 4) | 그대로 둔다. 정상이다 |
| `캐시 적중 — 새 판정 기록 없음` | 같은 질문을 다시 물었다 (비용 가드) | 저장하려면 계획을 만들고 다시 점검 |
| `decision_id 없음 — 판정이 기록되지 않았다` | 판정 로깅 실패 | 판정 결과는 유효하다. 재시도 안내 |

**`저장` 이벤트가 와도 `할일` 은 프론트가 따로 부르지 않는다.** 서버가 판정 직후
`tasks:sync` 를 자동으로 태운다 — §4-4 를 손으로 또 호출하면 **같은 할일이 두 벌** 생긴다.
§4-4 는 재판정·수동 재적재용으로만 남는다.

`결과` 이벤트 본문에는 `decision_id` 가 **없다.** 내부 id 는 `저장` 이벤트에만 실린다.

## 7. 프로필 · L3 업로드

### 7-1. `PUT /api/profile` — 실서버에서는 저장되지 않는다

응답 **모양**은 동결이지만 **쓰기는 배선돼 있지 않다.** 실 DB 모드(`SUDDOE_MOCK=0`)에서
`_실_프로필_저장()` 이 항상 이것을 돌려준다 (`server/main.py`):

```json
{ "저장": false, "이유": "f_profile 쓰기 경로 미배선 (tenant 소유는 E 세션)",
  "받은값": { ... } }
```

목 모드에서도 `"저장": false` 다 (`"이유": "목 모드 — 브라우저 상태로만 유지한다"`).
**프론트는 `저장` 필드를 반드시 본다.** 200 이 왔다고 저장된 게 아니다 —
`false` 면 "이 기기에만 유지됩니다"로 안내하고, 사용자에게 "저장됨"을 띄우지 않는다.
`GET` 은 정상이다(없으면 빈 값). 판정은 프로필이 없어도 되고 전제[] 가 늘 뿐이다.

### 7-2. L3 업로드 (화면 4)

#### `POST /api/l3/upload` — multipart, 202 Accepted

필드: `파일`(file) · `org_id`(form) · `기관명`(form, 선택)

- 받는 확장자: **PDF · HWPX · HWP**
- `.doc` · `.docx` → **415** (파서가 없다. 온보딩 안내 문구에서도 빼 주세요)
- 30MB 초과 → 413 · 빈 파일 → 400

```json
{ "doc_id": "l3-...", "파일명": "...hwpx", "확장자": "hwpx",
  "상태": "파싱대기", "조_건수": null, "dangling": [], "파싱품질": null,
  "메시지": "접수했습니다. 조문 분해가 끝나면 상태가 「완료」로 바뀝니다." }
```

#### `GET /api/l3/{doc_id}` — 상태 폴링

```json
{ "상태": "완료", "조_건수": 42, "파싱품질": "warn",
  "dangling": [ { "조": "제12조", "참조": "「연구개발비 사용기준」 제7조",
                  "사유": "상위 규범을 코퍼스에서 찾지 못했습니다" } ],
  "메시지": "42개 조를 등록했습니다. 참조 1건은 상위 규범을 찾지 못했습니다." }
```

`dangling` 은 **업로드 시점에** 알린다. 판정 화면까지 끌고 가지 않는다.
`상태` 가 `파싱대기`·`파싱중` 인 동안 스피너를 돌린다.

**`파싱품질`**(2026-09-04 추가) — `"대기" | "pass" | "warn" | "fail" | null`. `상태` 는
`완료`/`파싱대기`/`실패` 로 뭉뚱그려진 파생값이라 "조문은 뽑혔지만 품질이 낮다"
(`warn` + `조_건수>0`)를 못 구별한다 — 이 필드로 그 경우에도 배지를 달 수 있다.
`상태="완료"`인데 `파싱품질="warn"` 이면 `메시지`에 품질 확인 안내가 붙는다.

## 8. 만들지 않는 것 — 화면에서 걷어내 주세요

| 기능 | 사유 |
|---|---|
| AI 챗봇 (자유 질의) | 확정 원칙 — 판정 1건 = LLM 2~3회, 상한 3 고정(2026-09-05 갱신, `CLAUDE.md`) |
| 집행 일정 캘린더의 **서버 기능**(알림·메모·체크항목) | MVP 스코프 밖. 날짜 표시는 `/api/tasks?일정만=true` 로 가능 |
| 파일 업로드 3종 (계획서·견적서·증빙) | 판정 입력에 파일이 없다 |
| 일괄 N건 **동시** 점검 | GPU 직렬 큐. 한 건씩 순차 호출 + 진행률로 |
| 세목·세세목 / 지급수수료 세부유형 16종 | 룰 키가 `사업 × 비목` 단일 계층 |
| 거래처 검색 | 판정 스키마에 없다 (저장만) |
| 이름·연락처·소속 저장 · F4 인력 이름칸 | 저장 계층화 — 최소 수집 |
| 상태 어휘 7종 | 4-way 폐쇄 enum 밖 |
| 인용 카드에 **조문 원문 전체** 표시 | 인용은 S번호 추출이라 LLM 이 원문을 쓰지 않는다. 백엔드가 채울 수 없는 필드다 |
| 스캔 판독본(`extraction='vlm'`)을 **A등급 근거**로 표시 | 판독 오류 가능성이 남아 A등급을 못 준다. 등급 배지를 그린다면 이 값이 A로 섞이면 안 된다 |
| "아마 가능"·"검토 중" 같은 중간 상태 | 모든 실패의 기본값은 **판단불가**다. 없는 확신을 만들지 않는다 |

**CSV 는 브라우저에서 만든다** (요구서 §화면7-③ 확정). 서버 엔드포인트를 만들지 않았다.
⚠️ CSV "산출 근거" 열은 상세의 `용도` 를 쓴다. "현금/현물/합계" 열은 현물이 없어져
**현금 한 칸**만 남는다.

## 9. 실서버로 갈아끼울 때 — 버그로 오해할 것 2개

1. **"가능" 판정이 거의 안 나온다.** 룰 72행 중 19행이 미검수라 단독 "가능"이
   막혀 있다. **의도된 안전장치다.**
2. **TIPS 를 고르면 판단불가로 닫힌다.** 룰 0행이다.
3. **판정 한 건이 목보다 오래 걸린다** (2026-09-01 변경). 생성 상한을
   `max_tokens` 1500 → **3000** 으로 올렸다 — 1500 에서는 긴 판정이 **문장 중간에서
   잘린 채 "판단불가"로 닫혔다.** 모델의 판단이 아니라 잘림이었다.
   **응답이 최대 2배 길어지므로 `/api/judge` 스트림이 그만큼 오래 열려 있는다.**
   프론트 타임아웃을 1500 기준으로 잡아 뒀다면 끊긴다 — `event: 완료` 를 받을 때까지
   기다리게 하고, 유휴 타임아웃은 **keep-alive 주석(`: keep-alive`) 기준**으로 잡는다
   (서버가 주기적으로 보낸다). 스트림 무응답과 판정 지연을 같은 타이머로 재지 말 것.

→ **UI 개발은 목으로, 실서버는 연동 스모크용으로.**
