## 0. 30초 요약

- **mock 모드(`SUDDOE_MOCK=1`)로 DB·LLM 없이 실행할 수 있다.** 설정하지 않으면 live 모드다.
- **판정은 4종** (`가능`·`조건부`·`불가`·`판단불가`) + `null`(점검 전). **배지는 3종.**
- **모든 오류는 같은 형식** — `{"오류": str, "상태": int}`. 422·401 도 마찬가지다.
- 운영 서버로 전환해도 **프론트 코드는 바뀌지 않는다**. 필드 이름이 같기 때문이다.

```bash
PYTHONIOENCODING=utf-8 python -m uvicorn server.main:app --reload --port 8080
# SUDDOE_MOCK=1 고정 JSON(mock) · 설정하지 않으면 live(실제 DB·LLM)
```

CORS 는 `http://localhost:3000`, `http://localhost:5173` 기본 허용
(`SUDDOE_CORS` 로 바꾼다).

## 2. 공통 규약

### 2-1. 게스트 — 미결. 지금은 게스트끼리 서로 보인다

로그인이 없어서 `org_id` 없는 요청은 **공용 게스트 버킷**(`org_id IS NULL`)에 들어간다.
게스트가 전부 같은 버킷이라 **서로의 지출계획과 금액이 보인다.** 알고 있는 결함이고
"의도가 아니라 현재 상태"로 남겨둔다.

**2026-09-01 시도했다가 중단했다.** "게스트마다 `guest_<uuid>` 를 발급해 프론트가
보관한다"로 가려 했는데 **스키마가 거부한다** — `tenant.expense_plans.org_id` 는
`TEXT` 가 아니라 **`uuid`** 이고 **`tenant.orgs(org_id)` 를 참조하는 FK** 가 있다.
그래서 (1) `guest_` 접두사를 못 쓰고 (2) "DB 에 아무것도 안 쓰고 문자열만 발급"이
불가능하다 — `orgs` 에 행이 없는 org_id 는 계획 저장 자체가 안 된다.
남은 길은 게스트마다 `orgs` 행을 만들거나(브라우저 수만큼 증식) 타입·FK 를 바꾸는 것뿐이고,
둘 다 로그인 설계와 함께 정해야 한다.

**서버 쪽은 이미 준비돼 있다** — `_live_생성` 이 `org_id` 를 저장하고 목록·**집계 둘 다**
`_org조건()` 을 거친다. org_id 를 **발급하는 방법**만 정해지면 나머지는 0줄이다.

### 2-2. 오류 — 전부 이 형식

```json
{ "오류": "지출계획 999 을(를) 찾을 수 없습니다", "상태": 404 }
```

422 는 `필드` 가 하나 더 붙는다 (없으면 `null`).

```json
{ "오류": "품목·금액·용도(폼) 또는 질문(자연어) 중 하나는 필요합니다.", "상태": 422, "필드": null }
```

**오류 렌더러는 하나만 만들면 된다.** pydantic 기본 `{"detail":[...]}` 는 서버가 제거했다.

### 2-3. 상태 어휘 — 판정은 4종, 배지는 3종  *(v1.0 에서는 2-2 였다)*

| `판정` | 배지 | 설명 문구 |
|---|---|---|
| `가능` | 🟢 특이사항 없음 | 현재 기준으로 집행 가능합니다. |
| `조건부` | 🟡 확인 필요 | 아래 조건을 충족하면 집행할 수 있습니다. |
| `판단불가` | 🟡 확인 필요 | 규정만으로는 결론을 낼 수 없습니다. 주관기관에 문의가 필요합니다. |
| `불가` | 위험 | 현재 계획으로는 집행할 수 없습니다. 계획 수정이 필요합니다. |
| `null` | ⬜ 점검 전 | 판정이 아니라 진행 상태 |

**구분해야 하는 상태 값이 세 가지다.** 하나로 합치려 하지 말 것.

```text
판정        가능 · 조건부 · 불가 · 판단불가 · null     ← AI 결과
계획.상태   draft · judged                            ← 진행
할일.상태   준비필요 · 집행예정 · 완료                 ← 체크리스트
```

### 2-4. 페이지네이션

`?페이지=1&크기=20` → 응답의 `건수` 는 **필터 적용 후 총 건수**(페이지 건수 아님).

## 3. 지출계획

### 3-1. `GET /api/plans` — 목록 + 통계 한 번에

쿼리: `탭` `사업명` `확정비목` `q`(지출명 검색) `금액_최소` `금액_최대` `정렬` `페이지` `크기` `org_id`

- `탭` = `전체` · `확인필요` · `위험` · `특이사항없음` · `점검전`
- `정렬` = `최근수정순`(기본) · `금액많은순` · `금액적은순` · `지출일순`

```json
{
  "통계": { "전체": 5, "확인필요": 2, "위험": 1, "특이사항없음": 1, "점검전": 1,
            "금액합계": 7380000.0 },
  "건수": 5, "페이지": 1, "크기": 2,
  "항목": [
    { "plan_id": 5, "제목": "전시회 부스 임차", "확정비목": "광고선전비",
      "금액": 3300000.0, "판정": null, "집행예정일": "2026-10-02",
      "updated_at": "2026-09-01T11:00:00+09:00", "사업명": "초기창업패키지",
      "상태": "draft" }
  ]
}
```

🔑 **통계 전용 API 는 없다.** 요구서 §화면6-④ 의 "한 번의 JOIN 이면 다 나온다" 를 그대로
따라 목록 응답에 포함했다. 홈은 `?크기=5`, 목록은 `?크기=20` 으로 같은 경로를 쓴다.

통계는 필터 적용 "전" 전체 기준이다. 탭을 눌러도 배지 숫자가 흔들리지 않는다.

### 3-2. `POST /api/plans` — 저장 (201)

```json
{ "사업명": "초기창업패키지", "품목": "모니터", "금액": 400000, "용도": "개발용",
  "집행예정일": "2026-09-10", "거래처": null, "추가설명": null,
  "확정비목": "기계장치", "정규화": { }, "제목": null, "org_id": null }
```

`제목`·`질문원문` 을 안 보내면 서버가 채운다. 합성 문장 예:
`"초기창업패키지에서 개발용 모니터 400,000원을 사도 되나요?"`

### 3-3. `GET /api/plans/{plan_id}` — 상세

목록 필드 + `질문원문` `용도` `거래처` `추가설명` `정규화` `latest_decision_id`
`판정상세`(판정 전문 or null) `사용자답변[]`(`{질문문, 답}`, 최신 판정에 반영한 확인 질문, §6-2) `할일[]` `created_at`.

없으면 404 (`{"오류": "...", "상태": 404}`).

### 3-4. `PATCH /api/plans/{plan_id}` — 지출일 (2026-11-06)

`{"집행예정일": "2026-11-28", "일정이동": true}`. 보낸 필드만 바뀐다.

- `일정이동=true`: 완료 안 된 연결 일정을 지출일 차이만큼 옮긴다. `false`: 일정은 그대로 두고 다음 재점검이 덮지 않게 표시한다.
- 집행 줄은 항상 지출일을 따라간다. 날짜만 바꾸면 재점검이 필요하지 않다(판정이 집행예정일을 읽지 않는다).

## 4. 할일 "확인필요"

**체크리스트와 캘린더는 같은 행이다.** `due_date` 가 없으면 체크리스트에만,
있으면 캘린더에도 표시된다. 두 화면이 서로 다른 레코드를 보는 게 아니다.

### 4-1. `GET /api/tasks`

쿼리: `상태` `구분` `plan_id` `일정만`(true = 캘린더) `이후`(YYYY-MM-DD) `org_id`

```json
{ "건수": 3,
  "항목": [
    { "task_id": 11, "plan_id": 1, "출처": "ai", "code": "비교견적준비",
      "구분": "결제전", "항목": "비교견적 3곳 확보",
      "설명": "현재 금액이 250만원으로 「1건 100만원 이상」 기준을 넘습니다. 초기창업패키지 세부관리기준 제18조에 따르면 100만원 이상 구매는 비교견적 3곳을 남겨야 정산 시 인정됩니다.",
      "due_date": "2026-09-02", "유형": "비교견적",
      "날짜_사용자수정": false, "상태": "준비필요",
      "계획제목": "개발용 노트북 구매" }
  ] }
```

`설명` 은 **정적 문자열이 아니다** — 사용자 상태와 근거 조항이 들어간 문장이 온다.
말줄임 없이 2~3줄 들어갈 공간을 확보할 것.

### 4-2. `POST /api/plans/{id}/tasks` — 사용자 직접 추가 (201)

```json
{ "항목": "견적서 3부", "설명": null, "구분": "결제전",
  "due_date": "2026-09-05", "유형": "기타" }
```

`출처` 는 서버가 `user` 로 강제한다. **재판정이 절대 안 건드린다.**
`due_date` 를 보내면 `날짜_사용자수정` 이 자동으로 `true` 가 된다.

### 4-3. `PATCH /api/plans/{id}/tasks/{task_id}` — 토글·날짜

```json
{ "상태": "완료" }          // 또는 { "due_date": "2026-09-12" } / { "유형": "계약" }
```

보낸 필드만 바뀐다. 날짜를 한 번이라도 바꾸면 이후 재판정이 그 날짜를 덮지 않는다.

### 4-4. `POST /api/plans/{id}/tasks:sync` — 판정 결과 적재

판정이 끝난 뒤 프론트가 한 번 호출한다. 출처=`ai` 행만 만든다.

```json
{ "생성": 3, "갱신": 1, "보존_사용자": 2, "보존_날짜수정": 2,
  "코드매칭": 2, "코드미매칭": 1 }
```

`코드미매칭` 이 0 이 아닐 수 있다 — 판정 출력에 체크항목 코드가 없는 항목은
서버가 텍스트 매칭으로 코드를 추정하기 때문이다. 버그가 아니다. 화면에는 영향이 없다
(`항목`·`설명` 은 판정이 쓴 문장 그대로 나간다. 코드가 없으면 `구분` 이 기본값
`결제전`, `due_date` 가 `null` 이 될 뿐이다).

**판정에서 온 할일은 프론트가 이 엔드포인트를 부를 필요가 없다.** `/api/judge` 가
`plan_id` 를 받으면 서버가 자동으로 실행한다 (§6-1). 여기를 또 부르면 같은 할일이
중복으로 생긴다. 이 엔드포인트는 **재판정·수동 재적재** 전용이다.

`code` 값은 한글 슬러그다 (`비교견적준비`·`부가세제외`·`세금계산서수취` 등 마스터 52종).
프론트가 코드 문자열로 분기하지 말 것 — 표시는 `항목`·`구분`·`유형` 으로 한다.

### 4-5. `POST /api/tasks` · `PATCH·DELETE /api/tasks/{task_id}` — 계획 없는 일정 (2026-11-06)

- `POST`: `plan_id` 없는 일정을 `출처=user` 로 만든다. 게스트는 401.
- `PATCH`: 항목·설명·상태·`due_date`·유형. `due_date: null` 은 날짜 비우기다. 잘못된 날짜는 422.
- `DELETE`: `출처=user` 행만. ai 행은 재점검이 다시 만들므로 거부한다.
- 응답 행에 `집행예정일_연동`(지출일을 따라가는 집행 줄)이 있다. 유형에 사전승인·사전확인·증빙이 추가됐다.

## 5. 입력 (화면 8) — `POST /api/normalize`

**입력은 폼이다** (2026-09-01 방향 전환). 자연어 경로는 골든셋 재현용으로만 남는다.

```json
{ "품목": "맥북", "금액": 2500000, "용도": "디자이너 작업용",
  "집행예정일": "2026-09-03", "거래처": "애플코리아", "추가설명": null,
  "사업명": "초기창업패키지",
  "특수관계": { "친족거래": false, "전직임직원업체": false } }
```

- **필수**: `품목` · `금액` · `용도` · `사업명`
- `거래처` 는 **저장만** 한다 — 판정에 안 쓴다. 라벨에 그렇게 적을 것
- `질문`(자연어)과 폼 필드를 **동시에 보내면 422** 다. 하나만 쓴다
- 비목은 여기서 묻지 않는다. 응답의 `비목후보` 를 화면 9 에서 사용자가 확정한다. 후보는 `사업명` 에 있는 비목(`/api/vocab`) 안에서만 나온다
- `심층질문[]` 항목의 `비목` 이 null 이면 공통 질문이다. 후보가 없으면 모든 비목의 질문이 오므로, 프론트가 확정한 비목으로 다시 거른다
- 세목·세세목은 **없다**. 지급수수료 하위항목도 폼에서 묻지 않는다

SSE 이벤트 순서:

```text
event: 진행   {"단계":"정규화","설명":"입력에서 정보를 추출하는 중"}
event: 필드   {"품목":"맥북"}          ← 스트리밍 렌더용. 안 들어도 된다
event: 필드   {"금액":2500000}
event: 필드   {"비목후보":[{"비목":"기계장치","신뢰도":0.82}, ...]}
event: 결과   { 전체 JSON }            ← 이거 하나만 들어도 화면이 그려진다
event: 완료   {"캐시":false}
```

실패하면 `event: 오류` → `event: 완료 {"실패":true}`. **500 을 던지지 않는다.**

## 6. 판정 (화면 10~11) — `POST /api/judge`

기존 계약 그대로. mock 모드에서는 `?mock=가능|조건부|불가|판단불가` 로 **4종 판정 화면을 전부 그려볼 수 있다.**
요청의 `답변` 중 확인 질문 답(`질문세트` 와 함께 보낸 것)은 판정에 반영한다(§6-2). `정규화` 안의 `심층질문` 은 서버가 판정 전에 뺀다.

이벤트는 이 순서로 온다(`server/routes_judge.py`).

```text
event: 진행       {"단계":"검색|룰조회|판정생성", "설명":"..."}      ← 3회
event: 판정       {판정, 요약, 신뢰등급, 규정버전}
event: 해야할일    [ {항목, 설명}, ... ]
event: 인용       [ {조번호, 조제목, 원문, doc_id}, ... ]
event: 전제       [ {사실, 근거조항, 매핑[], 미충족시}, ... ]
event: 참조관계    [ {from{doc_id,조번호}, 참조문자열, 관계, to{...}, 해결근거}, ... ]
event: 문의초안    "..."        ← 판정이 "판단불가"일 때만. 참조관계와 결과 사이
event: 결과       { 전체 JSON }                ← 이것 하나만 들어도 화면이 그려진다
event: 저장       {저장: bool, 사유?: str, ...}   ← §6-1
event: 완료       {캐시: bool}
```

### 6-1. `저장` 이벤트 — 판정을 지출계획에 잇는다 (2026-09-01 추가)

요청에 `plan_id` 를 포함하면 판정이 그 계획에 붙는다. 붙은 뒤에야 `GET /api/plans` 의
`판정`·통계·탭 3종(확인필요·위험·특이사항없음)이 채워진다 — **`plan_id` 없이 판정만
실행하면 목록은 영원히 "점검 전"이다.** 계획에 비목이 없으면 요청의 `확정비목` 을 계획에 남긴다.

```json
{ "저장": true, "decision_id": 123, "plan_id": 45,
  "할일": { "생성": 2, "갱신": 0, "보존_사용자": 0,
            "보존_날짜수정": 0, "코드매칭": 2, "코드미매칭": 0 } }
```

`저장: false` 일 때는 `사유` 가 붙는다. 셋 다 **정상 경로이지 오류가 아니다** —
빨간 화면을 띄우지 말고 "이 판정은 계획에 저장되지 않았습니다" 정도로 알린다.

| 사유 | 언제 | 프론트가 할 일 |
|---|---|---|
| `plan_id 없음` | 계획 없이 단발 점검(화면 4) | 그대로 둔다. 정상이다 |
| `캐시 적중 — 새 판정 기록 없음` | 같은 질문을 다시 물었다 (비용 가드) | 저장하려면 계획을 만들고 다시 점검 |
| `decision_id 없음 — 판정이 기록되지 않았다` | 판정 로깅 실패 | 판정 결과는 유효하다. 재시도 안내 |

**`저장` 이벤트가 와도 `할일` 은 프론트가 따로 부르지 않는다.** 서버가 판정 직후
`tasks:sync` 를 자동으로 실행한다 — §4-4 를 손으로 또 호출하면 **같은 할일이 중복으로** 생긴다.
§4-4 는 재판정·수동 재적재용으로만 남는다.

`결과` 이벤트 본문에는 `decision_id` 가 **없다.** 내부 id 는 `저장` 이벤트에만 포함된다.

### 6-2. `POST /api/questions` — 판정 전 확인 질문 (2026-11-04)

**화면:** 비목을 고르고 「AI 점검하기」를 누르면 짧은 로딩 뒤 질문이 최대 3개 나온다. 사용자는 예 · 아니오 · 모르겠어요로 답한다. 물을 것이 없거나 질문 생성이 실패하면 오류 없이 바로 결과로 넘어간다. 프론트는 25초를 넘기면 기다리지 않는다.

요청 예시 (실제 코드 아님)
```json
{ "사업명": "예비창업패키지", "확정비목": "여비", "세부유형": null,
  "품목": "부산 출장 KTX 왕복", "금액": 120000, "용도": "거래처 미팅",
  "질문원문": "KTX 왕복 12만원 써도 되나요?" }
```

응답 예시 (실제 코드 아님)
```json
{ "상태": "있음", "질문세트": "ab12…",
  "질문": [{ "id": "Q1", "질문문": "…인가요?", "이유": "…로 한정돼요.",
             "선택지": [{"라벨":"예","값":"예"}, {"라벨":"아니오","값":"아니오"}, {"라벨":"모르겠어요","값":"모름"}],
             "근거": {"doc_id":"…", "조번호":"제43조", "조제목":"여비", "항호":"③", "원문":"…"} }] }
```

| `상태` | 뜻 | 화면 |
|---|---|---|
| `있음` | 질문 1개 이상 | 질문 화면. 모두 답해야 「결과 확인하기」가 켜진다 |
| `없음` | 물을 것이 없다 | 바로 결과 |
| `바로판정` | 금지 항목이거나 근거 규정을 못 찾았다 | 바로 결과 |
| `실패` | DB·LLM 오류 또는 요청 한도. `질문세트` 는 null | 바로 결과 |

- 실패해도 **HTTP 200** 이다. 422 는 비목이 10종 밖이거나 등록되지 않은 사업명일 때뿐이다
- `근거` 는 「규정 원문 보기」용이다. 문서 이름은 `문서명보기()` 로 바꿔 보여 준다(L3 는 서버가 파일 이름을 준다)
- org·계정은 토큰에서 정한다. 같은 입력이 다시 오면 저장한 질문을 돌려준다(24시간)

**답변 보내기:** `/api/judge` 요청에 `질문세트` 와 `답변` 을 넣는다.

요청 예시 (실제 코드 아님)
```json
{ "질문세트": "ab12…", "답변": [{"code":"Q1","값":"예"}], "확정비목": "여비", "정규화": { } }
```

- 서버는 저장한 질문 문장과 답 값(`예`·`아니오`·`모름`)만 판정에 넣는다. 프론트가 보낸 글은 쓰지 않는다. 답하지 않은 질문과 허용 밖 값은 `모름` 이다
- 답이 요건을 충족하지 않거나 `모름` 이면 「가능」으로 나오지 않는다. 충족하는 답이어도 코드가 판정을 올리지 않는다
- `모름` 이면 그 요건을 확인할 일이 `해야할일` 에 `구분: "결제전"`, `code` 없이 들어가고 계획의 할일에도 저장된다
- `질문세트` 를 읽지 못하면(만료·재시작·다른 계정 키) 오류 없이 판정하되 「가능」을 내지 않는다
- 응답 `결과` 와 `GET /api/plans/{id}` 에 `사용자답변: [{질문문, 답}]` 이 온다. 화면은 「확인한 내용」으로 보여 주고 `모름` 은 「모르겠어요」로 표시한다. 새 이벤트는 없다

## 7. 프로필 · L3 업로드

### 7-1. `PUT /api/profile` — 협약 네 값을 저장한다 (2026-11-03부터)

live 모드에서는 `협약` 의 네 값(`협약시작일`·`협약종료일`·`정부지원_현금`·`자기부담_현금`)을
로그인한 계정의 `tenant.profile_agreements` 에 저장한다(`server/routes_profile.py`).
저장한 값은 다음 판정부터 프롬프트 B5(협약·집행 현황)에 들어간다.

- **기관은 토큰으로만 정한다.** 본문·쿼리의 `org_id` 는 쓰지 않는다. 데모 세션 토큰도 그 데모 기관에 저장한다.
- **게스트는 401** (`"저장하려면 로그인이 필요합니다"`). `POST /api/plans`·`/api/l3/upload` 와 같다.
- **PUT 은 네 값을 통째로 바꾼다.** 날짜에 `null`·빈 문자열을 보내면 미입력으로 저장된다.
- **검증(422, 한국어 `오류`)**: 날짜는 `YYYY-MM-DD`, `협약시작일 ≤ 협약종료일`(둘 다 있을 때), 금액은 0 이상 1000조 이하.
- **프로필은 계정 단위다(2026-11-03).** 같은 기관(주관기관)의 다른 계정과 나눠 쓰지 않는다. GET·PUT·판정 B5 가
  모두 토큰의 계정 행만 읽고 쓴다. 데모 세션은 계정이 없어 그 데모 기관의 계정 없는 행을 쓴다. 응답 모양은 그대로다.
- 계정당 행은 1개다. 기존 행(최근 수정 순 첫 행)을 고치고 없으면 새로 만든다. 판정도 같은 순서로 한 행을 읽는다.
- `집행내역`·`참여인력` 은 받기만 하고 저장하지 않는다. 보내면 `사유` 에 그렇다고 적는다.
- 저장하면 이 계정의 판정 캐시를 지운다. 판정 캐시키에도 계정과 협약 프로필 해시가 들어간다.

예시 (실제 코드 아님)
```json
{ "저장": true, "사유": null,
  "받은값": { "협약": { "정부지원_현금": 60000000.0, "자기부담_현금": 15000000.0,
                       "협약시작일": "2026-03-01", "협약종료일": "2026-12-31" },
              "집행내역": [], "참여인력": [] } }
```

`받은값` 은 저장된 값(GET 과 같은 모양)이다. mock 모드는 저장하지 않고
`{"저장": false, "사유": "mock 모드(SUDDOE_MOCK=1)에서는 저장하지 않습니다", "받은값": <보낸 값>}` 을 준다.
v1.1 이전 이름(`이유`, `받은값` 안의 `f1`·`f3`·`f4`)은 한 릴리스 동안 함께 온다(§0-1).
**프론트는 `저장` 필드를 본다.** `false` 면 "이 기기에만 유지됩니다"로 안내하고 "저장됨"을 띄우지 않는다.
`GET` 은 저장된 값을 준다(없으면 빈 값). 판정은 프로필이 없어도 되고 전제[] 가 늘 뿐이다.

### 7-2. L3 업로드 (화면 4)

#### `POST /api/l3/upload` — multipart, 202 Accepted

필드: `파일`(file) · `org_id`(form) · `기관명`(form, 선택)

- 받는 확장자: **PDF · HWPX · HWP**
- `.doc` · `.docx` → **415** (파서가 없다. 온보딩 안내 문구에서도 빼 주세요)
- 30MB 초과 → 413 · 빈 파일 → 400

```json
{ "doc_id": "l3-...", "파일명": "...hwpx", "확장자": "hwpx",
  "상태": "파싱대기", "조_건수": null, "미해결참조": [], "파싱품질": null,
  "메시지": "접수했습니다. 조문 분할이 끝나면 상태가 「완료」로 바뀝니다." }
```

#### `GET /api/l3/{doc_id}` — 상태 폴링

```json
{ "상태": "완료", "조_건수": 42, "파싱품질": "warn",
  "미해결참조": [ { "조": "제12조", "참조": "「연구개발비 사용기준」 제7조",
                  "사유": "상위 규정을 등록된 규정에서 찾지 못했습니다" } ],
  "메시지": "42개 조를 등록했습니다. 참조 1건은 상위 규정을 찾지 못했습니다." }
```

`미해결참조` 는 **업로드 시점에** 알린다. 판정 화면에서 다시 보여 주지 않는다.
`상태` 가 `파싱대기`·`파싱중` 인 동안 스피너를 표시한다.

**`파싱품질`**(2026-09-04 추가) — `"pending" | "pass" | "warn" | "fail" | null`. `상태` 는
`완료`/`파싱대기`/`실패` 로 뭉뚱그려진 파생값이라 "조문은 뽑혔지만 품질이 낮다"
(`warn` + `조_건수>0`)를 못 구별한다 — 이 필드로 그 경우에도 배지를 달 수 있다.
`상태="완료"`인데 `파싱품질="warn"` 이면 `메시지`에 품질 확인 안내가 붙는다.

**기관당 L3 한 문서**(2026-11-03) — 새 문서의 파싱이 성공하면 그 문서로 교체되고 이전 문서는
판정에 쓰지 않는다. 파싱이 실패하면 이전 문서를 계속 쓴다. `메시지` 가 이 두 경우를 함께 알린다.

- `실패사유` — `상태="실패"` 일 때만 채운다. 원본없음·보호문서·추출실패·형식·스캔본·조문없음·
  분할실패·저장실패·서버오류·중단·쪽수초과·문자인식실패. 사용자 안내 문구는 `메시지` 에 이미 들어 있다.
- `적용중_문서` — 이 기관이 지금 판정에 쓰는 L3 파일명. `null` 이면 기관 규정 없이 상위 규정만으로 판정한다.
- `추출방식`(2026-11-03, `/current` 의 문서에도 있음) — `"ocr"` 이면 스캔본 PDF 를 CLOVA OCR 로 읽은 문서다.
  `파싱품질` 은 항상 `warn` 이고, 이 문서를 인용한 "가능" 은 조건부로 낮아진다. 그 밖의 값은 `native`·`hwpx`·`hwp`.
- `파싱대기` 로 10분 넘게 남은 문서(서버 재시작 등으로 파싱이 끊김)는 `실패`(`실패사유="중단"`)로 바뀐다.
- `GET /api/l3/current` 는 적용 중인 문서를 맨 앞에 두고, 처리 중 1건과 최근 실패 1건까지만 준다.

### 7-3. `POST /api/accounts` — 가입한 계정을 기관에 등록한다 (2026-11-04)

요청 `{"slug": "<GET /api/orgs 의 slug>"}`, 헤더 `Authorization: Bearer <Supabase 토큰>`. 응답 `{"기관명", "slug", "새계정"}`.

| 상태 | 뜻 |
|---|---|
| 201 | 새로 등록했다 |
| 200 | 이미 등록된 계정이다. 요청한 기관과 달라도 현재 기관을 돌려주고 바꾸지 않는다 |

| 404 | 없는 기관이거나 데모 기관이다 |
| 503 | DB 오류 |

## 9. 운영 서버로 전환할 때 — 버그로 오해할 것 3개

1. **"가능" 판정이 거의 안 나온다.** 룰 72행 중 19행이 미검수라 단독 "가능"이
   막혀 있다. **의도된 안전장치다.**
2. **TIPS 를 고르면 판단불가로 반환된다.** 룰 0행이다.
3. **판정 한 건이 mock 보다 오래 걸린다** (2026-09-01 변경). 생성 상한을
   `max_tokens` 1500 → **3000** 으로 올렸다 — 1500 에서는 긴 판정이 **문장 중간에서
   잘린 채 "판단불가"로 반환됐다.** 모델의 판단이 아니라 잘림이었다.
   **응답이 최대 2배 길어지므로 `/api/judge` 스트림이 그만큼 오래 열려 있는다.**
   프론트 타임아웃을 1500 기준으로 잡아 뒀다면 끊긴다 — `event: 완료` 를 받을 때까지
   기다리게 하고, 유휴 타임아웃은 **keep-alive 주석(`: keep-alive`) 기준**으로 잡는다
   (서버가 주기적으로 보낸다). 스트림 무응답과 판정 지연을 같은 타이머로 재지 말 것.

→ **UI 개발은 mock 으로, 운영 서버는 연동 스모크 테스트용으로.**
