# 계약 정정 (2026-09-02) — 서버가 바뀐 곳

루트 `프론트_API_계약_v1.0.md` v1.0.1 이후 서버가 실제로 바뀐 것만 싣는다.
엔드포인트 수는 안 늘었다 — **경로 18 · 메서드 20 그대로** (`app.openapi()` 실측).

---

## 1. `GET /api/l3/{doc_id}` — 살아났다 🟢

**전**: 실 DB 모드에서 **주인에게도 항상 404**. 화면 4 온보딩이 무한 스피너였다.
**후**: 정상 동작. 실측 5케이스 (`SUDDOE_MOCK=0`, TestClient):

| 호출 | 결과 |
|---|---|
| 주인이 자기 문서 (`org_id` 있음) | **200** — `조_건수: 11` 실제 응답 |
| 게스트 (`org_id` 없음) | 404 |
| 다른 기관의 `org_id` | 404 |
| 없는 `doc_id` | 404 |
| uuid 형식이 아닌 `doc_id` | 404 |

🔴 **프론트가 바꿔야 할 것**: 상태 폴링에 **`org_id` 를 반드시 실어라.**
빼면 404 다. 업로드(`POST /api/l3/upload`)가 이미 `org_id` 를 필수로 받으므로
그 값을 그대로 쓰면 된다.

---

## 2. 할일 쓰기 3경로 — `org_id` 쿼리 파라미터가 생겼다

| 경로 | 메서드 |
|---|---|
| `/api/plans/{plan_id}/tasks` | POST |
| `/api/plans/{plan_id}/tasks/{task_id}` | PATCH |
| `/api/plans/{plan_id}/tasks:sync` | POST |

셋 다 `?org_id=` 를 받는다. 안 보내면 **게스트**로 취급한다 (읽기 경로와 같은 규칙).

🔴 **동작이 바뀐 자리** — 기관 계획(`org_id` 가 있는 계획)에 `org_id` 없이 쓰면
전에는 **성공**했고 지금은 **404** 다. 게스트 계획(`org_id IS NULL`)은 전과 같다.
로그인이 아직 없어 실제 계획이 전부 게스트라 **오늘은 화면에 영향이 없지만**,
`org_id` 를 쓰기 시작하면 읽기·쓰기 **양쪽에 다** 실어야 한다.

실측 9케이스 (A·B 두 기관, A 소유 계획):

| | B(남) | A(주인) | 게스트 |
|---|---|---|---|
| POST tasks | 404 | 201 | 404 |
| PATCH tasks | 404 | 200 | 404 |
| tasks:sync | 404 | 200 | 404 |

동기화 후 `보존_user: 1` — 재판정 4원칙(사용자 행 불가침)은 안 깨졌다.

---

## 3. 판정 → 저장 경로 — 겉으로는 안 바뀐다

`POST /api/judge` 의 `저장` 이벤트 계약은 **그대로**다. 모양·순서·`저장:false` 처리
전부 동일하다. 내부적으로 `persist.py` 가 할일 동기화에 `org_id` 를 넘기도록 고쳤다 —
안 고쳤으면 §2 변경이 기관 계획의 저장을 통째로 깨뜨렸을 자리다.
**프론트 영향 0.**

---

## 4. 게스트 발급(`POST /api/guest`) — 만들지 않는다. 근거를 남긴다

계약 v1.0.1 §2-1 의 「시도했다가 접었다」가 **현재 상태이고 유지된다.**
`tests/test_contract.py` 에 남아 있던 `계약_보류 = {("POST","/api/guest")}` 잔재는 걷어냈다.

실측 (2026-09-02, `tenant.expense_plans` 에 실제 INSERT 후 롤백):

| 넣은 `org_id` | 결과 |
|---|---|
| `guest_<hex>` 문자열 | `InvalidTextRepresentation` — 컬럼이 uuid 타입 |
| `orgs` 에 없는 uuid | `ForeignKeyViolation` |
| `NULL` | **OK** — 지금의 공용 게스트 버킷 |

**관측**: 위 3행. **추론**: 남은 길은 (a) 게스트마다 `orgs` 행 생성 — 브라우저 수만큼 증식,
(b) 타입·FK 변경 — `orgs`·`l3_documents`·`l3_articles`·`decisions`·`plan_tasks` 의 RLS
(`org_isolation USING (org_id = tenant.current_org())`)가 같이 걸린다.
**둘 다 로그인 설계와 함께 정해야 한다.**

제3안(오너 판단 대기): `expense_plans` 에 nullable `guest_key TEXT` 를 부축으로 추가.
uuid·FK·RLS 를 안 건드리고 게스트만 갈라낸다. 대신 **테넌시 축이 둘**이 되므로
`plan_tasks` 에도 같이 넣어야 하고 RLS 가 그 축을 안 본다.

🔴 게스트끼리 서로의 지출계획이 보이는 결함은 **그대로 남아 있다.**
`tests/test_tenant_isolation.py::test_게스트끼리는_지금_서로_보인다_…` 가 현재 상태로 못박고 있다.
