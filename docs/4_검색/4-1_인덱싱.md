# 인덱싱 파이프라인

이 문서가 답하는 질문:
- 원문이 검색 가능한 청크가 되기까지 어떤 단계를 거치는가
- 청킹 단위와 임베딩 사양은 무엇인가
- 각 단계는 지금 어디까지 끝났는가

> 파싱 단계 **안의** 텍스트→조문 재구성 방식은 [[3-3_파싱_규칙]] 참조 — 여기서는
> 반복하지 않는다. DB 테이블은 [[3-5_저장소_스키마]] 참조.

## 흐름

```
원문 (XML / PDF / HWP→PDF · L3 업로드는 HWPX/HWP 직파싱)
  ├─ 파싱·조문 분할        text_extract.py · article_split.py → corpus.doc_articles
  ├─ 적용대상 태깅         → corpus.chunks.적용대상
  │                         절(節) 표제가 선언하면 상속, LLM 은 절 밖 조문만
  ├─ 참조 그래프 (정규식)   build_refs.py → corpus.refs
  ├─ 우선순위 조항 추출     → corpus.precedence_rules
  ├─ 룰 컴파일             → corpus.rules (docs/5_룰/)
  └─ 청킹·헤더·임베딩·BM25  bm25_index.py → corpus.chunks / chunk_terms
```

적용대상 태깅은 임베딩보다 먼저다 — 청크 적재 시 필드가 차 있어야 필터가 적용된다.
적용대상 태깅·참조 그래프·우선순위 조항 추출은 서로 독립이고(파싱 산출물만 읽음), 룰 컴파일은 표 추출 결과에 의존한다.
예전 문서의 Stage 0~2 번호는 이 순서를 가리킨다(Stage 0 = 파싱, Stage 2 = 청킹·임베딩).

모든 인덱싱 경로는 `scripts/retrieve.py` 의 FILTER 조건을 거친다 — [[3-1_검색_범위]] 참조.

## 청킹 규칙

| 규칙 | 값 |
|---|---|
| 기본 단위 | 1 조 = 1 청크. 900토큰 초과 시 항(①②③) 단위, 항도 초과 시 호 |
| 병합 | 50자 미만 청크 → 직전에 병합 |
| 오버랩 | 없음 — 조 경계가 의미 경계 |
| 표 | 청크에 넣지 않음 → 룰 테이블 |
| 첨부(별표·별지·서식·붙임) | 청크에 넣지 않음 — 대부분 세무 서식·감독 표 |
| 범위 제외 | 모두의창업 제3편(로컬트랙)은 청크에서 제외. `doc_articles`에는 남긴다 |

코드: `scripts/corpus_ingest.py` · `청크_최대토큰`
```python
청크_최대토큰 = 900
임베딩_최대토큰 = 1024
청크_최소글자 = 50
```

임계가 문자수가 아니라 토큰수인 이유: 한국어 3,000자 ≈ 1,500~2,000토큰이라
`max_seq_length` 1024를 넘으면 조문 뒷부분(단서·예외)이 임베딩에서 빠진다.

## 임베딩

| 항목 | 값 |
|---|---|
| 모델 | `nlpai-lab/KURE-v1` (1024차원, bge-m3 계열) |
| 정규화 | L2 정규화 후 저장 → 코사인 = 내적 |
| `max_seq_length` | 1024 |
| 임베딩 입력 | 컨텍스트 헤더(`[L2 \| 사업명 \| 문서 \| 장 \| 조]`, ~50토큰) + 본문 |
| 실행 | 앱 서버 CPU |

코드: `scripts/retrieve.py` · `임베딩_모델()`
```python
                m = SentenceTransformer("nlpai-lab/KURE-v1", device="cpu")
                m.max_seq_length = 1024
                _모델 = m
```

헤더는 임베딩·BM25 입력 전용 — `chunks.text`(인용 검증 대상)는 불변, 가공 금지.

코드: `scripts/bm25_index.py` · `_헤더()`
```python
def _헤더(layer, 사업, doc_id, 장, 조번호, 조제목) -> str:
    """`[layer | 사업 | 문서명 | 장 | 조번호(조제목)]` 형식의 컨텍스트 헤더."""
    문서 = re.sub(r"^(붙임\d*\.\s*|첨부\s*)", "", doc_id).strip()
    조 = f"{조번호}({조제목})" if 조제목 else str(조번호)
    필드 = [layer, "·".join(사업) if 사업 else "공통", 문서[:60], 장 or "-", 조]
    return "[" + " | ".join(필드) + "]"
```

사례 인덱스(`corpus.case_chunks`, 193행)는 쓰지 않는다. 테이블을 삭제했고 `scripts/`·`db/init/`
에도 정의와 참조가 남아 있지 않다(`git grep case_chunks` 기준).

BM25는 형태소 분석(kiwipiepy) 결과 토큰만 DB에 적재해 SQL로 계산한다.
ANN 인덱스(HNSW/IVFFlat) 미사용 — 근사 검색의 재현율 저하가 곧 인용 누락.

## 재적재 시 빠뜨리기 쉬운 것 — BM25 세 테이블

`retrieval_scope` 변경 후 재적재가 `corpus.chunks` 만 변경하고 `chunk_terms`·
`chunk_len`·`term_df`(BM25 토큰 테이블)를 건드리지 않아 53청크가 검색 색인에서만 빠진 적이 있다
(로컬·운영 양쪽, `dee9594`에서 수정). `bm25_index.py --증분`이 `chunk_len`을 기준으로
누락분만 색인한다 — 전체 재구축(TRUNCATE) 없이. 재적재 절차에 이 단계를 필수로 넣는다.
