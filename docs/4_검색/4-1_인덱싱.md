# 인덱싱 파이프라인

이 문서가 답하는 질문:
- 원문이 검색 가능한 청크가 되기까지 어떤 단계를 거치는가
- 청킹 단위와 임베딩 사양은 무엇인가
- 각 단계는 지금 어디까지 끝났는가

> Stage 0 **안의** 텍스트→조문 재조립 메커니즘은 [[3-3_파싱_규칙]] 참조 — 여기서는
> 반복하지 않는다. DB 테이블은 [[3-5_저장소_스키마]] 참조.

## 흐름

```
원문 (XML / PDF / HWP→PDF · L3 업로드는 HWPX/HWP 직파싱)
  ├─ Stage 0    파싱·조 분해            → corpus.doc_articles
  ├─ Stage 0.5  적용대상 태깅           → corpus.chunks.적용대상
  │              절(節) 헤딩이 선언하면 상속, LLM 은 절 밖 조문만
  ├─ Stage 0.7  참조 그래프 (정규식)    → corpus.refs
  ├─ Stage 0.8  우선순위 조항           → corpus.precedence_rules
  ├─ Stage 1    룰 컴파일               → corpus.rules (docs/5_룰/)
  └─ Stage 2    청킹·헤더·임베딩·BM25   → corpus.chunks / chunk_terms
```

적용대상 태깅은 임베딩보다 먼저다 — 청크 적재 시 필드가 차 있어야 필터가 걸린다.
Stage 0.5/0.7/0.8은 서로 독립(Stage 0 산출물만 읽음), Stage 1은 Stage 0-T(표 추출)에 의존.

모든 인덱싱 경로는 `scripts/archive/eval/index_guard.py` 통과 조건을 거친다 — [[3-1_검색_범위]] 참조.

## 청킹 규칙

| 규칙 | 값 |
|---|---|
| 기본 단위 | 1 조 = 1 청크. 900토큰 초과 시 항(①②③) 단위, 항도 초과 시 호 |
| 병합 | 50자 미만 청크 → 직전에 병합 |
| 오버랩 | 없음 — 조 경계가 의미 경계 |
| 표 | 청크에 넣지 않음 → 룰 테이블 |
| 첨부(별표·별지·서식·붙임) | 청크에 넣지 않음 — 대부분 세무 서식·감독 표 |
| 범위 컷 | 모두의창업 제3편(로컬트랙)은 청크에서 제외. `doc_articles`에는 남긴다 |

임계가 문자수가 아니라 토큰수인 이유: 한국어 3,000자 ≈ 1,500~2,000토큰이라
`max_seq_length` 1024를 넘으면 조문 꼬리(단서·예외)가 임베딩에서 소실된다.

## 임베딩

| 항목 | 값 |
|---|---|
| 모델 | `nlpai-lab/KURE-v1` (1024차원, bge-m3 계열) |
| 정규화 | L2 정규화 후 저장 → 코사인 = 내적 |
| `max_seq_length` | 1024 |
| 임베딩 입력 | 컨텍스트 헤더(`[L2 \| 사업명 \| 문서 \| 장 \| 조]`, ~50토큰) + 본문 |
| 실행 | 앱 서버 CPU |

헤더는 임베딩·BM25 입력 전용 — `chunks.text`(인용 검증 대상)는 불변, 가공 금지.
사례 인덱스는 같은 모델로 Q&A 한 쌍 단위, **질문 텍스트만** 임베딩.

BM25는 형태소 분석(kiwipiepy) 결과 토큰만 DB에 적재해 SQL로 계산한다.
ANN 인덱스(HNSW/IVFFlat) 미사용 — 근사 검색의 리콜 손실이 곧 인용 누락.

`chunk_len`·`term_df`(BM25 토큰 테이블)를 안 건드려 53청크가 검색 색인에서만 빠졌다
