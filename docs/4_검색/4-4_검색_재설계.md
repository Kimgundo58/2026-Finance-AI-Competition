# 검색 재설계 — 온톨로지 우선 + 하이브리드 보충

이 문서가 답하는 질문:
- 사용자 입력이 어떻게 질의로 바뀌는가
- 온톨로지 후보와 검색 후보는 각각 무엇을 내고 어떻게 합치는가
- L3 · 실패 · 지연은 어떻게 다루는가. 지금(4-1 ~ 4-3)과 무엇이 다른가

상태: 설계안 v2.1 (2026-11-06). 구현: 모두의 창업 로컬 끝, 운영 미적용, 판정 효과 미측정(2026-11-07, `ontology/진행상황.md`). 온톨로지는 [[5-4b_온톨로지_스키마]], 조회 함수는 [[5-8_저장과_조회]], 엔드포인트는 [[5-6b_API와_화면_변경]], 측정은 [[5-9_검증과_측정]].

## 흐름

```
사용자 입력 (사용 내용 · 용도 · 금액 · 부가세 구분 · 사용일자)
  → ① 질의 변환 (LLM 1회)     품목 표현 · 세목/비목 후보(온톨로지 레이블 중에서만) · 규정 용어 질의문 · 수치
  → ② 온톨로지 후보 (코드)     노드 결정 → 적용 규범 → 근거 조문 → 준용 사슬 → 공통 규범 조문 → 경계 비목 조문 → 별지 해당 행
  → ③ 검색 후보 (코드)         BM25 + dense(KURE-v1) → RRF → 참조 확장 1단. 온톨로지 후보에 없는 조문만 남긴다
  → ④ 문맥 구성 (코드)         L3 연결 조문 → 온톨로지 후보 → L3 미연결 조문 → 검색 후보 → 중복 제거 → 글자 상한 → 문장맵(S01…) → 규범 요약문
  → 확인 질문 LLM · 판정 LLM
```

## ① 질의 변환 (query rewriting)

| 항목 | 명세 |
|---|---|
| 자리 | 지금 `/api/normalize` 의 정규화 LLM 호출(코드 이름은 `정규화` 로 남긴다). 입력 단위 캐시는 유지한다 |
| 모델 | `qwen3.8-flash`(현재 폴백 모델)를 후보로 두고 정확도 · 지연을 잰 뒤 정한다 |
| 입력 | 사용자 입력 + 사업 + 비목 · 세목 레이블과 별칭 목록(온톨로지). 용어 풀이는 넣지 않는다 |
| 출력 (JSON 스키마 고정) | 품목 표현, 세목 · 비목 후보 1~3개(레이블 목록 안에서만), 규정 용어로 바꾼 질의문(BM25 용), 수치(금액 · 부가세 구분 · 인원 · 일수 · 시간 · 계약총액), 거래처 유형 |
| 제약 | 레이블 밖 비목을 내면 버리고 사용자 확정으로 넘긴다. 호출 실패 시 판단불가(기존 규칙) |

KURE-v1 은 임베딩 모델이다. 용어 변환은 이 LLM 이 하고, KURE 는 변환된 질의문을 벡터로 바꾼다.

## ② 온톨로지 후보

1. 노드 결정: 별칭 정확 일치 → 없으면 ① 의 후보 → 화면 확정값(필수)
2. 적용 규범: 대상 노드 + 상위 노드(상속) + 공통(`비목:창업/*`) → 우선순위 규범으로 정리
3. 근거 조문: 규범의 근거(조 · 항) + 준용 사슬(깊이 3) + 별지 해당 행
4. 경계 보충: 대상 비목과 공통 서로소인 이웃 비목의 경계 규범 조문. 분류 오류에 대비한다(모두의 창업에는 서로소 공리가 없어 지침 것만 쓴다)
5. 출력: 조문 목록 + 경로(왜 들어왔는지). 경로는 화면 "근거 경로" 와 측정의 놓친 유형 분류에 쓴다

규범이 없는 대상(위임만 있는 창업활동자금 등)은 빈 후보가 정상이다. 조회 오류는 판단불가다.

## ③ 검색 후보

| 항목 | 명세 |
|---|---|
| 질의 | ① 의 규정 용어 질의문(BM25) · 같은 문장의 KURE 벡터(dense) |
| 범위 | 지금 FILTER 그대로(`retrieve.py:26-28`: `embedding IS NOT NULL` · active · `parse_quality='high'` · 검색대상 · L1/L2 · 적용대상 창업기업/공통) + 사업 필터. BM25 도 같은 FILTER 다(`:51`). 통과 청크 1,270개(로컬) |
| 결합 | RRF, 상위 10(지금 질문 생성은 5). 참조 확장은 1단 |
| 역할 | 온톨로지 후보가 놓친 것(분류가 틀렸을 때, 규범이 없는 조문)을 보충한다. dense 를 없애지 않는다. 실제 질문 자료로 다시 잰다 |

## ④ 문맥 구성 (context assembly)

- 우선순위: L3 연결 조문 → 규범 발췌 → 대상 세목의 근거 조 전체 → 준용 깊이 1 → L3 미연결 조문 전부 → 준용 깊이 2~3 → 검색 후보. 같은 조 · 항은 한 번만
- 글자 상한 60,000(`ontology_context.글자_상한`, 2026-11-11 40,000 에서 올림: 모두의 창업 기관 L3 + 창업활동비 문맥 최대 55,524자). 넘으면 뒤에서부터 뺀다. L3 미연결 조문까지 못 넣으면 판단불가 + 화면 안내(결정 대기 6, [[5-3_룰_온톨로지_설계]])
- 문장맵(S01…)과 규범 요약문(B4)은 코드가 만든다. LLM 재랭킹은 넣지 않는다(호출 수 고정, 효과 미측정)
- 한 조문이 여러 경로로 들어오면 경로를 합쳐 둔다

## L3

| 시점 | 동작 |
|---|---|
| 업로드 때 | 파싱 → 조문 → 연결 초안(LLM, 50조씩) → 화면 확인 → `concept_ids` 저장 ([[5-6b_API와_화면_변경]]) |
| 판정 때 | 연결된 조문 중 대상 비목 · 세목 · 공통만 우선 넣고, 미연결 조문(`NULL`)은 전부 넣는다(놓치지 않기). 확인 전 문서는 전부 넣는다 |
| 지금 | 판정 프롬프트는 L3 전체(`assemble_context.py` B1 블록), 질문 생성만 12,000자에서 자른다(`question_generate.py`). 재설계는 둘 다 ④ 규칙 |
| 교체 | HEAD 에 구현돼 있다(커밋 07f9407). 운영 반영 여부는 P4-5 에서 확인 |
| 너무 길 때 (2026-11-06 결정) | 안 A 로 시작: 판단불가 + "연결 확인" 안내. 안 B(사용자 제안): 미연결 조문이 상한을 넘을 때만 **선택 전용 LLM 호출 1회**를 더해 관련 조문 ID 만 고르게 한다(본문을 고쳐 쓰지 않으므로 인용은 원문 그대로). 호출 수는 그 경우에만 3 → 4. 켜는 조건: 「2026 모두의 창업 2차 1R 진출자 지원 안내 책자」(34쪽)를 테스트 L3 로 올려 놓침률(정답 조문 중 선택에서 빠진 비율)을 재고 사용자가 승인 |

## 지금과의 차이

| 지금 | 재설계 |
|---|---|
| 정규화 LLM 이 비목 추천(규정 안 봄) → 검색(RRF, 상위 5) → 참조 확장 | 질의 변환 LLM 이 온톨로지 레이블 안에서 고름 → 온톨로지 후보 + 검색 후보(상위 10) |
| 룰 근거 + 공통 조문(`조문_후보()`)은 질문 생성에만 | 같은 후보 집합을 질문 생성과 판정이 함께 쓴다 |
| 검색은 FILTER 통과 1,270청크만 봄 | 범위는 유지. 넓힐지는 측정 뒤 |
| L3 통째 주입 | 연결 조문 우선, 미연결 전부 |

## 지연 예산 (목표, 미측정)

변환 LLM ≤ 3초 · 온톨로지 후보 ≤ 0.1초 · 검색 후보 ≤ 0.8초(모델 상주) · 구성 ≤ 0.1초. 서버 한도 180초.
