# 검색 규약

이 문서가 답하는 질문:
- L3는 왜 검색하지 않고 전체를 읽는가
- L1·L2 검색 전에 무엇을 먼저 걸러내는가
- 두 검색기(dense/BM25)는 어떻게 합쳐지는가

> 이 문서는 **현재 확정된 규칙**만 적는다.

## L3 — 검색하지 않고 전체 로드

```sql
SELECT 조번호, 조제목, 본문
  FROM tenant.l3_articles
 WHERE org_id = :org AND 장 IN (:사업비관련장)
 ORDER BY 조순번;
```

L3 조항(30~80개)을 수천 개짜리 풀과 경쟁시키면 순위에서 밀려 선택되지 않을 수 있다 — 경쟁 자체를
없앤다. 전문이 아니라 사업비 집행 관련 장만 넣는다(소형 모델 컨텍스트 예산).

## L1·L2 — pre-filter가 검색보다 먼저

```sql
WHERE status = 'active'
  AND parse_quality = 'high'
  AND retrieval_scope = '검색대상'
  AND layer IN ('L1','L2')
  AND 적용대상 IN ('창업기업','공통')      -- NULL 은 통과하지 못한다
  AND (사업명 IS NULL OR :사업 = ANY(사업명))
```

`적용대상`은 적재 시점에 NULL이 남아 있으면 안 된다. SQL의 `NULL`은 `IN`을
통과하지 못해 비워 둔 조가 조용히 검색에서 사라진다. 태깅 대상 밖(주체 구분이
없는 규정)과 부칙·붙임의 기본값은 `공통`이다 — `null`이 아니다.

`retrieval_scope`: 직접 검색 대상(`검색대상`)과 참조 확장으로만 컨텍스트에 들어가는 문서(`참조확장전용`)를 구분한다.
기준은 "이 돈 써도 되나요의 답이 그 문서 안에 문장으로 적혀 있는가" — 적혀 있으면
`검색대상`, 정의·절차만 제공하면 `참조확장전용`. 부처 메타데이터로 구분하지 않는다.

`retrieval_scope`는 `documents`와 `chunks` 양쪽에 있고, 검색 필터는 청크 쪽을
읽는다. 174건이 다른데, 불일치 오류가 아니라 붙임·별표·참고 계열 청크만 골라 의도적으로
`참조확장전용`으로 바꾼 것이다 — 후보 풀을 셀 때는 반드시 `corpus.chunks.retrieval_scope` 기준.

## RRF 결합

```python
K = 60
def rrf(dense_ranked, sparse_ranked, w_dense=0.9, w_sparse=0.1):
    score = defaultdict(float)
    for rank, cid in enumerate(dense_ranked, 1):
        score[cid] += w_dense / (K + rank)
    for rank, cid in enumerate(sparse_ranked, 1):
        score[cid] += w_sparse / (K + rank)
    return sorted(score, key=score.get, reverse=True)[:5]
```

임베딩 코사인 top-50 + BM25 top-50 → RRF → **top-5**(L3가 별도 유입되므로 8이 아니라 5).
**RRF 가중을 바꾸지 말 것** — 병목은 랭킹이 아니라 필터에서 제외된 조항(제품 정의 결정, 미결 목록 참조).

게이트 B(검색결과 없음): 골든셋 74문항에서 hit/miss 의 dense 최고유사도 분포가 겹쳐 **분리 임계가
존재하지 않는다**(2026-09-01 실측). 그래서 임계는 `0.0` 으로 확정했고(`SUDDOE_RETRIEVAL_MIN_SIMILARITY`),
게이트 B 는 top-5 가 0건일 때만 즉시 판단불가를 반환한다(예외: L3 상위 규정 확인).
`scripts/orchestrate.py` 상단 주석이 근거다.
