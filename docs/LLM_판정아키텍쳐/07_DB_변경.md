# 07. DB 변경

이 문서가 답하는 질문:
- 어떤 컬럼과 제약이 바뀌는가
- 어떤 데이터를 고치는가

파일: `db/migrations/2026-11-04_확인질문.sql`. 멱등으로 쓰고 `db/init/` 도 같이 고친다. 질문 자체는 저장 테이블을 새로 만들지 않고 응답 캐시에 둔다.

## 스키마

| 대상 | 변경 | 왜 |
|---|---|---|
| `tenant.judge_cache` `종류` CHECK | `questions` 추가 (`db/init/13_judge_cache.sql:23`) | 질문세트를 저장한다 |
| `tenant.decisions` | `"사용자답변" jsonb NOT NULL DEFAULT '[]'` 추가 | 결과 화면과 계획 재열람, 감사 |
| `decisions_검증코드_check` | `ANSWER_UNCONFIRMED` 추가 | 새 하향 코드 |

`suddoe_app` 권한은 테이블 단위로 이미 있어 추가하지 않는다. 적용 후 `suddoe_app` 으로 INSERT 를 한 번 확인한다.

## 데이터: `corpus.refs` 5행

`scripts/build_refs.py` 의 조문 대응표가 13차 지침 「제40조」를 14차 제37조(재료비)로 잘못 옮겼다. 13차 제40조는 여비이고 14차에서는 제43조다.

| 출처 (로컬 ref id) | 지금 | 고친 뒤 | 근거 |
|---|---|---|---|
| 13차 조번호로 쓴 문서 4행 (207611, 207883, 207946, 208119) | 14차 제37조 | 14차 제43조 | 원문이 여비를 말한다 |
| 초격차 제10차 참고2 1행 (208001) | 14차 제37조 | 14차 제40조, `resolved` | 14차 조번호로 쓴 표다. 같은 표가 여비를 「지침 제43조」로 적는다 |

- ID 를 직접 쓰지 않는다. 운영과 로컬의 id 가 다를 수 있어 원문 표기와 대상 조문으로 찾는다.
- 적용 전후 행 수를 찍고 5행(또는 이미 적용된 0행)이 아니면 `RAISE EXCEPTION` 으로 멈춘다. 운영 행 수는 적용 전에 따로 확인한다.
- 같은 대응표의 제13차 제39·41·42조도 조문과 맞지 않는 것으로 보인다. 이번에 고치지 않고 백로그에 둔다.
- 재적재해도 잘못되지 않게 `build_refs.py` 대응표를 함께 고친다. `_refs.json` 은 그대로다.

## 적용 순서

코드보다 먼저 적용한다. 새 코드가 `사용자답변` 컬럼을 쓰기 때문이다. 옛 코드는 이 컬럼을 몰라도 동작하고, CHECK 추가는 옛 코드에 영향이 없다. **api 를 멈추지 않는다.**

`db/migrations/` 가 바뀌면 자동 배포가 멈춘다. 적용 후 `./deploy.sh --force` 를 실행한다(`docs/8_운영/8-8_CI_CD.md`).

## 검증

- 임시 컨테이너에서 `db/init` 전체 → 마이그레이션 → 다시 한 번 실행(멱등).
- `db/init` 만으로 만든 DB 와 마이그레이션을 적용한 DB 의 컬럼·제약이 같은지 확인.
- 로컬 개발 DB 에는 임시 컨테이너 확인 뒤에 적용한다. `suddoe_pgdata` 볼륨은 지우지 않는다.
