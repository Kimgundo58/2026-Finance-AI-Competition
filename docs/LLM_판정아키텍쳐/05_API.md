# 05. API 변경

이 문서가 답하는 질문:
- `/api/questions` 의 요청·응답·실패 처리는 무엇인가
- `/api/judge` 에서 무엇이 바뀌는가

## 화면이 받는 것

질문 화면은 `질문문`, `이유`, `선택지` 를 그대로 그린다. 「규정 원문 보기」는 `근거` 를 쓴다. 문서 이름은 프론트의 `문서명보기()` 로 바꾼다(L3 는 서버가 이미 파일 이름을 준다). 실패해도 HTTP 200 이고 `질문` 이 비어 있으면 화면은 바로 결과로 넘어간다.

## `POST /api/questions` (신규, `server/routes_questions.py`)

요청

설계 예시 (미구현)
```json
{"사업명": "예비창업패키지", "확정비목": "여비", "세부유형": null,
 "품목": "부산 출장 KTX 왕복", "금액": 120000, "용도": "거래처 미팅",
 "질문원문": "KTX 왕복 12만원 써도 되나요?"}
```

응답

설계 예시 (미구현)
```json
{"상태": "있음", "질문세트": "ab12…",
 "질문": [{"id": "Q1", "질문문": "…인가요?", "이유": "…로 한정돼요.",
           "선택지": [{"라벨": "예", "값": "예"}, {"라벨": "아니오", "값": "아니오"},
                     {"라벨": "모르겠어요", "값": "모름"}],
           "근거": {"doc_id": "…", "조번호": "제43조", "조제목": "여비", "항호": "③", "원문": "…"}}]}
```

| `상태` | 뜻 | 화면 |
|---|---|---|
| 있음 | 질문 1개 이상 | 질문 화면 |
| 없음 | LLM 이 물을 것이 없다고 했거나 모두 검사에서 빠졌다 | 바로 결과 |
| 바로판정 | 금지 항목이거나 근거 없음(LLM 호출 안 함) | 바로 결과 |
| 실패 | DB·LLM 오류 또는 요청 한도 | 바로 결과 |

처리 순서:
1. 비목·사업명 표준화. 비목이 10종 밖이거나 등록되지 않은 사업명이면 422. 사업 목록을 못 읽으면(DB 장애) `상태:"실패"`.
   비목 없이 온 요청(새 화면, JSON 이어도)은 조사 세션 경로로 가 서버가 품목 → 세목 → 비목으로 정하고 응답 `분류`({비목, 세목, 표시문, 품목}) · `분류안내` 로 알린다(v045). 화면은 그 비목 · 세목을 판정 요청의 `확정비목` · `확정세목` 으로 보내고, 판정 결과 `분류.표시문` 을 결과 화면에 보인다. 계약 전체: 루트 `프론트_정렬_수정목록.md` 8-2.
   조사 답은 후보마다 `맞아요` | `직접입력`(정정 필수)이고 모든 후보에 답해야 한다(아니면 400, `research_sessions._답_결합`). 사용자가 쓴 품목 설명(조사 · 재조사 답 중 제품성격 후보의 정정 · 품목설명)은 분류 LLM 을 부르기 전에 LLM 1회로 {품목, 성격, 설명, 용도} JSON 으로 바꿔 `<확인한정보>` 에 넣는다(v047, `item_classify.설명_반영`, 실패하면 문장 그대로, 세션 `설명정리` 에 둬 같은 문장은 한 번). 다른 유형의 정정은 그대로 넣고, 넣는 글은 모두 `이스케이프` 한다. 질문 · 판정 프롬프트의 사용자 진술은 쓴 문장 그대로다.
   맞는 분류가 없으면 `상태:"분류없음"` 에 `다음행동` 을 싣는다(v048, `routes_questions._분류없음_다음`): 재조사를 아직 안 했으면 ③-R 재조사 한 번(`_재조사`, 분류 LLM 의 `필요정보` 가 조사 목적, ④-2 몫 120초를 남길 때만 최대 60초) → 찾으면 `재조사확인` + `재조사.후보`, 못 찾음 · 실패 · 시간 부족이면 설명을 받은 적 없을 때 `설명입력`, 있으면 `판정`. DB · LLM 장애는 재조사 없이 `다시시도`. 재조사 후보에 답하지 않고 새 `품목설명` 만 오면 400.
2. MOCK 이면 `server/selftest.py` 의 `mock_질문`. `SUDDOE_JUDGE_ANSWERS=0` 이면 `상태:"없음"`. 답을 쓰지 않을 때는 묻지 않는다.
3. 입력 해시로 `질문세트_조회()`. 적중하면 저장값을 `질문_공개()` 로 바꿔 돌려준다. `조회()` 는 쓰지 않는다. 아직 카운트를 올리지 않아 되돌릴 것이 없다.
4. `제한.통과()` 를 부른다. 막히면 `상태:"실패"` 로 200 을 돌려준다. 판정 요청이 자기 한도 오류를 낸다.
5. `question_generate.질문생성()` 을 부른다. LLM 응답을 받지 못했으면 일일 카운트를 되돌린다. 실패가 아니면 응답 캐시에 저장한다. **키가 곧 `질문세트` 다.** 질문이 있는데 저장에 실패하면 `상태:"실패"` 로 답한다. 답을 받아도 판정에서 질문을 찾지 못하기 때문이다.

캐시 키 조각: `"questions", org, account, 사업명, 비목, 세부유형, 품목, 금액, 용도, 질문원문, l3_해시(org)`.

한도: 판정과 같은 일일 한도와 IP 시간당 한도를 쓴다. 새 지출 1건이 정규화·질문·판정으로 3건을 쓰므로 기본 IP 한도 60건/시간이면 약 20건이다.

## 응답 캐시 변경 (`server/response_cache.py`)

- `저장(..., ttl초=None)`: `questions` 는 24시간 둔다. 질문 화면을 띄워 놓고 오래 있어도 답변이 사라지지 않게 한다. 메모리 캐시 항목에도 만료 시각을 넣는다.
- `질문세트_조회(k, org, account)` 를 더한다. `조회()` 와 달리 **`제한.카운트_복원()` 을 부르지 않는다.** 판정 요청 안에서 부르는 조회라 일일 카운트를 되돌리면 안 된다.
- `tenant.judge_cache.종류` CHECK 에 `questions` 를 더한다([[07_DB_변경]]).

## `POST /api/judge` 변경

- `판정요청` 에 `질문세트: str | None` 추가. `답변` 은 `[{code:"Q1", 값:"예"}]` 그대로.
- 캐시 키에 `질문세트` 를 더한다(`답변` 은 이미 들어 있다).
- 라우트가 `질문세트_조회` → `답변_구성` 으로 사용자답변을 만들어 `orchestrate.판정(사용자답변=)` 으로 넘긴다. 미들웨어 컨텍스트가 있는 라우트 안에서 읽는다.
- `질문세트` 가 왔는데 저장값을 못 읽으면(만료·재시작·DB 오류) `답변유실=True` 로 판정한다. 사용자가 「아니오」라고 답했을 수 있으므로 「가능」을 내지 않는다([[06_판정_반영]]). 화면에는 오류를 내지 않는다.
- `정규화` 안의 `심층질문` 은 판정 전에 뺀다. 저장 질문 목록이 판정 프롬프트 B6 에 들어가지 않게 한다.
- 응답에 `사용자답변: [{질문문, 답}]` 을 더한다. `충족답`·`근거조문`·`할일` 은 내보내지 않는다. `GET /api/plans/{id}` 도 같은 키를 돌려준다.

자세한 판정 변경은 [[06_판정_반영]].

## `POST /api/normalize` 변경

프론트 배포 뒤 `심층질문` 을 뺀다. 옛 프론트가 쓰는 동안 남긴다.

## 환경변수

`.env.example` 과 `deploy/ncp/docker-compose.yml` `api.environment` 에 모두 넣는다. 이 목록에 없으면 컨테이너에 들어가지 않는다.

| 변수 | 기본 | 뜻 |
|---|---|---|
| `SUDDOE_QUESTION_MODEL` | 비면 `SUDDOE_QWEN_MODEL` | 질문 작성 모델. [[10_측정_결과]] 로 정한다 |
| `SUDDOE_QUESTION_TIMEOUT` | 20 | 질문 LLM 제한 시간(초). 프론트 대기 25초보다 짧게 둔다 |
| `SUDDOE_JUDGE_ANSWERS` | 1 | 0 이면 질문을 내지 않고 답변도 판정에 넣지 않는다 |
