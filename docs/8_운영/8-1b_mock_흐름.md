# 8-1b mock 서버로 새 점검 흐름 눌러 보기

`SUDDOE_MOCK=1` 로 띄운 서버는 실제 검색 · LLM · DB 없이 새 지출 계획 화면(`프론트_정렬_수정목록.md` 2-1절)의
가지를 끝까지 돌려준다. 프론트 dev 서버(`localhost:3000`)가 이 서버(`localhost:8080`)를 본다. CORS 는 `localhost:3000` 을 늘 허용한다(`server/main.py` `allow_origin_regex`).

```powershell
$env:PYTHONIOENCODING = 'utf-8'; $env:SUDDOE_MOCK = '1'
uvicorn server.main:app --port 8080
```

## 화면에서 하는 것

지출 항목 칸에 아래 낱말을 넣으면(한 문장 입력이면 문장 안에) 그 가지가 나온다. 낱말이 없으면 기본 가지다.
낱말은 `server/mock_flow.py` `가지_낱말` 이 기준이다. 진행 줄은 0.4초 간격으로 쌓인다(`mock_flow.지연초`).

| 낱말 | 화면에서 보이는 것 | 서버 응답 순서 |
|---|---|---|
| (없음) | 검색 줄 → 품목 확인 카드 → 분류 안내 + 질문 1개 · 인원 칸 → 결과 가능 | ① 조사확인 → ② 분류됨 · 상태 있음 |
| 별칭 | 검색 없이 분류 안내 + 질문 | normalize `품목확인.별칭일치` true → 웹조사 false 한 번에 분류됨 |
| 검색실패 | 「공개 정보를 확인하지 못했어요」 줄 → 한 문장 설명 칸만 | ① `조사.상태` 실패 · 후보 없음 → ② 설명 있든 없든 분류됨 |
| 재조사 | 「품목을 더 알아보고 있어요.」 → 품목 확인 카드가 새 내용으로 다시 → 분류됨 | ② 분류없음 · 재조사확인 + `재조사.후보` → ③ `재조사답변` 넣으면 분류됨 |
| 설명필요 | 「품목을 더 알아보고 있어요.」 → 「더 찾은 품목 정보는 없어요.」 → 「품목 설명을 직접 입력해 주시면 다시 찾아볼게요」 + 설명 칸 → 분류됨 | ② 재조사(못 찾음) 뒤 분류없음 · 설명입력 → `품목설명` 넣은 ② 에서 분류됨 |
| 분류장애 | 「지금은 분류를 확인하지 못했어요」 + [다시 시도] → 분류됨 | ② 분류없음 · 다시시도 → 같은 요청 다시 보내면 분류됨 |
| 분류끝내없음 | 재조사 카드 → 설명 칸 → 분류 없이 판정 → 결과 확인 필요 + 문의 초안 | ② 재조사확인 → ③(`재조사답변`) 설명입력 → ②(`조사답변` + `품목설명`, 재조사답변 없음) 판정(분류 null) |
| 처리실패 | 「확인할 내용을 받지 못했어요」 + 다시 요청 → 분류됨 | ② 상태 실패 · 분류 키 없음 · `조사.상태` 실패 → 다시 보내면 분류됨 |
| 질문없음 | 분류 안내만 보이고 멈추지 않고 판정 | ② 분류됨 · 상태 바로판정 · 질문 0 · 추가입력 0 |
| 입력칸만 | 질문 없이 인원 입력 칸만 있는 추가 확인 화면 | ② 분류됨 · 질문 0 · 추가입력 1 |
| 옛경로 | 옛 비목 고르기 단계(TIPS 같은 옛 경로 사업) | normalize 에 `품목확인` · `분류후보` 없음, `비목후보` 2개 → 고른 비목으로 질문 · 판정 |

- 「분류장애」 · 「처리실패」 는 조사ID 마다 처음 한 번만 실패한다(다시 시도 화면 확인용). 서버를 다시 켜면 처음부터 다시 실패한다.
- 「재조사」 · 「분류끝내없음」 에서 재조사 카드를 [직접 입력하기] 로 답하면 설명을 받은 것으로 본다(분류끝내없음은 바로 판정으로 간다).
- 재조사 여부 · 「설명을 받았다」 는 조사 세션으로 본다. `재조사답변` · `품목설명` 은 한 번 보내면 세션에 남아 다음 요청이 빼고 보내도
  되고, 같은 값을 다시 보내도 같은 결과다. 재조사는 조사ID 마다 한 번이다(`세션.재조사` 가 있으면 다시 하지 않는다).
- 재조사 후보에 답하지 않고 새 `품목설명` 만 보내면 조사 답과 같은 규칙으로 받지 않는다(JSON 400, SSE 는 요청 처리 실패). 후보가 0개면 검사하지 않는다.
  그래서 후보에 답하지 않은 채 ② 답만 바꿔 다시 분류해도 없으면 설명입력 대신 저장된 후보로 재조사확인 을 다시 낸다(재조사는 다시 안 함).
  진행 줄 문장(「품목을 더 알아보고 있어요.」 → 「품목 정보를 더 찾았어요.」 | 「더 찾은 품목 정보는 없어요.」)도 실제 경로와 같다.
  실제 경로(v048 `routes_questions._분류없음_다음` · `_재조사`)도 같은 순서 · 같은 응답 모양 · 같은 안내 문장이다.
- 재조사로 확인한 정보는 판정 결과 `조사.확인한정보` 에 ② 확인 답과 같은 모양으로 들어간다(결과 화면 「검색해 확인한 공개 정보」).
- 거래처 칸을 채우면 품목 확인 카드에 판매자 · 업체 이용 조건 카드가 더 나온다.
- 한 문장 입력: 문장 전체가 지출 항목, 「30만원」 같은 금액만 뽑고 사용 목적은 「사업 운영에 사용」 으로 채운다.
  거래처는 문장에 「거래처: 쿠팡」 처럼 적었을 때만 나온다(없으면 null).

## 결과 화면(판정 mock)

`/api/judge?mock=가능|확인 필요|불가|근거부족` 으로 고른다(근거부족 = 문의 초안이 붙는 확인 필요). `?mock=` 이 없거나 모르는 값이면
비목이 있는 요청은 가능, 비목 없이 온 요청(분류를 끝내 못 찾음)은 근거부족이다. 비목 없이 온 요청은 `?mock=가능` 이어도 근거부족이다. 결과의 `분류` 는 질문 단계에서 서버가 정한 분류(없으면 null)다.

## 서버 쪽 연결 (외부 호출 0)

```
POST /api/normalize   routes_normalize → mock_flow.정규화(body)
POST /api/questions   routes_questions.작업
   ① 웹조사 true · 조사답변 없음 → mock_flow.품목조사(품목, 거래처)        (web_research.research 대신)
   ② ③ 조사답변 · 재조사답변 · 품목설명 → research_sessions.재조사_답변 → 세션.재조사확인 · 세션.품목설명
        → 재조사_붙이기(확인한정보 에 합침) · 설명_붙이기 → 답변키
        _분류 → mock_flow.분류(body, 조사확인, 조사ID, 재조사함, 대기재조사) (item_classify 대신, 재조사함 = 세션.재조사 있음,
                                                                          대기재조사 = 답 없는 재조사 후보)
        분류됨 → mock_flow.판정조사(비목) 진행 줄                          (④-2 판정용 조사 대신)
             → _기존_질문 → mock_flow.질문(품목)                          (question_generate 대신)
POST /api/judge       routes_judge MOCK 분기 → mock_판정[?mock= | 비목 없으면 근거부족]
                      답변_검증 이 세션.품목설명 · 세션.재조사확인 으로 답변키를 다시 만든다
```

검사: `SUDDOE_MOCK=1 python -m server.selftest` 의 「새 점검 흐름 mock — 가지별」 구역이 위 가지마다 응답 모양을 본다.
