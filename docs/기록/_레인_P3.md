## 3. 항호 문법 — 「안 벗어나는 안」 채택 (ai-e8 승인)

**행 분해는 프롬프트 텍스트에서만 하고 s맵의 항호는 article 갈래 그대로 `None` 을 유지한다.**
`llm_validate`(P1) · `eval_e2e`(P4) · `server/main.py` 변경 0줄. 코드에서 확인한 근거 셋:

1. `_항_추출(본문, None)` → `(본문, "조전체")`. 이 표들이 **이미** 그 경로다 → 인용 원문 치환이 현행과 바이트 동일
2. `CITE_HANG_MISMATCH` 는 `항호_DB and 항호` 둘 다 참일 때만 깎는데 `s번호_메타` 가 article 을 `항호_DB=None`
   으로 세운다(`llm_validate.py:150`) → 행이 늘어도 새로 울릴 수 없다
3. 등급·판정 로직에 인용 **개수** 기반 규칙이 없다(전부 any/all) → 같은 표의 여러 행을 인용해도 부작용 없음

ai-2c(P1) 확인(2026-09-03): 오늘 `_항_추출`·`s번호_메타` 를 한 줄도 안 고쳤으므로 근거 1·2 는 유효하다.
🔴 ai-2c 가 보탠 검사 항목 하나 — `신뢰등급` 은 `any(extraction=='vlm')` 이라 **개수는 무관하지만
「vlm 문서가 인용에 처음 들어오는가」는 바뀔 수 있다.** 같은 조를 쪼개기만 하면 문서 집합이 안 변해 무해하나,
**전/후 인용 doc 집합이 같은지 ROWSPLIT 구현 뒤에 확인해야 한다** (아직 미확인 · §5 에 포함).

이 제약은 **양쪽 기록에 대칭으로 박혀 있다** — [[_레인_P1]] §3-b 「내 파일에 걸린 외부 제약」에 안 A 의 근거
1·2 와 vlm 단서가 적혀 있고, 다음 P1 세션이 `_항_추출`·`s번호_메타` 를 고치기 **전에 P3 에 알린다**가 명시돼 있다.
한쪽에만 있으면 다음 사람이 못 찾는다(ai-2c 제안, 2026-09-03).

🔴 **버린 중간안이 이 결정의 핵심이다.** 행 시작 문자열을 지금 문법 그대로 항호에 넣으면 `본문.find()` 는
맞게 서지만 끝을 `_항마커`(①~⑳)로만 잡는데 표엔 그 마커가 없다 → **끝이 조문 끝까지 흘러서 범위를 「항」이라
적으면서 실제로는 여러 행을 담는다.** 조용히 절반만 성공하는 경로라 배제했다.
문법을 넓히는 안(안 B)은 인용 원문이 달라져 run 191 과의 기준선 비교가 끊긴다 — 이득을 수로 보일 때만 연다.

## 4. 코드 변경 — 블록 경계 정의 한 곳 (완료 · 부작용 없음)

`scripts/assemble_context.py` 에 순수 함수 3개를 추가했다. **`조립()` 은 한 글자도 안 바뀌었다.**
P3 의 측정표와 P4 의 `eval.runs` 가 같은 숫자를 쓰게 하려는 것이다(ai-e8 지시: 정의가 둘이면 안 맞는다).

```
블록분해(프롬프트) -> {블록: 원문}   블록자수(...) -> {블록: 문자수}   블록해시(...) -> {블록: sha1 12자}
```

경계 규칙 = 줄머리 `## B<숫자>.` 매치 시작 위치 · B0 은 첫 매치 앞 전부 · 사이의 `\n\n` 은 **앞 블록**에 든다 ·
같은 이름 두 번이면 합산(V3 이 B4 를 앞으로 옮긴다) · 자수는 문자 수(바이트도 토큰도 아니다) ·
🔴 값들의 합 == `len(프롬프트)` 가 항상 성립한다 → **부르는 쪽에서 검산으로 쓴다.**
정의를 ai-e6(P4)에 보냈고, 내 하네스도 이 함수를 부르도록 바꿔 재실행해 **같은 표가 나오는 것을 확인**했다.

프롬프트를 잡는 자리: orchestrate 가 `from assemble_context import 조립` 로 이름을 들여왔으므로
**`orchestrate.조립` 을 감싸야** 잡힌다. `assemble_context.조립` 을 갈면 안 잡힌다.

## 5. 다음 한 걸음 (다음 세션이 여기서 이어받는다)

1. **ROWSPLIT 앵커 구현** — `SUDDOE_B3_ROWSPLIT=1` (기본 off). 앵커 후보 넷:
   ① 반복 머리글 `비 목 주요 내용` ② 페이지 꼬리 `- N -` ③ 비목 어휘 사전 31종 ④ `※`·`-` 항목 머리.
   🔴 **넷으로 못 자르면 자르지 않고 통째 1항으로 둔다**(ai-e8 강한 승인: 「반쯤 자른 표는 안 자른 표보다 나쁘다」).
   별표 갈래는 괘선(`┠─`)이 있어 훨씬 쉽지만 12/98뿐이라 우선순위가 아니다.
2. **DEDUP** — `SUDDOE_B3_DEDUP=1` (기본 off). 같은 비목 해설표류 다중 적중 시 질문 사업 우선, 없으면 RRF 상위 1개.
   🔴 **가드를 바꿨다**(ai-e8 승인): `eval_e2e` 의 근거적중은 **top5 청크**만 보므로 B3 를 잘라도 안 움직인다 —
   가드로 못 쓴다. 대신 「정답 근거 좌표가 B3 폐포에 남아 있나」를 하네스에서 따로 센다.
3. **플래그 off 에서 93문항 조립 출력이 바이트 단위로 현행과 같음을 증명** (생략 불가 · `블록해시` 로 잰다).
   같은 자리에서 **ROWSPLIT on 의 전/후 인용 doc 집합이 같은지**도 센다 — 집합이 늘면 `VLM_DOWNGRADE` 가
   새로 울릴 수 있다(ai-2c 지적, §3).
4. 전/후 표 + `docs/9-3` 프롬프트 병목 절 갱신안. 판정 효과는 P4 가 잰다.

- **행 분해가 판정을 좋게 하는지는 아직 «가정»이다.** 이 레인이 낸 것은 전부 프롬프트 쪽 실측이고,
  「S번호가 조준되면 인용적중·일치율이 오른다」는 P4 의 GPU run 전에는 증거가 없다. 순증 b−c 로 재야 한다.
- 붙임2 를 검색 진입점에서 빼는 것과의 충돌(hit@5 55.4→60.8)은 **여전히 아무도 안 정했다.** P3 은 그 충돌을
  건드리지 않고 크기만 다뤘다 — 진입점은 그대로다.
- 표 고유 16종 중 상위 4종 밖 12종을 아직 눈으로 안 봤다. 앵커가 그쪽에서도 서는지는 미확인.
- 별표(괘선 갈래)에 행 분해를 넣을 값이 있는지 — 12/98 이라 지금은 안 넣기로 했을 뿐, 재지는 않았다.
