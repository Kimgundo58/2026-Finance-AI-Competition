### 강등코드 기준을 DB CHECK 로 옮겼다 (P1 권고)

소스 훑기는 `SUDDOE_GATE_B` 같은 환경변수 이름도 같은 그물에 걸린다 — 거르는 접두어 목록
자체가 손으로 적은 것이라 또 낡는다. `tenant.decisions` 의 CHECK 는 선언적이고, 거기 없는
코드는 애초에 저장이 안 되니 그게 진짜 경계다. 소스 훑기는 대조 닻으로만 남기고 **양쪽
차집합을 run 이 찍는다**(오늘 실측 CHECK 22 · 소스 22 · 차집합 양방향 0).

🔴 **「원리적으로 못 태우는」 코드는 2종이 아니라 3종이다** (P1 정정, 받는다).
`PRECEDENCE_FLIP` · `TENANT_LEAK` · `L3_ONLY_DOWNGRADE` — 셋째는 조건이
「판정=='가능' and 인용층 all=='L3'」라 L3 0/93 에서는 참이 될 수 없다.
**L3 를 지키는 방어 코드 셋이 전부 정답셋 밖에 있다.** 제품의 축인데 한 번도 안 울렸고
정답셋으로는 앞으로도 못 울린다.

### P2 의 「가능」 표본 — 13 에서 12 로 줄였다 (`P2_선택12`)

P2 가 준 13건을 DB 로 재확인하니 13/13 정답=가능이었는데, **본세트 1건(g338)이
`미사용41`(held-out) 이었다.** 물어봤고 ai-e8 이 제외로 확정했다 — held-out 은 튜닝에 안 쓴다.
`P2_선택12`(잃은8 + 대조4)로 다시 박았고, 12건이 **전부 튜닝52** 임을 DB 로 확인했다.

🔴 **이 표본의 해석이 두 번 바뀌었다. 최종은 이것이다.**
- 「조건 명시 때문에 새는 문항」이 **아니다.** ai-a3 독립 분류로 그 축은 손실을 못 가른다 —
  조건을 «안» 적은 쪽의 조건부 비율이 오히려 높았다(75% vs 66.7%). 그 라벨을 붙이지 마라
- **12건이 100% 튜닝52 다.** (ㄱ)이라는 성질이 튜닝 세트의 성질과 겹친다 —
  여기서 얻은 이득은 「문체 밖에서 선다」는 증거가 아니다. **수를 옮길 때 이 문장을 같이 옮긴다**
- g338 은 held-out41 정규 집계 안에 그냥 둔다. 「held-out 검증 1건」으로 떼지도 않는다 — n=1

유보를 파일에만 두면 표에서 사라지므로 `_부분집합()` 이 `설정.부분집합_유보` 로 나르고,
run 시작에도 찍는다.
