### 판단 — 고친 오류 4개

**① 이상치 하나가 문서 전체를 1단으로 오판시켰다.**
`is_two_column()` 이 "전 표본이 median ±20pt" 를 요구했다.
실측 거터: 0쪽 x372(표지) / 1~5쪽 x421 / 6~8쪽 x418~423.
0쪽 하나 때문에 예비·초기창업이 1단으로 판정됐다.
-> median 근처 **과반**이면 2단으로 본다.

**② 문서 대표 거터로 일괄 자르면 표지에서 글자를 가른다.**
"2단인가" 는 문서 단위, **자르는 위치는 페이지별** 거터로 분리했다.
거터가 없는 페이지(전면 표)는 자르지 않는다 — 표를 반토막 내는 것보다 낫다.

**③ `return left + "
" + right` 의 `
` 이 파일 기록 시 실제 개행으로 치환됐다.**
구문 오류가 났다. `NL = chr(10)` 상수로 우회하고 주석을 남겼다.

**④ 인용을 조 헤딩으로 오인했다.**
`제30조(권리 의무 이전) ① … 지침 **제65조(권리 의무 이전)** 에 따른다` 에서
제65조가 34번째 조로 잡혀 뒤를 전부 삼켰다(본문 7,220자).
`stage0_articles._is_citation()` 신설 — 매치 앞 14자에 규범어
(`지침|요령|관리기준|기준|법|법률|시행령|시행규칙|규정|규칙|조례`)가 붙으면 인용으로 본다.

⚠️ **여기서 한 번 과잉 차단을 냈다.** "규범어 접두 **또는** 줄머리가 아니면 인용"
으로 잡았더니 조가 36 -> 21로 줄었다. 컬럼 crop 후 텍스트에서 조 헤딩 앞이 항상
마침표로 끝나지 않는다. **규범어 접두 하나로만** 판정하도록 되돌렸다.
조 헤딩을 놓치는 것이 인용을 하나 더 잡는 것보다 나쁘다.

### 함정

**검증 스크립트를 `timeout 100 … | tail -3` 로 돌려 결과가 갱신되지 않았다.**
파이프 뒤 `tail` 의 종료코드가 0이라 성공으로 보였고, JSON 은 옛 값 그대로였다.
"전후가 동일하다" 는 잘못된 결론을 낼 뻔했다. **파이프 뒤에 timeout 을 두지 말 것.**

## 2026-08-28 · `pdftext.py` 2단 조판 해소 + `build_refs.py` 조 단위 스캔

컬럼 분리를 `pdftext.py` 에 넣었다. 그 과정에서 `refs` 의 더 큰 결함을 찾았다 —
**2단 조판과 무관하게 `src_조번호` 가 처음부터 비어 있었다.**

### 입력

- `scripts/pdftext.py` (44줄)
- `scripts/build_refs.py`
- `scripts/stage0_articles.py` (기존 조 분해기 — 쓰이고 있지 않았다)
- `2026_Finance_DATA_FOR_RAG/_refs.json` (1,136 엣지)

### 판단

**거터(gutter) 검출을 x0 이 아니라 덮인 구간으로 했다.** 단어의 `x0` 만 모아 빈 구간을
찾으면 표에서 오탐이 난다 — 열 시작점이 몰려 있어도 실제 텍스트는 그 사이를 덮는다.
`(x0, x1)` 구간을 합쳐 실제로 아무 글자도 없는 띠를 찾는다.

**거터 판정을 페이지가 아니라 문서 단위로 했다.** 페이지마다 정하면 표가 있는 한 페이지
때문에 그 페이지만 2단으로 잘린다. 8쪽을 표본으로 뽑아 절반 이상에서 같은 x(편차 20pt
이내)가 나올 때만 채택한다.

**단어를 직접 재조립하지 않고 `page.crop()` 후 pdfplumber 에 다시 맡겼다.** 줄바꿈·
들여쓰기 복원 로직을 다시 만들 이유가 없다.

**`extract()` 시그니처를 유지했다.** 호출부가 2곳(`build_refs.py`, `build_precedence.py`)
이고 둘 다 2-튜플로 언팩한다. 진단 정보가 필요한 곳을 위해 `extract_meta()` 를 따로 뒀다.

**`build_refs.py` 를 `stage0_articles.split_articles()` 에 연결했다.** 아래 결함 때문이다.

### 실측 — 🔴 `refs` 의 실제 결함

```
_refs.json  엣지 1,136개 중 src_조번호 가 채워진 것: 0개
```

`build_refs.py` 의 엣지 딕셔너리에 `src_조번호` 키 자체가 없었다.
문서 전체 텍스트에 정규식을 돌려 참조 문자열만 뽑고 있었다.

**결과 두 가지**

1. **`RAG.md` §4-3 참조 폐포 SQL 이 동작하지 않는다.**
   `WHERE (src_doc_id, src_조번호) IN :진입점집합` 인데 `src_조번호` 가 없다.
   문서 단위로 조인하면 그 문서의 참조가 **전부** 딸려온다
   (예: 모두의창업 세부관리기준 1건 = 86 엣지).
2. **같은 참조 문자열이 문서 안에서 여러 번 나오면 1건만 남았다.**
   `seen` 중복제거 키가 `(kind, 참조문자열)` 이고 범위가 문서 전체였다.

`db/init/01_schema.sql` 의 `refs` 테이블은 `src_조번호 TEXT NOT NULL` 이고
`UNIQUE (src_doc_id, src_조번호, 참조문자열)` 이다. **스키마와 산출물이 어긋나 있었다.**

**원인**: `scripts/stage0_articles.py` 에 섹션 분리(부칙·붙임/별표) + 3단 fallback +
V1~V6 검증이 이미 구현돼 있는데 `build_refs.py` 가 그걸 쓰지 않고 자체 정규식만 돌렸다.

### 함정

**2단 조판은 `refs` 를 오염시키지 않았다.** `src_조번호` 를 안 쓰니 조 경계가 틀려도
영향이 없었다. 다만 조 단위 스캔으로 바꾸는 순간부터는 영향을 받는다 —
그래서 컬럼 분리가 선행돼야 한다.

**`rules` 19행·`chunks` 는 다르다.** 이쪽은 조-내용 대응이 그대로 값이 되므로
2단 오염이 직접 반영된다. 미확인.

### 남은 것

- `build_precedence.py` 재실행 미실시

### 판단

**코드의 역할을 추출까지로 잘랐다.** 조 경계·비단조·붙임 판정을 코드에 맡기려다
바꿨다. `RAG.md` §3-1이 열거한 함정(부칙 덮어쓰기, 붙임 헤더 vs 본문 참조,
다단 혼입)은 전부 원문을 봐야 갈린다. 코드는 후보와 이상 플래그만 낸다.

**`제N조(제목)` 패턴으로 뽑았다.** `제\d+조` 만 쓰면 본문 안의 인용까지 잡는다.
실측: 같은 문서에서 42건 → 33건으로 줄었고, 33이 `작업 현황.md` 프로토타입 실측과 일치한다.

**F 태깅을 통계가 아니라 런타임 필드로 재정의했다.** 아키텍처 §8의
"집계하면 F축이 빈도로 도출된다"만 보고 통계로 잡았으나, 실제 용도는
검색 결과 조항들의 F 태그를 합집합해 `(4)-b` 프롬프트에 넣을 F를 정하고
없는 F를 `전제[]`로 내는 것이다(`Agent.md` §4).

**적용대상에 `혼재` 값을 추가했다.** `제18조 ① 일반수용비는… ② 주관기관 소속
인력 수당은…` 처럼 조 안에서 대상이 갈리는 경우가 있다. 혼재 조 개수는
`RAG.md` §5 미결 #1(청킹 단위 조 vs 항)의 판단 근거가 된다.
혼재 조를 항 단위로 쪼개는 것은 이번에 하지 않는다 — 청킹 단위 결정을 앞지른다.
