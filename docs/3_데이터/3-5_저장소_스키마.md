# 저장소 스키마 — 테이블 목록

이 문서가 답하는 질문:
- DB 안에 스키마가 몇 개고 각각 무엇을 담는가
- 어느 테이블이 무슨 역할을 하는가
- RLS는 어디에 적용되는가

> **DDL 전문은 여기 없다.** 기준은 `db/init/*.sql`(파일명 순 적용)과 운영 변경분 `db/migrations/`.
> 이 문서는 표만 본다. 운영 DB 는 NCP VM 의 PostgreSQL 17 + pgvector 컨테이너(`deploy/ncp`),
> 로컬은 `db/docker-compose.yml`. 데이터 보정 SQL 은 `db/seed/`(수동 실행).
> 테이블·컬럼의 이전 이름은 [[용어집]] 과 `db/migrations/2026-11-02_용어_정리.sql`.

## 스키마 4분할

| 스키마 | 내용 | RLS |
|---|---|---|
| `corpus` | 공개 규정·룰·refs·체크항목. 전 사용자 공통 | 없음 |
| `tenant` | 사용자 데이터 (L3·계정·기업 프로필·지출계획·판정로그·캐시). org별 격리 | 전부 |
| `eval` | 골든셋·평가 run. **검색 인덱스 투입 금지**(`retrieve.py` FILTER). 운영 DB 에는 없다 | — |

`public` 은 비워둔다. `ops` 스키마는 쓰지 않는다(남아 있는 DB 는 `db/migrations/2026-11-01_drop_ops_schema.sql` 로 지운다).

## `corpus` 테이블 (15)

| 테이블 | 내용 |
|---|---|
| `documents` | 문서 목록 (`status`: staged/active/superseded · `index_target` · `retrieval_scope` · `extraction` · `parse_quality`) |
| `doc_articles` | 조 단위 원문 |
| `chunks` | **검색 인덱스** — `vector(1024)` · `적용대상` · `retrieval_scope`(검색대상/참조확장전용) · 원문 그대로 |
| `chunk_terms` / `chunk_len` | BM25 역색인 (`term_df` 는 문서 빈도 materialized view) |
| `ingest_jobs` | 규정 적재 API 업로드 기록 ([[8_운영/8-7_규정_적재_API]]) |
| `refs` | 참조 그래프 (`해결상태`: resolved / remapped / dangling) |
| `rules` / `precedence_rules` | 룰 테이블 ([[5-1_룰_테이블]]) · 효력순위 9행 |
| `item_vocab` / `item_alias` | 비목 어휘집(비목체계별) · 품목 → 비목 별칭 |
| `programs` | 사업 8종 메타 |
| `check_items` | "결제 전/후 확인" 고정 목록 52행 · 심층질문 문안(`질문문`·`선택지`·`질문유형`·`필요프로필필드`) · `기한근거` |
| `evidence_sources` | 증빙 발급처 안내 |
| `recheck_queue` | 규정 개정으로 재검토가 필요한 룰·체크항목 |
| `xref_mismatch` | 교차 참조 불일치 |

사례 인덱스(`case_chunks`)는 없다.

## `tenant` 테이블 (13)

| 테이블 | 내용 |
|---|---|
| `orgs` / `org_programs` | 기관 413행 · 사업×연도별 기관 목록 1,063행 |
| `accounts` | 계정 (`email` ↔ `org_id`, `pw_hash` 비움) |
| `l3_documents` / `l3_articles` | L3 원문 목록 / 조 단위 (벡터 없음 — 검색 안 함) |
| `profile_agreements` / `profile_expenditures` / `profile_personnel` | 기업 프로필 — 협약 · 집행내역 · 참여인력 |
| `unmapped_premise` | 미매핑 전제 집계 (정책 없음 — 앱은 쓰지 않는다) |
| `expense_plans` / `plan_tasks` | 지출 계획 · 체크리스트 |
| `decisions` | 판정 로그 (+`plan_id` · `처리단계` · `검증코드[]` · 전제 · 검색 시점 상태) |
| `judge_cache` | 판정 캐시 (키에 `데이터버전_해시` 포함 — 코퍼스·룰·우선순위·체크항목·별칭이 바뀌면 자동 무효) |
| `incidents` | 운영 인시던트 기록 |

`decisions`는 corpus가 아니라 tenant다 — 전제·검색 시점 상태에 기업 프로필 정보가 남는다.

## `eval` 테이블 (4)

`golden_set` (골든셋 342행) · `golden_chunks` (정답 근거 청크 매핑) · `runs` / `run_items` (평가 실행과 문항별 결과).

## RLS

**1차 방어는 코드다** — 앱이 항상 `org_id`를 명시적으로 건다. RLS는 2차 방어선.

코드: `db/init/01_schema.sql` · `tenant.current_org()` · `org_isolation`
```sql
CREATE FUNCTION tenant.current_org() RETURNS uuid
LANGUAGE plpgsql STABLE AS $fn$
...
        v := current_setting('request.jwt.claims', true)::json ->> 'org_id';
...
    IF v IS NULL OR v = '' THEN
        v := nullif(current_setting('app.org_id', true), '');
    END IF;
    RETURN v::uuid;
...
CREATE POLICY org_isolation ON tenant.l3_articles   USING (org_id = tenant.current_org());
```

앱은 트랜잭션마다 `SELECT set_config('app.org_id', %s, true)` 를 건다(`scripts/l3_load.py` · `_rls_org_설정()`).

- 앱 롤은 비특권 `suddoe_app`(`rolbypassrls=false`). 로컬은 `10a_rls_guc.sql` 이 롤을 만들고
  `10b_app_grants.sql` 이 권한을 준다(운영 복원도 같은 파일). 로컬 `postgres` 는 superuser 라 RLS 가
  적용되지 않으므로 격리 테스트는 반드시 `suddoe_app` 으로 실행한다
- 새 커넥션을 열면 GUC 가 없다. `판정()` 이 커넥션을 새로 열 때 `set_config` 를 다시 건다
  (2026-09-04 인시던트 — GUC 없는 INSERT 가 RLS 에 막혀 판정이 저장 없이 200 을 냈다)
- 게스트 행은 `org_id IS NULL` 이라 이 정책을 구조적으로 못 넘는다
