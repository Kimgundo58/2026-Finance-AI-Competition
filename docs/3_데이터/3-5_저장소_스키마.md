# 저장소 스키마 — 테이블 지도

이 문서가 답하는 질문:
- Supabase 안에 스키마가 몇 개고 각각 무엇을 담는가
- 어느 테이블이 무슨 역할을 하는가
- RLS는 어디에 걸리는가

> **DDL 전문은 여기 없다.** 기준은 `db/init/01_schema.sql`(corpus 21테이블) +
> `02_frontend.sql` + `03_input_fields.sql`. 이 문서는 표만 본다.

## 스키마 4분할

| 스키마 | 내용 | RLS |
|---|---|---|
| `corpus` | 공개 규범·룰·refs. 전 사용자 공통 | 없음 |
| `tenant` | 사용자 것 (L3·계정·F축·판정로그). org별 격리 | 필수 |
| `eval` | 정답셋. Supabase에 안 올림(덤프 제외) | — |
| `public` | 비워둔다 (PostgREST 자동 노출 방지) | — |

## `corpus` 테이블

| 테이블 | 내용 |
|---|---|
| `documents` | 문서 목록 (`index_target`·`retrieval_scope`·`extraction`·`parse_quality`) |
| `doc_articles` | 조 단위 원문 |
| `chunks` | **판정 인덱스 (A등급)** — `vector(1024)`·`적용대상`·원문 그대로 |
| `case_chunks` | **사례 인덱스 (B등급)** — 물리 분리, 판단불가 경로 전용 |
| `rules` / `precedence_rules` | 룰 테이블 (`rule_base.md` 소관) |
| `refs` | 참조 그래프 (resolved/shifted/dangling) |
| `chunk_terms` / `chunk_len` / `term_df` | BM25 역색인 |
| `item_alias` | 상품명 → 비목 별칭 |
| `xref_mismatch` | 크로스 레퍼런스 불일치 |
| `check_items` | "결제 전/후 확인" 폐쇄 목록 |
| `evidence_sources` | 증빙 발급처 안내 |

## `tenant` 테이블

| 테이블 | 내용 |
|---|---|
| `orgs` | 기관 (기관명·사업명[]·주소·부서) |
| `l3_documents` / `l3_articles` | L3 원문 목록 / 조 단위 (벡터 없음 — 검색 안 함) |
| `accounts` | 계정 (이메일·해시) |
| `f_profile` / `f_exec` / `f_personnel` | F1·F3·F4 |
| `unmapped_premise` | 결핍 루프 |
| `expense_plans` / `plan_tasks` / `decisions`(+`plan_id`) | 지출 계획·체크리스트·판정 로그 |

`decisions`는 corpus가 아니라 tenant다 — 전제·검색 시점 상태에 F축 흔적이 남는다.

## RLS

**1차 방어는 코드다** — 앱이 항상 `org_id`를 명시적으로 건다. RLS는 2차 방어선.

```sql
ALTER TABLE tenant.l3_articles ENABLE ROW LEVEL SECURITY;
CREATE POLICY org_isolation ON tenant.l3_articles
    USING (org_id = (auth.jwt() ->> 'org_id')::uuid);
```

`public`을 비우는 것도 방어선이다 — anon 키만으로 `GET /rest/v1/<table>`이 되므로
정답셋은 `eval`로 분리하고 덤프에서 제외한다.
