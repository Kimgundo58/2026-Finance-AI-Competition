## 2. DB

### 2-1. 켜져 있나

Docker Desktop → `suddoe` 그룹 → `suddoe-db`·`suddoe-pgweb` 둘 다 Running(초록).
`localhost:8081` 이 안 열리면 Docker Desktop 자체가 실행 중인지부터 본다.

```powershell
cd db
docker compose up -d
```

### 2-2. 데이터가 들어왔나 — http://localhost:8081

왼쪽에서 `v_적재현황` 클릭 — 테이블별 건수가 나온다. 절대값보다 **비율과 존재**를 본다:
`documents` 대비 `doc_articles`·`chunks` 가 수십 배인가, `rules`·`refs`·`precedence_rules` 가
비어 있지 않은가, `golden_set` 이 **인덱스 테이블에 섞여 있지 않은가**.

### 2-3. 품질 점검 SQL

```sql
SELECT '통합관리지침 조 개수(80↑ 정상)' AS 항목, count(*)::text AS 값
  FROM doc_articles WHERE doc_id LIKE '%통합관리지침%제14차%'
UNION ALL SELECT '붙임 분리 존재', count(*)::text
  FROM doc_articles WHERE 조번호 LIKE '붙임%'
UNION ALL SELECT '임베딩 누락(0이어야 함)', count(*)::text
  FROM chunks WHERE embedding IS NULL
UNION ALL SELECT '적용대상 태깅 누락', count(*)::text
  FROM chunks WHERE 적용대상 IS NULL
UNION ALL SELECT '판정검색 대상 청크', count(*)::text
  FROM chunks WHERE status='active' AND parse_quality='high' AND layer IN ('L1','L2')
UNION ALL SELECT '검수 완료 룰', count(*)::text
  FROM rules WHERE verified;
```

| 항목 | 합격 | 불합격이면 |
|---|---|---|
| 통합관리지침 조 개수 | 80 이상 | PDF 추출 실패 — `pdftext.py` 경유 여부 확인 |
| 붙임 분리 | 존재 | 섹션 분리 실패 (`RAG.md` §3-1 Step 1) |
| **임베딩 누락** | **0** | `build_index.py` 재실행 |
| 적용대상 태깅 누락 | 0 (Stage 0.5 후) | 태깅 전이면 전건 NULL 이 정상 |
| 검수 완료 룰 | D단계 진행에 따라 증가 | |

> `doc_id` 명명 규칙이 바뀌면 첫 두 쿼리의 LIKE 패턴도 같이 고친다.
> `layer` 는 파일명이 아니라 발행주체 기준이다.

### 2-4. 원문이 안 깨졌나 (제일 중요)

```sql
SELECT 조번호, 조제목, left(text, 120) AS 본문앞부분
FROM chunks WHERE doc_id LIKE '%통합관리지침%' AND 조번호 IN ('제39조','제45조') LIMIT 4;
```

**사람이 읽을 수 있는 문장**이어야 한다:

```
❌ "...집기 가구 기구 등은 집행할 수 없으며 노트북 및 , , , PC("   ← 추출 실패
✅ "제39조(기계장치, 공구·기구) ① 사업계획서 상의 사업화를 위해..."
```

쉼표·괄호가 문장 끝으로 밀려 있으면 그 상태로는 쓸 수 없다 — 인용은 원문 그대로여야 한다.

## 3. RAG 품질

측정 층이 셋이다 — 아래로 갈수록 파이프라인이 더 필요하다.

```
(a) 검색   — 정답 조항을 물어오는가        ← eval_retrieval.py (15문항)
(b) 판정층 — 근거를 주면 옳게 판정하는가    ← 골든셋 근거_원문으로 검색 없이 (격리 테스트)
(c) 전체   — 질문부터 판정까지             ← 골든셋 70± (검색+판정+인용)
```

### 3-1. 눈으로 — smoke 5문항

```powershell
python scripts/smoke_search.py
```

판단 기준 하나: **"내가 이 조항만 보고 사용자에게 답할 수 있나?"**

| 결과 | 판정 |
|---|---|
| 1등이 정확히 그 비목 조항 | ✅ 좋음 |
| 1~3등 안에 있음 | ✅ 합격 (실제로는 top-5 를 쓴다) |
| 관련 비목인데 다른 조항 | ⚠️ 청킹 문제 가능성 |
| 엉뚱한 비목 / 주관기관 조항 | ❌ 필터·태깅 문제 |
| 텍스트가 깨져 있음 | 🔴 치명 — §2-4 |

### 3-2. 숫자로 — 15문항 자동 채점

```powershell
python scripts/eval_retrieval.py
```

| 지표 | 의미 | 합격선 |
|---|---|---|
| **Recall@5** | 정답 조항이 LLM 에 넘어가는 top-5 안에 있는 비율 | **0.85 이상** |
| Recall@3 / @1 | 참고 | |
| MRR | 정답의 평균 순위 (1등=1.0) | 0.6 이상 |

**Recall@5 가 상한선인 이유** — 여기서 못 찾은 조항은 ④ 컨텍스트에 아예 안 들어간다.
없는 근거로는 어떤 모델도 답할 수 없다. (단, 참조 폐포가 끌어오는 조항은 예외 — 진입점만
잡히면 된다.)

실패 문항은 무엇이 대신 나왔는지로 진단한다:

| 나온 것 | 진단 | 처방 |
|---|---|---|
| 같은 비목 다른 조항 | 청킹 경계 | 분할 임계 재검토 (`RAG.md` §3-4) |
| 다른 비목 | 임베딩 열세 | 컨텍스트 헤더 확인 → bge-m3 비교 |
| 정확 용어를 못 찾음 | BM25 문제 | 토큰화 정책·동등성 검증 (`RAG.md` §2-4) |
| 구버전·타사업·주관기관 조항 | 필터 버그 | `status`·`사업명`·`적용대상` 필터 확인 |

**운영 규칙: 뭐든 바꾸면 재실행. 점수 없이 "좋아진 것 같다"로 머지 금지.**
모델 비교 시 검색 결과 스냅샷 고정.

### 3-2b. 회귀 5종 — 무엇을 바꾸든 이게 안 움직여야 한다

2026-09-01 부터 회귀는 3종이 아니라 **5종**이다. 순서대로 돌리고 하나라도 어긋나면 멈춘다.

```powershell
$env:PYTHONIOENCODING="utf-8"
python scripts/rule_lookup.py --self-test   # DB 불필요 · 순수 함수 회귀 70여 건
python scripts/rule_lookup.py --smoke       # 270조합 실 커넥션 (타입·예외·enum·누출)
python scripts/audit_db.py                  # 전 표 NULL + 계약 11종 감사 · exit 0 이어야 한다
python scripts/score_judgment.py            # 치명 오답 0.0% · exit 0 이어야 한다
python scripts/eval_retrieval.py            # RRF hit@5 52.9% 기준선 (6분 걸린다)
```

판정 자체를 한 줄로 돌려 보려면 `python scripts/judge_cli.py --help`.

🔴 **«통과» 가 «판정이 맞다» 는 뜻이 아니다.** 4단 검증 통과·dangling 0·스모크 270조합은
«올바르게 뽑았다 / 안 죽는다» 의 증거지 «판정이 맞다» 의 증거가 아니다. 판정 품질은
3-3 골든셋으로만 잰다.

### 3-3. 정식 평가 — 골든셋 77문항

구성·지표(치명 오답률 1순위)·채점 규칙은 `LLM.md` §5 가 정본. 실행 전 확인:

- [ ] 골든셋·적대적 세트가 **인덱스에 없는가** (`index_guard` + `golden_set` 테이블 격리)
- [ ] 연구재단 QA 홀드아웃을 떼어낸 뒤 나머지만 사례 인덱스에 넣었는가
- [ ] 문항 전량 `verified=true` 인가 (검수 전 점수는 baseline 으로 쓰지 않는다)
- [ ] 적대적 세트 검수 시 `검수_포인트` 필드 확인 (A9 는 사업별 정답 갈림)
