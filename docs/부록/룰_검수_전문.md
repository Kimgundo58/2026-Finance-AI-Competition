## 1. 왜 사람이 해야 하나

`rule_base.md` §1이 정한 규칙입니다:

> 룰 테이블은 fast path라서 여기 오류가 나면 **매 판정에 반복 전파**된다. 비목 수십 개 × 사업 2개 규모라 검수는 반나절이면 된다. 자동화로 아낄 곳과 사람이 봐야 할 곳을 구분하는 지점이 여기다.

### LLM에게 검수를 맡기면 안 되는 이유

LLM이 추출한 값을 LLM이 검증하면 **같은 오해를 두 번 반복**합니다. 예를 들어 원문이

> "PC(노트북 및 태블릿 PC 포함) 구입의 경우 대표자 및 신규 채용인력 **1인당 1대**에 한하여 구입 가능"

인데 LLM이 "1인당 100만원"으로 잘못 뽑았다면, 검증하는 LLM도 같은 문장을 같은 방식으로 읽을 가능성이 높습니다. **사람 눈이 들어가야 끊깁니다.**

### 틀리면 어떻게 되나

| 오류 | 결과 |
|---|---|
| 한도를 100만원 → 1,000만원으로 잘못 읽음 | 사용자에게 **"가능"이라고 답변** → 환수 + 제재부가금 5배 |
| 사전승인 필요를 `false`로 잘못 표기 | 승인 없이 결제 → 정산에서 반려 |
| 증빙 항목 하나 누락 | 서류 미비로 반려 |

설계 원칙(`서비스 아키텍쳐.md` §1): **"틀린 '가능'이 최악이다."** 그 최악이 가장 잘 발생하는 지점이 룰 테이블입니다.

## 5. 각 칸을 무엇으로 판단하나

### `허용`

| 값 | 기준 |
|---|---|
| `가능` | 유의사항에 제약이 없거나, 절차적 조건만 있음 (예: 재료비, 교육훈련비) |
| `조건부` | 한도·사전승인·금지 예시가 하나라도 있음 (예: 기계장치, 외주용역비) |
| `불가` | 비목 자체가 금지 — **현재 19행에는 없어야 정상** |

> 개별 항목 금지(예: 광고선전비의 기프티콘)는 `불가`가 아니라 **`조건부` + `금지예시`**입니다. 비목 전체가 막힌 게 아니니까요.

### `한도`

원문에서 **숫자를 찾아 그대로** 옮깁니다. 해석하지 마세요.

| 원문 표현 | 유형 | 값 | 단위 |
|---|---|---|---|
| "선급금은 계약 총액의 50% 이하" | 비율 | 50 | % |
| "1인당 1대에 한하여" | 개수 | 1 | 대/인 |
| "1인 1일 최대 30만원" | 금액 | 300000 | 원/인/일 |
| "월 50만원 한도" | 금액 | 500000 | 원/월 |
| 언급 없음 | (비움) | (비움) | (비움) |

🔴 **자주 나는 실수**

- "2천만원 초과 시 사전심의"를 **한도로 착각** → 이건 한도가 아니라 **사전승인 조건**입니다. 2천만원 넘게 써도 됩니다, 심의만 받으면.
- "취득가액 500만원 이하는 자산관리대장 제외"를 한도로 착각 → 이건 **관리 의무 기준**이지 집행 한도가 아닙니다.
- 단위 누락 → `50`만 있고 `%`가 없으면 코드가 50원인지 50%인지 모릅니다.

### `사전승인`

**"결제하기 전에 누군가의 허락이 필요한가?"** 만 봅니다.

| 비목 | 값 | 조건 |
|---|---|---|
| 외주용역비 | `true` | 2천만원 초과(부가세 포함) 시 사업운영위원회 사전심의 |
| 인건비 | `true` | 4대보험 가입 예외 적용 시 주관기관 사전승인 |
| 여비 | `true` | 국외출장은 **출국일 이전** 주관기관 보고 |
| 나머지 | `false` | |

> "사전 보고"도 `true`로 봅니다. 안 하면 집행이 안 되는 건 마찬가지입니다.

### `증빙`

붙임2의 `증빙서류` 칸을 **빠짐없이** 옮깁니다. 이게 화면 6 "해야 할 일" 체크리스트가 됩니다.

- 괄호 안 대체 표기는 유지: `세금계산서(신용카드 영수증)`
- 조건부 서류는 조건까지: `선급금이행보증보험(필요시)`
- 지급수수료는 **세부항목이 13개**라 가장 깁니다. 여기가 제일 빠뜨리기 쉽습니다.


본문 조항이 근거면 `"조번호": "제22조"`. **둘 다면 둘 다 적습니다.**

## 6. 완료 조건

```sql
SELECT 사업명, count(*) AS 전체,
       sum(CASE WHEN verified THEN 1 ELSE 0 END) AS 검수완료
FROM rules GROUP BY 사업명;
```

**19행 전부 `verified = true`가 되면 D 완료입니다.** ✅ 1차는 2026-08-31 에 종결됐다.
2차(현재 미검수 19행)는 `scripts/_work/_G_룰검수요청.md` §6 을 따른다.

검수를 안 하고 넘어가면 어떻게 되냐면 — 코드가 이렇게 막습니다:

> `verified = false`인 룰만으로는 **"가능" 판정을 낼 수 없다.** 반드시 근거 조문 인용이 동반되어야 하고, 인용이 없으면 `조건부`로 강등된다. (파이프라인 문서 §6.4)

즉 검수를 건너뛰면 시스템이 "가능"이라고 확답을 못 하고 계속 애매하게 답합니다.

## 7. 틀린 걸 발견하면

1. 검수 도구에서 `n`을 누르고 무엇이 틀렸는지 메모
2. pgweb `Query` 탭에서 직접 수정:

```sql
UPDATE rules
SET 한도_유형='개수', 한도_값=1, 한도_단위='대/인',
    verified=true, 검수자='김건도', 검수일=CURRENT_DATE
WHERE rule_id = 3;
```

3. **같은 유형의 오류가 3개 이상 나오면** 추출 프롬프트 자체가 잘못된 것이니, 19행을 다시 뽑는 게 빠릅니다.

| 명시적 금지 | "홍보용 기프티콘 뿌려도 되나요?" | 불가 |
| 규정에 없음 | "ChatGPT Plus 구독료요" | 판단불가 |

마지막 유형을 꼭 넣으세요. **판단불가율**이 지표 3개 중 하나인데, 판단불가가 정답인 문항이 없으면 측정이 안 됩니다.

### 🔴 골든셋 확정 시 반드시 할 일

연구재단 QA사례집은 **사례 인덱스와 골든셋을 겸하는 파일**입니다. 지금은 전체가 `case_chunks`에 들어가 있습니다.

골든셋으로 쓸 Q&A를 정한 뒤, **그 Q&A를 `case_chunks`에서 삭제해야 합니다.** 안 하면 검색이 정답지를 그대로 찾아와서 평가 점수가 거짓으로 높아집니다.

```sql
DELETE FROM case_chunks
WHERE doc_id = '사례집_한국연구재단_정부연구비사용QA사례집_2025개정'
  AND case_id IN ( ...골든셋으로 뺀 것들... );
```
