# GPU Guideline

RunPod 에서 Qwen3 32B 를 띄우고 골든셋을 재는 절차. `LLM.md` §1(슬롯·vLLM 운영규칙)과
§6(사다리)의 실행편이다. 충돌하면 `LLM.md` 가 이긴다.

실측일 2026-08-30. GPU 재고와 가격은 변하니 착수 전 `get-gpu-type` 으로 다시 본다.

## 0. 전제 — few-shot 은 가중치를 만들지 않는다

few-shot 은 프롬프트에 예시를 끼워 넣는 것이다. 모델 파일은 안 바뀐다.
**"few-shot 해놓고 그 가중치를 저장한다" 는 성립하지 않는다** — 산출물이 없다.

| 무엇 | 어디에 저장 | 언제 바뀌나 |
|---|---|---|
| few-shot 예시·프롬프트 | git (`LLM.md` §3) | 우리가 고칠 때 |
| 베이스 가중치 (Qwen3 32B) | RunPod 네트워크 볼륨 | 안 바뀐다 |
| LoRA 어댑터 | 볼륨 `outputs/` | 사다리 5단계에 가야 생긴다 |

가중치를 볼륨에 두는 이유는 학습이 아니라 **재다운로드 방지**다.

## 0-b. GPU 는 작업마다 다르게 고른다 (2026-08-31 추가)

**이 문서의 A100·L40S 표는 ④-b 판정(Qwen3 32B) 기준이다.** 다른 작업에 그대로 쓰면 과잉이다.
요구 VRAM 은 가격이 아니라 **모델 크기**에서 나온다.

| 작업 | 모델 | 요구 VRAM | 근거 |
|---|---|---:|---|
| **임베딩** | KURE-v1 (bge-m3 568M) | **8GB** | fp16 가중치 1.1GB + 활성값 2~4GB |
| ① 정규화 · ⑤ 문장생성 | Qwen3 8B | 24GB | bf16 ≈ 16GB + KV. AWQ 면 12GB |
| ④-b 판정 조립 | Qwen3 32B AWQ + 투표 N=3~5 | 48GB+ | 가중치 20GB + 동시 시퀀스 KV. bf16 원본은 66GB |

임베딩에 A100(80GB)을 잡는 것은 8GB 짜리 일에 10배를 쓰는 것이다.
RTX A4000(16GB) · A5000/4090(24GB) · A6000(48GB) 중 **재고 있는 싼 것**이면 된다.
실제 계산이 2~4분이라 GPU 등급이 총비용에 거의 영향을 주지 않는다 — **재고가 더 중요하다**.

### 고르는 절차

```bash
export RUNPOD_API_KEY=...
python scripts/pick_gpu.py --task embed        # 프리셋: embed | llm8b | judge
python scripts/pick_gpu.py --min-vram 24       # 직접 지정
python scripts/pick_gpu.py --task judge --need-volume
```

`runpodctl gpu list` 를 실행 시점에 조회해 **VRAM 충족 × 재고 있음** 으로 거르고 $/h 로 정렬한다.
표로 박지 않는 이유는 §0 그대로다 — 가격과 재고가 계속 변한다.

🔴 **제일 싼 게 항상 정답이 아니다.** A40 이 그 사례다(§1) — 싸지만 네트워크 볼륨을 지원하는
DC 에 없어서 못 썼다. 그래서 선택기는 가격만 보지 않고 제약을 같이 건다:

- `--need-volume` : 가중치를 **재사용할 때만** 켠다. 1회성 작업이면 볼륨을 만들지 않는 게 싸다
  (KURE-v1 은 2.3GB 라 매번 받아도 2~3분. 볼륨은 DC 를 묶고 상시 과금만 붙는다)
- `--dc` : 볼륨이 이미 있는 DC 로 한정할 때
- `--community` : 커뮤니티 클라우드가 더 싸지만 안정성이 낮다. 짧은 배치 작업에만

### 비용 가드

🔴 **서버측 자동종료는 없다** (2026-08-31 실측, 이전 기술은 틀렸다).
`runpodctl 2.12.0` 의 `pod create`·`update`·`start`·`stop` 어디에도 `--terminate-after` /
`--stop-after` 가 없고, REST v1 `PodCreateInput` 스펙(154KB)에 "After" 를 포함하는 키가 0개다.
**팟은 누군가 지울 때까지 돈다.**

그래서 가드가 클라이언트에 있다. 세 겹이고 셋 다 완전하지 않다:

| 겹 | 무엇 | 언제 뚫리나 |
|---|---|---|
| 워치독 | `runpod_pod.py open --hours N` 이 떼어놓는 로컬 프로세스 | PC 가 꺼지거나 절전에 들면 같이 죽는다 |
| 대장 | `.claude/_runpod_open.json` — `ls` 가 실물과 대조 | 사람이 `ls` 를 안 보면 소용없다 |
| 잔액 | 크레딧이 떨어지면 RunPod 이 멈춘다 | 손실 상한 = 남은 잔액 |

**정본은 사람이 닫는 것이다.** 워치독은 사고 방지용이지 설계가 아니다.

```bash
PYTHONIOENCODING=utf-8 python scripts/runpod_pod.py ls       # 도는 팟 + 경과 비용
PYTHONIOENCODING=utf-8 python scripts/runpod_pod.py close    # 대장의 팟 전부
runpodctl user                                                # 잔액·시간당 지출
```

## 1. GPU 와 데이터센터

⚠️ **A40(48GB) 는 폐기했다** (2026-08-30, `LLM.md` §1 동시 수정).
A40 이 있는 DC 는 CA-MTL-1 / EU-SE-1 둘뿐인데 **둘 다 네트워크 볼륨을 지원하지 않는다**
(`networkVolumeTypes: []`). A40 과 "가중치 볼륨 상주" 는 동시에 만족되지 않는다.

볼륨이 되는 DC 와 교차해서 남는 조합:

| GPU | VRAM | 볼륨 되는 DC | $/h (secure) | 쓸 곳 |
|---|---|---|---|---|
| L40S | 48 | EU-NL-1, US-TX-3 | 0.99 | AWQ 4bit |
| **A100 SXM** | **80** | **EUR-IS-1**, EU-RO-1, US-KS-2, US-WA-1, US-CA-2 | **1.59** | **AWQ / bf16 둘 다** |
| RTX PRO 6000 | 96 | EUR-IS-1, US-NC-2, US-NE-1 | 2.09 | bf16 여유 |

✅ **US-KS-2 · `suddoe-weights` · 50GB · 볼륨 id `fv5cl1y1ww`** (2026-08-31 생성)

~~EUR-IS-1~~ 에서 **US-KS-2** 로 바꿨다. 판단 근거 둘:

**① 48GB 로 충분하다 — A100 80GB 가 필요 없다.** 배포 구성이 `Qwen3-32B-AWQ`(4bit, 약 20GB)
라 투표 N=3~5 의 KV 캐시를 얹어도 48GB 안이다. 80GB 가 필요한 건 bf16 원본 66GB 일 때뿐인데
우리는 AWQ 로 간다. `LLM.md` L42 의 "A100 SXM 80GB" 는 낡은 값이다.

**② US-KS-2 는 48GB+ 카드가 5종이고 최저가도 거기 있다** (2026-08-31 실측):
```
US-KS-2   5종  L40 $0.82 · RTX 6000 Ada $0.84 · A100 SXM $1.59 · H100 PCIe $2.89 ...
US-NE-1   4종  최저 $1.09
EUR-IS-1  2종  최저 $2.09   <- 구 선택. 48GB 급이 없고 96GB 부터다
```
🔴 **볼륨은 DC 에 못박힌다** — 한 종류만 있는 DC 에 두면 그 카드 재고가 빠질 때 볼륨을 못 쓴다.
A40 함정(§1 상단)과 같은 구조다. **카드가 여러 종 있는 DC 를 고르는 것이 요점이지
특정 GPU 를 고르는 게 아니다.**

**크기는 100GB 가 아니라 50GB 다.** 실제 필요량은 32B AWQ 20GB + 8B AWQ 6GB ≈ 26GB 이고,
사다리 5단계의 LoRA 어댑터를 얹어도 여유가 있다. 상시 과금이 절반이다 (월 $7 -> $3.5).

```bash
# 팟 생성 시 볼륨을 붙인다 — 🔴 나중에 못 붙인다 (§7)
python scripts/runpod_pod.py open --gpu "NVIDIA L40" --hours 2     --template-id runpod-torch-v280 --dc US-KS-2 --volume-id fv5cl1y1ww
```

한국에서 가장 가까운 볼륨 지원 DC 는 AP-JP-1 이지만 H100 SXM 만 있고 재고 LOW 다.
제출본은 테스트 데이터만 다루므로 지연보다 재고를 우선한다.

모델은 `Qwen/Qwen3-32B-AWQ` (4bit, 약 20GB). bf16 원본은 66GB 라 80GB 카드에서 KV 캐시가
모자란다 — 투표 N=3~5 는 동시 시퀀스가 늘어나므로 AWQ 로 간다.

## 4. 저장 위치

같은 볼륨인데 **팟과 서버리스에서 경로가 다르다.** 대표적인 함정이다.

```
네트워크 볼륨 (EUR-IS-1, 100GB)
  |
  +- 팟에서는        /workspace           <- 마운트 경로를 내가 정한다
  +- 서버리스에서는  /runpod-volume       <- 고정, 못 바꾼다
  |
  +- hf/                    HF 캐시 (HF_HOME 을 여기로)
  |    +- Qwen3-32B-AWQ     약 20GB   -> [vLLM]
  +- outputs/               사다리 5단계 전까지는 빈다
       +- lora-out/         adapter_config.json + adapter_model.safetensors
                                      -> [vLLM] 서빙 시 베이스 위에 얹는다

컨테이너 디스크 (20GB)      팟이 죽으면 같이 죽는다
  +- 이미지 / 파이썬 패키지만
```

팟에서 `/workspace/outputs/x` 에 쓴 것은 서버리스에서 `/runpod-volume/outputs/x` 로 읽는다.
같은 바이트, 다른 경로.

**볼륨 대안 — `--model-reference`.** 서버리스로 갈 때는 볼륨 없이 HF 모델을 엔드포인트에
붙일 수 있다. DC 고정이 없고 다운로드 시간에 과금되지 않는다.
`--model-reference https://huggingface.co/Qwen/Qwen3-32B-AWQ:main` — **`:main` 을 빼면
해석에 실패한다.** runpodctl v2.4.0 이상.

이미지에 굽는 방식은 32B 에는 안 쓴다. worker-vllm 의 10GB 이미지도 첫 pull 이 20분을 넘겼다.

## 5. 명령

### (1) 볼륨 — 최초 1회

티어를 지정하려면 MCP 로 만든다. runpodctl 에는 티어 플래그가 없어 DC 기본값이 잡힌다.

```
create-network-volume  name=qwen-weights  size=100
                       dataCenterId=EUR-IS-1  volumeType=STANDARD
```

**티어는 만든 뒤 못 바꾼다.** 바꾸려면 새로 만들어 복사해야 한다.

### (2) 팟

🔴 **MCP `create-pod` 에는 `networkVolumeId` 파라미터가 없다.** 볼륨을 붙이려면 runpodctl 을
써야 한다. MCP 의 `volumeInGb`/`volumeMountPath` 는 팟 전용 디스크지 네트워크 볼륨이 아니다.

```bash
# SSH 키를 먼저 등록한다 — 부팅 시점에 주입되므로 나중에 넣으면 재시작해야 한다
runpodctl pod create \
  --gpu-id "NVIDIA A100-SXM4-80GB" \
  --data-center-ids EUR-IS-1 \
  --network-volume-id <vol-id> \
  --volume-mount-path /workspace \
  --container-disk-in-gb 20
```

이미지·포트 플래그명은 버전마다 달라진다. `runpodctl pod create --help` 로 확인한다.
🔴 자동종료 플래그는 없다 (§0-b 비용 가드). 직접 부르지 말고 `runpod_pod.py open` 을 거친다 —
대장 기록과 워치독이 거기 붙어 있다.

### (3) 가중치 — 최초 1회

```bash
export HF_HOME=/workspace/hf          # 볼륨 안으로 캐시를 돌린다
pip install --break-system-packages -q vllm huggingface_hub
hf download Qwen/Qwen3-32B-AWQ
```

PyTorch 템플릿은 PEP 668 이라 `--break-system-packages` 가 필요하다.
새 `uv venv` 를 파면 템플릿의 torch 를 상속받지 못한다.

### (4) vLLM

구성은 `LLM.md` §1 vLLM 운영규칙이 정본이다. 아래는 그걸 명령으로 옮긴 것이다.

```bash
export HF_HOME=/workspace/hf
vllm serve Qwen/Qwen3-32B-AWQ \
  --reasoning-parser qwen3 \
  --enable-prefix-caching \
  --max-model-len 20000 \
  --gpu-memory-utilization 0.92 \
  --port 8000
```

- `--reasoning-parser qwen3` — 추론 종료 후 출력부터 문법을 적용한다. **측정도 이 구성으로** 한다
- `guided_json` 은 기동 플래그가 아니라 요청 본문에 넣는다 (§3-4 [1겹] 스키마)
- 기동 로그에 `awq_marlin` 커널이 잡혔는지 확인한다. 다른 커널이면 처리량이 떨어진다
- `--max-model-len` 은 프롬프트 예산(1~2만 토큰)에 맞춘다. 무작정 늘리면 KV 캐시를 먹는다
- OOM 이면 `--gpu-memory-utilization` 과 `--max-model-len` 을 먼저 내린다
- 플래그명은 vLLM 버전마다 갈린다. 안 먹으면 `vllm serve --help`

### (5) 워밍업

기동 후 더미 1회. `guided_json` 첫 호출에는 스키마 컴파일이 붙어서, 이걸 안 하면
첫 판정 지연이 튄다.

### (7) 종료

```bash
runpodctl pod delete <pod-id>     # 볼륨은 남는다
```

팟을 지우기 전에는 볼륨을 지울 수 없다.

## 6. 비용

| 항목 | 단가 | 실제 |
|---|---|---|
| A100 SXM (secure) | $1.59/h | 골든셋 1회 2~3시간이면 $4 내외 |
| 볼륨 STANDARD | $0.07/GB·월 | 100GB = 월 $7, **존재하는 동안 계속** |
| HIGH_PERFORMANCE | DC별 상이, 공개가 없음 | 처리량 3배·IOPS 4배. 지금은 불필요 |

볼륨은 팟을 껐어도 과금된다. 실험이 길어지면 볼륨 요금이 GPU 요금을 넘는다.

## 7. 함정

- **볼륨은 팟 생성 시점에만 붙는다.** 나중에 붙이지도 떼지도 못한다
- **SSH 키는 팟 생성 전에 등록한다.** 부팅 시 주입되므로 나중에 넣으면 재시작이 필요하다
- 팟·볼륨·엔드포인트가 **전부 같은 DC** 여야 한다. 아니면 스케줄링이 실패한다
- 볼륨 DC 고정이 **GPU 재고를 좁힌다.** 여러 DC 에 볼륨을 두면 완화되지만 **자동 동기화가 없다**
- 컨테이너 디스크는 중지·종료 시 지워진다. 남길 것은 전부 볼륨에
- 새 팟이 불량 머신에 걸려 런타임이 안 올라오는 경우가 있다. 기다리지 말고 지우고 다시 만든다
- 학습·다운로드 같은 긴 작업은 `setsid` 로 떼어 실행한다. SSH 가 끊겨도 살아남는다
- 서버리스의 `/runsync` 는 **Cloudflare 100초 제한**에 걸린다. 첫 호출은 `/run` + `/status` 폴링
- `/health` 가 `workers.ready:1` 을 보고해도 vLLM 은 아직 부팅 중일 수 있다

## 8. 사다리 5단계에 갔을 때

`LLM.md` §6 기준 1~4단계를 마치고 격차가 남을 때만 편다. 표적은 **판정 캘리브레이션**이다.

어댑터는 `adapter_config.json` + `adapter_model.safetensors` 로 수백 MB 다.
학습 팟에서 `/workspace/outputs/lora-out` 에 쓰고, 서빙에서 `/runpod-volume/outputs/lora-out`
으로 읽는다. `HF_HOME` 을 볼륨에 둬야 베이스 가중치를 재다운로드 없이 재사용한다.

미결 둘:

1. **vLLM LoRA 서빙 절차가 RunPod 문서에 없다.** 골든패스는 transformers + PEFT 핸들러만
   검증했고 `--enable-lora` 계열 플래그 언급이 전무하다. upstream vLLM 문서를 따로 봐야 한다
2. **AWQ 4bit 위에 LoRA 를 얹는 조합이 까다롭다.** 사다리 6단계가 "AWQ 배포 양자화 그대로
   골든셋 재실행" 이므로, 5단계 진입 시 이 조합을 먼저 결정해야 한다
